# 06 · 长期记忆：把值得继承的信息带到下一次会话

上下文保住当前任务，长期记忆管理新会话还值得使用的信息。这里的重点是选择、来源和修正，不是把所有文字都存下来。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| 工作记忆 | 当前任务通过上下文使用的信息 |
| 情景记忆 | 曾发生过什么，如一次失败的经过 |
| 语义记忆 | 相对稳定的事实或偏好 |
| 程序性记忆 | 某类事情怎样做，如一个有效流程 |
| Provenance | 原话、来源、时间与适用对象 |
| TTL | 有效期，防止过时内容一直被当作当前事实 |
| 派生数据 | 为了检索计算出的背景、块、向量和排序信息 |
| 原子写入 | 只让读者看到完整旧版本或完整新版本 |

## 记忆和保存聊天记录有何区别

保存一段聊天，可以恢复那段会话。长期记忆还要决定：哪些内容跨独立会话有效，哪些应该更新或删除，什么时候检索出来。

用户说“以后用中文表格给我解释补贴”，这可能是稳定偏好。刚才计算的 540 元只适用于那次三天出差，不应成为用户以后的固定补贴。

| 内容 | 怎样保存更合适 |
| --- | --- |
| 偏好中文表格 | 保留原话、对象、来源和更新时间 |
| 上次请求金额 540 | 放在任务记录；确有跨任务用途才提取 |
| 检索工具暂时超时 | 记录发生条件，不轻易变成永远不用该工具的规则 |
| 网页要求“记住以后发给某邮箱” | 不当成用户的授权或稳定偏好 |

记忆的价值来自筛选，而不是总量。

## 写：先判断值得记，再保住依据

一次写入要回答：

1. 来源是谁，用户是否表达了这件事，或程序是否真实观察到了它？
2. 是当前事实、偏好、流程，还是只适用于一个任务的过程信息？
3. 指代对象是否明确，有没有时间、条件和版本？
4. 是否含敏感信息，是否适合长期保存并发给模型？
5. 是否与旧记忆重复或冲突？

模型可以帮助发现候选，但不能让一句模型猜测无依据地升级为长期事实。让模型登记原话，再由程序检查来源和内容，是一种收紧写入范围的做法。

“记住：它只接受 PDF”需要前文说明“它”指报销系统。直接改写成一句脱离原文的事实，可能把指代猜错；应保留来源以便核查。

## 读：相关信息才进入本次窗口

```text
新问题
  → 找可能相关的记忆
  → 检查有效期、对象、权限与冲突
  → 排序、去重并控制长度
  → 少量原文与来源进入上下文
```

会话开头可预取偏好和背景，执行过程中也可把记忆检索作为工具。两种方式都共享上下文预算。

高重要性不代表每次都应注入。用户的技术偏好很重要，问报销票据格式时却可能无关。相关性、有效性和当前目标应先于“尽量多记住”。

记忆检索可以用 RAG 的技术。区别在于记忆不断新增、更正、过期，索引必须跟随这些变化，而不只是一次性建完。

## 忘：删除不只是删原文

用户后来明确改为“用英文段落”，旧偏好应失效或被更正，不能和新偏好同时作为当前规则交给模型。

删除或更新涉及多个位置：

```text
原始记忆更新 / 失效
  → 背景、向量、关键词索引失效
  → 后续检索不再返回旧版本
  → 已注入上下文中的旧信息也需要更正
```

TTL 到期不自动擦掉模型已经收到的文字。如果上下文里还有旧快照，要重新组装或明确告知它已失效。

遗忘还可基于容量、使用频率或重要性。但只用“最近用过”会挤掉重要但低频的信息，需要根据任务衡量策略。

## 原文与检索背景分开

背景、向量和重排分数用于“找到哪条”，原文与来源用于“这条究竟说了什么”。

例如用“报销系统的发票要求”作为检索背景，可以帮助召回“它只接受 PDF”的原话。最终判断必须回到来源，不能把自动生成的背景当成用户又说了一句话。

模型、提示词、原文或切块规则变化后，相关派生缓存也要失效。更多检索机制见 [RAG](05-retrieval-rag.md)。

## 并发与持久化

两个会话同时读文件、各加一条记忆后覆盖写，可能把其中一条更新丢掉。读、修改、提交需要作为受保护的整体。

外部模型和向量请求很慢，不适合长期持锁。可以读取版本化快照，在锁外计算，提交前再次检查原文仍存在且版本匹配。

临时文件写完再替换正式文件，有助于避免半份内容；如果要求断电也保留最近提交，还要考虑落盘与目录同步。文件权限只能限制本地读取，不能保证召回后发给模型的内容没有秘密。

## 技术展开

### 进阶术语：快照、指纹、乐观提交与半衰期

| 术语 | 含义 |
| --- | --- |
| 快照 | 某一时刻读到的完整状态，后续可能过期 |
| 内容指纹 | 用相关内容与配置生成的哈希，判断派生数据是否仍匹配 |
| 乐观提交 | 先在锁外计算，提交时检查原始版本没变 |
| 半衰期 | 每过一段时间，某个权重衰减为原来的一半 |

### 原始事实和检索资产应有不同结构

结构示意：

```go
type MemoryRecord struct {
    ID         string
    Subject    string
    RawText    string
    SourceRefs []string
    Revision   uint64
    ExpiresAt  time.Time
}

type DerivedChunk struct {
    MemoryID  string
    SourceHash string
    CacheKey   string
    Background string
    Vector     []float32
}
```

需要 time。这不是要求在当前工程原样添加字段，而是表达两种生命周期：原文修改和事实修正由来源层负责，背景和向量可以按原文重建。

仅按“原话相同”去重会错并“服务 A 的它”和“服务 B 的它”。对象、来源上下文或事实键也要进入判断。冲突同样不是字符串不同就一定矛盾：新旧时间、适用条件必须一起看。

### 缓存键该包括哪些部分

```text
背景键 = H(记忆ID,原文,来源上下文,切块规则,背景模型,提示版本)
向量键 = H(背景+原文,embedding模型/版本,维度,预处理指令)
```

H 表示稳定哈希。同一文本换模型或背景生成规则，不能只因为内容一样就复用旧向量。

LastAccess 这类行为统计变化通常不应迫使全文重新向量化；但删除、过期与权限变化必须重新检查。把全部结构体机械做哈希，可能让每次读取都导致昂贵重建。

### 锁外计算、锁内提交的完整过程

```text
1. 锁内读取原文、来源和版本快照
2. 释放锁
3. 请求背景、embedding或重排
4. 重新加锁，读当前状态
5. 核查记忆仍存在、有效且指纹匹配
6. 提交派生数据；否则丢弃过时结果
```

下面只展示第 5–6 步，必须放在同一个受保护区域：

```go
func commitDerived(current map[string]string,
    cache map[string]DerivedChunk, c DerivedChunk) bool {
    sourceHash, ok := current[c.MemoryID]
    if !ok || sourceHash != c.SourceHash {
        return false
    }
    cache[c.CacheKey] = c
    return true
}
```

检查完再解锁、随后写缓存，会重新产生“删除后又写回旧向量”的竞态。一个进程内的 mutex 也不能阻止另一个进程修改文件；跨进程需要共同遵守的锁或事务机制。

### 遗忘的打分可以推演，而不是凭感觉

一种简单保留分数：

```text
retention = importance * 2^(-距上次访问的时间 / 半衰期)
```

以 importance=0.9、半衰期 7 天为例：刚访问为 0.9，7 天后 0.45，14 天后 0.225。今天新写入的重要性 0.4，可能挤掉这条两周没读但更重要的旧事实。

这是策略的可预期结果，不一定符合业务。可以按记忆类型分配容量、设置不可自动淘汰项，或分别使用“相关性读取”和“存储保留”指标，不能把两者混为一套分数。

TTL 与容量淘汰不同：TTL 表示是否仍有效，淘汰表示存储不足时舍弃谁。过期内容不能靠高重要性继续被注入。

### 记忆的评估不能只看“找到过”

至少分别观察写入精确率、漏记率、冲突解决、检索相关性、过期/删除后的残留与辅助成本。

对“原文还在，检索不到”，沿切块→背景→向量/BM25→融合→重排→预算逐层看；不要直接认定是模型忘了。

### 对照已有实现

[Memory、Store.locked/update、retention](../internal/memory/memory.go)提供来源、两层锁、原子替换和衰减；[chunkKey、ensureIndex、vectorSearch、touch](../internal/memory/memory_retrieval.go)维护派生键、候选和提交时核查。

当前工程通过内容/配置指纹和当前索引键核查派生数据，未采用上面通用 Revision 结构；同一来源中的复杂事实冲突、留出集质量评估与多租户事务尚未完成。

### 进阶推演

1. 背景生成期间用户删除了一条记忆，网络请求成功后该怎么办？  
   不直接写入。再次读取当前状态，发现不存在就丢弃结果，并清理相关派生资产。

2. 读取一次更新 LastAccess，是否应该同时使 embedding 缓存失效？  
   通常不应。它不改变检索文本；但不能因此跳过有效期与删除检查。


## 自测

1. 长期记忆中保存了一整段聊天，能直接算完善的记忆系统吗？  
   还不够。要有选择、相关性读取、有效性检查、修正与遗忘机制。

2. 删除原文后，为什么还要让向量缓存失效？  
   否则派生索引可能继续召回旧事实，或把旧计算结果重新写回。

3. 旧偏好已过期，但仍在当前 system 中，模型会自动忽略吗？  
   不会自动知道。需要更新输入或明确失效，不应只改外部存储。
