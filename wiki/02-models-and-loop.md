# 02 · 模型调用与执行循环：行动请求怎样变成下一步

这篇解释一次模型请求包含什么，以及为什么单次请求之外还需要循环。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Message | 带角色的一条输入，角色说明它从哪里来 |
| System / user / assistant / tool | 系统规则、用户要求、模型输出、工具返回 |
| Tool calling | 模型以结构化字段提出工具调用 |
| ReAct | 通过推理、行动、观察交替推进任务 |
| Observation | 实际执行返回的结果或错误 |
| Routing，路由 | 把一次模型请求交给合适的模型或供应商 |

## 一次请求包含两类信息

一类是消息：角色规则、用户问题、之前的回答与工具结果。另一类是工具定义：有哪些能力、怎么描述参数。

在原生工具调用协议里，定义通常放在单独的 tools 字段；它不是一段必须手写进 system 的文本，但仍会被转换成模型可理解的输入。

常见消息角色：

| 角色 | 内容例子 |
| --- | --- |
| system | 根据检索资料回答；操作前检查权限 |
| user | 查出差补贴并计算三天金额 |
| assistant | 提出检索请求，或生成回答 |
| tool | 返回制度片段、来源和检索状态 |

“请求里有历史”说明程序发送了它；对无状态的聊天请求，模型不会自动读取程序保存在别处的历史。

## 模型可能返回什么

**普通回答**：直接给出文字。是否把它当成完成，要结合是否有正常内容、是否截断、是否满足任务要求。

**工具调用**：给出工具名、参数和调用 ID。模型提出行动；执行器决定能否运行。

以一种常见的聊天协议为例：

```json
{
  "id": "call_search_1",
  "type": "function",
  "function": {
    "name": "search_docs",
    "arguments": "{\"query\":\"出差 补贴\",\"k\":3}"
  }
}
```

这里 arguments 是 JSON 字符串。程序要先解析模型响应，再解析这段参数，不能直接拿它当可信的命令。

## 循环多做了四件事

| 职责 | 具体动作 |
| --- | --- |
| 解析 | 分辨回答与 tool_calls，读取工具名、参数与 ID |
| 调度 | 找到工具、校验输入、安排执行和并发 |
| 状态维护 | 保存模型请求与工具结果，组装下一轮输入 |
| 终止 | 遇到完成、预算耗尽、熔断、取消等条件停止 |

流程可以写成：

```text
组装本轮输入
  → 请求模型
  → 如果提出工具调用：检查、执行、写回结果
  → 再请求模型
  → 如果完成或触发停止条件：结束
```

“查制度 → 得到每日 180 元 → 算三天金额 → 得到 540 → 回答”需要多次请求。第一次模型提出检索时，还没拿到制度内容，不能依赖它生成计算参数。

## ReAct 不要求固定输出 Thought

Reason 是根据目标和已知情况做判断；Act 是行动；Observe 是读取反馈。这个结构有助于行动被外部事实纠正。

早期教程用 Thought、Action、Observation 的文字标签解析动作。原生工具调用已经把行动放在结构化字段里，回答可以自然表达。

模型的内部推理可能不公开。程序可观测的输入、工具请求、实际结果和停止条件，才是调试的基本依据；有一段“思考”文字并不保证判断正确。

## 选择模型也是一个独立职责

路由可以手动选择，或按任务用途分配。例如主任务需要综合判断，摘要只需整理已有内容。但使用小模型前也要检查它能不能满足契约。

两家接口都兼容某种消息格式，不代表所有细节兼容。需要核对工具调用、参数支持、上下文限制、推理字段回传与错误格式。

在已经开始的对话中换模型，还可能遇到旧推理字段无法解析、缓存无法复用、行为变化。迁移时需要重新组装可接收的历史，不能只换地址和模型名。

## 技术展开

### 进阶术语：消息闭包、适配与增量解析

| 术语 | 含义 |
| --- | --- |
| 消息闭包 | 一组调用请求和对应结果都在输入中，关系完整 |
| Provider adapter | 处理供应商字段、错误与计量差异的适配层 |
| Opaque field | 程序不能随意解释或改写、需要按协议保留的字段 |
| Delta | 流式响应每次到达的一小段增量 |

### 完整消息序列比“拼一段结果文字”更重要

以下为一种聊天协议的教学示例，展示调用 ID 的配对关系：

```json
[
  {"role":"system","content":"核查规则与金额后回答"},
  {"role":"user","content":"按已知每日180元计算三天补贴"},
  {"role":"assistant","content":null,"tool_calls":[
    {"id":"calc_1","type":"function","function":{
      "name":"calculator","arguments":"{\"expression\":\"3*180\"}"
    }}
  ]},
  {"role":"tool","tool_call_id":"calc_1","content":"{\"value\":540}"}
]
```

下一次模型请求必须同时带上 assistant 的调用和 tool 的结果。如果只加一句“结果 540”，虽然模型可能读懂，协议中的调用关系却丢了。

并行返回也要满足：每个 ID 唯一、每项结果正确配对、没有悬空请求与孤立结果。多结果不应只靠数组位置或工具名关联。

### Go 里怎样保留字段

一种通用结构示意：

```go
type WireMessage struct {
    Role       string                       `json:"role"`
    Content    json.RawMessage              `json:"content"`
    ToolCalls  []json.RawMessage             `json:"tool_calls,omitempty"`
    ToolCallID string                       `json:"tool_call_id,omitempty"`
}
```

RawMessage 可以暂时保留一段 JSON，而不把复杂内容强行压成字符串。若要保留未知顶层字段，还需额外字段映射或自定义编解码；仅使用这个 struct 仍会丢掉未声明字段。API 的具体用法见 [Go JSON 文档](https://pkg.go.dev/encoding/json)。

适配层要说明哪些推理字段需要原样回传，哪些不能回传。不要把返回给用户的可见文字当作完整 assistant 消息。

### 终止要看 finish_reason 和响应内容

| 情况 | 建议处理 |
| --- | --- |
| 正常文字结束 | 检查内容有效，作为候选最终答案 |
| 工具调用结束 | 完整解析参数并进入执行 |
| length 或其他截断 | 不把半段参数或半段回答当成完整结果 |
| 空 choices、空回答 | 返回明确模型协议错误 |
| 要求工具结束但没有调用 | 按不一致响应处理 |

程序可以判断响应是否完整，不能仅由这些字段证明答案符合业务目标；后者属于结果校验与评估。

### 流式工具调用必须先重组，再执行

工具名、ID 和 arguments 可能分多次到达：

```text
delta 1：工具索引0，arguments = {"expression":
delta 2：工具索引0，arguments = "3*180"}
最终：确认流完整 → 得到完整JSON → 校验 → 执行
```

需要按协议给出的索引与 ID 累积状态。不能每收到一段就执行，也不能在连接断开时假装 arguments 完整。

流式能较早展示文字，不等于工具可较早产生副作用。要定义断流、重复片段、超长输入和多调用交错时的处理。

### 路由不能只换 URL

可以把供应商差异组织成契约表：

```text
输入变换：消息角色、内容块、工具格式、支持参数
输出变换：工具调用、推理字段、finish_reason
计量：输入、缓存、推理、可见输出各是什么口径
错误：参数、认证、限流、超窗、服务故障
```

故障转移前要确认历史能被目标模型接受、请求是否包含不兼容字段。辅助摘要可以单独路由，主对话迁移则需要更严谨的历史转换。

### 对照已有实现

[callModel 与 Client.CallKeeping](../internal/llm/llm.go)负责结束原因、请求计数和用途；[Message](../internal/llm/protocol.go)保留已知的 reasoning_content、encrypted_content 和工具字段。

现有请求是非流式，消息是明确的结构体，尚未实现上述通用 RawMessage 适配和 delta 重组。这些代码与流程是技术设计示意，不代表已接入所有供应商。

### 进阶推演

1. arguments 在断流后恰好可以解析成 JSON，是否可以直接执行？  
   还不能只凭 JSON 可解析判断。需要协议层确认调用完成、身份完整、没有未收到的修正或其他必要字段。

2. 把原 assistant 改写为“我调用了计算器”会丢掉什么？  
   调用 ID、结构化参数、供应商要求的附加字段；下一轮的 tool 配对与推理状态可能不再合法。


## 自测

1. 模型提出 calculator 调用之后，为什么还要再请求一次模型？  
   程序要把计算结果交回，模型才能结合制度、问题和结果给出回答。

2. 工具定义放在 tools 字段，是否就不占上下文？  
   不是。字段位置是协议组织方式，工具说明仍会被模型处理并占用输入资源。

3. “没有 tool_calls”能不能直接等同于“任务完成”？  
   不能。还需要检查回答是否正常、是否被截断，以及实际目标是否得到满足。
