# 11 · 任务调度：一批任务怎样排队、执行与去重

执行循环解决一个任务怎样往前走，调度解决多个任务怎样共享执行资源。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Queue | 存放待执行任务的队列 |
| Worker | 领取并执行任务的工作单元 |
| 并发上限 | 同时执行的任务数量限制 |
| Lease | 一段时间内对某任务的执行权 |
| 投递语义 | 失败后任务会丢失还是再次出现 |
| Idempotency key | 表示同一业务意图的去重标识 |
| Dead-letter queue | 多次失败后移入的待人工检查区域 |

## 队列位于循环外面

```text
用户或系统提交任务
  → 去重与入队
  → worker 领取
  → 执行一个 Agent 任务
  → 保存结果并确认完成
```

队列不必知道模型每一步怎样选择工具，只需要管理任务身份、执行权、结果与重试。

一天要处理一百份报销说明，不宜直接同时启动一百个模型循环。并发限制保护模型配额、内存、浏览器和下游服务。

## 并发多不代表整体更快

十个任务，每个固定用 20 秒，三个 worker 一次做三个，需要四批，约 80 秒完成。最后一批只有一个任务，其余 worker 会空闲。

这是简化例子。实际任务时长不同，还会等待工具与限流；总耗时取决于瓶颈、尾部任务和资源争用。

任务内部的工具并发与队列并发要分别计数。三个任务各调用四个工具，可能有十二项工具请求同时在途。

增加 worker 前，先看哪层已成为瓶颈；否则只会把排队移到下游。

## 崩溃后会怎样再次领取

| 语义 | 思路 | 代价 |
| --- | --- | --- |
| 至多一次 | 领取后不再投递 | 没有完成就崩溃时可能丢失任务 |
| 至少一次 | 未确认完成就可能重新投递 | 执行端必须能处理重复 |
| 效果恰好一次 | 允许重投，但执行端正确去重或协调提交 | 需要幂等与可靠状态机制 |

租约让某 worker 暂时拥有任务；它崩溃或超时后，任务可以重新出现。长任务要续约，但续约失败后也要防止旧执行者继续写入。

“消息只送来一次”和“业务效果只发生一次”不同。网络中的重复投递可以被允许，外部效果仍需被正确去重。

## 幂等键表达的是业务意图

用户提交三天出差的说明请求，网络重试应使用同一个键。如果用户明确要求重新按更新后的制度做一次，可能是一个新意图。

同一个键配了不同请求内容，应拒绝或显式处理冲突，不能返回旧结果冒充新结果。

只按内容哈希去重也有局限：完全相同的文字，用户可能确实想再次执行。自动内容去重适合某些批处理，不是所有交互场景。

## 先查后做为什么会重复

```text
worker A：没有这个键 → 开始执行
worker B：没有这个键 → 也开始执行
```

两个查询都正确，却仍产生重复。需要原子地占有键或执行权，再执行。

任务级去重也不够。任务只有一个执行者，内部“提交单据”仍可能在超时恢复后被重复提交。幂等要到真正产生副作用的一端才有业务效果。

## 失败、停止与恢复

暂时失败可在预算内退避；有检查点时从已有状态继续。参数非法、权限问题、已触发预算或熔断的任务，不应无条件自动重跑。

多次失败的任务进入死信队列，记录原因，避免一直占用正常任务的执行机会。

调度停止时应不再发新任务、通知在途任务停止、等待保存状态，报告完成、中断和未开始的任务。重启后可以分别返回已有结果、恢复中断任务、安排未开始任务。

## 技术展开

### 进阶术语：吞吐、利用率、租约与fencing

| 术语 | 含义 |
| --- | --- |
| 吞吐量 | 单位时间内完成多少任务 |
| 利用率 | 执行能力中实际被占用的比例 |
| 租约 | 有限时间内领取任务的权利 |
| Fencing token | 每次执行权的递增代号，接收端拒绝旧持有者提交 |
| 背压 | 队列满或执行繁忙时让提交方等待/失败 |

### 用容量关系判断瓶颈

稳定系统中的利特尔法则：

```text
L = lambda * W
L：系统内平均任务数（包括排队）
lambda：平均到达/完成速率
W：平均停留时间（包括排队）
```

若 p 个 worker 都忙、每项执行时间均值为 S，理论服务能力近似 p/S。以 p=3、S=20 秒为例，约 0.15 任务/秒；但有限十项任务仍可能需要四批、80 秒，不是直接除出67秒就必然完成。

到达速率接近或超过可服务速率时，排队会增长。模型延迟有波动，工具还会等待；仅按均值刚好配满通常缺少余量。

### 请求并发、任务并发与速率分别限制

```text
任务worker上限p
  × 每任务工具并发q
  × 子任务展开与重试
  → 下游真实在途请求数
```

一个 semaphore 控制在途数量，不保证每分钟请求数或 token 数合格。请求变快后，同一个许可可以每秒反复使用。

应按实际瓶颈分别管理：任务槽、模型请求/令牌速率、工具类别资源与子任务总预算。全局限流不能只存在于每个子进程自己的变量里。

### 领取要原子，占有状态要可恢复

一种持久化任务状态：

```text
queued → running(owner, lease_until, generation)
            ├─ done(result_ref)
            ├─ retry_wait(next_time, attempts)
            └─ dead_letter(error_ref)
```

两个 worker 同时看到 queued，只有一个能原子完成 queued→running。单机可用统一锁，多实例可用事务/条件更新；“先查一次再执行”不构成占有。

租约到期后旧执行者可能仍活着。新持有者拿到更高 generation，结果端需要检查它，才能拒绝旧提交；只设置 lease_until 却不检查提交代号，仍会发生双写。

### 幂等ID应绑定哪些请求内容

```text
同一task_id：
  同意图重试 → 恢复或返回已有结果
  不同关键参数 → 拒绝冲突，不复用旧结果
```

关键参数可能包括问题、工具范围、业务对象和策略版本。只对问题文字做哈希，不一定表达相同授权与相同任务。

哈希截断需要考虑碰撞与长度约束。生成键与比较原请求两者都重要，不能只说“用了SHA256所以不会有任何冲突”。

任务幂等只管理任务身份；工具副作用的 OperationID 仍要传到实际执行端。

### 任务级重试为什么要保留状态

因模型503中断的任务，有检查点就从保存状态继续；因预算耗尽、无进展熔断停止的任务，重复恢复通常只是再次停止。

重试次数、剩余预算、next_time 与错误原因应属于任务生命周期，而不是 worker 进程里的局部计数。否则调度器重启就把次数清零，死信队列永远不会触发。

停止应先停止派发，再取消在途、等收尾、记录未开始项；不要把队列中尚未领取的工作标成已执行失败。

### 对照已有实现

[queue.Run、runTask](../internal/queue/queue.go)使用固定 worker 和通道；[RunChild](../internal/agent/child.go)根据任务ID决定新跑、恢复或返回存档，子进程会再次获取 [任务锁](../internal/agent/checkpoint.go)。

当前是单机文件任务队列，主要核对 Question；没有多机租约、fencing、死信持久化或全局模型速率控制。前面的状态结构是工程设计边界，不是已经部署的分布式队列。

### 进阶推演

1. 三个worker空闲，但供应商TPM超限，继续增加worker有什么用？  
   不能解决token速率瓶颈，反而可能增加限流与重试；需要限制对应资源。

2. 租约失效的旧worker仍写结果，为什么只有心跳不够？  
   心跳只能表达执行权仍在续期，失效后阻止旧写入需要结果端的generation/fencing检查。


## 自测

1. 队列只保留一个任务 ID，内部写接口就不会重复吗？  
   不保证。执行后响应丢失仍需要下游幂等或状态核查。

2. 没收到完成确认的任务再次出现，是否说明队列出了 bug？  
   不一定。至少一次投递本来就允许重投，需要执行端配合去重。

3. 为什么不能把所有失败都从头重跑？  
   它可能已经有有效结果和副作用；重跑会浪费成本甚至重复修改。
