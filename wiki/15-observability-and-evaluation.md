# 15 · 观测与评估：先看清过程，再判断效果

观测回答“发生了什么”，评估回答“是否达到了目标”。两者需要关联，却不能互相代替。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Trace | 用 ID 串起任务、模型、工具与子任务的执行链 |
| Span | 链路里一项有起止时间的操作 |
| Log | 记录事件与状态的文字或结构化信息 |
| Metrics | 汇总很多次执行的数值 |
| Turn | 一次用户提问及其执行过程 |
| Step | 用户回合内的一次任务模型调用与工具执行 |
| Recall / Precision | 该找的资料找到了多少 / 找回的资料有多少相关 |
| Evaluation | 根据目标、数据与检查方法衡量效果 |

Turn、Step 是本书选用的展示语义，不保证所有产品使用同样的命名。

## 一条轨迹至少要关联什么

```text
用户回合
  ├─ 模型请求：实际输入、工具定义、输出、用量
  ├─ 工具调用：名称、参数、ID、尝试、状态与结果
  ├─ 摘要 / 记忆辅助请求：用途、输入、输出与成本
  ├─ 子任务：父子关系、自己的过程与交付
  └─ 结束：停止原因、完成结果、未确认动作
```

模型提出了工具请求，不代表已经执行。工具的成功、失败、未执行和结果未知都应被记录。

只代理模型请求能看到消息怎样往返，但任务在下一次请求前停止时，某些工具结果还没发给模型。完整观察还要结合终端或执行事件，不能把代理数据当作所有外部动作的完整审计。

## 事件与输入快照为什么不应混着数

假设同一个用户问题经历检索、计算、回答：

```text
Step 1 输入：system、user
Step 2 输入：上面的历史 + 检索请求 + 检索结果
Step 3 输入：上面的历史 + 计算请求 + 计算结果
```

Step 3 的输入可能有六条消息，但主表并没有发生六个新事件。旧消息是这一次重发的上下文，不是用户再次提问。

UI 可以在主表展示新事件，在每个 Step 的详情显示实际完整输入。这样既能数清步骤，也能核查模型究竟看到了什么。

压缩请求应单独标用途，保留下来的旧用户原话不应被误认成新的 Turn。

## 原始输入输出有什么价值

摘要卡片适合快速看懂，原始数据适合核查字段与消息关系：工具定义是否存在、调用 ID 是否配对、响应是否截断、用量是否包括辅助调用。

展示中的“相关”“成功”“绕路”常由规则推断，应让人看到判断依据。存在引用不等于事实正确，输出了一段思考也不等于执行成功。

原始数据可能包含业务秘密。不要只去掉认证头就认为日志安全；消息、工具参数、结果与记忆也需要权限、脱敏和保留期限。

## 成本与延迟看哪一层

主请求少了一次，可能只是把工作移到摘要、记忆背景或子任务。应把相关辅助成本一起看。

向量请求、模型请求和外部服务可能使用不同计量单位，应分别记录后按规则计算，不盲目相加。

耗时要区分用户等待、模型等待、工具执行、队列等待和空闲。并行工具总耗时不能把各自时长简单累加。非流式只知道请求总耗时时，也不能凭空推断首 token 时间。

## 评估应该分层

| 层次 | 检查什么 | 错误例子 |
| --- | --- | --- |
| 检索 | 应找到的证据是否进入候选 | 标准藏在未召回的片段 |
| 答案 | 数字、条件、引用是否正确 | 540 算对，却漏掉适用条件 |
| 行动 | 外部动作与用户意图是否一致 | 说明已生成，但文件没写出 |
| 可靠性 | 出错、取消、中断是否有正确状态 | 超时后把未知写成成功 |
| 安全 | 权限和外发是否符合授权 | 为读制度访问了私人文件 |
| 效率 | 成本和耗时是否合理 | 每次都重复检索相同资料 |

资料相关只是第一层，不等于整个任务完成。好的拒答也可能是正确结果：资料确实不足时，不应把拒答算成“必须编出金额才合格”。

## 一组小型对比怎样做

准备相同的问题、期待证据和判断依据，分别运行不同策略。固定任务条件，保留库外问题、冲突资料和失败场景，逐题核对。

例如一题需要“每日标准”和“节假日例外”两条资料。只找到其中一条，命中“至少一条相关片段”，但没有召回全部必要证据。应区分命中率与召回覆盖。

用于调试过的问题，不能直接当作独立验证集。先给小样本观察结论，扩大或更换数据后再判断是否普遍有效。

本章整理现有轨迹展示与 RAG 分层评估知识；完整指标平台、自动评分与大规模回归仍需另外建设。

## 技术展开

### 进阶术语：事件账本、输入快照、统计单位与区间

| 术语 | 含义 |
| --- | --- |
| 事件账本 | 按顺序记录真正发生的事件，而非重复历史 |
| 输入快照 | 本次提交的完整messages、tools和参数 |
| 统计单位 | 一次任务、一次请求或一次尝试等被计数对象 |
| 留出集 | 没参与策略调试、用于检查泛化效果的数据 |
| 置信区间 | 在统计前提下表达样本估计的不确定范围 |
| 指标基数 | 某个指标标签组合的数量，任务ID等无限变化值会使它持续增长 |
| TTFT | 请求开始到首个模型token的时间，不能由非流式总耗时倒推 |
| Wilson区间 | 对二元成功/失败样本计算比例不确定范围的一种方法 |
| z | 置信水平对应的标准正态分位数，95%双侧区间常取1.96 |

### 事件结构要能恢复因果关系

结构示意：

```go
type TraceEvent struct {
    Seq        int64
    RunID      string
    TaskID     string
    ParentTask string
    Turn       int
    Step       int
    CallID     string
    Attempt    int
    Kind       string
    Purpose    string
    Body       json.RawMessage
}
```

需要 encoding/json。TaskID关联父子执行，CallID关联调用/返回，Attempt区分重试，Purpose区分主任务、摘要与重排。

时间戳有助于算耗时，不能单独作为跨进程因果顺序。序号可以提供接收顺序，还要通过ID和父子关系解释真正依赖。Trace/Span的基础关系见 [OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/)。

指标标签适合用provider、工具名、状态等有限集合；不要直接把每个TaskID、问题全文放进指标标签。它们会产生高基数，增加存储与查询成本；精确身份应保留在轨迹和日志的关联字段中。

### 重发历史不应重复计作新事件

比较连续请求的消息前缀，可以辅助观察新增输入：

```go
func commonPrefix(a, b []json.RawMessage) int {
    n := min(len(a), len(b))
    for i := 0; i < n; i++ {
        if !bytes.Equal(a[i], b[i]) { return i }
    }
    return n
}
```

需要 encoding/json、bytes。该片段比较字节；要得到语义比较需规范化完整消息，不能只比较content而忽略tool_calls或其他字段。

“前缀一致”不是供应商缓存命中的证明；tools和请求配置还在messages之外。压缩重建后，前缀很短也不表示全部历史都是新用户事件。

展示归属应优先由start/continue、任务关系、模型/工具ID与压缩用途决定，完整输入独立显示为快照。

### 指标公式要明确分母

设某题需要证据集 R，前k结果为 G：

```text
Hit@k       = 1 if G与R交集非空 else 0
Recall@k    = |G与R交集| / |R|
Precision@k = |G与R交集| / k
MRR         = 各题首个相关结果名次倒数的平均；未命中记0
```

这里Precision@k按前k个位置计算，不足k视为空位置；若按实际返回数量作分母，应另标“返回结果精确率”，避免同名不同口径。

需要{A,B}、返回前3为{A,C,D}：Hit=1、Recall=0.5、Precision=1/3，首相关名次为1。这题虽然“命中”，却只覆盖了一半必要依据。

任务成功率还要固定统计单位：用户任务还是工具尝试？取消和超时是否算未完成？只统计成功返回的任务会隐藏失败。

### 小样本的不确定性可以量化

8/10成功不等于真实成功率已确定为80%。在独立、代表性二元试验前提下，可用Wilson区间：

```text
p = success/n
den = 1 + z^2/n
center = (p + z^2/(2n))/den
half = z*sqrt(p*(1-p)/n + z^2/(4n^2))/den
interval = center ± half
```

取z=1.96，8/10的区间约为49%到94%。这说明样本很少时结论很宽；参与调试的固定十题也不满足“对所有生产任务作保证”的前提。

同一问题复跑多次可以看模型波动，但不能把重复次数当成等量的新任务覆盖。策略对比宜使用相同任务成对核查，并区分调参集与留出集。

### 成本和延迟要按真实活动拆分

```text
总成本 = 主模型 + 摘要 + 记忆背景/重排 + 子任务
        + embedding + 其他计费服务
```

模型token、向量请求、计算资源可能不同单位，先分别计量，再按明确规则换算。总耗时还包括队列和等待，并行阶段取实际墙钟时间，不把各项span直接加起来。

非流式响应不能推断准确TTFT；第一次网络字节也未必就是第一段可见模型token。指标名称应对应实际能观测的事实。

### 实验报告需要失败归因

若答案漏了“节假日不适用”，区分：

- 资料没入库或切掉条件。
- 召回未找回正确块。
- 重排或预算把正确块丢掉。
- 模型看到了证据却误读。
- 工具/恢复导致旧状态被当作当前依据。

沿数据经过的阶段查证，比统一记为“模型幻觉”更能指导修复。

### 对照已有实现

[observer.proxy、add、streamEvents](../internal/observer/server.go)记录请求、用途、任务与事件；[embedding请求](../internal/retrieval/embedding.go)另走向量接口，[检索实验](../internal/labs/rag_lab.go)提供现有固定对比。

### 进阶推演

1. 一题召回了一条相关片段，为什么Hit=1但任务仍可能失败？  
   任务可能需要两条互补证据，还要检查条件、生成答案与外部交付。

2. 两个策略各跑十题，成功8和9题，能直接决定9题那个更可靠吗？  
   不能只看比例。需要成对结果、随机波动、任务代表性与更多独立样本，差异可能并不稳健。


## 自测

1. 一次请求的 messages 有六条，是否等于本轮六个新事件？  
   不是。它是输入快照，可能包含此前已发生的多条历史。

2. 所有工具都 exit 0，任务成功率是不是 100%？  
   不能据此判断。目标可能没完成，答案或外部效果也可能错误。

3. 新策略少了两次主模型调用，一定更便宜吗？  
   不一定。要加上辅助请求、子任务、向量检索和其他外部成本。
