## 先认识术语

| 术语 | 在本章中的意思 |
| --- | --- |
| Agent | 模型、工具和控制程序围绕目标协作的系统 |
| LLM | 生成语言和行动请求的模型 |
| Tool | 能计算、读取或修改外部信息的实际程序 |
| Loop | 把决定、行动和反馈反复接起来的执行循环 |
| Workflow | 步骤由代码预先安排的流程 |
| State，状态 | 当前已知信息、执行进度和未完成动作 |

## 模型和 Agent 的边界

用户问“三天，每天一百八十元，一共多少”，模型可以直接输出答案。但如果用户问“按最新制度计算”，系统就必须拿到那份制度。

模型发出“搜索制度”的请求，不能证明制度已被读到。执行器要真正运行搜索，把结果交回来，模型才能根据它继续。

```text
模型：提出下一步
程序：检查并执行下一步
工具：返回外部世界的结果
模型：根据结果继续决定
```

模型自己输出“已发送”，也不能证明消息已经发送。是否发生了外部动作，要看工具结果与外部状态。

## 用一个任务串起模块

用户要求查三天出差的补贴并生成说明。假设资料中找到“补贴每日 180 元；报销需要 PDF 发票”。

| 阶段 | 系统做什么 | 相关模块 |
| --- | --- | --- |
| 接到任务 | 放入用户目标、规则和已有偏好 | 上下文、长期记忆 |
| 决定查资料 | 模型提出检索请求 | 模型调用、工具编排 |
| 拿到制度 | 检索片段带来源进入下一次请求 | RAG、执行循环 |
| 计算金额 | 计算工具执行 3 × 180，返回 540 | 工具执行 |
| 整理说明 | 使用已核查的规则与金额回答或生成文件 | Skills、受限代码执行 |
| 处理异常 | 查询失败、超时或取消时反馈真实状态 | 运行时 |
| 保存进度 | 留下可以恢复的消息和调用状态 | 检查点 |
| 检查过程与答案 | 看是否查了对的制度、算对金额、引用正确 | 观测与评估 |

不必一次装上所有模块。一个简单查询可能只需要模型、一个工具和循环。模块的价值在于处理任务出现的新要求。

## Agent 与工作流怎样分工

一个固定报销流程可以由程序安排：“读表 → 校验 → 计算 → 生成文件”。这是工作流；里面也可以调用模型解释自由文本。

若资料可能缺失、需要选择检索方式、遇到失败后要调整下一步，模型可在边界内决定行动，这体现 Agent 的作用。

两者可以组合：程序固定高风险操作的确认步骤，模型灵活处理查资料和解释。任务越可预测，越值得把流程写清楚；任务越需要探索，越需要反馈驱动的循环。

## 三条理解主线

**信息线**：资料、用户话语、工具结果、记忆怎样进入本次上下文。

**行动线**：谁提出动作、谁运行它、动作能不能重做、由谁授予权限。

**状态线**：现在完成了什么，失败后保留什么，恢复时怎样判断真实结果。

很多看起来复杂的问题，沿着其中一条线就能找到原因。例如“有记录却忘了”属于信息线，“超时后重复创建”属于行动与状态线。

## 技术展开

### 进阶术语：状态机、契约与不变量

| 术语 | 含义 |
| --- | --- |
| 状态机 | 用有限状态和允许的转换描述执行过程 |
| 契约 | 每个边界对输入、输出、错误和权限的约定 |
| 不变量 | 不论走哪个分支都必须成立的条件 |
| 控制面 / 执行面 | 决定能否行动的部分 / 真正运行行动的部分 |

一个 Agent 可以理解为“模型提出候选行动，控制程序验证并改变状态”。不是所有模型输出都能直接触发状态转换。

### 一条可推演的任务状态机

```text
ready → model_pending → model_replied
                         ├─ 普通有效回答 → done
                         └─ 工具请求 → action_persisted → tools_running
                                                        ↓
                                                results_persisted
                                                        ↓
                                                      ready
任意非终态 → stopping → stopped
```

这不是要求每个项目都使用这些字段名，而是区分几个事实：

- model_replied：只收到决定，外部动作还没被确认。
- action_persisted：执行意图已记录，恢复时可以核查。
- results_persisted：拿到的结果已保存，下一步可以使用。
- stopped 与 done：前者不代表用户目标完成。

若直接把“模型说已完成”当作 done，就把语言输出和业务效果混成了一个状态。

### 五个必须保持的不变量

| 不变量 | 破坏后会怎样 |
| --- | --- |
| 每个 tool_call_id 最终有一个明确结局 | 消息不能配对，或已执行动作从报告消失 |
| 未确认的副作用不标成成功 | 恢复可能误报、重复创建 |
| 任务恢复沿用已用预算 | 重启可以绕过费用与失控限制 |
| 只有当前执行者可提交进度 | 两个进程相互覆盖检查点 |
| 权限在行动发生前验证 | 模型输出或外部内容变成了授权依据 |

“一个清晰的 loop”不是代码短就够了，而是能说明各个转换怎样维护这些条件。

### 模块之间交换什么

```text
上下文层 → 模型层：本次输入快照与预算
模型层 → 执行器：调用 ID、工具名、参数
执行器 → 状态层：结局、结果、错误、尝试次数
状态层 → 模型层：带来源与配对关系的 observation
状态层 → 观测层：事件、时间与关联 ID
```

把接口里的“结果”和“结局”分开：没有业务结果可能是未执行、失败或未知；不能只靠 error != nil 推断外部世界。

### 对照已有实现

读 [agent.Run](../internal/agent/react.go) 的模型响应、执行前保存与逐项回填，再读 [Checkpoint](../internal/agent/checkpoint.go) 的 Messages、Calls、Step 与状态字段。

现有实现已经区分请求、调用和恢复。它没有实现完整的分布式执行权、业务事务或通用规划器；这些不能从“有状态机”自动推出来。

### 进阶推演

1. 模型响应已收到，但进程在写检查点前结束，是否一定可以重做外部工具？  
   要先证明工具尚未执行。如果执行严格位于持久化之后，这个位置还没有副作用；若程序顺序不同，不能沿用这个结论。

2. 为什么任务状态要和工具状态分开？  
   一个任务可能完成两项、第三项未知；把任务统一标成失败，会丢掉部分结果和恢复依据。


## 自测

1. 模型输出“已读制度”，但没有检索工具结果，能认为查到了最新制度吗？  
   不能。只有文字声明，缺少实际读取与来源证据。

2. 一个 Agent 用了五个工具，是不是比只用一个更好？  
   不一定。应该看目标有没有完成、结果可靠性和成本；多余工具可能增加噪声和风险。

3. 为什么需要在循环之外设计运行时？  
   循环负责推进动作，运行时负责约束执行过程。会选择下一步，不代表能处理超时、取消和资源回收。
