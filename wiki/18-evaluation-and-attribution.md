# 18 · 评测与失败归因：用数据判断做得好不好、为什么不好

第 15 篇回答“发生了什么”，本篇回答“做得好不好”和“错在哪、为什么”。观测给出过程，评测给出判断，归因把判断变成能修的东西。三者要关联，但不能互相代替。

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| 完成 / 答对 | 正常结束并给出回答 / 回答真的满足任务要求 |
| 题目（task） | 一个输入加上成功标准 |
| 尝试（trial） | 对一道题的一次运行；同一题常跑多次 |
| 打分器（grader） | 判断某一方面是否达标的逻辑：程序检查、模型评审或人工 |
| 轨迹（transcript） | 一次尝试里模型说了什么、调用了哪些工具 |
| 结果（outcome） | 尝试结束时外部世界的最终状态 |
| pass@k / pass^k | k 次里至少一次成功 / k 次全部成功 |
| 留出集（holdout） | 调试时不看、只在最后报告时运行的题 |
| 消融（ablation） | 同一批题“开 / 关某个能力”各跑一遍，看分差 |
| 回归 | 以前会做的，改动后还会不会 |
| 第一个上游错误 | 一串连锁错误里最早的那个；归因只记它 |
| 反事实回放 | 从中间状态恢复，只改一处再跑，看结局是否翻转 |

## 完成不等于答对

**完成**是运行层面的：任务正常结束，没被预算、熔断、取消打断，从运行状态里就能读出来。**答对**要有打分器去判断结果。只报告完成率时，要写明它不代表答对。

评分以**结果**为主：Agent 回复“已经帮你订好了”，这只是轨迹；要检查是不是真有这笔预订。但过程也要读：打分器本身可能有错，只有翻看过程才会发现“明明做对了却被判错”。

## 一个指标不够：成功、可靠、延迟、成本

| 维度 | 看什么 | 常见误区 |
| --- | --- | --- |
| 成功 | 完成率 + 答对率 | 把完成率当答对率 |
| 可靠 | 多次运行是否每次都对；异常结局里能续跑的比例 | 只跑一次 |
| 延迟 | P50 典型体验、P95 尾部体验，连同样本数 | 只看平均值 |
| 成本 | 每次成功的成本 = 总花费 ÷ 成功数 | 只看每任务成本 |
| 工具可靠性 | 各工具的失败率、重试、耗时 | 用工具成功率代替任务成功率 |

例：10 个任务每个 3000 tokens、成功 6 个，每任务 3000，每次成功 5000。新版本成功率升到 80%、每任务涨到 3500，每次成功反而降到 4375。

**pass@k 与 pass^k 讲的是相反的故事**。某任务跑 8 次成功 6 次：单次 75%，pass^4 只有约 21%。k 越大，pass@k 越接近 100%，pass^k 越接近 0。用户每次只用一次，面向用户的 Agent 更该看 pass^k。

**分母最容易出错**：运行中的不算（还没有结局）；崩溃的必须算（最容易漏）；子任务单独统计；同一任务重试、续跑不算新任务；缺字段的样本单独报告，不拿 0 去平均。

**数据从持久状态取**。只从调用链统计成功率，崩溃的任务没有根 span，既不进分子也不进分母，成功率被高估。所以结局、耗时、成本以检查点这类持久状态为准，调用链只用来回答“慢在哪、哪个工具在出错”（见 [第 15 篇](15-observability-and-evaluation.md#指标的数据从哪里取)）。

## 评测集：固定题目，不固定回答

一道好题：

- **无歧义**：两个懂业务的人独立判断，结论相同。
- **有参考答案**：写一个能通过全部打分器的答案，证明题可解、打分器配置正确。
- **正反平衡**：有“该搜索”的题，也有“不该调用任何工具”的反例，否则优化结果会变成“什么都搜”。
- **从真实失败里来**：起步 20–50 道就够，早期每次改动的效果都很明显。
- **可复现**：时间、网页这类会变的东西不写死期望值。

题目文件固定的是**输入、参考答案和判定标准**，不是模型的回答或工具顺序。

## 打分器：先便宜的，后贵的

| 类型 | 适合 | 局限 |
| --- | --- | --- |
| 程序检查：数值、包含、正则、文件状态、工具调用次数、结局 | 能精确判断的部分 | 对合理的不同写法太死板 |
| 模型评审：按 PASS/FAIL 条件判断 | 开放题 | 有随机性和偏差，要校准 |
| 人工 | 校准前两种 | 慢、贵 |

一题两个打分器：一个看结果，一个看过程。**过程只查关键约束，不查顺序**：“有副作用的操作最多一次”“没授权时不联网”要查；“必须先 A 后 B”会误伤合理的其他路径。

模型评审的偏差：偏好自家模型、偏好长回答、位置偏差、随机波动。对策：评审模型与被测模型不同家；一次只判一个维度；把工具记录等证据给全；允许回答“不确定”；每项投 3 票；抽样与人工比对。

## 比较两个版本：小样本下的结论要谨慎

20 道题每题跑 3 次，pass@1 = 75% 时 95% 区间约 59%–91%。“这次 75%、上次 70%”不能说明变好了。

- **标准误按题聚类**：同一题的几次尝试不独立，先题内平均，再按题算。
- **逐题配对**：同一批题求每题的分差，再看差的均值和区间，题目难度在相减时抵消。
- **回归看逐题**：真正要报警的是“以前每次都对、这次没全对”的题。
- **留出集**：调试时看过的题会被针对性优化，只有留出题的分数代表泛化。
- **消融**：“开检索 3/3 通过”不知道是检索的功劳还是模型本来就会；开关各跑一遍看 Δ。

## 失败归因：在哪一步，为什么

“模型幻觉了”不是归因：说不出在哪一步、改什么。归因要回答两件事：**决定性错误在哪一步**（改掉它结局就会变好），以及**原因属于哪一类**。

做法：

1. **先分清是谁错**：打分器错了（格式过严、证据不全、期望值写死）就改打分器、重新打分，不算进 Agent 的失败。
2. **再分稳定与偶发**：k 次都没过是稳定失败，优先查；时过时不过是偶发失败，多跑几次再下结论。
3. **只记第一个上游错误**：第 2 步查错资料，第 5 步算错、第 8 步答错，多半都是它连锁引起的。
4. **开放编码 → 轴心编码**：先逐条用自己的话写备注，再把相似的归类计数。不先套通用分类表，太粗的类别不知道改什么。
5. **回放验证**：读轨迹得到的根因只是假设。从那一步恢复、只改一处、多跑几次，看结局是否翻转。

自动让模型找出错步骤目前不可靠：公开评测里最好的方法找对步骤只有约 14%。所以程序列线索（工具序列、第一个异常结果、没通过的检查、同题其他尝试），根因由人判断，再用回放证实。

## 闭环

```text
失败样本 → 先排除打分器的错 → 归因卡片 → 开放编码（第一个上游错误）→ 轴心编码（归类计数）
        → 选计数多、证据清楚的根因 → 反事实回放（纠正组 + 安慰剂组）
        → 修复（落在工具描述、规则或执行器上）→ 同一批题逐题配对回归
        → 失败样本沉淀为回归题
```

一次只改一处；修复必须被评测证实：目标题从失败变通过，而且没有别的题从“全对”变成“没全对”。

## 技术展开

### 进阶术语：聚类标准误、Wilson 区间、安慰剂对照与饱和

| 术语 | 含义 |
| --- | --- |
| 聚类标准误 | 把同一题的多次尝试视为一组计算的标准误，比把每次尝试当独立样本更大、更诚实 |
| 配对差 | 两个版本在同一题上的分数差 dᵢ，对 dᵢ 做统计 |
| Wilson 区间 | 二元成功/失败比例的一种区间估计，小样本下比正态近似稳 |
| z | 置信水平对应的标准正态分位数，95% 双侧常取 1.96 |
| 安慰剂对照 | 回放时插入一句不含信息的话（如“继续。”），排除“任何打断都能让模型换路”的可能 |
| 饱和 | 评测接近 100%，只能发现退步、不能再衡量进步 |
| 静默失败 | 没有任何报错、工具都成功，答案却错了 |

### 指标的分母与口径

```text
完成率         = 正常完成 / 有结局的顶层任务        （运行中不计，崩溃计入，子任务另算）
可续跑比例      = 异常里可续跑的（取消、超时、模型请求失败、进程消失） / 全部异常
每次成功的成本  = 全部 token / 成功数                （失败的任务同样花了钱）
P95            = 排序后第 ceil(0.95 × n) 个值        （n 小时就是最大值附近）
pass^k(单题)   = C(c,k) / C(n,k)                    （n 次里成功 c 次的无偏估计，再对题取平均）
```

算例：一个任务跑 5 次成功 4 次，pass^2 = C(4,2)/C(5,2) = 6/10 = 60%。

检索评测是答案评测的上游，口径也要写清。设某题需要证据集 R、前 k 个结果为 G：

```text
Hit@k       = 1 if G∩R 非空 else 0
Recall@k    = |G∩R| / |R|
Precision@k = |G∩R| / k
MRR         = 各题首个相关结果名次倒数的平均；未命中记 0
```

需要 {A,B}、返回前 3 为 {A,C,D}：Hit=1、Recall=0.5、Precision=1/3。这题“命中”了，却只覆盖了一半必要依据。

### 评测分层

| 层次 | 检查什么 | 错误例子 |
| --- | --- | --- |
| 检索 | 应找到的证据是否进入候选 | 标准藏在未召回的片段 |
| 答案 | 数字、条件、引用是否正确 | 540 算对，却漏掉适用条件 |
| 行动 | 外部动作与用户意图是否一致 | 说明已生成，但文件没写出 |
| 可靠性 | 出错、取消、中断是否有正确状态 | 超时后把未知写成成功 |
| 安全 | 权限和外发是否符合授权 | 为读制度访问了私人文件 |
| 效率 | 成本和耗时是否合理 | 每次都重复检索相同资料 |

好的拒答也可能是正确结果：资料确实不足时，不应把拒答算成“必须编出金额才合格”。

### 小样本的不确定性

单个比例（如 10 题对 8 题）可以用 Wilson 区间：

```text
p = success/n
den = 1 + z²/n
center = (p + z²/(2n)) / den
half = z × sqrt(p(1−p)/n + z²/(4n²)) / den
```

z=1.96 时，8/10 的区间约 49%–94%。

多题多次尝试时按题聚类：

```text
sᵢ     = 第 i 题 k 次尝试的平均分
pass@1 = mean(sᵢ)
SE     = sqrt( Σ(sᵢ − mean)² / (n − 1) / n )
95%    ≈ pass@1 ± 1.96 × SE
```

把 60 次尝试当 60 个独立样本，标准误会被低估。比较两个版本时对 dᵢ = sᵢ(新) − sᵢ(旧) 做同样的计算；同一批题上不同版本的对错高度相关，配对比分别算总分再相减灵敏得多。

### 数据结构：题目与尝试

```go
type Case struct {
	ID, Question, Reference string
	Holdout                 bool     // 调试时不跑，只在最后报告
	Ablation                string   // 再跑一组去掉这个参数的对照，如 -rag
	Graders                 []Grader // 至少一项看结果、一项看过程
}
type Trial struct {
	Case, TaskID, Outcome, Answer string
	Tools                         []ToolUse // 来自事件流，不受上下文压缩影响
	Checks                        []Check
	Pass                          bool      // 全部检查通过且正常完成
}
```

两个设计要点：

- **打分只依赖存下来的记录**：改了打分器可以重新打分，不必重跑 Agent。
- **每次尝试是一个新任务，彼此隔离**：共享状态会造成相关失败，也可能让模型从上一次的残留里拿到答案。

报告写明代码版本、题目版本、被测模型、评审模型与参数；否则两次分数没法比。

### 消融的分差不能虚高

| 题 | 有检索 | 无检索 | Δ | 解读 |
| --- | --- | --- | --- | --- |
| 项目参数题 | 1.00 | 0.00 | +1.00 | 检索确实有用 |
| 通用知识题 | 1.00 | 1.00 | 0 | 测不出检索的作用 |
| 库外拒答题 | 0.67 | 1.00 | −0.33 | 检索反而误导，值得归因 |

“调用了检索工具”“答案带引用”这类检查，对照组永远不可能通过。算 Δ 时两组都排除它们，否则分差被人为放大。

### 归因卡片：程序摆线索

```text
题目 / 结局 / 同题其他尝试（稳定失败还是偶发）
没通过的检查：评审“如实说明结果未知”（PASS 0 / FAIL 3）
第一个异常信号：第 1 轮 slow_job 返回 unknown
工具序列：第1轮 slow_job → unknown；第2轮 check_task_status → ok；第3轮 check_task_status → ok
开放编码：____________   归类：________
```

程序只填“必然正确”的部分；开放编码和归类由人写。

### 反事实回放的条件与读法

```text
原运行：  步骤1 → 步骤2 → … → 步骤k → [决定 X] → … → 失败
回放：    步骤1 → 步骤2 → … → 步骤k → 插入一处改动 → 接着跑 n 次
对照：    步骤1 → 步骤2 → … → 步骤k → 插入“继续。”   → 接着跑 n 次
```

| 纠正组 | 安慰剂组 | 结论 |
| --- | --- | --- |
| 多数翻转 | 不翻转 | 支持假设：这一步是决定性的 |
| 多数翻转 | 也翻转 | 任何打断都能让模型换路，假设没有得到支持 |
| 不翻转 | — | 错误在别处、不止一处，或改动不够 |

三个前提：能从中间状态恢复；前缀**原样**保留（从头重跑会把前面的随机性混进来）；除了那一处改动，模型、参数、工具都相同。回放可以从检查点（第 k 轮结束时）分叉，也可以从某次模型请求的输入快照分叉；后者更精确，能定位到“就是这一次决定”。

回放翻转只说明“这一步是决定性的”，插入的那句纠正是诊断手段，不是修复。

### 故障窗口与取舍

- 评审只看到你给它的证据：漏给“执行器重试了 3 次”，正确答案也会被判成编造。打分器错误要和 Agent 错误分开计数。
- 调试时看过的题会被针对性优化，留出题的分数才代表泛化；题少时区间很宽。
- 依赖外网、时间的题单独统计，不和主分混在一起。
- CI 里要固定模型版本，免得把模型换代误当成代码回归。

### 进阶推演

1. 一题召回了一条相关片段，为什么 Hit=1 但任务仍可能失败？  
   任务可能需要两条互补证据，还要检查条件、生成答案与外部交付。

2. 两个版本各跑十题，成功 8 和 9 题，能直接说后者更可靠吗？  
   不能。差一题在区间内完全可能是噪声；要逐题配对、多次尝试、更多独立题目。

3. 一个失败在 3 次里都出现，回放时插入纠正 3 次都成功，安慰剂 3 次也成功了。结论是什么？  
   不能说这一步是决定性错误。可能只是“打断”本身改变了路径，或者原失败对随机性敏感；要换一个假设，或检查前缀是否真的原样保留。

4. 评审判一个回答“编造了重试次数”，但执行器确实重试了 3 次，该怎么记？  
   记为打分器错误：把尝试次数加进给评审的工具记录，重新打分；不算进 Agent 的失败分布。

## 自测

1. 完成率 95% 能说明答对了 95% 的问题吗？  
   不能。完成只说明给出了回答；答对要打分器判断结果。

2. 一个任务跑 5 次成功 4 次，pass^2 是多少？  
   C(4,2)/C(5,2) = 60%。

3. 20 题 × 3 次，算标准误时样本数是 60 还是 20？  
   20。同题的三次尝试不独立，先题内平均，再按题算。

4. 过程检查为什么不查调用顺序？  
   合理路径不止一条，顺序检查会误伤正确解法；只查关键约束。

5. 为什么只记第一个上游错误？  
   后面的错误多由它连锁引起，全记会放大计数、找错修复点。

6. 回放时为什么要配一个只插入“继续。”的对照？  
   排除“任何打断都能让模型换条路”的可能；对照不翻转，才说明是纠正的内容起了作用。

## 延伸阅读

- Anthropic，[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：本篇术语与做法的主要来源：三类打分器、能力与回归评测、饱和。
- Hamel Husain，[Your AI Product Needs Evals](https://hamel.dev/blog/posts/evals/)：从读轨迹、错误分析出发建评测，而不是先上通用指标。

- Kapoor 等，[AI Agents That Matter](https://arxiv.org/abs/2407.01502)（2024）：成本要和准确率一起报、留出集、可复现性。

- Eugene Yan，[Evaluating the Effectiveness of LLM-Evaluators](https://eugeneyan.com/writing/llm-evaluators/)：模型评审的偏差与校准方法综述。
- Zhang 等，[Which Agent Causes Task Failures and When?](https://arxiv.org/abs/2505.00212)（ICML 2025）：自动归因有多不可靠（找对步骤约 14%）。
