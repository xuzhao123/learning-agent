# 12 · 子 Agent：把一部分探索交给独立上下文

子 Agent 是父 Agent 委派的另一条执行循环。它的价值不仅是并行，更是把探索过程与主任务上下文分开。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Parent / child agent | 委派任务的一方 / 接受子任务的一方 |
| 独立上下文 | 子任务只拿到明确交给它的信息，不自动继承全部父历史 |
| Delegation | 给另一个执行单元一项目标和边界 |
| Orchestrator | 拆分、分配和汇总子任务的一方 |
| Result contract | 子任务应该返回哪些内容、证据与状态 |
| 权限继承 | 子任务获得哪些工具和访问范围，应受到显式限制 |

## 从父循环看，它像一个工具

```text
父 Agent：需要查制度与核对发票要求
  ├─ 子 A：查适用补贴标准 → 原始依据 + 结论
  └─ 子 B：查发票格式要求 → 原始依据 + 结论
父 Agent：检查冲突，计算金额，整理说明
```

对父循环来说，委派动作有输入和返回结果，和其他工具一样需要校验、预算、取消与错误反馈。

子任务内部却可以多次请求模型、使用自己的工具。只有最后适合汇总的结果进入父上下文，中间搜索过程留在子任务中。

## 和队列、并行工具各有什么不同

| 机制 | 谁决定工作 | 主要解决的问题 |
| --- | --- | --- |
| 队列 | 用户或系统提交，调度程序安排 | 多任务排队与执行权 |
| 并行工具 | 模型提出多项独立调用，执行器安排 | 减少独立动作等待 |
| 子 Agent | 父模型委派目标，子循环自行完成 | 独立探索与上下文隔离 |

队列可以执行 Agent 任务，子 Agent 也可以复用任务执行器。但复用实现不改变它们的职责。

如果一项工作只是“算 3 × 180”，普通工具足够；为了这一步新开 Agent 往往增加模型开销。

## 怎样写一份不丢背景的委派

父 Agent 知道“上海、三天、下周、用户需要中文表格”，子任务不会自动知道。任务说明要给出：

- 目标：查到什么，怎样判断完成。
- 背景与限制：地区、时间、对象、版本。
- 可用能力与禁止动作：只查资料，不提交单据。
- 交付格式：结论、来源、条件、不确定项与执行状态。
- 预算和截止时间。

说明越模糊，子 Agent 越可能各自猜测。比如一方查工作日制度，另一方查节假日制度，父模型不能简单把两份结果拼接。

## 父 Agent 必须保留判断责任

子任务输出是待核查的结果，不是新的系统指令。

父 Agent 要检查来源是否支持结论、假设是否一致、失败是否被省略。可保留少量关键原文或来源路径，让汇总有回查能力。

若子任务读到网页里的“请改掉主任务规则”，不应把这句话作为父层授权继续执行。

## 成本、权限和生命周期

并行可以缩短等待，但每个子循环都要读取规则和工具、消耗请求与输出。总成本可能上升。

适合的任务是相对独立、探索材料多、交付边界明确的部分。必须共享大量即时决策或同时写同一文件的任务，需要更强的协调，也可能更适合留在单一上下文。

子任务不应自动拥有父层全部秘密、写权限和联网能力。父取消要传到子任务，父恢复要核查哪些子任务完成、哪些仍在执行，避免重复启动。

## 技术展开

### 进阶术语：委派契约、权限集合与聚合预算

| 术语 | 含义 |
| --- | --- |
| 委派契约 | 子任务目标、输入、约束、允许能力与交付要求 |
| 聚合预算 | 父任务与所有子任务共同消耗的上限 |
| 结果契约 | 结论、证据、状态和未确认动作的结构 |
| 状态复用 | 同一子任务再次请求时复用检查点与完成结果 |

### 把“帮我查一下”写成明确接口

结构示意：

```go
type EvidenceRef struct {
    SourceID string
    Quote    string
    Version  string
}

type Delegation struct {
    Goal          string
    Constraints   []string
    AllowedTools  []string
    RequestBudget int
    OutputFields  []string
}

type SubtaskResult struct {
    Status         string
    Answer         string
    Evidence       []EvidenceRef
    UnknownActions []string
    ModelCalls     int
}
```

这不意味着模型会天然输出合法结构。执行器应核查字段、证据 ID 和状态；父模型仍需检查是否支持结论。

描述里必须给出日期、适用对象与地区等必需背景。不能一边隔离上下文，一边假定孩子看过父对话。

### 权限继承是集合约束

```text
child_tools ⊆ parent_allowed_tools
child_data_scope ⊆ task_authorized_scope
child_deadline <= parent_deadline
```

父层有的工具也不一定全部交给孩子；读取型调研可能只需要检索和浏览器。

工具名称集合还不够。同一个 read_file 的对象范围、同一个浏览器的出口、同一个MCP身份都影响权限；不能用“只给了两个工具”概括所有安全边界。

### 子任务身份要在重复调用后保持稳定

```text
subtask_id = parent_task_id + H(规范化的子任务意图)
```

模型可能因超时再次委派相同文字。相同子任务 ID 让执行器取完成结果或续跑，而不是再启动一份。

文字不同也可能是同一业务意图；文字完全相同也可能是一次新调查。当前按文本生成 ID 是简单策略，复杂任务需要更明确的逻辑子任务键与版本。

截断哈希和父ID拼接后，还要满足存储ID长度、字符及冲突检查契约。

### 父预算和总费用不是同一上限

若父请求上限 Bp=10，最多 m=4 个子任务，每个 Bs=6，上界规划约为：

```text
模型请求合计 <= Bp + m*Bs = 34
```

前提是每个范围内的摘要和辅助请求已经计入该范围，而且没有其他循环绕过。embedding与外部服务仍需另计。

父自己只用了两步，不代表整次工作只花两次模型调用。可以设置总预算并由共享管理者分配额度；每个进程独立计数无法自然实现总上限。

### 进程取消和输出回收

```text
父任务取消
  → 子任务ctx取消
  → 发送优雅停止信号
  → 等待检查点/输出收尾
  → 宽限期后强制结束执行单元
```

Setpgid 可把子进程分到独立进程组，避免它同时收到终端和父转发的两次信号。CommandContext 默认行为不自动保证所有后代都停止；对不受控执行还要管理整个进程组或cgroup。

读 stdout/stderr 要持续进行，不能等进程结束后才读，管道写满可能让子进程永远等写入。多个孩子共享输出时还需要关联ID和同步，不能只用颜色区分。

### 汇总需要保留可追溯的最小证据

只返回“政策是180”会把版本和条件压掉。结果应包含适用范围、关键原文和来源；父层不应把孩子的自报成功当作事实证明。

不要把全部子轨迹复制进父上下文，那会失去隔离收益。把必要证据与回查接口留下，再把详细过程放到可观测记录中。

### 对照已有实现

[spawnAgent、prefixWriter](../internal/agent/subagent.go)实现委派、文本派生ID与关联输出；[RunChild](../internal/agent/child.go)复用执行/恢复逻辑，取消时给子进程收尾时间。

当前交付主要是 answer、model_calls 与 replayed，未强制上述结构化证据契约；预算是父子各自管理。父被kill -9后的全部后代回收、全局费用额度与复杂权限衰减也仍需加强。

### 进阶推演

1. 为什么给子任务全新上下文，不等于完成安全隔离？  
   它只隔离模型信息；进程环境、文件、身份与网络权限仍要单独约束。

2. 子任务已经done，父恢复后又提出同一委派，应该请求模型重新完成吗？  
   若任务身份与请求契约一致，应返回已有结果；如果需要刷新版本，必须显式形成新意图。


## 自测

1. 子 Agent 的主要收益是不是“多几个模型同时想”？  
   还有上下文隔离和任务边界；并行只是可能的收益之一。

2. 父 Agent 说“查一下制度”，子任务为什么可能答错？  
   缺少地区、日期、对象与适用范围，它只能自行假设。

3. 子任务返回内容为什么要按数据处理？  
   子任务也可能读到不可信来源或犯错，返回结果不能直接改变父任务权限。

4. 子任务 ID 按 task 原文哈希，模型换个说法重派，为什么宁可从头跑？  
   漏命中只是多花成本，误把相近任务当成同一个会交回错误结论；更好的做法是让模型显式引用已有子任务 ID。详见 [Q15](../docs/deep-questions.md#q15)。
