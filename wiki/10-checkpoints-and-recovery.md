# 10 · 持久化与恢复：进程结束后任务怎样继续

检查点保存任务进度；恢复逻辑解释这个进度。真正困难的部分是“可能已经执行，却来不及记录结果”。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| 持久化 | 把需要跨进程保留的内容写到可靠存储 |
| Checkpoint | 可以恢复任务的状态快照 |
| 写前日志 | 执行前先记录打算做什么 |
| Crash window | 外部动作和本地记录之间可能突然中断的间隙 |
| Atomic write | 读者看到完整旧状态或完整新状态 |
| Lock | 防止两个执行者同时修改或恢复同一任务 |
| Idempotency | 重复提交同一业务操作，效果不重复产生 |

## 检查点需要保存什么

只存“做到第 3 步”不够。恢复后的程序还要知道那一步依据什么、已经拿到哪些结果、哪些动作仍未确认。

常见内容包括：

- 任务 ID、目标和运行配置。
- 实际模型视图与已有工具结果。
- 当前状态、停止原因、未完成调用。
- 已用预算与重复动作计数。
- 已确认完成的输出或子任务结果。

预算也要持久化。否则每次恢复都重新获得完整预算，一个失控任务就可以靠反复续跑一直消耗。

不同目的的数据要区分：完整轨迹用于查经过，检查点用于恢复，最终输出用于交付。它们不一定需要同一份结构。

## 先记录意图，再执行

```text
模型提出操作
  → 保存“准备执行”的调用与 ID
  → 运行工具
  → 保存结果与状态
  → 请求模型继续
```

这让崩溃后的程序看见：存在一项准备执行的操作，但没有确认结果。

它不能证明操作一定执行了，也不能证明没执行。写前日志保留了需要核查的窗口，没有消除窗口。

## 用四个中断位置理解恢复

| 中断位置 | 已知情况 | 恢复策略 |
| --- | --- | --- |
| 调用意图未保存，工具也未运行 | 没开始 | 从此前状态继续决定 |
| 意图已保存，工具是否开始不明 | 可能未执行，也可能正在执行 | 保守处理未确认调用 |
| 外部已成功，本地结果没保存 | 外部效果可能已存在 | 查状态或用相同幂等键核对 |
| 结果已保存，下一轮未开始 | 已有可信结果 | 使用已有结果，避免重复动作 |

其中第三种最危险。任务级检查点不能代替外部接口的幂等设计。

只读工具通常可以重新读取，但数据可能已经变化，读取也可能计费。应记录这是一次恢复后的新观察，而不伪装成旧结果。

## 两类恢复模型

**从头重跑**较简单，适合任务便宜、可重复、外部状态可安全重置的情况。

**从检查点继续**减少重复成本，适合长任务和已有有效结果的情况，但需要维护消息配对、版本兼容和未确认动作。

例如制度检索结果和金额已经保存，生成说明前进程结束。恢复时可继续生成，而不再查制度和算金额。若制度需要实时更新，则要显式决定是否重新核查版本。

## 存储可靠性有不同层次

临时文件写完整再原子替换，有助于避免半份检查点；要承受断电，还要考虑文件落盘、目录同步和存储本身的保证。

单机文件锁可阻止两个进程同时续跑一个 ID。多机上的执行权需要其他协调机制，不能把本机锁当成全局锁。

程序升级也可能改变状态结构或工具语义。检查点应有兼容策略，不适配时明确拒绝或迁移，避免悄悄用新代码解释旧状态。

## 完成结果也应保留

已完成任务再次被领取，直接返回已保存结果，而不是重新调用模型。这样节省成本，也避免重复副作用。

但同一个任务 ID 配了不同内容时不能静默返回旧答案。应检查身份与参数是否一致，更多说明见 [任务调度](11-task-scheduling.md)。

## 技术展开

### 进阶术语：原子性、耐久性与日志粒度

| 术语 | 含义 |
| --- | --- |
| 原子性 | 不看到一半新状态、一半旧状态 |
| 耐久性 | 成功提交后，按存储契约能否承受断电等故障 |
| 事务边界 | 哪几项状态一起成为可见的新版本 |
| 日志粒度 | 以整任务、整批还是每项动作保存进度 |
| 执行权 | 当前谁有资格继续并提交这个任务 |
| Fencing token | 每次取得执行权时使用更高代号，结果端拒绝旧持有者提交 |

### 把检查点理解成一个恢复契约

结构示意：

```go
type PendingAction struct {
    CallID      string
    OperationID string
    Tool        string
    Args        json.RawMessage
    State       string
}

type Snapshot struct {
    SchemaVersion int
    TaskID        string
    RequestHash   string
    CallsUsed     int
    View          []json.RawMessage
    Pending       []PendingAction
}
```

需要 encoding/json。CallID 服务模型配对，OperationID 服务业务恢复；不应随着执行器重试随意改变。SchemaVersion 用来拒绝或迁移不兼容状态。

同一个任务 ID 的配置、问题与参数也要匹配；否则“恢复旧任务”会变成“拿旧结果回答新任务”。

### 存盘的三个保证不能混为一个

| 操作 | 主要保证 | 不自动保证 |
| --- | --- | --- |
| 持锁 | 避免多个遵守同一锁的写者竞争 | 断电不丢失 |
| 临时文件+rename | 文件内容原子替换 | 文件和目录都已稳定落盘 |
| 文件Sync+目录Sync | 在支持的文件系统上增强耐久性 | 网络业务动作与本地日志一起提交 |

更完整的本地写入函数示意：

```go
func atomicWrite(path string, data []byte) error {
    dir := filepath.Dir(path)
    f, err := os.CreateTemp(dir, ".checkpoint-*")
    if err != nil { return err }
    name := f.Name()
    defer os.Remove(name)
    defer f.Close()

    if err := f.Chmod(0o600); err != nil { return err }
    if _, err := f.Write(data); err != nil { return err }
    if err := f.Sync(); err != nil { return err }
    if err := f.Close(); err != nil { return err }
    if err := os.Rename(name, path); err != nil { return err }

    d, err := os.Open(dir)
    if err != nil { return err }
    defer d.Close()
    return d.Sync()
}
```

需要 os、path/filepath；目录必须已存在。示例针对支持相应语义的本地文件系统。rename 已成功后目录 Sync 失败，函数仍返回错误，但新文件可能已经可见；不能简单等同于“没有提交”。文件与目录同步的区别见 [fsync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)。

### 外部动作和本地日志无法靠rename一起原子提交

```text
本地：记录op-1准备创建
外部：创建成功
崩溃：未记录业务结果
恢复：只看到op-1未确认
```

即使本地写入完全可靠，也不知道外部是否成功。需要下游接受同一个 OperationID 去重，或能按它查询结果。

“至少一次恢复 + 可靠执行端去重/事务”可以追求一次业务效果；只有本地检查点无法产生这一保证。跨边界更复杂时要讨论补偿流程，而不是把分布式事务当作文件写入问题。

### 保存粒度改变恢复代价

整批有十项调用，九项完成后进程结束：

- 按批保存：可能十项都没有本地确认，需要逐项核查。
- 按调用保存：可以只核查剩下的一项，但写入次数与同步成本增加。
- 事件日志：逐项追加，再定期快照，需要回放、完整性与序号设计。

即使每项及时保存，外部成功到记录之间仍存在窗口，只是窗口更小。

### 预算持久化也存在崩溃窗口

已保存的 CallsUsed 可以跨恢复沿用；但模型请求已发出、还没记录计数时被 kill，账面可能少计一次。

强预算要求在发出请求前持久化预占，或使用独立的计费/调用账本。单靠任务结束时保存次数，不能做到精确费用审计。

### 单机锁与分布式执行权不同

文件锁只能协调共享该锁语义的执行者。多实例使用租约时，旧执行者暂停后恢复，可能在租约过期后继续提交。

常见更强办法是给每次执行权一个递增 fencing token，由结果接收端拒绝旧 token。它不是“多加一个时间戳”，必须实际参与写入校验。

### 对照已有实现

[Checkpoint.write、LockCheckpoint、resumeContext](../internal/agent/checkpoint.go)提供临时文件替换、flock 和未确认调用恢复；[Run 与 replayBatch](../internal/agent/react.go)以执行边界保存消息，恢复可重复调用或回填未知。

当前写入没有文件/目录 fsync、状态版本迁移或分布式 fencing；模型请求计费也不是独立耐久账本。上述更强写入和状态结构是学习用设计，不作为当前实现保证。

### 进阶推演

1. rename 成功、目录Sync失败，能不能删掉新文件并说回滚了？  
   不能随意这样解释。新状态可能已对其他读者可见，处理要报告提交阶段与耐久性不确定，遵守明确恢复契约。

2. 为什么每个工具结果都存盘，仍不能单独保证恰好一次？  
   外部完成与结果记录不是同一事务，最小窗口仍可能产生未确认副作用。


## 自测

1. 有写前日志，是否就能保证每个外部动作只执行一次？  
   不能。外部成功到本地记录之间仍可能崩溃，需要执行端去重或查询结果。

2. 为什么检查点要包含预算？  
   恢复是同一任务继续，不应借重启绕过成本与失控上限。

3. 恢复历史里只有工具请求、没有结果，应怎样处理？  
   先当成未确认动作，根据只读、幂等或可查询性决定恢复；不能直接补一句成功。

4. 把有副作用的工具误标为可重复，或者检查点只存 View，续跑会怎样？  
   前者会让程序替模型把副作用再做一遍；后者能保证下一步输入相同，但不保证之后的压缩与不中断时一致。详见 [Q13](../docs/deep-questions.md#q13)、[Q14](../docs/deep-questions.md#q14)。
