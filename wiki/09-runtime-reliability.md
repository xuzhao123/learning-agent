# 09 · 运行时与可靠性：出错以后怎样有序停下或继续

运行时负责把“模型会行动”变成“行动有时间、成本与状态边界”。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Budget | 一次任务最多使用的请求、时间或资源 |
| Retry | 再尝试同一个操作 |
| Backoff / Jitter | 重试前逐渐等待 / 给等待加随机变化 |
| 熔断 | 达到失控条件后暂停或停止继续执行 |
| Timeout | 超过等待时限 |
| Cancellation | 请求执行链路停止 |
| Deadline | 最晚结束的时间 |
| 结果未知 | 动作可能发生，但没有确认结果 |

## 三个护栏分别防什么

| 护栏 | 防止的问题 | 没有解决的问题 |
| --- | --- | --- |
| 请求预算 | 无限调用模型、持续消耗 token | 单次请求一直等待 |
| 有限重试 | 暂时抖动造成任务立即失败 | 永远无效的参数、重复副作用 |
| 无进展熔断 | 原地重复执行相同动作 | 合法但很长的任务 |

预算 10 次容易打断长任务；50 次给正常任务更多空间，也允许失控过程消耗更多成本。需要按任务确定，并计算主请求、摘要和其他辅助调用的开销。

相同工具与参数连续多次出现，可作为无进展信号，但不应只看名字。轮询可能每次结果都在变；A、B 交替也可能永远没有进展。应结合动作、结果变化和任务推进情况判断。

## 先记录结局，再看能不能重试

| 结局 | 当前知道什么 |
| --- | --- |
| 成功 | 拿到足以确认的执行结果 |
| 确定失败 | 知道执行没有完成目标；是否有部分副作用仍需工具说明 |
| 未执行 | 尚未开始，通常没有本次动作的副作用 |
| 结果未知 | 开始过，可能完成，也可能没完成 |

读超时只能证明“没有及时拿到响应”，不能证明“外部没有执行”。

```text
提交报销单
  → 服务端已创建
  → 响应在途中丢失
  → Agent 只看到超时
```

此时重新创建可能产生两张单据。应查询状态，或复用服务端认可的幂等键；否则返回未知，等待核查。

## 错误处理要同时问原因和安全性

参数缺失、工具不存在、无权限，重复相同请求通常没用。应回填有用错误，让模型修正参数或请求人处理。

网络抖动、限流或服务端故障可能暂时恢复。但“值得再试”还不等于“可以安全再试”：一个 5xx 响应前也可能已经写入部分业务状态。

工具封装最了解这些语义，应返回明确的分类与结果状态；执行器依据结构化标记处理，不靠错误文本里有没有某个词。

一个实用判断顺序：

```text
任务已取消 / 超预算？        → 停止
同参数一定还会失败？         → 回填错误，不自动重试
结果可能已发生副作用？       → 先核查或使用幂等
属于可恢复且安全的操作？     → 有限退避重试
```

模型改了参数后再调用，是一个新决策，不是执行器偷偷重复旧请求。

## 退避与重试放大

等待可以按 0.2、0.4、0.8 秒增长，加入抖动让大量客户端错开时刻；具体间隔应按服务情况设置。

如果工具封装、执行器、任务队列各重试三次，一个失败可能触发多达 27 次下游尝试。重试策略要有明确归属和总预算，不能每一层都独立觉得“我只重试三次”。

重试耗尽后，错误应作为 observation 回流。隐藏错误会让模型以为外部动作成功，或继续使用同一组无效参数。

## 取消为什么需要协作

Go 的 context.Context 用于传递取消与截止时间。它不会强行停止一个任意函数。

网络请求要接收取消，等待要监听取消，长循环要定期检查。父任务取消应传到子任务；下层截止时间不能晚于上层。

若总任务还剩 5 秒，工具自己的 30 秒上限也只能用剩下的 5 秒。

不配合取消的函数可能在后台继续运行。需要强制回收的执行，应放到可被整体结束的进程或沙箱中。

## 停止不是撤销

有序停止包括：不再接收新工作、取消在途动作、记录它们的结局、保存进度、回收资源。已经发生的写入不会因为取消而自动回滚。

“生成文件”执行到一半，可能留下临时文件；“提交单据”执行到一半，可能已经完成。结果报告应区分，而不是统一说“已停止，所以未发生”。

## 技术展开

### 进阶术语：逻辑调用、尝试与未知结果窗口

| 术语 | 含义 |
| --- | --- |
| 逻辑调用 | 一项由模型提出的工具动作 |
| Attempt | 执行器对该动作的一次尝试 |
| Retry budget | 整个生命周期允许额外尝试的上限 |
| 未知结果窗口 | 外部开始处理到程序得到可信确认之间 |
| Cancel propagation | 停止信号沿调用树向下传递 |

### 错误分类需要两个轴

只分“暂时/永久”不够，还要分“未执行/已执行/未知”。

| 原因 | 外部结局 | 处理 |
| --- | --- | --- |
| 参数错误 | 未开始业务执行 | 回填，等待新参数 |
| 限流 | 服务明确保证未执行 | 按预算和Retry-After重试 |
| 连接中断 | 可能已创建单据 | 查询或同幂等键核查 |
| 单据已部分写入，后续步骤报错 | 已有部分副作用 | 补偿或继续，不盲目整项重做 |

HTTP 5xx、读超时甚至业务 error 都不能单独证明“没有效果”。最了解下游语义的封装层应报告原因与结局，执行器不要猜。

### 退避公式与时间预算

```text
backoff(i) = min(cap, base*2^i)
full_jitter(i) = Uniform(0, backoff(i))
最坏等待 ≈ sum(backoff(i))
逻辑调用时间 ≈ 各次尝试时间 + 各次等待
```

base=0.2 秒，三次额外重试的最大退避为 0.2+0.4+0.8=1.4 秒。若每次最多等 5 秒，初次加三次重试的最坏耗时约 21.4 秒，还未计调度开销。

deadline_left 小于等待时间时，不应睡完再开始一个已经来不及的尝试。错误文本回填也应保留最后结局，不能说“重试四次所以肯定没执行”。

### 取消信号与goroutine生命周期

结构片段：

```go
var ErrResultUnknown = errors.New("result unknown")

func waitAttempt(ctx context.Context,
    invoke func(context.Context) (any, error)) (any, error) {
    type outcome struct { value any; err error }
    done := make(chan outcome, 1)
    go func() {
        value, err := invoke(ctx)
        done <- outcome{value, err}
    }()
    select {
    case o := <-done:
        return o.value, o.err
    case <-ctx.Done():
        return nil, fmt.Errorf("%w: %v", ErrResultUnknown, ctx.Err())
    }
}
```

需要 context、errors、fmt。带缓冲的 done 防止调用方先返回后，工作 goroutine 永远卡在发送结果；它并不能停止 invoke，也没有处理其中的 panic。

ctx 取消后 invoke 若不配合仍会继续。父 goroutine 的 recover 不能捕获子 goroutine 的 panic。对必须强制终止的代码，需要独立进程与整个执行单元的清理。

结果与取消同时到达时，select 可以选中不同分支；保守返回未知是合理的，但不能因此宣称动作被撤销。详细取消契约见 [Go context 文档](https://pkg.go.dev/context)。

### 熔断键与“没有进展”要分开

工具内部重试不是模型新动作，不能每次 attempt 都增加模型重复动作计数。

一个动作键可由工具名与规范化参数组成；进展还可由结果摘要或任务状态变化表达：

```text
recent = [(action_key, result_hash, progress_marker), ...]
```

A、A、A 且结果不变很可疑；A、B、A、B 也可能卡死；相同轮询但进度从 10% 到 30% 不应误判。

结果哈希应排除时间戳、随机追踪 ID 等噪声，否则无进展结果每次都表现为“不同”。窗口和阈值仍需业务评估，不能只加一个计数就解决全部循环。

### 工具非零退出与执行器错误不同

Shell exit 2 可以是可解释的命令结局，返回 stdout/stderr 和退出码给模型。沙箱无法启动则属于执行器失败。两者不应走同一条无条件重试分支。

若命令已开始，后续等待超时，仍应标未知并清理进程；清理成功证明它不再继续，不证明此前没有写文件。

### 对照已有实现

[runWithRetry、runAttempt、replayBatch](../internal/agent/react.go)区分尝试、不可重试与未知；[runTool](../internal/agent/dispatch.go)在工具边界处理 panic。可重复工具通过显式集合控制。

当前退避没有随机抖动，重复检测主要针对相邻动作；结果未知仍需要工具本身的幂等或查询能力。上面的多轴分类与滑动进展窗口是扩展思路，不是已完成实现。

### 进阶推演

1. goroutine 超时后返回未知，为什么还可能越过并发上限？  
   外层释放许可，但不配合取消的底层工作仍在运行。要控制真实在途数量，需生命周期可管理的执行单元。

2. 客户端、执行器、队列各允许三次总尝试，为什么会到27次？  
   每层的一次可能触发下一层三次；三个独立重试层相乘。需要统一总预算或明确重试归属。


## 自测

1. 收到超时，为什么不能一律标为失败？  
   外部可能已经成功，当前只是没有收到确认。

2. 429 可以重试，是否意味着所有创建操作遇到 429 都直接重发？  
   还要看请求是否已执行、服务契约和幂等支持；状态码只是分类线索。

3. max_steps 很小，是否就不需要超时？  
   仍需要。一次请求可能永远不返回，步数预算限制不了等待时间。
