# 13 · 浏览器与代码执行：连接动态页面和计算环境

普通查询工具返回数据，浏览器和 Shell 则让程序进入更复杂的外部环境。能力变强，执行边界也要更明确。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| DOM | 浏览器解析页面后形成的结构树 |
| CDP | 程序控制 Chrome 等浏览器的协议 |
| 渲染 | 把 HTML、样式和脚本计算成用户看到的页面 |
| 等待条件 | 指定什么出现才算可以继续，而不是固定睡几秒 |
| Screenshot / Screencast | 某一刻截图 / 连续推送画面帧 |
| Shell | 接收命令，启动其他程序的解释器 |
| Exit code | 命令结束状态，0 常表示成功，其他值需结合具体程序理解 |
| Sandbox | 限制代码可使用的文件、网络、权限和资源 |

## 什么时候需要真实浏览器

资料通过简单 HTTP 返回完整正文时，普通请求更轻量。页面内容依赖脚本、动态加载或交互时，真实浏览器才能看到相关状态。

```text
打开页面
  → 页面加载与脚本运行
  → 等待正文条件
  → 提取可见文本和来源
  → 返回工具结果
```

浏览器并不自动把网站上的所有信息变成事实。还要检查页面是否正确、是否过期、是否需要登录、是否显示验证码。

## 等什么比等多久重要

“页面 load 完成”不一定表示制度正文已经加载。页面可能先显示框架，再异步读取资料。

应等待具体条件，如正文元素出现、内容非空或目标结果可用，同时设置截止时间。

固定等 3 秒，快时浪费时间，慢时仍没加载完。等待条件也会失败，失败后应如实说明，不能把空页面当作没有制度。

## 工具返回内容要可用

返回标题、URL、正文片段和必要的链接，标明截断。很长的页面可以按关键词定位、分页或按章节读取。

例如先查“补贴标准”，再定位“180 元”附近的条件，比每次返回完整网页更节省窗口。但要避免只拿数字而丢掉适用范围。

同一页多次查找是否重新加载、多个动作是否共享会话，都应成为工具契约。独立调用不等于保留登录、当前标签页和页面状态。

## 画面与执行结果用途不同

截图帮助人看出页面是不是没加载、是否卡在验证。连续帧帮助看过程。

画面显示“成功”不一定证明后端动作成功；文字结果也可能只截到了提示。操作型浏览器需要核查外部状态，不能只看按钮已经点击。

图像数据会增加传输和存储成本，可只保留必要帧与步骤证据。

## Shell 能带来什么

Shell 可以组合文件、程序和计算，把“生成说明文件”从一段回答变成实际交付物。

模型只生成命令文本，执行器负责决定是否执行，并记录 stdout、stderr、退出码、超时和产出位置。

非零退出码也有信息价值。有些程序用它表达未找到匹配；有些表示编译失败。应把实际结果交回模型，不能只抛出一个通用异常让循环崩溃。

输出过长时要明确截断，并说明是否能够再读取；不能伪装成完整日志。

## 有副作用的命令不要偷偷重做

一条命令可能先写完文件，再因为后续步骤失败而退出非零。整个命令“失败”不代表没有发生修改。

命令超时后也可能仍有后台子进程。执行器要结束整个执行单元，并记录已知与未知结果。默认自动重试任意 Shell 命令容易重复产生副作用。

沙箱目录可在任务中保持，单次 Shell 的环境却可能不会持续。下次调用是否保留文件、工作目录、环境变量，要明确说明。

## 浏览器与 Shell 组合的边界

Shell 断网，并不意味着它读出的内容无法外发。模型可以把 Shell 返回的秘密放进浏览器 URL。

浏览器与代码执行的安全设计要联合分析，不能各自检查一次就宣布整个系统安全。下一篇详细解释这些边界。

遇到网站验证或禁止自动访问，应报告状态，选择可用接口、其他合法来源或由用户协助。把验证绕过去不应成为这个工具的正常策略。

## 技术展开

### 进阶术语：条件等待、远程对象与背压

| 术语 | 含义 |
| --- | --- |
| 条件等待 | 等待目标状态成立，同时接受取消与截止时间 |
| Remote object | 浏览器脚本求值返回的协议对象，不一定就是正文字符串 |
| Backpressure | 帧或输出消费不及时，限制后续积累 |
| 退出信号 | 进程被信号结束，与正常非零退出要区分 |
| 启动阶段 | 执行器、沙箱或业务命令尚未完成启动的阶段 |

### 读取正文需要一个明确的完成谓词

```text
ready(page) =
  目标元素存在
  AND 正文非空
  AND 需要核查的页面状态已加载
```

不是所有页面都能用同一个 selector，也不能把“body出现”当作业务资料就绪。

执行路径需要总截止时间、检查频率、脚本异常与结果长度上限。脚本返回远程对象或异常时，要正确解析协议结果，不能把undefined当成空制度。

源代码里的脚本不是无害字符串：必须由可信工具组装，正确编码输入。把模型参数直接拼进JS表达式会产生脚本注入，应用参数化或JSON编码。

### 标签页与ctx的生命周期

```text
共享浏览器进程
  ├─ 一次工具调用的标签页ctx
  │     └─ 本次网络/求值/画面订阅
  └─ 另一次工具调用的标签页ctx
```

父任务停止应关闭自己的标签页与订阅；单页关闭不应误关其他任务。浏览器崩溃则会影响共享进程中的所有页，需要另一类处理。

“打开新标签页”不自动保证完全独立的登录、cookie、缓存。真正隔离会话状态需要浏览器上下文或独立进程策略；工具要说明自己的状态保持方式。

### 画面流不能无限排队

screencast 有帧和session ID，消费后需要协议ack。否则浏览器会限制继续发帧；不要把帧订阅当作没有流控的视频管道。

可以使用容量1的“最新帧”通道，丢掉过时画面而保留最新状态：

```go
func publishLatest(ch chan []byte, frame []byte) {
    select {
    case ch <- frame:
        return
    default:
    }
    select {
    case <-ch:
    default:
    }
    select {
    case ch <- frame:
    default:
    }
}
```

这是队列策略片段，不包含CDP订阅或ack。假设通道由明确的生产者/生命周期管理，frame在发送后不被修改。发送者退出前不能关闭通道，否则发送会panic；并发生产时“最后发起”等于“最新画面”还需序号判断。

新调用开始后，旧调用迟到的帧也可能覆盖界面。帧需要带任务、调用与序号，页面只接受当前订阅范围。协议方法见 [CDP Page](https://chromedevtools.github.io/devtools-protocol/tot/Page/)。

### 命令状态不能只靠err != nil

函数片段，返回“调用结局、命令退出码、执行错误”三个维度：

```go
func commandOutcome(ctx context.Context, err error,
    started bool) (string, int, error) {
    if !started { return "not_run", -1, err }
    if ctx.Err() != nil { return "unknown", -1, ctx.Err() }
    if err == nil { return "ok", 0, nil }

    var exitErr *exec.ExitError
    if errors.As(err, &exitErr) {
        return "ok", exitErr.ExitCode(), nil
    }
    return "unknown", -1, err
}
```

需要 context、errors、os/exec。ok表示获得一次命令结局，不表示业务成功。沙箱启动失败还需要独立阶段标签；包装进程退出也不能总被当作业务命令退出。

### 输出捕获也有正确性要求

CombinedOutput 会积累完整输出，不适合不受控命令。受限捕获器应保持：

```text
保存内容大小 <= head_limit + tail_limit
实际写入字节数单独统计
Writer.Write即使丢弃内容，也返回原len(p)
展示时标明中间遗漏，不伪装完整输出
```

保留头尾要避免短输出重复、UTF-8截断乱码、多个写者竞争和stdout/stderr混淆。压缩采集量不等于限制进程生成输出的CPU/磁盘成本。

超时还要清理整个执行单元。CommandContext终止直接子进程，不自动证明其后台后代全部结束；只等Wait返回也不能替代进程树或cgroup回收。

### 对照已有实现

[inTab、waitFor、guard、writeFrame](../internal/browser/browser.go)已有业务轮询、标签页取消与画面；[sandbox.run、capture](../internal/sandbox/sandbox.go)提供命令结果与头尾捕获。

上面的队列与命令分类片段是通用设计，不是当前函数的逐行副本；会话隔离、协议覆盖与资源回收仍应结合实际运行检查。

### 进阶推演

1. 固定睡三秒改成“每100ms看一次”，是否就一定正确？  
   还要检查谓词、异常、总截止时间及目标状态变化；只是换了等待形式还不够。

2. 输出只保存16KB，是否就能防止命令写满磁盘？  
   不能。捕获器控制进入内存/模型的内容，工作目录写入仍需配额和资源限制。


## 自测

1. 等到 load 事件，为什么仍可能提取不到制度？  
   页面可能还在动态请求或渲染正文，需要等待业务条件。

2. 命令退出码非零，是否就可以认定没有任何文件被修改？  
   不能。此前步骤可能已经成功，必须结合输出和外部状态判断。

3. 浏览器截图与工具文字结果，哪个是绝对可靠的证明？  
   都不是。要看它们能证明哪个状态，并对重要外部动作进行核查。
