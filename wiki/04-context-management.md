# 04 · 上下文管理：让模型看到足够而不过量的信息

模型能利用的是本次请求。上下文管理负责选择这一次给它看什么，以及窗口不足时怎样保留任务的关键部分。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Token | 模型处理内容的单位，不能固定用字符数精确换算 |
| Tokenizer | 把文本转换成 token 的具体规则或程序 |
| Usage | 模型服务返回的用量统计，用来校准本地估算 |
| Context window | 一次处理的容量限制 |
| Transcript | 系统保存的完整原始记录 |
| View | 实际发送给模型的内容 |
| Truncate / Trim | 缩短单条内容 / 移除一部分历史 |
| Summarize | 用有损摘要替代一段历史 |
| Prefix cache | 复用相同输入前缀的计算，不负责存储业务记忆 |

这里的“上下文”是模型输入。Go 的 context.Context 是取消与截止时间的传递对象，两者只是中文名称相同。

## 记录还在，为什么模型仍会忘记

把完整记录想成资料柜，把 View 想成桌面上摊开的几页材料。柜里保留着原文，只能证明系统存了它；模型本次没有收到，也没有查询工具，就无法使用它。

```text
原始消息和工具结果
  ├─ 完整记录：保留原文，供审计或重新取回
  └─ 模型视图：按当前任务与预算组织
```

压缩通常替换 View，而不改写完整记录。若要重新读取原文，必须有真实的取回路径；一个“内容已省略”的占位符本身没有读取能力。

## 先做容量规划

一个便于理解的预算模型是：

```text
可用输入 = 总窗口 − 计划输出空间 − 安全余量
```

例如按 10,000 token 规划，输出预留 2,000、安全余量 500，可用输入约 7,500。系统规则、工具定义、用户消息和历史都要占这部分空间。这是估算例子，具体供应商的输入、输出与推理计量方式要另行核对。

本地预留输出空间和向 API 传输出上限是两件事。一个决定“输入最多装多少”，另一个决定“模型最多生成多少”。把输出限制设得太低，推理或回答可能被截断。

使用 tokenizer 或 API 的真实 usage 校准粗估；中文、JSON、工具定义与密文的估算误差可能很不同。

## 三种处理各损失什么

| 方法 | 怎么做 | 收益 | 风险 |
| --- | --- | --- | --- |
| 单条截断 | 保留长结果的关键字段或头尾 | 不让一个输出吃满窗口 | 丢掉中间的条件或证据 |
| 历史裁剪 | 移除旧消息或旧消息组 | 快、无需摘要调用 | 早期目标和约束可能丢失 |
| 历史摘要 | 用短说明替换较长历史 | 保住重要任务信息 | 额外成本、摘要有损、重复摘要会漂移 |

旧工具结果不一定都该进摘要。一次性的长列表可以清理；决定后续行动的具体数字、错误状态和来源则应保留或可重新读取。

最好的减量常发生在工具入口：分页、按关键词过滤、返回需要的字段，比事后截断整页更可靠。

## 保留消息组，不拆断调用关系

一次 assistant 工具请求与它对应的所有 tool 结果形成一个相互关联的组。裁剪不能留下一个缺结果的请求，也不能留下找不到请求的结果。

最近原文应该按完整组保留。只数“最近六条”容易切进一个并行调用的中间，破坏协议结构。

系统规则通常作为稳定来源重新提供；用户的关键目标、修改与约束应优先保留。最近消息则保障正在执行的局部流程。

## 摘要到底压成什么

一个常见结构：

```text
系统规则
关键用户原话
交接摘要：目标、已做事项、结果、未解决问题
最近的完整消息组
当前新输入
```

摘要应区分已确认事实、推断、失败和结果未知，并保留后续需要核查的来源。

“压到最小”不是唯一目标。保留内容越多，最低占用越高；压得太狠会省 token 却丢掉继续执行的能力。合理目标是足够短、关键信息不失真。

压缩先在副本上生成和检查。成功且符合预算后再替换 View，避免摘要失败时连旧上下文都丢掉。

## 什么时候触发，为什么会看到锯齿曲线

系统可按用量、剩余空间或上游超窗错误触发处理。触发线和压缩后目标应留出间距，否则每轮都要重新摘要。

平时输入积累，压缩后下降，再继续增长，于是形成锯齿。谷底由保留的原话、摘要、最近消息和固定规则决定，不要求每次一样。

前缀相同可能有利于缓存，但不能保证供应商命中。压缩改变历史后，部分前缀可能继续复用；不能一概说全部缓存必然失效。

## 技术展开

### 进阶术语：校准、滞回与保留区

| 术语 | 含义 |
| --- | --- |
| 校准 | 用 API 真值修正本地粗估口径 |
| 滞回 | 触发处理和处理后目标分开，避免阈值附近来回抖动 |
| 保留区 | 不参加本次摘要的系统规则、原话或最近消息组 |
| 摘要预算 | 重建窗口后可分配给交接摘要的空间 |
| rho | 真实用量与粗估值的比例，用于当前范围内的布局校准 |

### 两套计量不能混用

粗估可以用于消息增量和布局，API usage 用于校准。一个实用估计是：

```text
used ≈ 上次请求的可复用用量 + 之后新加入消息的估算
```

这里“可复用”要按协议确定：输出哪些内容会被再次送入输入，推理字段跨用户回合是否保留。不能把所有供应商的总 token 都直接当下一轮输入。

例如真实报告 5,400、对应视图粗估 3,600，比例 rho=1.5。若当前可用容量是 9,000，布局计算可先使用约 6,000 的粗估容量，再给误差留余量。

这只是当前范围内的校准。工具定义变化、大图像、新用户回合丢弃旧推理等都可能使比例变化，不应永久套用一次观测。

### 把压缩布局写成方程

```text
A = 总窗口 - 输出预留 - 安全余量
S = system与tools
U = 保留用户原话
R(K) = 最近K个完整组
D = 新摘要

压缩后需要：S + U + R(K) + D <= 接受上限
摘要空间：D_budget = 接受上限 - S - U - R(K)
```

如果 D_budget<=0，摘要模型再聪明也装不下。应减少可变的最近组、重新选择原话或拒绝继续，不能无限重试摘要。

数值例子：接受上限 4,000，S=700、U=1,000、R(2)=2,000，只剩 300 给摘要；减少一组到 R(1)=900，则有 1,400。保留组数本身需要参与容量计算。

### 一次压缩算法应该有哪些分支

```text
1. 校验当前消息组，估计used
2. 没达到触发条件：直接请求模型
3. 在副本中清理旧工具结果
4. 清理收益足够：校验组并提交该副本
5. 否则选择最近K组和原话，计算摘要空间
6. 固定内容过大：逐步减K，必要时拒绝
7. 用旧视图前缀请求摘要，明确禁止工具执行
8. 检查摘要和组装后的长度/消息结构
9. 检查成功才替换View，并重置用量校准状态
```

摘要失败时应保留旧视图；怎样继续取决于它是否还在硬预算内。旧视图也超窗时，不能假装没有失败继续发请求。

摘要会花一次模型请求。预算只剩一次时，再摘要就没有后续任务决策空间，应该提前报告或保留那次用于解释未完成状态。

### 用户原话保留和最近组保留有什么不同

最近组保障当前局部执行；原话保障目标、约束和用户修改。它们不应共用简单的“最后 N 条”规则。

选择较新的用户原话时，还需按时间顺序重排回输入，避免让模型误读修改先后；摘要消息不能被误当成用户原话。

上次摘要与新淘汰内容可以共同生成新摘要，但这会累计有损误差。需要特别保留编号、金额、否定、时间和未知动作，不只保留自然语言大意。

### 缓存为什么影响算法

稳定的 system、工具定义和旧消息前缀有利于复用计算。若每轮都改写旧观察或插入不同时间戳，前缀会频繁改变。

原生消息前缀摘要能减少格式变化，却不保证命中。工具选择参数是否改变服务端处理、摘要是否复用相同模型，都需要真实计量。

不能为了缓存接受无关或不合法历史；缓存是效率优化，消息正确性与预算是约束。

### 进阶推演

1. 摘要目标 500 token，固定部分已经占了 3,900，接受上限 4,000，该做什么？  
   实际可用只有 100，不能只照着 500 生成。先调整保留区或报告不可行，再校验实际结果。

2. 压缩后用量立刻超过触发线，为什么不一直再摘要？  
   可能是固定部分或一个新输出太大，重复摘要只增加成本和漂移，需要检测无收益处理并停止或改变输入方式。


## 自测

1. 原始工具结果保存到文件，模型就能读到吗？  
   不能。要把内容放回请求，或提供具备读取权限的工具。

2. 摘要为何不能吞掉最近的一条 tool 结果？  
   当前决策可能依赖它的精确内容，还必须维护请求与结果的完整关系。

3. 触发压缩后降到很低的用量，就代表策略更好吗？  
   不是。还要检查目标、约束、精确结果和未完成动作是否保留。
