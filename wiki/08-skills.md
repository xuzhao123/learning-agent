# 08 · Skills：把一类任务的做法按需交给模型

工具提供能力，Skill 提供使用这些能力完成某类任务的方法。

[阅读目录](README.md) · [技术展开](#技术展开) · [基础自测](#自测)

## 先认识术语

| 术语 | 通俗解释 |
| --- | --- |
| Skill | 一类任务的说明、步骤、注意事项与参考材料 |
| SKILL.md | 用 Markdown 保存 Skill 定义与正文的常见文件 |
| Frontmatter | 文件开头描述名字、用途等的元数据块 |
| 渐进加载 | 先给简短索引，相关时再读取正文和资源 |
| 工具 | 实际查询、计算或修改的能力 |
| 程序性记忆 | 从经验中保存的做事方法，不一定与 Skill 有相同格式 |

## 用报销任务理解分工

一个“报销说明” Skill 可以要求：

1. 查找适用制度与版本。
2. 核对出差日期和天数。
3. 用计算工具得到金额。
4. 按中文表格组织说明并标注来源。
5. 条件缺失时询问，不替用户猜测。

Skill 不能自己查制度或生成真实单据。它告诉模型怎样组织工具；工具和执行器完成实际动作。

| 对象 | 回答的问题 |
| --- | --- |
| Tool | 能做什么 |
| Skill | 这类任务怎样做 |
| 长期记忆 | 这个用户或系统以前有什么已确认信息 |
| 系统规则 | 这次运行应遵循什么约束 |

系统规则可以要求先核查权限，用户记忆可以说偏好中文表格，Skill 可以安排报销说明步骤。它们互补，不应互相冒充。

## 为什么不把所有 Skill 正文都塞进去

十个 Skill 都写成长文，模型每次都读取，容易占满窗口，还可能看到互相冲突的流程。

渐进加载分为三层：

```text
启动：名字 + 适用描述
  ↓ 与任务有关
读取：Skill 正文
  ↓ 确有需要
读取：参考资料、示例或其他资源
```

索引决定能不能选对，所以描述要说明触发场景与边界。“帮助工作”不如“根据制度与行程计算补贴并生成可核查说明”。

按需读取减少常驻内容，不代表无限读取。正文和资源仍要遵守上下文预算。

## Skill 怎样被选中

可以由用户明确指定，由程序根据场景选择，或让模型依据索引请求加载。

每种方式都有取舍：明确指定可控，但用户要知道名称；自动选择省操作，但要评估漏触发、误触发和冲突。

评估不能只看“是否加载”。还要看模型是否正确使用流程、是否把无关步骤硬套到任务、是否因为读了更多内容而变慢。

## 加载知识不等于执行脚本

有的 Skill 包含资源或脚本。读到“运行下面命令”，不代表程序已经获得运行权限。

执行仍需走工具入口，检查来源、参数、文件范围、网络、资源和审批。路径应由可信索引映射，不能让模型任意拼接路径读取敏感文件。

同样，Skill 里写“提交后给某人发消息”，不能代替用户实际授权。知识描述与行动授权要分开。

## 怎样写一份容易被使用的 Skill

用清楚的任务边界和输入输出，避免大量空泛要求。把稳定方法写在正文，把长材料放到按需资源。

高风险步骤要说明需要什么真实条件，而不是让模型在文字上自我确认“已经安全”。

处理例外也很重要：资料缺失、版本冲突、工具失败时应停止哪一步、如何报告。只是列出顺利完成的流程不够。

## 技术展开

### 进阶术语：注册表、版本固定与路径竞态

| 术语 | 含义 |
| --- | --- |
| Registry | 可信名称到资源位置的索引 |
| Version pinning | 一次任务固定使用某个正文/资源版本 |
| TOCTOU | 检查与实际使用之间，目标可能被改变 |
| Trusted root | 允许读取资源的目录边界，不等于里面每份内容都可信 |
| YAML | 常用于配置的数据表达格式，通常用缩进组织字段，语法比简单键值更丰富 |

### 从文件到运行时索引的完整处理

```text
扫描候选目录
  → 读取frontmatter边界
  → 检查名字/描述、重复名称与长度
  → 建立名称到真实资源的映射
  → system仅放索引
  → load_skill(name)查表读取正文
```

用户或模型提交的是已登记名称，不应直接成为任意文件路径。坏文件要报告并跳过，不能让无关 Skill 的解析错误拖垮所有任务。

结构示意：

```go
type SkillMeta struct {
    Name, Description string
    BodyHash          string
    ResourceRoot      string
}
```

BodyHash 可用于确定版本并识别变化，不是内容安全证明。一段恶意正文也可以有稳定哈希。

### 手写frontmatter解析不等于实现YAML

若只支持 name 与 description 的简单字段，就应明确拒绝或限制复杂的多行、类型、重复键与嵌套结构。不能既用简化解析器，又宣称接受完整 YAML。

描述进入系统索引前也要控制长度和来源；索引本身可携带恶意指令，并不是只有长正文才有风险。

重复名称应给出明确策略，避免一次扫描覆盖另一个定义，导致相同名字加载到意外内容。

### 路径检查为何不能只看字符串

```text
resources/allowed.txt
  → 检查：看起来在允许目录
  → 目标被改成指向外部的符号链接
  → 实际读取：越过原目录
```

先 EvalSymlinks，再稍后 Open，也可能出现检查后被替换的间隙。

Go 1.24 起提供基于目录根的读取接口。函数片段：

```go
func readResource(dir, relativeName string) ([]byte, error) {
    root, err := os.OpenRoot(dir)
    if err != nil { return nil, err }
    defer root.Close()

    f, err := root.Open(relativeName)
    if err != nil { return nil, err }
    defer f.Close()

    return io.ReadAll(io.LimitReader(f, 64<<10))
}
```

需要 os、io。它有助于抵抗越出根目录的路径访问，详见 [Go 的遍历防护文件接口](https://go.dev/blog/osroot)。

这段示意仍需由可信注册表选择 dir、规定只读普通文件、处理长度截断与取消。它不是脚本执行沙箱，也不会判断目录内文件是否含秘密；64 KiB 只是示例读取上限。

### 渐进加载也需要版本与预算

一个任务开头看到索引 A，运行中加载到已更新的正文 B，可能造成行为不一致。可以按任务固定版本，或记录并显式处理刷新；不能默默改变流程。

正文、参考材料与其他工具结果共享窗口。资源很多时应按问题读取需要部分，不是“选中 Skill 后把整个目录都加载”。

资料来源、版本、工具调用参数与结果应可以关联，才能解释某次行为依据的是哪版流程。

### 从知识型到执行型多了一条信任边界

知识型 Skill 只返回文字。带脚本的 Skill 还要把动作交给受限执行器，明确工作目录、输入、网络、资源和审批。

“可以加载某个 Skill”与“可以执行其中任何命令”必须是两个决定。即使正文可信，用户当前任务也可能没有授权对外发送或修改数据。

### 对照已有实现

[Scan、parseFrontmatter、Prompt、Load](../internal/skills/skills.go)提供简化元数据解析和按索引加载，当前是知识型 Skill。

上面的 os.Root 资源读取、正文版本固定与脚本执行管理是供学习的扩展设计，尚未在现有 Skill 模块中接入；不能据此宣称当前路径与脚本隔离已经完备。

### 进阶推演

1. 正文哈希相同，是否可以省掉权限检查？  
   不可以。内容版本与操作授权独立；也要确认资源根和当前调用身份。

2. 为什么把模型参数当作目录传给 os.OpenRoot 仍然不安全？  
   若模型可以选择任意根目录，就失去了预先限定的边界。根必须由可信配置或注册表决定。


## 自测

1. 加载“报销处理” Skill，是否代表已经报销成功？  
   不是。只是读取了方法，执行与外部结果还没有发生。

2. Skill 正文和用户的一项稳定偏好有什么区别？  
   前者说明这类任务怎样做，后者描述用户；稳定偏好还需要来源与更新机制。

3. 为什么 Skill 名字短、描述清楚很重要？  
   名字和描述通常先进入常驻索引，影响任务是否选中正确正文。
