DAY 02 · LEARNING AGENT

让循环在失败时可控

任务跑得太久要停，工具短暂失败要再试，模型原地打转要打断。三种失败，需要三种不同的护栏，而且它们由 Go 程序执行，不靠模型自觉。

01 · 总览

三种失败，三种护栏

一直行动，迟迟不结束

max_steps 请求预算

10

默认最多 10 次模型请求。用完就停，返回已经做了什么。

当前这次工具调用失败

有限重试 + 指数退避

2 次

首次失败后最多再试 2 次，依次等 200ms、400ms。仍失败就把错误交回模型。

连续提出相同的动作

重复动作熔断

第 3 次

同一工具、同一参数连续第三次出现时拦下，不再执行。

任务没完成，可能有三种原因。只加一个停止条件，处理不好所有情况。

第一种：步骤太多或走错路。用请求预算兜底。

第二种：工具暂时不可用。在执行层有限重试，不打扰模型。

第三种：工具正常，但模型原地打转。熔断盯的是模型的决策。

Day 3 之后

上下文摘要也是一次模型请求，同样计入这个预算。

例子：查笔记里的职责数量，再乘以 25。

一次请求里可以提出多个工具调用。工具在本地重试，不增加请求次数。

预算不够时，“已查到笔记”是有效进度，应该告诉用户。

现在 -max-steps 的含义是：这次任务所有模型请求的总数。

04 · 取舍

上限设 10 还是 50

上限得到什么付出什么
10更早停止错误路径，耗时和费用好控制正常的长任务也可能被截断
50长任务更有机会完成失控路径也有更多空间消耗预算

每次请求的输入：历史越来越长

第 1 次第 10 次

请求上限翻 5 倍，总 token 和费用不止翻 5 倍：每次请求都要带上越来越长的历史。

max_steps 也不是超时。次数和时间是两种不同的限制。

上限不是越大越好，也不是越小越好。

两个数字各有代价，要按任务类型选。

每一轮都把完整历史重新发一遍，单次输入越来越大。

所以总消耗大致随请求次数的平方增长。这也是 Day 3 要管理上下文的原因。

// runWithRetry：一个调用最多尝试 1 + retries 次 delay := 200 * time.Millisecond * time.Duration(1<<attempt) select { case <-timer.C: // 等够了，再试 case <-ctx.Done(): // Ctrl+C 能打断等待 }

同一个调用 id，attempts 从 1 加到 3。用完后不让程序崩溃，而是把错误作为 Observation 交回模型。

时间轴按比例画。默认 retries=2：首次执行之后，最多再试两次。

第一次失败，等 200ms。可能只是临时网络抖动。

还失败，等待翻倍到 400ms。等待时间是 200ms × 2^r。

第三次仍失败，停止重试。200ms 是方便观察的起点，不是生产标准。

最后的错误写回历史，下一轮交给模型处理。

检查在启动工具之前，按 tool_calls 数组顺序进行，不看谁先跑完。触发时，整批都不启动。

实验工具 check_task_status 永远返回 pending，模型被要求一直查。

工具每次都正常返回，所以重试机制不会触发，任务却没有推进。

第三次相同请求出现时，程序拦下它。前两次已执行，第三次不执行。

调用 id 每次都可能不同，空格和键顺序也不代表任务变了，所以要先归一化。

只盯“连续相同”。交替调用能绕过，最后靠请求预算兜底。

判定和运行快慢无关，同样的输入总得到同样的结论。

08 · 计数

最容易混淆的三个数字

场景模型请求工具尝试连续重复
一轮提出两个不同工具，各成功一次1各 1没有连续重复
一个工具失败，又重试两次1同一调用 3只提出过 1 次
三轮提出同一工具和参数3前两次各 1，第三次 03 → 熔断

“重试两次”不会触发“三次重复熔断”：一个计数在工具执行内部，另一个在模型和执行器之间。

还要分清“工具执行成功”和“任务完成”：查询成功返回 pending，任务仍未完成。

三个计数器，分别在三个不同的层次。

一次请求可以带多个调用。

重试发生在执行层，模型只看到最后的结果。

熔断数的是模型连续提出的动作。

读终端日志时，先问自己：这个数字在数哪一层？

09 · 生产

重试之前，先判断该怎么恢复

稍后再试

服务繁忙、临时限流

在预算内退避重试，加随机抖动，遵守服务端的等待提示。

换一种做法

缺参数、除数为 0

等再久参数也不会自己长出来。回填给模型修正。

修配置或授权

Key 无效、无权限

不原样重试，也不能让模型换工具绕过权限。

停止

用户取消、截止时间到

不再重试，报告已有进度。

自动重试的条件（同时满足）： 可能通过等待恢复 且 同一操作可以安全重放 且 次数和时间还有预算 且 没有被取消

层层重试会相乘

Agent、工具封装、HTTP 客户端各试 3 次，一次逻辑操作最坏变成 3×3×3 = 27 次底层请求。约定由哪一层负责重试。

课程实现统一重试所有工具错误。生产中要先分类。

四种情况，四种不同的处理。判断依据是错误码和接口语义，不是错误文案里的某个词。

“暂时性”和“能否安全重放”是两个独立的问题。

次数、总耗时和费用要一起限制。

超时了，但操作可能已经成功

换新 id 重发 → 又建了 T-124（重复）
复用幂等键 op-001 重放
服务端去重：返回已有的 T-123

有副作用的操作，最难处理的失败是“不知道成功没有”。

Agent 发起创建工单，带上业务操作 id。

服务端其实已经创建成功，但响应在网络上丢了。

Agent 只看到 timeout。正确的状态是“结果未知”，不是“没有创建”。

直接换个新请求重发，会产生第二张工单。

按服务端的幂等协议复用同一个键，或先用操作 id 查询结果。tool_call_id 不能代替业务操作 id。

执行器

管规则：是否重试、等多久、何时停止

模型与主循环

定方向：补参数、换方案或说明无法完成

对应 runTool
对应 runWithRetry
对应 runAgent 和历史
create_ticket 的结果工具封装说明后续处理
本地校验缺 title，未发请求参数错误，未执行不重试，回填给模型补齐
服务返回临时限流，保证未执行临时故障，无效果预算内退避重试
请求已发出，读取响应超时结果未知幂等重放或查询；否则报告待核实
服务返回无权限权限拒绝不重试，报告受阻原因
HTTP 成功，业务状态 pending已受理，未完成返回真实状态，不宣布完成

业务知识不必全堆进主循环，重试逻辑也不必每个工具重写一遍。

工具封装最懂这个接口：错误码是什么意思，操作有没有副作用。

执行器统一应用规则：次数、退避、截止时间、取消。

模型根据结果调整计划，主循环守住预算并保存结果。

同一个 timeout，查询可以考虑重试，创建必须先处理重复副作用。

13 · 自测

用自己的话复述

预算用完后，为什么不再请求模型写摘要？

那会突破预算。执行记录在程序手里，本地生成即可。

一个工具执行了 3 次，为什么不一定熔断？

它们属于同一个调用请求。熔断数的是模型连续提出的动作。

换了调用 id，工具和参数没变，会怎样？

id 不参与判定，仍然算相同动作。

创建工单超时，能立即换新 id 重发吗？

先当作结果未知：查询原操作，或复用同一个幂等键。

max_steps = 10 能保证十分钟内结束吗？

不能。次数和耗时不同，还需要超时和取消链路。

只做熔断为什么不够？

交替调用或不断改参数能绕过它，请求预算仍要兜底。

先自己回答，再按 → 看参考答案。
