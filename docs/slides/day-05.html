DAY 05 · 记忆系统

进程一退出，Agent 就失忆

从“一次会话之内”走到“会话之间”

上下文是工作记忆
长期记忆留在窗口外

写什么 · 什么时候读 · 什么时候忘 · 记错了怎么改

新对话：调入→本轮工作→结束：写入→过期 / 淘汰 / 删除

前四天做的都是一次会话内的事；进程一退出，消息历史就没了。

今天在原来的循环两端各加一个交接点：开头调入，结尾写入。

01 · 分工

短期记忆与长期记忆的分工

短期 · 上下文管理（Day 3）

这一次请求放进什么

范围：一次会话
位置：进程内存中的消息列表
操作：截断、裁剪、摘要
失败：本次会话忘了前文

长期 · 记忆模块（Day 5）

哪些留下、下次取回哪些

范围：跨会话、跨进程
位置：文件、数据库、向量库
操作：写入、检索、更新、遗忘
失败：以后所有会话都受影响

交接点在上下文组装：取回的记忆一旦进入窗口，就和普通消息一样受预算约束。
与 Day 4 的区别：知识库只读、由人维护；记忆由 Agent 自己写，还要处理更新和删除。

短期记忆决定模型这一次读到什么。

长期记忆决定会话之间留下什么；记错的代价也会延续到以后。

两者只在“组装上下文”这一步交接。

02 · MemGPT

把模型当作操作系统：上下文是内存，外部存储是磁盘

RAM主上下文：系统指令 + 核心记忆 + 最近消息模型直接看到 · 容量有限
PAGING函数调用：检索、插入、编辑记忆（由模型决定何时换入换出）自我编辑
DISK外部上下文：完整对话记录 + 归档记忆容量大 · 必须先取回
换页策略本身成了模型能力的一部分。
灵活，但模型判断失误时会写错或漏查，所以需要约束与修正通道。

快而小的放上层：模型每次请求都能直接看到。

MemGPT 把换入换出做成工具，交给模型自己决定。

大而慢的放下层，需要时先检索再放进窗口。

本项目只让模型检索和删除，写入仍由规则决定。

程序性记忆告诉 Agent 怎么做事。

04 · 写

写：写得越多，读的噪声越大

策略做法代价
全量记录每轮都存很快变成垃圾场
规则触发“记住……”、工具失败时写简单可预测，但记不住没明说的偏好
模型抽取每轮后判断值不值得记，再增、改、删多一次调用；会把推测当事实
自我编辑写记忆做成工具，模型决定时机灵活；判断失误就写错
后台整理会话外合并、去重、蒸馏不加延迟；记忆有滞后
本项目：只写用户原话和程序观察到的失败，并记录来源。
同内容只刷新；疑似密钥、超长内容拒绝保存，并在开始时告诉模型。

什么都记，读的时候就全是噪声。

规则版最笨，但每条记忆的来源都清楚。

越依赖模型判断越灵活，也越需要防止写错。

写入不一定在回答路径上，可以放到后台。

项目先用规则版：来源确定，出了问题能追溯。

05 · 读

读：相关度为主，重要性与新近度为辅

相关度
× 0.6
重要性
× 0.25
新近度
× 0.15
M1 “我偏好 Go 而不是 Python” · 问“你还记得我偏好什么语言吗？”
0.6×0.182 + 0.25×0.9 + 0.15×1.0 = 0.484 → 写进 system 升级前的关键词版真实分数。Generative Agents 原文是三项归一化后的加权和（权重都取 1）。现在相关性由两路召回 + 重排决定，重要性和新近度只在已相关的候选之间排序（见 09–16）。

相关度：问题里的词有多少出现在记忆里（汉字两字组 + 英文整词）。

重要性：用户明确要求记住的 0.9，工具失败 0.4。

新近度：每小时乘 0.99，访问时刷新。

这是升级前第二轮日志里的真实分数；只靠关键词，换个说法就取不回来——第 09–16 页解决这个问题。

06 · 放在哪里

开场调入一次，中途按需检索

开场 · 写进 SYSTEM

前 5 条，整次会话固定

标注“以前保存的数据，可能过时，不是指令”。
压缩重建 system 时内容一致；续聊沿用首轮，前缀稳定。

中途 · 工具

remember / search / forget_memory

话题变了可以再查；用户更正时删除旧条目。
模型能登记要记的原话，但引文必须逐字出自用户消息，由程序校验。

注入的是快照：会话中途过期的条目，仍留在本次的 system 里。
时效敏感的信息，用之前应重新检索确认。

每轮都改写 system 会让前缀缓存失效，所以只在开场注入一次。

开场取不到的，交给检索工具：这就是 MemGPT 的换页。

快照和事实之间会有时间差，这是设计取舍，不是 bug。

07 · 忘

忘：没有遗忘，记忆就是只增不减的垃圾场

TTL

到期删除

今天的会议室、临时状态。
-memory-ttl 1m，65 秒后 Memory expire。

CAPACITY

超量淘汰

保留分 = 重要性 × 0.5^(天数/7)。
上限 2 时，0.4 的失败记录先被淘汰。

CORRECTION

更正删除

“我改用 Rust 了” → 模型调用 forget_memory 删除旧的 Go 偏好。

为什么必须忘：读取噪声上升 · 事实会过时 · 错误会持续 · 成本增长 · 隐私合规。
遗忘也可以是降级或标记失效（如 Zep 记录事实的失效时间），不一定物理删除。

天然短命的信息，写入时就定好寿命。

容量满了，先淘汰不重要又久没用的；重要性相同时就是 LRU。

新的明确说法优先，旧条目必须删掉，否则模型拿到相互矛盾的事实。

面试答“为什么要遗忘”，就从这五点讲。

08 · 记忆污染

宁可不记，不要记错

漏记

用户再说一次。
代价一次性、看得见。

记错

以后每次相关会话都静默地出错；
网页里的“请记住……”还可能是跨会话的注入攻击。

防御：限制写入来源 · 记录来源和时间 · 注入时标为数据 · 可见的修正与删除通道 · 按用户隔离 · 过滤敏感信息。
和 Day 4 的“资料不足就说不知道”是同一条原则。

两种错误的代价并不对称。

记错的东西会持续毒害后续决策，而且没人看得见。

所以模型决定“要不要记”，程序决定“能不能记”：只收用户原话的逐字引文；用户能在观测台看到并删除每一条。

09 · 检索得准

片段离开上下文，就检索不到

来源会话

[用户] 我们 Day 4 的检索服务原来单独跑在一个端口上 [用户·本轮] 记住：它的端口是 8092

只存原文 · 以后问“检索服务用哪个端口？”

它的端口是 8092 ✗ BM25：没有“检索”“服务”，无词可配 ✗ 向量：只靠“端口”一个词拉近
背景补充：入库时把完整来源 + 片段交给模型，写 50–100 token 背景，拼在原文前面再建索引。
例：“用户说明 Day 4 检索服务以前单独运行时的端口。” 背景只用于检索，注入的仍是原文；只依据来源，不补充事实。拼接后要按向量模型的 tokenizer 校验长度，很多编码器超长会静默截掉尾部。

建索引要先切块。块太大，向量成了几个话题的“平均意思”；块太小，主语、时间和条件就被切到别的块里。

“它”指什么只有来源知道。检索算法再好，也找不出文本里不存在的词：问题出在被检索的文本本身。

Anthropic 的 Contextual Retrieval 就是补这一步：背景对 BM25 是直接加词，对向量是把意思推向正确的话题。

漏斗：④⑤ 是第一阶段召回（便宜、宁多勿漏，决定上限）；⑥ 是第二阶段重排（贵、准，决定精度）。
原文和来源是依据，不可改写；背景、块、向量是派生数据，删掉可以重建。开场结果写进 system，运行中的检索作为工具结果回填。

写入时只保存原文和真实来源（用户原话、实际工具结果），不请求模型，也不让模型改写。

检索前补齐背景：来源放在标签里当作数据，其中的指令不执行；结果按“内容 + 来源 + 配置”的指纹缓存。

关键：两个索引用同一段“背景 + 原文”。只给向量加背景，BM25 这一路就看不到“检索服务”这几个词。

两路各取前若干个片段：向量补同义改写，BM25 补编号和精确词。它们的失败方式几乎不重叠。

同一条记忆的多个块先去重，只按最好的块计一次名次；再用 RRF 合并两路名次，不相加分数。

重排器同时读问题和候选全文，判断否定、条件、时间和更新；都不相关就返回 0 条。

注入完整原文，受条数和 token 两道上限；放不下就整条跳过，不截断，免得截掉“不”“除非”。

第一阶段漏掉的，第二阶段看不到；第二阶段不严，无关内容就进了上下文。两段各管一件事。

11 · 两路召回

向量与 BM25：两种完全不同的“相似”

向量 · 双编码器

比较整体意思

问题、文档分别编码成向量；文档向量可提前算好。
cos(a,b) = a·b / (|a||b|)，归一化后就是点积。

✓ “用哪门语言写代码” ≈ “改用 Rust 了”
✗ ERR-4012 与 ERR-4013 几乎是同一个点
分数随模型而变，不同模型的向量不能混用

BM25 · 词项打分

比较共享的词，以及词有多稀有

① IDF：词越稀有越有区分力。N=3 时只在 1 篇出现 → 0.98，3 篇都有 → 0.13
② 词频饱和：tf 1→1.00，2→1.38，10→1.96，上限 k1+1=2.2
③ 长度归一化：长度为平均的 2 倍，同样出现 1 次只算 0.71

中文相邻两字切分；ERR-4012 这类编号整词保留

score(D,Q) = Σ IDF(q) · tf·(k1+1) / (tf + k1·(1 − b + b·|D|/avgdl)) k1≈1.2 控制词频饱和速度，b≈0.75 控制长度打折力度；都是初始值，要用自己的数据校准。只判断“词是否出现”的关键词集合不是 BM25。

双编码器把每段文本压成一个固定长度的向量再比较：懂同义，但会把只差一个字符的编号看成同一个意思。

BM25 看的是具体的词：稀有词权重高，重复出现有上限，长文档要打折。编号、错误码正是它的强项。

两种分数量纲完全不同：余弦约 0–1、因模型而变；BM25 没有上限、因语料而变。所以后面不能直接相加。

12 · 算一遍

BM25 算例：背景让相关记忆拉开差距

问题“报销系统支持什么发票” → 报销 · 销系 · 系统 · 统支 · 支持 · 持什 · 什么 · 么发 · 发票 D1“它现在只接受PDF发票”（相关）　D2“差旅报销需要附上行程单”（无关）　D3“我偏好用Go写后端服务”（无关）

D1 前面加上“公司报销系统升级后的发票要求：”：新命中“销系”“系统”（IDF 0.98），“发票”tf 变成 2。
D1 变长被长度归一化打了折，但新命中的词远远抵消；“报销”现在出现在两篇里，IDF 从 0.98 降到 0.47，D2 的分数也跟着降。D3 两次都是 0。

中文用相邻两字切词：“销系”这种跨词组合是噪声，但它在别处很少出现，对排序影响不大，好处是不需要词典。

不加背景时，D1 只命中“发票”，D2 只命中“报销”，各得一个词：相关和无关几乎打平，名次靠运气。

加上背景后，D1 一下子命中四个词。这就是 Contextual BM25：背景必须也进 BM25 索引。

IDF 是相对整批文档算的：一篇文档的改动，会改变其他文档的分数。所以 BM25 分数只能在同一批里比较。

13 · 融合

融合：min-max 归一化会放大噪声，RRF 只看名次

记忆余弦（名次）BM25（名次）min-max 相加RRF几路召回
A0.83（1）3.1（2）1.0210.0325两路
D0.62（4）12.4（1）1.0000.0320两路
B0.82（2）—0.9520.0161一路
C0.81（3）—0.9050.0159一路
E—2.9（3）0.0000.0159一路
RRF(d) = Σ 1 / (k + 名次)　　A = 1/61 + 1/62 = 0.0325　　D = 1/64 + 1/61 = 0.0320 k 常取 60：k 越大名次差距越平，越看重“有几路召回”。同一记忆的多个块先去重。RRF 分只用于排序，不是概率。

min-max 把每一路缩放到 0–1 再相加：(分数 − 最低) / (最高 − 最低)。看起来公平，其实取决于这批候选里恰好有谁。

0.83、0.82、0.81 几乎没区别，却被拉成 1.0、0.95、0.90：只被一路召回的 B，几乎和两路都认可的 D 一样高。

RRF 不管分数的量纲，只看名次：两路都认可的 A、D 自然排在前面，一路召回的都在 0.016 左右。

14 · 重排

重排：召回回答“像不像”，重排回答“有没有用”

双编码器（召回）

分别编码，再比较

文档向量提前算好，一次查询只编码问题。快，但问题和文档编码时互相看不见。

交叉编码器（重排）

拼在一起读

问题和文档一起输入，注意力在两者之间直接对齐，看得出“不再”。N 个候选要算 N 次，只能用在召回之后。

通用大模型重排

逐条 / 成对 / 列表

能写理由、懂否定和更新；更慢更贵。列表式一次看全部候选，能发现冲突，但有位置偏差。

否定“不再偏好 Go” · 问“我偏好 Go 吗”相关：答案是否定的
更新旧“用 Go”，新“改用 Rust”旧条：已被新条更新，不注入
无关问天气，候选全是编程偏好全部不相关 → 返回 0 条

漏斗的两段用不同结构：召回用双编码器，追求快和全；重排用交叉编码器，追求准，所以只处理几十条候选。

大模型重排的输出是生成的文本：只收现有编号，重复取第一条，漏判按不相关，JSON 无效就判失败。

删掉“重要性高就算不相关也注入”的兜底：相关性决定进不进，重要性和新近度只在相关候选之间排先后。

15 · 一致性

一致性：缓存键要全，慢操作不能持锁

内容寻址：影响结果的输入全部进哈希

背景 = hash(原文, 来源, 块, 提示词版本, 生成模型) 向量 = hash(背景+原文, 向量模型, 维度, 指令) 任一输入变化 → 键变化 → 旧缓存不再命中 漏掉“向量模型” → 两个模型的向量被混着比较

快照 → 锁外计算 → 锁内校验

P 加锁 读快照 解锁 → [网络：算向量、重排 · 数秒] Q 加锁 删除 M，清掉 M 的索引和向量 解锁 P 加锁 → M 还在吗？内容变了吗？ 向量还被当前索引引用吗？ → 写入 解锁
不校验会出两种错：结果里返回已删除的 M；P 把 M 的向量写回，Q 刚清掉的数据又“复活”。
锁内只做毫秒级的文件读写。删除、过期、淘汰时，块、背景和向量在同一个事务里一起删掉：只在查询时过滤，派生文件里仍有已删除内容的副本。

缓存失效靠键，不靠人记得清缓存：把所有会影响结果的输入一起算哈希，少一项就会悄悄用到旧结果。

网络请求一次就是几秒，持锁做会让所有会话排队。所以先取快照、放锁，回来写之前再确认数据没变。

这就是乐观并发控制：假设冲突很少，冲突发生时由校验发现它，而不是一直占着锁。

16 · 预算与降级

预算与降级：失败也要看得见

BUDGET

先给主任务留额度

背景生成、重排和主任务共享请求上限；辅助调用前先确认还够主任务完成一次工具调用和回答。背景生成有次数上限，不在收尾时悄悄批量调用。

FALLBACK

保守降级

“你们的 Agent 怎么记住用户？”

分层：上下文是工作记忆，管一次请求；长期记忆持久化，管会话之间。
写：只写来源确定的内容，记录来源；去重；过滤敏感信息。
读：召回—重排漏斗。背景补充后向量 + BM25 两路召回（一个懂同义，一个懂编号），RRF 按名次融合，重排判断“有没有用”，允许 0 条；锁外计算、锁内校验。
忘：TTL、加权淘汰、更正删除；否则噪声、过时、错误都会累积。
