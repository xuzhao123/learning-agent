DAY 01 · LEARNING AGENT

模型如何通过工具完成任务

模型只提出“要调用什么”，Go 程序真正执行，再把结果交回模型。这几步连起来，就是最小的 Agent 循环。

01 · 全景

一个问题走一遍

用户
模型
Go 程序
计算 floor(sqrt(1234×5678))，今天星期几？
判断：要计算，也要查时间
tool_call · calculator(expression)
tool_call · get_current_datetime()
真正执行两个函数
tool 结果 · {"result": 2647}
tool 结果 · 2026-10-03 星期六
回答：结果是 2647，今天星期六

三个角色：用户提问，模型决定下一步，Go 程序负责真正执行。

问题连同工具定义，一起发给模型（第 1 次请求）。

模型没有算。它只返回两个调用请求：工具名 + 参数。

Go 真正执行函数，把实际结果作为 tool 消息交回模型（第 2 次请求）。

模型读到结果，组织成回答。一个问题，请求了模型两次。

02 · 协议

三样不同的东西

工具定义 放在 tools 字段

{ "name": "calculator", "description": "计算数学表达式", "parameters": { "type": "object", "properties": { "expression": {"type": "string"} }, "required": ["expression"] } }

告诉模型：能做什么、参数长什么样

调用请求 模型返回的 tool_calls

{ "id": "call_calc", "type": "function", "function": { "name": "calculator", "arguments": "{\"expression\": \"floor(sqrt(1234*5678))\"}" } }

告诉程序：这一次要做什么

执行结果 role 为 tool 的消息

{ "role": "tool", "tool_call_id": "call_calc", "content": "{\"result\":2647}" }

告诉模型：实际发生了什么

失败时写回错误信息。结果必须来自真实执行，不能让模型的猜测冒充结果。

工具调用里有三样东西，名字相近，作用完全不同。

工具定义只描述名字、用途和参数结构，里面没有任何实现代码。

调用请求是模型这一次的决定。注意 arguments 是“装着 JSON 的字符串”。

执行结果是 Go 实际执行后写回的 tool 消息。

请求和结果靠同一个 id 对应。下一页会看到，不能用工具名代替 id。

03 · 参数

arguments 要解析两次

API 响应
一整段 JSON
tool_calls[0]
第一次解码得到
Arguments
仍然是 string
args.Expression
第二次 Unmarshal
var args struct { Expression string `json:"expression"` } err := json.Unmarshal([]byte(call.Function.Arguments), &args) // 检查 err，再把 args.Expression 交给 calculate

解析失败怎么办

不执行工具，把“参数不是有效 JSON”或“缺少 expression”作为结果交回模型。模型下一轮可以修正参数。

模型给的参数，要经过两层解析才能变成 Go 能用的值。

第一层：解码整个 API 响应，拿到 tool_calls 列表。

这时 arguments 还只是一个字符串，Go 还不能直接用。

第二层：把这个字符串再 Unmarshal 成结构体，见 internal/agent/dispatch.go 的 runTool。

参数可能写错。错误也是一种结果，要回到模型手里。

04 · 请求

一次请求里装了什么

POST /chat/completions { "model": "（方舟模型）", "messages": [ {"role": "system", "content": "你是一个工具助手，按需使用 工具帮助用户，并用中文回答。"}, {"role": "user", "content": "…"} ], "tools": [calculator, get_current_datetime, search_notes], "parallel_tool_calls": true }

system prompt 只有一句

不再要求模型输出 Thought、Action 这类文本前缀。调用协议交给 API 字段表达。

工具说明放在 tools

模型需要工具时，通过 tool_calls 返回结构化请求；普通回答放在 content 里。

只有 prompt，没有 tools
模型不知道本地有哪些函数

只有 tools，没有执行器
模型只能提出请求，没人执行

定义 + 执行器 + 结果回流，三者缺一不可。

internal/llm/llm.go 的 callModel 每次都发送这样一个请求体。

提示词很短，因为“怎么调用工具”不靠文字约定。

工具清单单独放在 tools 字段，每次请求都带上。

两种残缺的情况，都走不通。

这三样连起来，模型才真正“用上了”工具。

05 · 历史

消息历史是下一轮的依据

第 1 次请求

system工具助手
user查循环职责，再 ×25

第 2 次请求

system工具助手
user查循环职责，再 ×25
assistanttool_calls: search_notes
tool找到 4 项职责

第 3 次请求

system工具助手
user查循环职责，再 ×25
assistanttool_calls: search_notes
tool找到 4 项职责
assistanttool_calls: calculator(4*25)
tool{"result": 100}

assistant：循环职责有 4 项，乘以 25 是 100。没有新的调用，结束。

// 存模型的请求（连同 usage） conversation.RecordReply(response) // 存程序的结果 conversation.Append(Message{ Role: "tool", ToolCallID: observation.ID, Content: string(data), })

例子：先查学习笔记里的循环职责，再把职责数量乘以 25。

第 1 次请求只有 system 和用户问题。模型不知道答案，需要先查。

模型要求查笔记。程序先把这条 assistant 消息原样存进历史……

……再把执行结果作为 tool 消息存进去。两处追加缺一不可。

第 2 次请求带着前面全部 4 条。模型看到“4 项”，才能发起 4×25。

计算结果同样写回历史。

第 3 次请求，模型直接回答。注意：每次请求都把完整历史重发一遍。

06 · 对应

为什么必须用 tool_call_id

模型同一轮提出

call_acalculator(2+3)
call_bcalculator(10*10)

Go 并行执行（完成先后不定）

先完成

results 数组（按调用顺序）

results[0]call_a → 5
results[1]call_b → 100

写回历史的 tool 消息

tooltool_call_id: call_a　content: 5
tooltool_call_id: call_b　content: 100

只靠工具名会怎样

两次调用都叫 calculator。如果按名字或完成先后对应，5 和 100 可能被配错，模型会拿错误的数字继续推理。

同一轮里，模型对同一个工具提出两次调用。

并行执行时，后提出的 call_b 可能先完成。

每个 goroutine 只写自己的 results[i]，结果顺序与调用顺序一致，不受完成先后影响。

写回历史时，每条 tool 消息带上原调用的 id。

id 标识的是“某一次调用”，不是“某个工具”。

07 · 循环

loop 比一次 API 调用多做了什么

请求模型
解析输出
调度工具
并行执行
维护历史
写回 tool 结果
判断终止
还有调用吗？
无调用且有回答 → 结束
// runAgent 主线（简化，略去 Day 2/3 的护栏） for step := 1; step <= maxSteps; step++ { reply := 请求模型(历史) 历史 = append(历史, reply) if len(reply.ToolCalls) == 0 { return // 回答并结束 } results := executeBatch(reply.ToolCalls) 历史 = append(历史, tool 结果...) }

结束只表示模型这一轮不再行动，不自动证明回答正确。还要对照实际工具结果理解答案。

一次 API 调用只拿到当前响应。loop 让模型能根据新信息继续行动。

职责一：请求模型，并解析它返回的内容和调用请求。

职责二：调度工具，独立的调用可以同时执行。

职责三：维护消息历史，让下一轮看得到发生了什么。

职责四：判断是否终止。有调用就继续绕圈。

没有调用、并且有正常回答时，循环结束。

08 · 并行

三个数量，别混在一起

3

种工具可用
加载：准备名字、描述、schema 和处理函数

2

次调用由模型本轮提出
批次：同一轮的 tool_calls

4

个执行名额 -parallel
并发：Go 同时执行几项

串行：一个接一个

≈ 5 秒

并行：同时开始

≈ 3 秒
0s1s2s3s4s5s6s

批量调用减少模型往返；并行执行减少工具等待。真正的并行来自 Go 执行器。

“并行”这个词，经常把三件事说成一件。

可用的工具、本轮提出的调用、同时执行的名额，是三个不同的数。

两个独立工具分别耗时 2 秒和 3 秒。串行执行约 5 秒。

并行执行约 3 秒，由最慢的那个决定。

本项目的本地工具很快，重点是看清流程，而不是省下的时间。

09 · 并发

executeBatch：名额、结果槽、等待

每个调用一个 goroutine

go #0calculator
go #1datetime
go #2search_notes
go #3calculator

slots：容量 2 的 channel（-parallel 2）

go #0执行中…
go #1执行中…
go #2执行中…
go #3执行中…

results：每项只写自己的格子

[0]2647
[1]2026-10-03 星期六
[2]笔记 4 条
[3]100

WaitGroup：4 → 0

wg.Wait() 等整批都结束，主循环才继续。

主循环统一写回历史

按 results 顺序追加 4 条 tool 消息。goroutine 从不直接改历史，避免并发写冲突。

模型一轮提出 4 个调用，每个调用启动一个 goroutine。

有缓冲的 channel 当作执行名额，容量就是 -parallel。

两个 goroutine 拿到名额先执行，结果写进各自的 results[i]。

有名额释放，等待的 goroutine 接着执行。名额为 1 时也不保证按数组顺序。

WaitGroup 计数归零，说明整批结束。

最后由主循环一次性写回历史，见 internal/agent/react.go 的 ExecuteBatch。

10 · 依赖

哪些调用可以放进同一批

互不依赖：同一轮，一起执行

“计算 floor(sqrt(1234×5678))，并查询今天星期几”

第 1 轮calculator　+　get_current_datetime
第 2 轮直接回答

有依赖：必须分轮

“先查笔记里的职责数量，再乘以 25”

第 1 轮search_notes → 得到 4
第 2 轮calculator(4*25) → 100
第 3 轮回答

后一个调用的参数或执行效果依赖前一个时，不能放进同一批。把 -parallel 设为 1 也不能代替这种先后关系，因为名额为 1 时执行顺序同样不保证。

模型同一轮提出几个调用，取决于它判断这些调用是否互相依赖。

计算和查日期互不影响，可以同轮提出、同时执行。

“乘以多少”要等查询结果出来才知道，只能分成多轮。

真正需要先后顺序的任务，靠分轮决策，而不是靠调低并发数。

11 · 自测

用自己的话复述

模型返回 calculator 请求后，谁真正计算？

Go 的工具函数。模型只提供名字和参数。

为什么下一轮要保存 assistant 和 tool 两种消息？

前者记录请求，后者记录结果，两者用 id 关联。

工具结果只打印到终端会怎样？

下一次请求里没有它，模型无法据此继续判断。

为什么两次工具调用不一定能并行？

后一次的参数或执行效果，可能依赖前一次的结果。
