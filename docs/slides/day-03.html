01 · 基本概念

保存过，不等于这次发给了模型

完整记录

程序保留的原文

用户输入、模型输出、工具结果。用于回看、恢复与排查。

Codex 将记录写入 rollout。保存原文，不代表每次重发全部原文。

活动上下文

本次模型能读到的内容

初始指令、保留原话、近期消息，以及已有的压缩产物。

本项目中叫 View。模型只能基于本次实际收到的内容继续。

临时摘要请求

为压缩准备的一份副本

复制待处理的历史，再追加摘要指令；必要时在副本上腾空间。

这是 Codex 本地压缩中的材料，不是程序仅剩的唯一历史。

问“这条消息还在吗”时，先确定：在原始记录、活动上下文，还是摘要请求副本里？

记录是程序保存的材料；模型不会自动读取存档。

某条原文没有放进本次输入，模型就不能直接使用它。

临时请求可以裁剪，但要区分它和原会话历史。

后面“副本删了姓名，原话仍能保留”的动画，就建立在这个区别上。

02 · 基本概念

三种缩短输入的方法，损失发生在不同位置

截断一条内容

保留头尾，省略中间

开头中间结尾

常用于很大的工具输出。标明省略范围，避免把片段当完整结果。

裁剪消息

一些条目不再发送

旧消息后续消息

按规则删除条目。涉及工具时，调用和结果必须保持配对。

模型压缩

把历史变成交接材料

多条历史压缩产物

保留进度、约束、关键数据和下一步，用更少内容继续任务。

这里讲动作含义。具体先做哪一步、处理哪些消息，取决于所选实现。

它们都让输入变短，但不是同一种操作。

截断发生在一条内容内部，例如保留工具输出的开头和结尾。

裁剪直接移除条目；它不承诺把被移除的事实搬到别处。

压缩让模型生成交接材料，但材料之外的细节仍可能丢失。

03 · 核心结论

压缩后的大小，由留下的内容决定

目标是用精简的上下文继续任务，
同时保留必要状态和用户原话。

稳定指令 / 工具定义
按预算保留的用户原话
摘要 / compaction 条目

多少原话，多少状态

较长的用户要求、项目规则、未完成的工作，都会影响重建后的大小。

Codex 不设固定压后百分比

不是压到某条目标线就停，也没有反复压到“绝对最小”的循环。

组成示意，块宽不代表真实 token 数。Codex 本地重建源码 ↗ · 官方压缩说明 ↗

“尽可能精简”包含一个前提：下一步仍有足够的信息继续工作。

稳定指令和工具定义有固定开销；它们不会因为生成摘要就消失。

用户原话有独立的保留预算。预算是上限，不要求一定用满。

再加上压缩产物，才是压缩后真正要发送的上下文。

判断压缩是否有用，要同时看任务能否继续、信息是否保留，以及省出了多少空间。

04 · 用量变化

上下文变短，但没有固定的谷底

下降多少：取决于稳定指令、保留原文和压缩产物的总量。

下一段：从新上下文继续追加，而非围绕固定目标线反复微调。

机制示意，不是实际 token 监控曲线；真实用量不保证每一步都单调增长。

图里只保留触发阈值，去掉固定压后目标线。

问题、回答和工具结果不断进入活动历史，用量通常逐步增加。

第一次压缩后，剩下的是新上下文本身的大小。

后续请求从这份新上下文继续，不需要每一步都重新摘要。

第二次保留的内容不同，谷底也不同；没有固定比例要求。

目标是为后续工作腾出空间，并让必要信息仍可使用。

历史改写可能使变更点之后的缓存失效；未变的前缀仍可能复用。以 cached_tokens 等实际 usage 为准。

缓存与信息保留是两个问题：信息仍在输入里，也不代表这次会命中缓存。

普通请求尽量只追加，可以保持前面的内容相同。

共同前缀只是条件；模型、请求配置和服务端策略也会影响缓存。

压缩会重建历史，复用范围可能随之改变。

因此不能说“每次都命中”，也不能说“压缩后所有缓存必然失效”。

06 · 检查方法

变短只是一个结果，还要能继续任务

关键内容是否仍可用

目标、约束、账号、数值和下一步，要能从新上下文或明确的工具来源得到。

消息结构是否完整

工具调用和对应结果保持配对；片段与摘要标明来源，不能冒充完整原文。

过程是否能解释

区分直接裁掉、交给摘要、原样保留三种去向。压缩后再看实际用量与任务表现。

失败是否能收场

准备成功后再替换活动历史；失败保留已有状态并报错，为重试和循环设限。

这些是学习与评估的检查点；“模型曾答对一次”不能证明长期记忆可靠。

没有一个固定的“压后百分比”，能独自证明压缩成功。

把姓名删掉，只留下更短的摘要，可能省了 token 却损害任务。

更短的消息仍需遵守模型接口的协议。

“裁了 8 条、摘要读了 6 条”与“摘要了 14 条”是不同的事实。

压缩只是 Agent 循环中的一步，也需要预算、失败反馈与状态保护。

07 · 自测

先自己回答，再展开参考理解

压缩是否必须到固定百分比？

不是。Codex 重建后的大小由保留内容与压缩产物决定。

越短就一定越好吗？

还要保住继续任务所需的状态，不能只优化 token 数。

副本删了姓名，姓名一定丢了吗？

不一定。Codex 本地会从会话历史独立选择用户原话。

存档里还在，模型就能用吗？

需要放回实际输入，或有可用工具取回；存档本身不等于上下文。

有共同前缀，能证明缓存命中吗？

不能。需要核对实际 cached_tokens 等返回值。

这次 allo 对照证明了什么？

真实文本可放进 Codex 原话配额；这是源码推演，不是模型实测。
