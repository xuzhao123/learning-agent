01 · 信息边界

压缩与检索，解决两个方向

DAY 3

已经进入窗口的信息

对话、工具结果越来越多。
压缩与裁剪决定哪些继续保留。

DAY 4

尚未进入窗口的信息

笔记、FAQ 放在文档库。
检索决定这次取回哪些片段。

外部知识库 ≠ 自动保存聊天记忆
今天不会把用户每句话自动写进向量库。

上下文管理针对模型这次实际收到的输入。

检索面对窗口外的资料，只把选中的内容放进来。

两个模块会配合：检索结果进窗口后，仍受 Day 3 的预算与截断规则约束。

03 · GO INDEX

保存向量与原文

归一化后算点积、排序；编号与来源随片段返回。

原文是事实来源，索引是派生缓存。
修改语料后重新启动Agent；内容指纹变化才重建索引。

把一个 FAQ 当作一条短文档，先让它自身能够被读懂。

同一模型也负责把用户 query 转成向量，才能在相同空间里比较。

本地模式无需embedding密钥；线上模式复用ARK_API_KEY调用方舟。

本地首次下载权重；两种模式各自缓存文档向量，不混用。

03 · CHUNKING

切块要保住主体与条件

过小

“额外重试 2 次”

谁重试？什么情况下？
第一次算不算？

当前 FAQ

完整的一件事

本项目工具失败：额外2次，总共3次；等待200ms、400ms；耗尽后回填错误。

过大

整个工程手册

混入并发、压缩、部署……
命中了也可能带来大量噪声。

语义边界先行，长度上限兜底。
启动时用 embedding tokenizer 检查长度；超长要求拆分，不静默截尾。

只保留一句孤立数字，很容易把条件丢掉。

一个完整 FAQ 保留了答案成立的范围与必要数字。

长块不等于更好的证据，尤其当里面同时讨论很多主题时。

本地模型按128个模型token检查长度；超长时要求按语义拆分。

05 · 一次完整调用

片段回流，仍然是原来的 loop

user 工具失败总共尝试几次？等待多久？
assistant tool_calls：search_docs(query, k=3)
Go 进程内检索 query embedding → Go top-k → 片段、score、来源
tool tool_call_id 对上请求；Observation 包含 D05 的正文
assistant 总共最多3次，等待200ms、400ms。[D05]

第一次请求没有整份文档库，只有问题、规则与工具定义。

模型选择调用与query，Go才开始真正执行。

检索工具像 calculator 一样，返回一次实际执行的结果。

先追加到消息历史，再发下一次模型请求，资料才能被模型使用。

引用让用户找到证据；仍要核对证据与结论是否一致。

06 · 覆盖与成本

k 控制候选数，不保证证据数

这个项目压缩时承诺保留最后两组消息吗？
k = 1

省空间，可能漏

首轮直接检索第一名D12，主要说压缩目标。

k = 3

当前起点

带回第二名D11，明确“最多2组，可以缩减到0”。

k = 6

更多候选

覆盖可能增加，也混入更多无关片段，消耗窗口。

分别观察：相关片段有没有被找回？最终答案有没有被支持？

只看第一名，可能错过回答所需的另一个片段。

这里k=3覆盖了真正解释K缩减规则的D11。

更多候选并非越多越好，还会增加阅读与截断风险。

参数好坏需要真实问题来衡量，不能只数返回了多少条。

07 · 两种资料不足

过阈值，也可能没有答案

Q09 · 酒店报销

主题就不在库里

Go本地模式最高分约0.213。
低于0.40，不能作为证据。

Q10 · TS-999

主题近，事实缺失

错误处理片段可能过阈值。
但没有TS-999的定义或修复方法。

资料不足，我不确定。
低分是一个信号，正文是否支持问题才是更关键的判断。

低分候选只保留元信息，正文不注入；观测台展示分数与过滤原因。

检索函数能直接识别“没有足够相似的候选”。

它不能仅凭相似度证明具体事实存在；TS-999必须由正文来核对。

应该清楚表达证据不足，而不是从相近主题编一个答案。

08 · 拓展概念

生产扩展各自补一个缺口

Contextual Retrieval

先补背景再索引

LLM为chunk生成通常50–100 token的文档背景，增加预处理成本。

BM25

补精确词项

与向量召回合并去重，补错误码、缩写等精确匹配。

Rerank

重排候选

联合读问题与候选，再筛更少片段进入上下文。

本日实现向量召回。以上是拓展，不把它们说成已实现功能。

Anthropic特定top-20实验：背景向量35% → 加背景BM25 49% → 加rerank 67%，均为检索失败率相对降幅。

标题元信息有帮助，但并不等于LLM生成的背景小抄。

语义相近和精确命中各有所长，组合后仍需评估。

重排提高候选选择能力，也增加计算或模型调用成本。

“下降49%”带有实验条件，不能当成任意项目的效果保证。

09 · 从输入到引用

观测时沿着证据走

① 工具卡片

先看取回了什么

query、k、片段ID、分数、阈值、正文和来源。

② 下一Step的输入

再看发送了什么

检索内容属于role=tool。点击“X条messages”查看该Step的全部输入。

③ 回答引用

最后核对结论

点击[D05]跳回对应检索；编号必须真实返回并过阈值。

检索成功 ≠ 引用有效 ≠ 回答正确
即使引用了正确的资料，也可能在生成时把“是”说成“不是”。

先确认工具真的被调用，而不是模型声称已经查过。

工具返回不代表原文全部进窗口；长结果还可能被Day 3截断。

点击引用能缩短核查路径，不能替代你阅读原文。

本次首轮就发现了“引用正确、否定关系说反”的问题。

资料里有一句“忽略系统规则”呢？

它只是文档中的文字，不能变成系统权限或执行命令。

Anthropic原文 ↗ · Manus原文 ↗ · 多语言模型 ↗
