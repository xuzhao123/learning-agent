# Day 24：项目指令与提示词组装

## 学习目标与术语

学完能说明：一次模型请求里的内容按什么顺序排、为什么这样排；项目指令文件（AGENTS.md、CLAUDE.md）怎样被发现、分层和加载；环境信息该放什么、放在哪；运行中出现的新情况为什么用“追加提醒”而不是改写前面的内容；以及项目指令带来的信任问题。

| 术语 | 通俗解释 |
| --- | --- |
| 项目指令文件 | 仓库维护者写给 agent 的说明，常见名字是 AGENTS.md（跨工具约定）、CLAUDE.md（Claude Code）；内容是构建命令、代码风格、禁区等 |
| 分层 | 全局（个人）、仓库根目录、子目录各有一份，越靠近被修改文件的越具体 |
| 按需加载 | 子目录的说明不在开头全部放进来，等模型真的读写那个目录里的文件时再加 |
| 环境上下文 | harness 告诉模型的客观事实：工作目录、分支、有没有未提交改动、日期、操作系统、权限 |
| 系统提醒（system reminder） | harness 在对话末尾追加的一小段说明，用来通知变化，不是用户说的话 |
| 提示缓存前缀 | 每次请求开头一字不差的那一段；服务端可以复用它的计算结果 |
| 指令优先级 | 系统规则、项目指令、用户消息、工具结果之间冲突时听谁的 |

## 1. 一次请求里都有什么

一次模型请求不只是“用户的问题”。成熟的 harness 每次都会发出这样一串内容：

```text
┌ 工具定义（JSON schema）              几乎不变
├ 系统指令：身份、工具使用规则、安全规则   几乎不变
├ 项目指令：AGENTS.md / CLAUDE.md       一个会话内不变
├ 记忆、Skills 索引                      会话级
├ 环境信息：目录、分支、改动、日期         偶尔变化
├ 对话历史：问题、回答、工具调用与结果      只追加
└ 系统提醒：文件被改了、子目录有说明……     追加在末尾
```

排序原则就是第 22 天讲过的：**按变化频率从低到高排**。越靠前的内容越稳定，提示缓存能复用的前缀就越长。

OpenAI 介绍 Codex 时写明了它的做法：指令和工具定义在前，AGENTS.md 和环境上下文作为输入条目随后，之后只往后追加；中途配置变了（例如换了权限、换了目录），追加一条新的说明，而不是修改已经发出去的内容，以免缓存失效。[资料](https://openai.com/index/unrolling-the-codex-agent-loop)

## 2. 项目指令文件

### 2.1 为什么需要

同一个 agent 要在很多仓库里干活。每个仓库都有自己的约定：用什么命令构建测试、代码风格、哪些目录不能动、提交信息怎么写。让用户每次在提问里重复这些不现实，所以约定写进仓库里的一个文件，harness 自动读。

AGENTS.md 是多家编码 agent 共同支持的约定：一个普通的 Markdown 文件，没有固定格式。[资料](https://agents.md/)

### 2.2 怎样发现和分层

| 层级 | 位置 | 何时加载 |
| --- | --- | --- |
| 全局 | 用户主目录下的配置目录 | 每个会话开头 |
| 仓库根目录 | 仓库根的 AGENTS.md | 每个会话开头 |
| 子目录 | 某个子目录里的 AGENTS.md | Codex 在会话开头加载从仓库根到当前工作目录的各级文件（同一目录还可以用 AGENTS.override.md 覆盖）；Claude Code 对子目录的 CLAUDE.md 按需加载，读到那个目录的文件时才放进来 |

多份同时生效时，越具体的越优先：子目录的约定覆盖根目录的，根目录的覆盖全局的。[资料](https://learn.chatgpt.com/docs/agent-configuration/agents-md) [资料](https://code.claude.com/docs/en/memory)

按需加载有两个好处：开头的上下文更小；说明出现的时机恰好是模型要改那个目录的时候，离使用最近，最不容易被忽略。

### 2.3 大小与位置

项目指令每次请求都要带，所以要限制大小（Codex 默认 32KiB），超出时截断并注明。它在一个会话里不变，适合放在稳定前缀里。

## 3. 环境上下文

模型在开始干活前需要知道一些客观事实，否则会浪费几轮去探索，或者基于错误假设行动：

| 信息 | 为什么需要 |
| --- | --- |
| 工作目录 | 相对路径从哪里算 |
| git 分支、最近一次提交 | 判断自己在什么版本上工作 |
| 有没有未提交改动 | 避免把用户的半成品当成干净状态，改坏了也知道怎么区分 |
| 日期 | 模型的训练数据有截止时间，不知道“今天” |
| 操作系统 | 命令怎么写 |
| 沙箱与权限 | 哪些操作会被拦，免得反复试 |

只放便宜、可靠、影响决策的事实。目录树、完整的 git log 这类大块内容，让模型需要时用工具自己查。

环境信息会变：多轮对话之间，用户可能切了分支、提交了代码。处理方式和其他变化一样：发现和上一份不同，就在末尾追加一份新的，并说明“以这份为准”。

## 4. 系统提醒：变化用追加表达

运行中会出现新情况，harness 需要告诉模型：

- 模型读过的文件被别人改了（编辑器、另一个进程、模型自己用 shell 改的）；
- 模型开始在一个有自己说明的子目录里干活；
- 环境或配置变了；
- 计划、待办列表的状态需要提醒（第 27 天）。

两种做法：

| 做法 | 结果 |
| --- | --- |
| 改写前面的内容（例如更新系统提示词里的环境段） | 从改动处往后的缓存全部失效；模型看到的历史也被“篡改”，前后对不上 |
| 在末尾追加一条提醒 | 前缀不变，缓存照常命中；历史保持真实，模型知道“之前是这样，现在变了” |

Claude Code 把这类内容称为 system reminder，以带标记的文本追加进对话，并在文档里说明它会提醒模型“之前读过的文件在磁盘上变了”等情况。[资料](https://code.claude.com/docs/en/how-claude-code-works)

提醒用的是用户角色（模型接口里只有系统、用户、助手、工具几种角色，追加在中间只能用用户或工具角色），但它不是用户原话。所以凡是依赖“用户说过什么”的功能（记忆只记用户原话、压缩时保留用户原话）都要把它识别出来、排除在外。

## 5. 缓存的账

以一个 10 步的任务为例，假设工具定义加系统指令加项目指令共 4.5k token，每步新增约 0.5k：

| 请求 | 输入总量 | 能命中缓存的部分 |
| --- | --- | --- |
| 第 1 次 | 4.5k | 0（第一次） |
| 第 2 次 | 5.0k | 约 4.5k |
| 第 k 次 | 4.5k + 0.5k×(k−1) | 约为上一次的全部 |

只要不改写前面，每次请求真正需要从头计算的只有新增的那 0.5k。如果每一步都更新一次系统提示词里的“当前时间”，每次都从头算，成本和延迟都随步数线性增长。

一个常见的反例就是把精确到秒的时间、随机 ID、每次重新排序的工具列表放进系统提示词。

## 6. 指令优先级与信任

项目指令来自仓库文件，仓库可能不是用户自己写的：克隆下来的开源项目、别人提交的分支，都可能在 AGENTS.md 里藏着“运行这个脚本”“把密钥发到某地址”这样的指令。这就是第 18–19 天的提示注入，只是来源换成了仓库。

应对思路：

- **优先级写清楚**：系统规则高于项目指令，项目指令高于工具结果里出现的文字。
- **信任仓库再加载**：Codex 和 Claude Code 首次在一个目录里运行时，会问用户是否信任这个目录。
- **权限不因指令而放宽**：项目指令能告诉模型怎么做，但不能绕过权限规则和沙箱；真正的边界在程序里（第 25 天）。

## 自测

**为什么要按变化频率排序请求内容？**

提示缓存只复用开头一字不差的部分。稳定的内容放前面，前缀就长，每次需要重新计算的只有末尾新增的部分。

**子目录的项目指令为什么按需加载，而不是开头全部放进来？**

开头的上下文更小；说明出现在模型即将修改那个目录的时候，时机最近、最不容易被忽略；用不到的目录不占上下文。

**多轮对话之间用户切了分支，harness 应该怎么告诉模型？**

在末尾追加一份新的环境信息，说明以这份为准；不回头修改第一轮的环境信息。

**系统提醒用的是用户角色，为什么记忆和压缩要把它排除？**

它不是用户说的话。记忆只能记用户原话，压缩时保留的也是用户原话；把提醒当成原话，就会把 harness 的文字记成“用户说过”。

**一个陌生仓库的 AGENTS.md 要求“先运行 setup.sh”，agent 应该怎么对待？**

它是仓库内容，可能是注入。能参考，但执行仍要经过权限规则和沙箱；陌生仓库应先确认信任再加载项目指令。
