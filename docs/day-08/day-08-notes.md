# Day 8：Agent 运行时——取消、超时与重试

## 学习目标

读完本文，应能回答以下问题：

1. 为什么取消是“协作式”的？调用方发出取消后，被调用的代码还要做什么？
2. 一次 agent 运行里有哪几层超时？它们之间是什么关系？
3. 一次工具调用有哪四种结局？哪几种可以放心重做？
4. 拿到一个错误时，怎样决定重试、不重试，还是交给模型处理？
5. 为什么“超时”不能等同于“失败”？
6. 进程收到停止信号时，优雅退出要按什么顺序做事？

## 1. 从“会停”到“能被控制”

Day 2 的护栏回答的是“循环自己什么时候该停”：步数预算、重试上限、重复动作熔断。它们都只看循环内部的计数。

生产中还有两类停止来自外部：

- **时间**：用户只愿意等两分钟；某个外部服务卡住了，迟迟不返回。
- **外部命令**：用户点了“停止”；运维要发布新版本，进程收到 SIGTERM；调度方决定放弃这个任务。

运行时（runtime）就是负责这些事的那一层：把“停”的命令可靠地传到正在干活的每一处，并且停下以后，能准确说清楚每个动作做到了哪一步。

## 2. 取消是协作式的

### 2.1 取消信号怎样传下去

一次运行可以看成一棵调用树：运行 → 每一轮 → 一次模型请求、几个并行的工具调用 → 工具内部的 HTTP 请求。取消信号从根往下传，每个节点都拿到一个“上下文”（Go 里是 `context.Context`），它带着三样东西：

- 一个 `Done()` 通道，取消时被关闭；
- 一个截止时间（可选）；
- 取消的原因（`Err()`：`Canceled` 或 `DeadlineExceeded`）。

子节点从父节点派生出自己的上下文，可以再加更短的时限。规则只有两条：

- **父取消，子全部取消**；子取消不影响父。
- **子的截止时间 = min(父的截止时间, 自己的时限)**。

```text
整次运行（时限 2 分钟）                       已用 100 秒
 └─ 第 3 轮
     ├─ 模型请求（自己的时限 5 分钟）        实际剩余 20 秒：受父限制
     └─ 工具 A（单次尝试时限 30 秒）          实际剩余 20 秒：受父限制
```

### 2.2 “协作”指什么

发出取消只是关闭一个通道，没有任何机制能强行中止一个正在运行的函数。被调用的代码必须**自己检查**并尽快返回：

- 阻塞操作（网络请求、等待、读队列）都要能被取消打断：HTTP 请求带上 ctx，等待用 `select` 同时等 `ctx.Done()`；
- 长时间计算在循环里定期检查 `ctx.Err()`；
- 子进程要转发信号，比如先发 SIGINT，过一段宽限期仍不退出再强制结束。

如果某个工具不配合（比如调用了一个不支持取消的第三方库），执行器只剩一个办法：**不等了**。让工具在单独的 goroutine 或线程里跑，执行器到时就返回。代价是那个工具可能在后台继续跑完，它的副作用照样发生。所以执行器放弃等待时，不能把结果写成“失败”，只能写成“未知”。

## 3. 超时的层次

| 层次 | 保护什么 | 太短的后果 | 太长的后果 |
| --- | --- | --- | --- |
| 整次运行 | 用户的耐心、总成本 | 正常任务被打断 | 卡住的任务长期占资源 |
| 单次模型请求 | 网络卡死、服务端排队 | 推理较长的请求被误杀 | 一次卡顿吃掉全部时间 |
| 单次工具尝试 | 外部服务无响应 | 正常的慢操作被误判 | 一个工具拖住整批 |
| 外部服务自己的超时 | 服务端资源 | — | — |

几条经验：

- **每一层都要有超时**。只要有一层没有，那一层卡住时上面的超时就只能“放弃等待”，而无法让它真正停下来。
- **时限向下传递**（deadline propagation）。gRPC 会把剩余时间放进请求头传给下游，下游据此知道“再算也来不及了”，不必白干。
- **按尝试设时限，而不是按逻辑调用**。一个逻辑调用最多尝试 3 次，每次 30 秒，总共最多 90 秒加退避时间；整次运行的时限再兜底。
- 步数预算不能代替超时：预算限制的是“请求几次”，不限制“每次等多久”（见 [Day 2 笔记](../day-02/day-02-notes.md) 第 7 节）。

## 4. 一次调用的四种结局

| 结局 | 含义 | 副作用 | 能否直接重做 |
| --- | --- | --- | --- |
| 成功 | 拿到了结果 | 已发生 | 不需要 |
| 确定失败 | 执行完了，返回了错误 | 通常没有 | 看错误类型 |
| 未执行 | 还在排队、或开始前就被取消 | 一定没有 | 可以 |
| 结果未知 | 开始执行了，完成前超时或被取消 | **可能有** | 只有幂等或只读的操作可以 |

“未知”是最容易被处理错的一种。比如转账请求发出后 30 秒没有响应：钱可能没转，也可能已经转了只是响应丢了。如果把它当“失败”重试，就可能转两次。正确的做法是：

- 只读操作（查询、计算）：直接重做，没有代价；
- 带幂等键的操作：用同一个键重做，服务端保证只生效一次（Day 10 详讲）；
- 其他操作：不要自动重做，先查询外部状态核对；没法核对时，如实告诉上层“结果未知”，由上层（模型或人）决定。

这四种结局还要**分开记录**。如果被取消的调用从报告里消失，或者“执行中被取消”被写成“失败”，看报告的人就会误以为可以放心重试。

## 5. 重试决策

拿到一个错误，按顺序问四个问题：

```text
① 整次运行已经被取消或到时了吗？        是 → 不重试，停下
② 这是确定性错误吗？（参数错、不存在、无权限）  是 → 不重试，把错误交给模型改正
③ 结果是未知的吗？（执行中超时）          是 → 只读或幂等才重试，否则交给上层核对
④ 其余（网络抖动、限流、服务端 5xx）      → 退避后重试，直到次数用完
```

| 错误 | 类型 | 处理 |
| --- | --- | --- |
| 参数格式错误、HTTP 400、表达式除以 0 | 确定性 | 不重试；回填给模型，让它改参数 |
| HTTP 401/403 | 确定性（对当前凭据而言） | 不重试；需要人介入 |
| HTTP 404 | 通常确定性 | 不重试 |
| HTTP 429 | 暂时性 | 重试，优先按 `Retry-After` 等待 |
| HTTP 500/502/503、连接被重置 | 暂时性 | 退避重试 |
| 读超时 | **结果未知** | 只读或幂等才重试 |

分类最好由**最了解错误的那一层**来做：工具封装知道“除以 0”永远会失败，在返回错误时就打上“不可重试”的标记；执行器只看标记，不去解析错误文本。没打标记的错误按暂时性处理，这样新加的工具不会因为漏标而失去重试。

还有两点：

- **重试要有总预算**。每层都重试 3 次，三层叠起来就是 27 次（Day 2 的“重试放大”）。服务大面积故障时，重试流量会让它更难恢复。常见做法是只在一层重试，或者限制重试请求占总请求的比例。
- **退避要加抖动**。很多客户端同时失败、又按同样的间隔同时重试，会形成一波波的尖峰（见 Day 2 第 3.2 节）。

## 6. 优雅停止

收到停止信号后，一个正确的退出顺序是：

1. **不再接新活**：不再请求模型、不再派发新的工具调用；
2. **打断正在做的事**：取消上下文，让在途的请求和工具尽快返回；
3. **记账**：每个调用按四种结局写清楚，包括没执行的和结果未知的；
4. **持久化**：把状态写到磁盘，供之后续跑（Day 9）；
5. **退出**。

还要给这个过程设一个上限：Kubernetes 删除 Pod 时先发 SIGTERM，默认等 30 秒（`terminationGracePeriodSeconds`），还没退出就发 SIGKILL。命令行程序的常见约定是：第一次 Ctrl+C 优雅退出，第二次立即退出。用户不必为一个卡住的清理过程干等。

优雅停止不能代替崩溃恢复：进程随时可能被 SIGKILL、OOM 或断电直接杀掉，一行清理代码都来不及执行。能应对这种情况的只有提前落盘的状态，这是 Day 9 的内容。

## 7. 常见错误

- **超时之后不取消**：调用方不等了，被调用方还在后台继续占着连接和内存。只要有超时，就要同时取消。
- **吞掉取消错误**：工具捕获了所有错误再包装成普通失败，执行器就分不清“工具失败了”和“我们取消了它”，于是又去重试。
- **用不可打断的等待**：退避时调用 `time.Sleep`，取消信号要等睡眠结束才生效。
- **把超时当失败**：对有副作用的操作自动重试，造成重复执行。
- **只在最外层设超时**：外层到时后，底层的请求仍在跑，资源泄漏。

## 8. 自测

**1. 父上下文剩 10 秒，子操作想设 30 秒的时限，实际是多少？**
10 秒。子的截止时间取父与自己的较小值；父到期时子一定被取消。

**2. 一个工具不检查取消，执行器怎样才能不被它卡住？**
让工具在单独的 goroutine 里运行，执行器同时等结果和超时，先到哪个算哪个。超时返回时把结果记为“未知”，因为工具可能仍在后台执行。

**3. 发送邮件的工具执行 30 秒后超时，执行器该重试吗？**
不该自动重试。邮件可能已经发出，重试可能让对方收到两封。应记为结果未知，先查发件记录；没法查时交给模型或人决定。

**4. 计算器工具超时了，执行器该重试吗？**
可以。计算是只读的，重复执行没有副作用。

**5. 为什么由工具封装给错误打“不可重试”的标记，而不是执行器去匹配错误文本？**
工具封装最清楚错误的含义；错误文本可能改写、翻译，按文本匹配既脆弱又容易漏判。标记是稳定的结构化字段。

**6. 第一次 Ctrl+C 后程序在清理时卡住了，用户该怎么办？好的程序该怎样设计？**
第二次 Ctrl+C 应当立即退出。第一次信号触发优雅停止后，程序应恢复默认的信号处理，让第二次信号直接结束进程。
