# Day 28：怎样复盘一个 harness

## 学习目标与术语

学完能说明：复盘一周的 harness 工作时，为什么要跟着一次真实请求走完全程，而不是逐个功能回顾；怎样判断一条约束由谁执行、能保证到什么程度；为什么问题大多出在边界上；遗留问题怎样分成修、推迟、不修；界面上的“结局”为什么不能用进程退出码代替；请求预算去掉之后，靠什么让循环停下来。

本周的串联图与本项目的证据见 [第四周复盘](../week-04-review.md)；本篇讲方法本身。

| 术语 | 通俗解释 |
| --- | --- |
| 端到端走查 | 拿一次真实请求，按发生顺序记下它经过的每个环节和当时实际发生的事 |
| 执行者 | 一条约束最终由谁保证：提示词、程序还是人 |
| 边界 | 两部分交接的地方：进程之间、上下文窗口的上限、预算的上限、自己的程序与外部工具之间 |
| 结局 | 一轮为什么结束：正常回答、预算用完、被取消、熔断等，是程序自己知道的语义 |
| 退出码 | 进程退出时的一个整数，只能区分“成功”和“某种不成功” |
| 熔断 | 发现循环没有进展时主动停下，比如同一个动作重复多次、连续几步没有新信息 |

## 1. 跟着一次请求走，而不是逐个功能回顾

逐个功能回顾（“这周做了工具、提示词、权限、hooks”）只能说明每个部件单独能用。部件之间怎么衔接、顺序对不对、一个部件的输出是不是另一个部件需要的输入，只有把它们按真实顺序排成一条链才看得出来。

做法是挑一次真实发生过的任务，在每个环节旁边写下**当时实际发生的事**，而不是这个环节“应该”做什么。例如一次编码任务：

```text
用户输入        → 命令展开、提交前检查         实际：每轮都通过
组装提示词      → 规则 + 项目说明 + 环境提醒    实际：换权限模式时追加了“环境变了”
模型要调用工具  → 工具前检查 → 权限 → 执行      实际：某条命令在沙箱里被外部工具改写了
上下文快满      → 压缩                        实际：压缩后同一个文件读了 7 次
模型想结束      → 结束前检查                   实际：预算先用完，检查没有机会运行
```

右边一列写不出来的环节，就是没被真实任务覆盖过的环节；右边一列和预期不符的地方，就是下周的工作。这和事故复盘的时间线是同一个思路：先还原事实，再讨论原因。[资料](https://sre.google/sre-book/postmortem-culture/)

## 2. 每条约束由谁执行

同一条规则（例如“计划阶段不能改文件”）可以由三种执行者保证，可靠程度完全不同：

| 执行者 | 例子 | 能保证什么 | 失效方式 |
| --- | --- | --- | --- |
| 提示词 | 在提醒里告诉模型“现在只读” | 大多数时候被遵守 | 模型忘了、误解了，或者觉得这次例外 |
| 程序 | 权限检查拒绝写工具；沙箱把目录挂成只读 | 每次都检查，模型绕不过 | 规则只看文本时可以换种写法；执行环境才是硬边界 |
| 人 | 审方案、看改动、验收 | 方向和事实对不对 | 慢、贵，不能每一步都看 |

复盘时把每条约束归到一行。归到“提示词”的，问一句：违反一次的代价能不能接受？不能接受的，就该下沉到程序里。归到“程序”的，再问一句：它看的是文本还是执行环境？只看文本的规则（比如命令字符串匹配）挡得住正常用法，挡不住刻意绕过。

## 3. 问题出在边界上

正常路径上的功能，在各自的验证里通常都能通过。一周的真实运行里反复出现的问题，几乎都在交接处：

- **进程边界**：某个状态只放在内存里，换一个进程（续跑、续聊）就丢了。
- **窗口边界**：上下文装不下时压缩，压缩丢掉的内容被模型重新读回来，又把窗口撑满。
- **预算边界**：活已经干完，只差最后一步，预算先用完；依赖“模型自己结束”才运行的检查因此没跑。
- **外部工具边界**：外部程序升级后行为变了（比如开始替换命令里的变量），自己的代码没改也会出错。

所以复盘时专门列一张“反复出现的问题”表，每一行写现象、出现在哪、原因。看共同点比逐条修更有价值：如果三个问题都是“状态没跟着检查点走”，那该改的是写检查点的原则，而不是三个地方各打一个补丁。

## 4. 遗留问题：修、推迟、不修

复盘会攒下一批问题。全部当场修，会把复盘变成没有边界的开发；全部推迟，同样的误导会一直存在。每一条按三个问题判断：

1. **每次都会误导人或模型吗？** 是，而且改动小，就现在修。
2. **它有没有一个更合适的位置？** 如果后面某个专题会系统地解决它，就推迟到那里，并写清推迟到哪。
3. **现在的兜底够不够？** 已有更可靠的执行者挡住了，而且保留现状还有观察价值，就可以不修，但要写出理由。

“不修”和“推迟”都要留下理由，否则下次复盘还会再讨论一遍。

## 5. 结局不是退出码

进程退出码只有一个整数，通常 0 表示成功、非 0 表示“某种不成功”。一轮 agent 运行可能因为很多原因没正常结束：预算用完、被人取消、上下文放不下、连续重复同一动作被熔断、外部检查拦下。对人来说，这几种情况的处理完全不同：

| 结局 | 人应该做什么 |
| --- | --- |
| 预算用完 | 活可能已经快做完了，看看改动，续一轮让它收尾 |
| 被取消 | 是人自己停的，按需要继续 |
| 重复动作熔断 | 模型卡住了，换个说法或给更多信息 |
| 出错 | 看日志找原因 |

如果界面只显示“失败：退出码 1”，这四种情况看起来一样，人只能去翻日志。程序其实知道自己为什么停，应该把这个语义作为结构化字段传给界面，界面直接显示；退出码只用来判断“是否正常结束”。这是一个通用原则：**界面显示的状态应该来自产生它的程序给出的语义，而不是从进程的副作用里反推。**

## 6. 去掉请求预算之后，靠什么停下

每轮最多 N 次模型请求，是最简单的循环终止条件。[资料](https://www.anthropic.com/engineering/building-effective-agents) 它的问题是 N 很难定：编码任务读几个文件、改几处、跑一次编译，就可能用掉几十次请求；N 定小了，活干到一半就停；定大了，又起不到保护作用。

把“次数上限”去掉，不等于没有终止条件。剩下的终止条件是：

| 机制 | 挡住什么 |
| --- | --- |
| 重复动作熔断 | 同一个调用、同样的参数反复执行 |
| 无进展熔断 | 连续几步没有新信息、没有新动作 |
| 人按停止 | 人觉得方向错了，或者太贵了 |
| 上下文与成本的可见性 | 界面实时显示请求次数、tokens，人能及时判断 |

实现上常见的做法是把“不限”表示成一个足够大的数，预算的加减与比较照常进行，不用在每个检查点判断“是不是不限”；只在显示时把它写成“不限”。存档或配置里如果原来用 0 表示“没设置、用默认值”，就要另选一个值（比如负数）表示“不限”，否则旧数据的含义会变。

## 自测

1. 为什么逐个功能回顾发现不了“预算用完时结束前检查没跑”？
   答：每个功能单独验证时都正常；只有按真实顺序把“预算检查”和“结束前检查”排在一条链上，才看得出前者先发生时后者没机会运行。
2. “计划阶段只读”写在提示词里，同时权限层也拒绝写工具。为什么两者都要？
   答：提示词让模型知道规则，避免它去试；权限层保证它试了也做不到。只有提示词时，违反一次就改坏了文件；只有权限层时，模型不知道为什么被拒，会反复尝试。
3. 三个问题分别是“续聊后丢了读文件记录”“压缩后丢了子目录说明”“环境提醒被压缩后误报变化”，复盘该得出什么结论？
   答：共同原因是影响下一步决定的状态没有跟着检查点或视图走。结论是一条原则：这类状态要么写进检查点，要么能从视图重新推出来。
4. 界面显示“失败：退出码 1”，用户能做什么判断？改成显示结局之后呢？
   答：只能知道没正常结束，要翻日志。显示“预算用完”后，用户知道活可能快完成了，可以直接看改动并续一轮收尾。
5. 配置里原来 0 表示“用默认值”，现在想让用户填 0 表示“不限”，存档里该怎么记？
   答：界面上的 0 在存档里换成一个原来不会出现的值（比如 -1），启动时再翻译回“不限”；旧存档里的 0 仍按默认值处理，含义不变。
6. 去掉请求次数上限后，一个模型反复调用同一个工具、参数完全一样，什么会让它停下？
   答：重复动作熔断。如果参数每次略有不同、绕过了重复检测，还要靠无进展熔断和人按停止。
