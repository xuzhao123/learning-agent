# 子 agent（Subagents）：把子任务交给一个新的上下文

## 学习目标

读完本文，应能回答以下问题：

1. 子 agent 是什么？它和“模型调用一个工具”有什么相同、有什么不同？
2. 为什么要用子 agent？它解决的首要问题是什么？
3. 子 agent 的代价有哪些？什么任务不适合拆给子 agent？
4. 交给子 agent 的任务说明要写清哪几样东西？
5. 子 agent 应继承父 agent 的哪些工具和权限？哪些不该继承？
6. 子 agent 和任务调度是什么关系？

## 1. 是什么

子 agent 是父 agent 在执行循环里派出去的另一个 agent：

```text
父 agent 的循环
  第 1 轮：模型决定 spawn_agent(task="调研 A") 和 spawn_agent(task="调研 B")（同一轮，并行）
            ├─ 子 agent A：全新上下文，只有 task；自己多轮调用工具 → 交回结论 A
            └─ 子 agent B：全新上下文，只有 task；自己多轮调用工具 → 交回结论 B
  第 2 轮：模型读到两条 tool 结果（结论 A、结论 B），汇总回答
```

从父 agent 的角度看，`spawn_agent` 就是一个普通工具：有参数，返回一个结果。差别在工具内部：它不是一个函数，而是一整个 agent 循环。这种结构在 Anthropic 的《Building effective agents》里叫“编排者—执行者”（orchestrator-workers）：由模型在运行时决定怎样拆分，而不是由程序预先写死。

与 Day 10 的任务队列对比：

| | 任务队列 | 子 agent |
| --- | --- | --- |
| 谁发起 | 用户或系统 | 父 agent 的模型 |
| 任务之间 | 互相独立，彼此不知道 | 父子结构，父等子的结果再继续推理 |
| 解决什么 | 排队、并发上限、幂等、重试 | 上下文隔离、并行探索 |
| 所在层次 | 基础设施 | agent 的行为 |

## 2. 为什么用

### 2.1 上下文隔离（首要原因）

调研类任务的中间过程很长：搜索结果、读过的网页、走过的弯路。全部留在一个上下文里，很快就会触发 Day 3 的压缩，早期的约束和细节被摘要掉。

子 agent 把探索过程关在自己的上下文里，只把**压缩后的结论**交回。父 agent 的上下文里每个子任务只占一条 tool 结果，可以同时管理更多的子任务，也更不容易被无关细节干扰。这本质上是一种上下文工程：用一次额外的“总结”换取父上下文的干净。

### 2.2 并行

互不依赖的子任务可以同时执行，总耗时接近最慢的那一个，而不是所有子任务之和。

### 2.3 专门化

每个子 agent 可以有自己的 system prompt、工具集合，甚至更便宜的模型。比如“读 100 个文件找出提到 X 的”交给小模型，父 agent 用大模型做判断。

### 2.4 故障隔离

一个子 agent 陷入死循环、超出预算或崩溃，只影响它自己的那一条结果；父 agent 可以看到失败，换一种方式完成。

## 3. 代价

- **成本**：每个子 agent 都要重新读 system prompt 和工具定义，自己的循环也要多轮请求。Anthropic 在介绍其多智能体调研系统时提到：单个 agent 的 token 用量约为普通对话的 4 倍，多智能体系统约为 15 倍。
- **丢失上下文**：子 agent 看不到父 agent 的对话。父 agent 认为显而易见的背景（“用户只关心 2024 年以后的”），子 agent 根本不知道。
- **决策冲突**：两个子 agent 分别做出互相矛盾的假设（一个按 A 方案写代码，一个按 B 方案），父 agent 汇总时才发现。Cognition 的文章《Don't Build Multi-Agents》以此为主要论据，主张需要共享决策的任务（如写代码）应当在单一线程里完成。
- **调试困难**：问题可能出在任务说明、子 agent 的执行、或汇总的任何一处，轨迹分散在多个上下文里。

## 4. 什么时候用

适合：

- **广度优先**的任务：同时调研几家公司、几篇论文、几个模块，彼此独立；
- 每个子任务都要**多步**工具调用，中间过程很长，而结论很短；
- 子任务需要的上下文能用一段话说清楚。

不适合：

- 一两步就能完成的任务：派子 agent 的开销比直接做还大；
- 子任务之间需要频繁交换中间结果，或者共同依赖同一组决定；
- 需要完整对话历史才能做对的任务。

## 5. 设计要点

### 5.1 任务说明

子 agent 只能看到 task 参数，所以它就是子 agent 的全部输入。一份好的任务说明包括：

- **目标**：要回答什么问题；
- **背景**：用户的约束、已经知道的事实、不要做什么；
- **输出格式**：要列表还是表格、要不要引用来源、长度多少；
- **边界**：用哪些工具、到什么程度就停。

Anthropic 的调研系统在早期就遇到过任务说明太短的问题：几个子 agent 做了重复的搜索，或者理解偏了任务。

### 5.2 权限与工具：按最小权限继承

- 子 agent 只需要完成子任务所需的工具。只做调研的子 agent 不该拿到写文件、发邮件的工具。
- **长期记忆通常不继承**：记忆的写入依据是“用户说过的话”，而子 agent 的“用户”是父 agent 的模型，它写下的任务说明不是用户原话。
- **限制深度**：子 agent 一般不能再派子 agent，否则一个错误的拆分会指数级放大。
- **限制数量与预算**：每次运行最多派几个、每个子 agent 最多请求几次模型。

### 5.3 结果是数据，不是指令

子 agent 读过的网页、文件可能含有提示词注入，它交回的结论也可能带着被注入的“指令”。父 agent 应把子 agent 的结果当作数据：汇总时核对彼此是否矛盾、是否有来源，而不是照着执行。

### 5.4 汇总与核对

父 agent 汇总时要处理三种情况：结论一致、结论矛盾、某个子 agent 失败。矛盾时可以再派一个子 agent 专门核对，或者如实报告分歧。

## 6. 与运行时、任务调度的关系

子 agent 本质上是“由模型发起的任务”，所以前几天的机制在这里全部要用上：

| 机制 | 在子 agent 上的作用 |
| --- | --- |
| 取消传递（Day 8） | 用户停止父任务，所有子 agent 一起停止 |
| 超时（Day 8） | 每个子 agent 的单次尝试有时限，一个卡住的子 agent 不会拖住父任务 |
| 检查点（Day 9） | 子 agent 有自己的检查点；父任务续跑时，已完成的子任务直接取回结论 |
| 幂等键（Day 10） | 子任务ID由父任务ID派生，父任务重放这次派发时找到同一个子任务，不会重跑 |
| 并发上限（Day 10） | 同时运行的子 agent 数量受控，不会一次请求打满模型配额 |

## 7. 自测

**1. 子 agent 与普通工具调用，在父 agent 看来有什么区别？**
在父 agent 看来没有区别：都是一个带参数的工具，返回一条结果。区别在工具内部：子 agent 是一整个多轮的 agent 循环，有自己的上下文和预算。

**2. “查一下今天星期几”适合派给子 agent 吗？**
不适合。一次工具调用就能完成，派子 agent 要多花一整份 system prompt 和至少两次模型请求，而且不能节省父上下文。

**3. 父 agent 让两个子 agent 分别写前端和后端代码，可能出什么问题？**
两者可能对接口格式、命名、错误处理做出不同的假设，汇总时才发现对不上。共享决策多的任务更适合在一个上下文里顺序完成，或者先由父 agent 定好接口再分派。

**4. 子 agent 为什么不该继承长期记忆的写入能力？**
记忆写入要求引文逐字来自用户原话；子 agent 收到的“用户消息”是父 agent 写的任务说明，不是真人说的话。让它写入，会把模型生成的内容当成用户偏好保存下来。

**5. 父任务崩溃后续跑，重放了一次 spawn_agent，怎样避免子任务从头再跑？**
子任务ID由父任务ID和派发内容确定性地派生，子任务有自己的检查点。重放时用同一个ID，已完成的直接返回存档结论，未完成的从检查点续跑。
