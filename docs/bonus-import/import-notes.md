# 扩展：导入其他 agent 的会话记录

## 学习目标与术语

学完能说明：为什么要用同一套观测工具看不同 harness 的运行；Codex 与 Claude Code 的会话记录各按什么单位记、怎样从里面切出“一次模型请求”；归一化到一种消息格式时哪些能对上、哪些只能估算或缺失；长会话为什么不能每次请求都存完整历史。

| 术语 | 通俗解释 |
| --- | --- |
| 会话记录 | agent 把一次会话里发生的事按行写进 JSONL 文件，用于恢复会话；不是原始请求的录像 |
| 条目（item） | 记录的基本单位：一条消息、一次工具调用、一次工具输出、一段推理 |
| 归一化 | 把不同来源的记录换成同一种数据形状，下游只写一套视图 |
| 增量存储 | 每次请求只存相比上一次新增的消息，读的时候再拼回完整输入 |
| 插话（steering） | 模型还在干活时用户又发来一句话，agent 在下一次请求里带上它，不等这一轮结束 |

## 1. 为什么要看别家的记录

自己的 harness 只能和自己比。把成熟 harness 的真实会话放进同一个观测台，可以直接对照：

- 系统提示词有多长、分几段、运行中追加了什么；
- 工具怎么设计：几十个细粒度工具，还是一个“写脚本编排其他工具”的总工具；
- 一轮用户问题平均发几次请求、缓存命中率多少、压缩何时发生；
- 并行工具调用、插话、中断在记录里长什么样。

前提是两边的数据能放进同一种形状里，这就是归一化要解决的问题。

## 2. 两种记录的结构

**按条目记、按用量切分（Codex 的 rollout）。** 每行是 `{timestamp, type, payload}`。发给模型和模型产出的东西都是 `response_item`：developer / user / assistant 消息、reasoning、函数或自定义工具调用、工具输出、工具定义。每次模型响应结束会写一条用量记录，正好可以当作“一次请求”的分界：两条用量记录之间的输出条目属于同一次响应，之前积累的输入条目就是这次请求的输入。界面事件（用户原话、一轮开始与结束、中断）另记一类，用来划分轮次。推理原文加密保存，记录里只有可选的摘要。

**按内容块记、用父指针串成树（Claude Code 的会话 JSONL）。** 一次 assistant 回复按内容块（思考、正文、每个工具调用）拆成多行，它们共享同一个 message.id。每行有 uuid 和 parentUuid：

```text
回复 A：工具调用 1 ── 工具调用 2 ── 工具调用 3
          │             │             │
        结果 1        结果 2        结果 3 ── 下一次回复 …
```

并行工具的结果各自挂在自己那一行下面，于是“从最后一条沿父指针往回走”只能走到其中一条支路。倒回重试也会留下真正的废弃分支。所以要先走出主干，再按回复判断：回复有一行在主干上，就把它的所有行和挂在下面的工具结果都收进来。压缩时写一条边界记录（父指针为空，用另一个字段接上前文）和一条摘要消息；子 agent 的记录存在单独的文件里。

两种设计各有取舍：按条目记、用用量切分，请求边界清楚，但同一次响应的输出会散在多行；按内容块记、用树串起来，能表达分支和流式过程中就开始执行的工具，但读的人要自己重建主干。

## 3. 归一化到 Chat 消息格式

| 归一化后 | Codex | Claude Code |
| --- | --- | --- |
| system | developer 消息 | 记录里没有 |
| user | user 消息（含注入的环境信息） | 用户原话、命令、注入的上下文 |
| assistant 正文 | assistant 消息（过程说明与最终回答） | text 块 |
| 推理 | reasoning 的摘要（原文加密） | thinking 块（新版本只留签名） |
| tool_calls | 函数调用、自定义工具调用（参数是原始文本） | tool_use 块（参数是 JSON） |
| tool | 工具输出条目 | tool_result 块（可带出错标记） |
| 工具定义 | 记录里有 | 记录里没有 |
| 用量 | 每次响应一条，含缓存与推理 token | 每条回复带用量，缓存的写入与命中分开 |

“一轮”的边界都来自用户原话，而不是消息角色：两家都会以 user 角色注入环境信息、技能说明、命令输出，这些只是上下文。只在客户端执行、没有请求模型的命令（清空、查看用量之类）不算一轮。

## 4. 还原不了的东西

- **原始请求**：记录是会话历史，不是请求录像。每次请求的输入只能按“到这一步为止的历史”重建；客户端在发送前做的裁剪、注入的系统提示词（记录里没有时）都看不到。
- **耗时**：只有条目的时间戳，请求耗时按“上一条输入到这次响应最后一条”估算，没有首字延迟。
- **推理原文**：Codex 加密，Claude Code 新版本只留签名。
- **子 agent**：在单独的文件里，只导入主会话时看不到它们的过程，只看到返回给主 agent 的结果。

这些缺失要在界面上说清楚，否则人会把“记录里没有”当成“模型没做”。

## 5. 为什么要增量存储

每次请求的输入都包含之前的全部历史。一段几百次请求、几百条消息的会话，如果每次请求都存完整输入，存储量是请求数乘以历史长度，会从几十 MB 膨胀到几 GB。做法和真实的提示缓存一样利用“前缀不变”：每次只存新增的消息，读的时候接在上一次后面；只有历史被重建（压缩之后）时才存完整列表。比较前缀时也先比对象引用，再比内容。

## 自测

1. 为什么 Codex 记录里用“用量记录”切分请求，而不是用 assistant 消息？
   答：一次响应可以产出多条条目（过程说明、推理、几个工具调用），用量记录每次响应只有一条，并且在这次响应的输出之后写入，是天然的分界。
2. 只沿 Claude Code 记录的父指针从最后一条往回走，会漏掉什么？
   答：并行工具调用里不在主干上的那几行调用和它们的结果。要按回复（message.id）把同一次回复的所有行收回来。
3. 导入后看到某次请求没有系统提示词，能得出“这个 agent 不用系统提示词”的结论吗？
   答：不能。Claude Code 的记录本来就不存系统提示词和工具定义，只能说记录里没有。
4. 插话为什么要单独算一轮？
   答：它是用户的新输入，后面的请求是对它的回应；不单独标出，就分不清哪些请求在回应原问题、哪些在回应插话。
5. 一段 700 次请求的会话，每次请求平均带 300 条消息，完整存储和增量存储各存多少条消息？
   答：完整存储约 21 万条；增量存储约等于消息总数（几百到一千多条），再加上压缩后的重建。
