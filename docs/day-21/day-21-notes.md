# Day 21：审计日志

## 学习目标与术语

学完能说明：审计日志和普通日志、调用链有什么区别，一条审计记录要回答哪几个问题，哈希链怎样让篡改“能被发现”，它防不住什么，以及谁来写、写在哪、写不进去怎么办。

| 术语 | 通俗解释 |
| --- | --- |
| 审计日志 | 记录“谁、在什么时候、对什么、做了什么决定、结果如何”，用于事后追责与核对 |
| 操作者（Actor） | 做出这个动作或决定的一方：人、模型、程序规则 |
| 只追加（Append-only） | 只能在末尾添加，不能修改或删除已有记录 |
| 篡改可发现（Tamper-evident） | 不能阻止有权限的人改文件，但改了能被校验出来 |
| 哈希链 | 每条记录带上一条记录的哈希；改动任何一条，后面的链就对不上 |
| 锚定（Anchoring） | 把某一时刻的最新哈希另存到攻击者改不了的地方，用来发现“整条链被重算” |
| 脱敏 | 只记录能核对的摘要（如哈希），不记录原文，避免审计本身泄露数据 |

## 1. 三种记录各管什么

一个 agent 系统里通常同时有三种记录：

| | 终端日志 | 调用链（trace） | 审计日志 |
| --- | --- | --- | --- |
| 回答 | 现在发生了什么 | 哪一步慢、哪一步错 | 谁批准了什么、到底做没做 |
| 读者 | 开发者 | 开发者、运维 | 用户、安全、合规 |
| 范围 | 越详细越好 | 每次调用的耗时与父子关系 | 只记关键动作与决定 |
| 可否丢弃 | 可轮转、可删除 | 可采样，进程崩溃会丢未结束的 span | 不能丢、不能改 |
| 内容 | 可能含原文 | 默认不含内容 | 只含摘要，不含原文 |

调用链不能兼作审计：它为排查性能而设计，允许采样，进程被 kill 时会丢掉没结束的 span，而且属性可以随时改。审计要求的恰恰相反：每一条都在、都没被改过。

OWASP 的日志备忘单把“安全事件”单独列出：认证与授权决定、高风险功能的使用、数据删除、权限变化等，都应记录，并给出每条要包含的字段：何时、何地（哪个应用、哪台机器）、谁、做了什么、结果如何。[资料](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

## 2. 一条审计记录要回答什么

把 OWASP 的五个问题换成 agent 的语境：

| 问题 | 字段 | 例子 |
| --- | --- | --- |
| 何时 | `time` | 统一用 UTC，避免时区混乱 |
| 谁 | `actor` | 人点了允许；模型提议了调用；程序规则判定需要确认 |
| 在哪个任务里 | `task`、`conversation`、`trace` | 能从审计跳到对话和调用链 |
| 对什么做了什么 | `event`、`tool`、`target`、参数哈希 | 对 `open_page` 发起确认请求；删除记忆 M12 |
| 结果如何 | `decision`、`status` | allow / deny / 没人回答；ok / denied / unknown |

“谁”在 agent 里比传统系统更需要分清：模型**提议**了删除，程序规则**判定**这需要确认，人**批准**了，执行器**执行**了。如果只记一句“删除了 M12”，出了问题就说不清是哪一环的责任。

## 3. 记什么、不记什么

**要记**：会改变外部状态或权限的动作，以及每个决定。

- 确认请求与答复，包括“没有界面所以自动拒绝”这种程序决定；
- 有副作用的工具执行与结局；
- 权限变更（联网白名单）、数据变更（记忆写入与删除）；
- 任务的开始与结束、恢复时“重做还是不重做”。

**不记**：只读查询的每一步（那是调用链的事），以及工具输出和私有数据原文。

审计日志通常比业务数据保存得更久、被更多人读，把原文写进去，它就成了新的泄露源。常见做法是记**哈希**：审计里只有参数的 SHA-256，原文留在有访问控制的业务存储里。事后要核对“批准的是不是这次执行的参数”，用原文重新算哈希比对即可。这里有个前提：参数如果是很短、可以穷举的值（比如一个四位数验证码），哈希可以被暴力猜出，就需要加盐的 HMAC，或者干脆不记。

## 4. 哈希链：改了能被发现

每条记录的哈希覆盖它自己的全部内容，加上上一条的哈希：

```text
h1 = SHA256(记录1 | prev="")
h2 = SHA256(记录2 | prev=h1)
h3 = SHA256(记录3 | prev=h2)
```

校验时从头重算：

| 篡改方式 | 校验到哪里会失败 |
| --- | --- |
| 改了第 2 条的内容 | 第 2 条的哈希与内容不符 |
| 改了第 2 条并重算它的哈希 | 第 3 条的 `prev` 对不上 |
| 删掉第 2 条 | 序号跳了，第 3 条的 `prev` 对不上 |

Go 里的核心只有几行：

```go
func hash(r Record) string {
    r.Hash = ""                   // 哈希覆盖除自己以外的所有字段
    data, _ := json.Marshal(r)    // 字段顺序固定，同一条记录每次结果相同
    sum := sha256.Sum256(data)
    return hex.EncodeToString(sum[:])
}
```

**它防不住的情况**：能写文件的人可以从被改的那条开始，把后面整条链全部重算。哈希链只保证“局部修改会被发现”。要发现整链重算，需要**锚定**：定期把最新哈希写到攻击者改不到的地方，比如另一台机器、只读介质、发给用户的邮件，或者公开的透明日志。证书透明（Certificate Transparency）把同样的思路做成了 Merkle 树，并让多方持有树根。[资料](https://www.rfc-editor.org/rfc/rfc6962) 也可以用云存储的“写一次读多次”（WORM）模式，从存储层禁止修改。

Crosby 与 Wallach 对篡改可发现日志做过系统研究，讨论了只靠哈希链时校验代价随长度增长、以及怎样用树结构高效证明“某条记录在日志里”。[资料](https://www.usenix.org/legacy/event/sec09/tech/full_papers/crosby.pdf)

## 5. 谁来写、写在哪

动作分散在多个进程里：agent 执行工具，界面收到人的点击，子 agent 在自己的进程里运行。如果只有界面写审计，命令行、定时任务和评测里发生的事就没有记录；如果只有 agent 写，就无法核对“人到底点了什么”。

通常的做法是**多方写同一份日志，各自记录自己亲眼所见的事**：

- 执行方记录：程序规则的判断、实际执行与结局；
- 界面记录：人的操作；
- 两边的记录用同一个调用 ID 和参数哈希关联，能互相核对。

多个进程追加同一个文件时，要保证一次只有一个写者，否则两条记录会交错、链会断。单机可以用文件锁；多机就要用一个集中的日志服务。

**写进去之后再继续**：审计记录写完要落盘（`fsync`），已经承认发生的决定不能因为断电丢掉。对高风险动作，**写不进审计就不执行**：没有记录的高风险动作，事后无法追责。普通记录写失败可以只报警，不阻断任务。

## 6. 审计之后：谁来看

日志没人看就只是存档。常见的使用方式：

- **定期校验**：每天校验整条链，失败立即报警；
- **按任务追溯**：从一个可疑的结果出发，列出这个任务的所有决定；
- **规则告警**：比如短时间内大量“拒绝”、同一个任务反复请求同一类高风险操作；
- **保留期限**：审计通常比运行数据保留更久，到期删除也要按规定流程，并保留删除记录。

## 自测

**调用链里已经有每次工具调用，为什么还要审计日志？**

调用链可采样、崩溃会丢、内容可改，也不记录“谁批准的”。审计要求每条都在、未被修改，并且能分清人、模型和程序各自的责任。

**审计里为什么只记参数哈希？要核对时怎么办？**

避免审计成为泄露源。核对时从业务存储里取原文重新算哈希，与审计中的值比对。

**有人删掉了中间一条记录，并把后面所有记录的 prev 和 hash 都重算了，哈希链能发现吗？**

只靠本地文件发现不了。需要把某一时刻的最新哈希锚定在别处，再拿它对比。

**界面记录了“人点了允许”，agent 也记录了“收到允许”，为什么要记两次？**

两方各记自己所见。两条对得上，说明决定确实从人传到了执行方；对不上，就说明中间某一环出了问题（转达错误、伪造答复、丢失）。

**审计写入失败时，任务该停下来吗？**

高风险动作应停下：不执行比“执行了但没有记录”更安全。普通记录可以只报警。
