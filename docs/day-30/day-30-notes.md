# Day 30：上下文预算

## 学习目标与术语

学完能说明：harness 怎样在不知道模型分词器的情况下估算上下文用量、误差主要来自哪里；工具输出太长时，截断和存成文件各丢掉什么；为什么要把用量告诉模型、什么时候告诉；提示词缓存为什么会让“隔一段时间再接着聊”变贵，以及能做什么。

| 术语 | 通俗解释 |
| --- | --- |
| 上下文预算 | 一次请求能放进模型的输入上限，扣掉留给输出的部分后，harness 自己能支配的量 |
| 分词器（tokenizer） | 把文字切成 token 的规则；不同厂商、不同模型各不相同，很多不公开 |
| 服务端用量（usage） | 模型服务在响应里返回的真实输入、输出 token 数，用的是它自己的分词器 |
| 增量估算 | 已知上次请求的真实用量，只估算之后新加的消息 |
| 输出落盘 | 过长的工具输出完整存成文件，上下文里只放预览和文件名，需要时再读 |
| 提示词缓存 | 服务端记住最近处理过的请求前缀，下次相同前缀直接复用，更快更便宜 |
| 缓存过期 | 前缀一段时间没被用到，缓存被清掉，下次要按全价重新处理 |

## 1. 不知道分词器，怎样计数

精确计数需要模型的分词器。现实中常常拿不到：Claude 的分词器不公开；国内很多模型也只在服务端计数。一个 harness 往往还要接好几家模型。

常见的做法是**服务端用量 + 增量估算**：

```text
当前用量 ≈ 上一次响应里服务端返回的总 token 数
         + 在那之后新加的消息（工具结果、用户输入）按字节粗估
```

大头来自服务端的真实数字，粗估只覆盖最近新加的一小段，所以整体误差很小。Codex 就是这样做的：它早期在本地带过 OpenAI 的分词器，后来删掉了，现在统一按“4 字节约 1 个 token”估算新增部分，接哪家模型都一样。[资料](https://github.com/openai/codex/blob/main/codex-rs/utils/string/src/truncate.rs)

粗估的误差在哪里？如果拿整份请求和真实值比，偏差可能很大，而且不同模型偏差不同：系统提示词、工具定义的结构，以及服务端自己加进去的内容，在不同分词器下差别很大。但这些都属于每次请求不变的前缀，已经包含在“上次的真实用量”里。新增的部分大多是工具结果和普通文字，按字节估反而相当准。

所以一个看起来合理的改进——用“真实值 ÷ 粗估”算出比例，再乘到新增部分上——反而会出错：这个比例反映的是前缀的偏差，套到新增部分上就会高估。粗估只在没有真实用量的时候误差大：第一次请求，以及压缩之后。

## 2. 工具输出太长：截断还是存文件

工具输出可能非常长：几千行日志、整页网页、一个大文件。放进上下文之前必须控制大小。

| 做法 | 模型看到什么 | 丢掉了什么 |
| --- | --- | --- |
| 只保留开头 | 前 N 字 | 结尾的错误信息、测试结果 |
| 保留开头和结尾，截掉中间 | 两头 | 中间的内容永久丢失 |
| 存成文件，上下文放预览 | 两头 + 文件名 | 什么都不丢，中间需要时再读 |

前两种做法的问题是：被截掉的内容模型再也拿不到。如果答案正好在中间，它只能重新执行一次工具；但有的工具重跑代价高，有的结果会变（网页、检索、子任务），没有 shell 的环境甚至没法重跑。

第三种做法是 Claude Code 的：输出太长时完整存进文件，模型看到开头一段预览和文件路径，需要时用读文件、搜索工具去取。[资料](https://code.claude.com/docs/en/how-claude-code-works) Codex 的主要工具是 shell，它选择截断并保留头尾，被截掉的部分让模型换个命令重跑（比如加 `grep`）。

存文件时有两个细节：

- **按行展开**。工具结果往往是一段 JSON，多行的命令输出、文件内容在 JSON 里被转义成一行。直接存 JSON，按行读、按行搜都用不上；应该把多行字符串还原成多行。
- **预览保留结尾**。只给开头时，命令的报错、测试汇总这些通常在最后的内容反而看不到。

还要注意上游的限制：工具自己往往也有输出上限（比如为了防止内存被撑爆）。如果工具先截掉了中间，上下文层存下来的也只是截过的版本。改成存文件之后，这类上限可以放宽到只防资源耗尽的程度。

## 3. 把用量告诉模型

harness 知道上下文快满了，模型却不知道。它会照常整份读大文件，等到压缩发生，前面读过的内容只剩摘要，它又去重读。

有两种提醒：

| 提醒什么 | 例子 | 解决的问题 |
| --- | --- | --- |
| 窗口还剩多少 | “上下文已用 75%，到 90% 会自动压缩” | 让模型在快满时改用分页、搜索，少整份读 |
| 整个任务还剩多少预算 | “还剩 1470 万 token” | 让模型知道还能做多少事，按预算安排工作 |

Claude Code 几乎每次请求都附一条后一种提醒（`<total_tokens>…tokens left</total_tokens>`）。窗口满的问题它由 harness 自己处理：先清理旧的工具输出，不够再做摘要。

什么时候提醒也有讲究。每次请求都附一条，提醒本身会一直留在上下文里，越积越多；只在越过几个档位（比如 50%、75%）时提醒一次，信息够用，占的地方少。

压缩之后也值得说一声：“较早的内容已经换成摘要，需要细节时重新读”。不说的话，模型以为之前读过的东西还在，找不到时只能猜。

## 4. 提示词缓存与续聊的代价

很多模型服务会缓存最近处理过的请求前缀。agent 每一步的请求，绝大部分是上一步的原样加上一点新内容，所以缓存命中率可以很高（九成以上），速度和费用都因此大幅下降。

缓存有保留期限。Anthropic 的提示词缓存默认 5 分钟，可以选 1 小时。[资料](https://docs.claude.com/en/docs/build-with-claude/prompt-caching) 其他厂商的期限不同，有的不公布，有的根本不自动缓存。

期限一过，下一次请求就要按全价重新处理整个上下文。上下文有几十万 token 时，“隔天接着聊”的第一句话又慢又贵。

一个办法是在缓存过期之前先压缩：用户闲置一段时间后，趁缓存还在，用很便宜的代价把上下文压成摘要；用户回来时，接着的是一段短的上下文。从 Claude Code 的会话记录看，它的几次自动压缩都发生在闲置约 55 分钟时，正好在 1 小时期限之前，而不是窗口满的时候。这是从时间规律推断的，文档里没有写明。

这个办法的前提是知道缓存多久过期。不知道的时候，先做到“代价可见”：每次续聊时显示闲置了多久、第一次请求命中了多少缓存，积累数据后再决定要不要提前压缩、提前多久。

## 自测

1. 不知道模型的分词器，怎样估算上下文用量？误差主要来自哪部分？
2. 拿整份请求算出“真实值 ÷ 粗估”的比例，再乘到新增消息上，为什么反而可能更不准？
3. 工具输出截掉中间和存成文件，各丢掉了什么？什么情况下截断就够了？
4. 为什么存文件时要把 JSON 里的多行字符串还原成多行？
5. 用量提醒为什么只在越过档位时发，而不是每次都发？
6. 为什么压缩之后要告诉模型？
7. 缓存过期前先压缩，前提是什么？不知道期限时应该先做什么？

### 自测答案

1. 用上一次响应里服务端返回的真实用量，加上之后新增消息的字节粗估。误差主要在没有真实用量的时候（第一次请求、压缩之后）；有真实用量时只有新增部分是估的，误差很小。
2. 整份请求的偏差主要来自每次都不变的前缀（系统提示词、工具定义、服务端加的内容），这部分已经包含在真实用量里。新增消息多是普通文字和工具结果，按字节估本来就准，再乘上前缀的偏差比例就高估了。
3. 截断永久丢掉中间的内容，模型只能重跑工具；存文件什么都不丢，代价是要多一个读回的办法和一些磁盘。工具有 shell、重跑便宜而且结果稳定时，截断就够了（Codex 的思路）。
4. 多行字符串在 JSON 里被转义成一行，存下来只有一行，按行分页、按行搜索都用不上；还原之后每一行都能按行号读、按正则找。
5. 提醒会留在上下文里，每次都发会越积越多、自己占掉窗口；越过档位时发一次就足够让模型调整做法。
6. 不说的话，模型以为之前读过的内容还在，找不到时只能猜；告诉它之后，它知道该重读，也知道可以去读存下来的文件。
7. 前提是知道缓存多久过期，而且在过期前有机会发起压缩。不知道期限时，先把每次续聊的闲置时长和第一次请求的缓存命中显示出来，积累数据再决定。
