## 1. 计数：先量，再决定改不改

用观测台存档里的真实请求（只读 `.data/`，不调模型）比较估算与服务端用量。

整份请求按字节粗估，与真实输入 token 的比值：

| 模型 | 请求数 | 中位数 | 10%–90% |
| --- | --- | --- | --- |
| DeepSeek | 397 | 0.93 | 0.90–1.01 |
| 方舟（豆包） | 957 | 0.75 | 0.41–1.25 |

看起来方舟偏差很大。但现在实际用的是“上次服务端用量 + 新增部分粗估”（日志里的 `usage+est`）。按这个算法预测下一次请求的输入量：

| 模型 | 样本 | 预测 / 实际 中位数 | 误差中位数 | 换算比例后 |
| --- | --- | --- | --- | --- |
| DeepSeek | 150 | 0.993 | 0.8% | 0.997（0.4%） |
| 方舟（豆包） | 63 | 0.986 | 1.9% | 1.299（30%） |

“换算比例后”是试过又撤掉的改动：用每次请求的“真实 ÷ 粗估”乘新增部分。方舟的偏差来自系统提示词、工具定义这些固定前缀，已经包含在服务端用量里；新增的工具结果按字节估本来就准，乘上比例反而高估三成。所以计数保持原样。粗估只在没有服务端用量时（第一次请求、压缩后）误差大，压缩布局里已有按当前视图换算的一步（`Compact scale`）。

## 2. 大输出：存文件与读回

`Append` 遇到超过上限的工具结果时：

```go
if saved, ok := saveOutput(m.Content, c.options.ToolOutput); ok {
	view.Content = saved          // 外层字段原样，result 换成预览
} else {
	view.Content = shorten(...)   // 实验、不是 JSON 的结果：照旧截掉中间
}
```

视图里的结果仍是同一个 Observation，状态与来源标记（D19 的 `source`、`authority`）都在，只是 `result` 变成：

```json
{"saved_output": "call_00_vg2T…", "total_lines": 4005,
 "preview": "     1\tresult.duration_ms: 22\n …\n…（省略第 119–3887 行，用 read_output 读取）\n …"}
```

文件里每个字段一行，多行字符串按原样分行（`result.output:` 下面就是命令输出的每一行），所以 `read_output` 的行号和 `pattern` 都直接对应原文。

几个取舍：

- 文件按对话存放：续聊各轮、续跑都能读之前存下的输出；子 agent 与回放分叉各有自己的目录，读不到父任务的。
- `read_output` 的名字只允许字母、数字、`_`、`-`，只在本对话目录里找，拼不出别的路径。
- `read_output` 自己的结果按工具输出上限的八成停下，给出 `next_offset`，不会再被存一次。
- 工具从第一次请求就提供。只在有输出存下之后才加，工具列表（请求前缀的一部分）会在中途变化，之前的缓存全部失效。

## 3. 用量提醒与压缩说明

```text
[上下文用量] 已用约 62%（11723 / 18880 token）。到 90% 会自动压缩，较早的工具结果与对话会换成摘要。读文件尽量用 offset/limit 或 grep 只取需要的部分，不要整份重读。
[上下文已压缩] 较早的工具结果或对话已经清理或换成摘要，原文不在上下文里了。需要其中的细节时重新读取；工具结果里有 saved_output 的，用 read_output 读。
```

都以 `<system-reminder>` 追加在视图末尾（D24），不算用户原话，压缩时不进保留区。档位在压缩后清零，用量回升时会再提醒；换进程（续聊）后从零计，第一次请求时如果已经过档会再提醒一次。

## 4. 缓存：只做观测

存档里续聊第一次请求的缓存命中：

| 模型 | 整体缓存命中 | 续聊第一次请求 |
| --- | --- | --- |
| DeepSeek | 92.5% | 闲置 60 分钟以内 91%–99%（18 次） |
| 方舟（豆包） | 15.5% | 7 次都是 0 |

DeepSeek 至少保留一小时，更久的还没有数据；方舟现在的调用方式下几乎不命中缓存。照搬“55 分钟时先压缩”没有依据，所以这次只让代价可见：观测台续聊的每条用户消息下面显示“闲置 X · 首次请求缓存命中 Y%（Z token 未命中）”。等有闲置超过一小时的数据，再决定要不要提前压缩。

## 5. 动手

```bash
# 大输出与读回：工具输出上限设小一点更容易观察
go run . -bash -provider deepseek -context-window 65536 -tool-output-tokens 1500 \
  -question '用 bash 运行一次：seq 1 4000 | awk ...（某一行带 KEY）。告诉我 KEY 在第几行。不要再次运行 bash。'
ls .data/outputs/<任务ID>/          # 存下的文件
# 用量提醒与压缩：窗口设小，连续读几个文件
go run . -workspace <仓库> -context-window 24000 -tool-output-tokens 2500 -question "依次读四个文件……"
```

终端里看 `Output saved:`、`Context reminder:`、`Compact:` 三类行。

## 6. 验证记录

2026-10-19，DeepSeek。

| 检查 | 结果 |
| --- | --- |
| bash 输出 4000 行（5.5 万字），关键行在中间 | 第一次：bash 自己先截到头尾各 8KB，关键行在被截的部分，模型只能从命令推断。放宽到 128KB 后重跑：存成 4005 行的文件，视图 1324 token；模型一步 `read_output(pattern="KEY")` 找到第 2718 行 |
| 续聊里问上一轮输出的第 1000 行，不许重跑 | 模型用 `read_output(offset=1001)` 读到原文 |
| 24K 窗口连续读四个文件 | 50%、75% 各提醒一次；90% 时压缩，之后收到压缩说明；模型对前三个文件依据摘要作答，只重读了第四个；之后用量回升又提醒了 50%、75% |
| 观测台打开一条三轮对话 | 第 2、3 轮显示“闲置 8 秒 · 首次请求缓存命中 95%（386 token 未命中）”等 |

## 7. 当前没有覆盖的范围

- **方舟的缓存**：几乎不命中，原因（是否需要显式开启上下文缓存）没有查；提前压缩等数据。
- **其他工具的上限**：`open_page` 正文 3000 字、MCP 结果等仍由各自工具先截，没有跟着放宽。
- **观测台查看存下的输出**：页面上只看得到预览，完整内容在 `.data/outputs/` 里，还没有入口。
- **保留期限**：输出文件随对话一直保留，没有清理（同 PROJECT“运行数据”）。
- **终端日志**：`Observation` 行仍打印完整结果，bash 上限放宽后可能很长。
