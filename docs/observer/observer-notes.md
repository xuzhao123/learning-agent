# 观测台：把 agent 的每次模型调用画出来

观测台是独立程序，放在 `observer/`，有自己的 `go.mod`。agent 只负责完成任务，观测台负责启动 agent、记录过程并在网页上展示。页面参考了 DeepSeek Harness 官方的 Trajectory 视图，以及社区插件 dsh-maze / trace compare 的展示方式，提供三个视图：轨迹、迷宫、对比。

## 1. 为什么在模型请求这一层观测

agent 每次请求模型都会把完整消息历史发出去：

```
第1次请求：system, user
第2次请求：system, user, assistant(tool_calls), tool
第3次请求：system, user, assistant, tool, assistant, tool
```

所以只要站在 agent 和方舟之间，看到每次请求与响应，就能还原全过程：

| 想看到的内容 | 来自哪里 |
| --- | --- |
| 模型收到了什么 | 请求 `messages`、`tools` |
| 模型怎么想、决定调用什么 | 响应 `reasoning_content`、`content`、`tool_calls` |
| 工具返回了什么 | 下一次请求里新增的 `role: "tool"` 消息，用 `tool_call_id` 对上调用 |
| 工具执行多久 | 上一次响应到下一次请求之间的时间 |
| 模型耗时与成本 | 代理计时；响应 `usage`，含 `cached_tokens`、`reasoning_tokens` |
| 为什么停止 | `finish_reason`、agent 进程退出码 |

这就是"协议即观测接口"：观测台只依赖 OpenAI 兼容的 Chat Completions 格式，不读取 agent 源码，也不需要 agent 调用任何埋点函数。以后新增工具、修改 prompt、增加轮次或改写循环，只要还按这个协议请求模型，页面就会自动显示新内容。

## 2. 运行链路

```
浏览器 ──POST /runs──▶ 观测台 ──go run . -question ...──▶ agent
                         ▲   LLM_API_URL=http://127.0.0.1:8090/llm/<运行ID>
                         │                     │
   SSE 实时事件 ◀────────┤◀── 请求/响应原文 ───┘ 观测台原样转发 ──▶ 方舟
                         └── agent 终端输出（stdout/stderr）
```

- 普通问答启动 `go run . -question ...`；页面选择“Day 3 上下文实验”则启动 `go run . -context-lab -max-steps 60 -reasoning-effort minimal`。两种模式使用同一套代理和事件展示。
- 每次运行用 `go run .` 启动 agent，所以 agent 代码改了也不用重新部署观测台。观测台自身代码或内嵌页面改动后，要重启观测台并刷新页面。
- 运行 ID 放在代理路径里，几次运行同时进行也不会混在一起。
- agent 读取配置时环境变量优先，新对话的密钥和模型来自 agent 自己的配置；续聊沿用存档中的模型与推理强度，密钥仍从本地读取。观测台把 `LLM_API_URL` 指向该记录的代理地址。
- 观测台转发 `Authorization`，但不记录。真实上游地址从环境变量或 agent 的 `.env` 里读取。
- 事件类型：`start`（首个问题）、`continue`（续聊问题）、`request`、`response`、`stdout`、`stderr`、`exit`。事件同时写入 `observer/runs/<运行ID>.jsonl`，该目录已加入 `.gitignore`。
- 观测台启动时会读回 `runs/*.jsonl`，重启后仍可查看、回放和对比历史运行。早期存档没有 `start` 事件，问题取自第一次请求里的 user 消息。
- SSE 先回放已有事件，再推送新事件；运行结束后发送 `end` 并关闭连接。

agent 通过 `llm.go` 接受本机 `http://127.0.0.1` 观测代理；通过通用的 `-history-stdin` 参数接收续聊上下文，不需要知道观测台存档的位置。

## 3. 对话界面与三个观测视图

页面参考 Codex 客户端：左侧是对话列表和“新对话”“Day 3 上下文实验”入口，主区默认是对话流，底部是输入框。顶栏的“对话 / 观测”切换同一条记录的两种看法。

### 3.0 对话流：从模型请求还原聊天记录

对话流没有单独的数据来源，仍然只读取代理记录的请求和响应：

```
用户消息        ← 每次普通请求末尾新增的 user 消息
✻ 思考了 4.8 s  ← 响应 reasoning_content，点开看全文
✓ calculator …  ← 响应 tool_calls；结果取自下一次请求里 tool_call_id 相同的 tool 消息
最终回答        ← 没有 tool_calls 的响应 content，按少量 Markdown 渲染
── 上下文已压缩 ── ← 摘要请求，点开看摘要原文
```

- 新的用户消息总在请求末尾：首轮是 `system, user`，续聊是旧历史加新问题，工具循环中末尾是 tool 消息，所以没有新用户消息。
- 压缩后的请求是 `system, 保留的用户原话, 摘要, 最近消息组`。末尾连续的 user 消息里，摘要之前的是旧原话，只取摘要之后的部分，避免旧问题重复出现。上游超窗后重试会再发同一个问题，未回答前重复的同一句只显示一次。
- 问题提交后、agent 还没发出第一次请求时（`go run` 编译需要几秒），先用 `start` / `continue` 事件里的问题占位。
- 运行中，等待模型显示“思考中…”，工具执行中显示转圈；运行异常结束或没有最终回答时，显示退出状态和最后几行终端输出。
- 每条回答下方有“在观测中查看”，跳到轨迹视图并选中这次模型调用。

Enter 发送，Shift+Enter 换行；输入法选词时的 Enter 不会发送。

切到“观测”后，左侧记录出现勾选框（勾选 2–5 条进入对比），中间是视图，右侧是共用的 inspector。点击任意事件、节点或格子，都会在 inspector 里看到详情。

### 3.1 轨迹：事件账本 + 瀑布时间轴（对应 Trajectory 视图）

```
#  类型      内容摘要                                   tokens  耗时    0 ms ─── 8.6 s ─── 17.2 s ─── 34.5 s
▾ Turn 1   6.4 s · 800 tokens · 1 个工具 · 1 处绕路
1  system   你是一个工具助手…
2  user     在学习笔记里查“MCP 服务器部署步骤”…
3  tools    calculator、get_current_datetime、search_notes
4  message  思考 73 字 → 调用 search_notes            800    6.4 s   ████
5  tool     search_notes {"query":…} → 空结果                5 ms        ▏(红)
▾ Turn 2 …
```

- 每个 Turn 是一次模型调用及它发起的工具，可以折叠；也可以搜索事件。
- 右侧时间轴按真实时间画条：紫色是模型调用，绿色是工具，红色是出错或绕路，执行中的条会闪烁。
- 在时间刻度上拖拽可以聚焦某一段时间，双击还原。
- 当前 agent 使用非流式响应，模型调用只有总耗时，不能像官方视图那样拆成 TTFT / decode 两段。
- 用户提问始终标为 `user`，不再把后续问题显示成 `context`。点击问题可查看它本身，并通过“查看本轮完整输入”查看发送内容。
- 存在历史对话的Turn才显示 `history` 入口，点击后只展示历史消息：此前问题、assistant回答、工具调用及结果、交接摘要，不包含system或本轮输入。当前用户问题点击 `user` 查看；点击 `message` 查看完整模型调用，输入按“系统规则”“历史消息”“本轮输入”三部分展示，并保留完整请求JSON。本轮新收到的tool结果放在完整输入的“本轮输入”中，也会按调用ID关联到工具事件。
- 新对话Turn 1是1条system、0条history、1条user，共2条messages；工具定义在tools字段。Turn 2是1条system、2条history（hello、问候回答）、1条当前user问题，共4条messages。上次assistant回答虽然首次进入下一次请求，也已经是历史，因此不能只按请求的共同前缀统计。
- 压缩后的保留原话与交接摘要放在history，当前问题仍显示为user。摘要注明“历史摘要”，程序追加的压缩指令注明来源；它们在API中的角色仍是user。
- 点击message行，inspector会显示token构成、finish_reason、请求参数、可展开的历史、本轮输入、Thinking、Output、工具调用请求，以及请求和响应原文。工具定义单独位于请求的tools字段。

### 3.2 迷宫：探索路径 + 数据轨（对应 dsh-maze）

```
          Turn 1          Turn 2            Turn 3
 M1 ─────────────── M2 ─────────────── M3 ──────── A ── ■
   ╲               ↗ ╲               ↗ ╲
    [search_notes]─✕  [↺ search_notes]─✕ [↺ search_notes]─✕     绕路（红，死胡同）
       ╰──── 回退弧线（紫，虚线）─────╯
```

- **主干**：模型调用 M1、M2…，最后是回答 A 和进程结束 ■。
- **主路径工具**：返回有效结果的工具，显示为绿色，分叉出去后再汇合到下一次模型调用。同批工具上下并排展开。
- **绕路**：返回错误、空结果，或用相同参数重复调用的工具，显示为红色，以 ✕ 结尾。
- **回退**：同名工具在绕路之后再次被调用，用紫色虚线弧连起来，节点名前标 ↺。
- 所有判定都是确定性规则，不调用模型；判定依据会显示在 inspector 里。
- 地图下面有三条数据轨，与地图按轮次对齐：
  1. **工具调用密度**：每轮工具数，绕路部分标红。
  2. **Token 脉冲**：每次调用的 token 构成，按缓存命中输入、未缓存输入、推理、输出堆叠。
  3. **上下文压力**：每次请求的输入 tokens 占输入容量的比例，画出70%和90%两条线。优先从 agent 的 `Context: ... cap=...` 输出获取容量，旧记录没有该信息时手工填写。曲线展示 API 输入量；agent 的触发判断使用 `used`（包含上次完成量与增量估算），两者不要混淆。压缩标记来自摘要或视图重建。
- 地图下方的绕路清单可以逐条点击。

### 3.3 对比：多次运行按轮次对齐（对应 trace compare）

- **指标表**：问题、模型调用、工具调用、主路径步数、绕路、回退、总 tokens、缓存命中、推理 tokens、模型耗时、总耗时、结果、回答摘要。"越少越好"的指标会把最低值标成绿色。
- **泳道**：每次运行一行，每个 Turn 一列。格子里显示该轮的耗时、tokens 和工具芯片，红色芯片是绕路，↺ 是回退。点击格子或芯片会打开该运行对应事件的详情。

### 3.4 回放

已结束的运行可以按真实时间间隔重放，速度 1×–300×。打开"折叠空闲"后，长时间的等待会被压缩。回放时，轨迹和迷宫都会逐步生长。

## 4. 启动

```sh
cd observer
go run .
# 打开 http://127.0.0.1:8090
```

参数：`-addr` 指定页面地址，默认 `127.0.0.1:8090`；`-agent` 指定 agent 目录，默认 `..`。

要继续对话：

1. 回答结束后，直接在底部输入框写下一句话，按 Enter 发送，会延续当前对话。
2. 要继续之前的对话，先点击左侧记录。新回答和工具调用会追加到同一条对话流和轨迹里。
3. 点击“新对话”开始独立任务；不会删除旧记录。
4. 运行中和回放中不能续聊。失败或中断的任务暂不续接，避免把未完成的工具调用重新执行。

续聊并不要求原进程一直存活。观测台从已有JSONL取出最后一次成功的普通请求messages，加上对应的完整assistant回答，经stdin传给新的agent进程。原生工具调用ID、工具结果、摘要和assistant的加密字段都保留；agent恢复View，追加新问题，再走原来的预算检查与ReAct循环。以前的工具结果是历史输入，不会重新执行。

恢复的是最后的模型视图，不把压缩前的全部原文重新塞回去。新进程的Transcript从这个恢复点继续记录；更早的原始轨迹仍保留在观测台存档里。每个新提问使用新的默认10次请求预算，包含摘要；观测台Turn编号跨提问连续递增，服务重启后也不会重置。总耗时仍按整条记录的时间跨度计算，包含两次提问之间的等待。

Day 3实验包含两个独立场景；首次续聊接在33轮学习对话之后，保留账号与范围约束，不混入后面的大工具演示。之后按普通续聊处理。

要观察 Day 3：

1. 点击左侧“Day 3 上下文实验”并确认，不用填问题。
2. 对话流里能看到实验程序发出的33轮问题和回答，压缩位置显示为“上下文已压缩”分隔线，点开是摘要原文。
3. 切到“观测”：轨迹中的每个 Turn 是一次模型请求，摘要也会单独占一次，所以不等于对话轮数。点击模型调用看右侧请求消息与回答；摘要调用显示为 `compact`。
4. 点击“终端输出”查看压缩前后大小、`Recall` 账号与学习范围、`Large tool` 截断情况和最终统计。运行中也能查看。
5. 切换“迷宫”看输入量增长和压缩后的下降。实验默认输入容量7168 token，页面从实际输出读取。

原来的终端命令直接请求方舟，没有经过代理，因此不会自动出现，也无法补录已结束的对话。通过页面重新运行才能完整观测；运行结果仍存到已有的 `observer/runs/`，每日学习目录不新增日志。

## 5. 兼容边界

- 自动兼容：工具、prompt、轮次、并行数量、消息内容、请求参数（如 `reasoning_effort`）的变化，以及将来新增的消息角色。
- 需要调整观测台的情况：agent 改用流式响应（`stream: true`）、改用其他协议格式，或命令行不再支持 `-question`。流式响应时原文仍会记录，但页面不会拆分事件；改成流式后才能补上 TTFT / decode 分段。
- 绕路规则依赖工具结果的形状：带 `error` 字段算错误；结果为空、或所有数组字段都为空算空结果。工具结果格式变化时，可能需要调整这条规则。

## 6. 学习建议

1. 打开迷宫视图看 `trace-detour.jsonl` 那次运行：三次检索都是空结果，模型换了两次关键词，所以有两条回退弧。再对照 Token 脉冲，可以看到每次重试都让输入变长。
2. 在对比视图勾选同一问题的两次运行，比较路径是否相同，以及耗时差异来自哪一轮。同样的问题，模型每次的表现也会有波动。
3. 在轨迹视图拖拽时间刻度，聚焦到工具执行那几毫秒，再和模型调用的耗时比较，判断延迟主要花在哪里。

## Day 3 上下文压缩的观测

摘要请求沿用原生messages，末尾user消息以`[上下文压缩请求]`开头。页面将它标为独立的上下文摘要调用；它的输出不作为最终回答，返回的工具请求也不会被显示为已经执行。

视图重建后消息长度可能下降。历史与本轮输入按本次请求的messages实际分组，不把重组后再次出现的旧问题误标为新问题；tool结果按调用ID跨历史请求关联。上下文压力轨的压缩标记来自摘要或主请求视图重建，不再把任意输入token下降都当成压缩。详情同时展示共同前缀消息数和服务端usage；前缀相同不等于缓存一定命中。
