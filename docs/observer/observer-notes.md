# 观测台：把 agent 的每次模型调用画出来

观测台是独立程序，放在 `observer/`，有自己的 `go.mod`。agent 只负责完成任务，观测台负责启动 agent、记录过程并在网页上展示。页面参考了 DeepSeek Harness 官方的 Trajectory 视图，以及社区插件 dsh-maze / trace compare 的展示方式，提供三个视图：轨迹、迷宫、对比。

顶栏显示当前对话 ID，点击可复制；它与 `runs/<ID>.jsonl` 的存档编号一致，续聊不会改变 ID。选择或新建一条实际对话后，URL 自动更新为 `/?run=<对话ID>`，复制链接、刷新页面都能打开同一条记录。切换对话支持浏览器前进与后退；点击“新对话”清除 URL 中的 `run` 参数，提交首个问题后再写入新 ID。

## Turn、Step 与原始输入输出

Turn表示一次用户回合，Step表示其中一次任务模型调用及工具执行。一次用户提问可以跑多个Step；续聊开启下一个Turn，Step从1重新编号。摘要是独立的压缩调用，不计入任务Step，但仍计入模型请求总数和预算。

在“观测 → 轨迹”的每个Step标题右侧，点击 **原始输入 / 输出**，可直接展开本次模型调用的两张原始数据卡片；点击“X条messages”在右侧查看全部输入。对话页每次“Turn X · Step Y · 请求 #N”旁也有同一原始开关。

- 输入是代理记录的完整请求体，包含 `messages`（system、历史和本轮输入）、`tools` 和请求参数；不是只显示本轮用户提问。
- 输出是本轮实际响应体，包含完整 `choices`、工具调用、推理字段及 `usage` 等；请求进行中显示等待状态，返回后自动更新。
- JSON 以缩进、行号和语法着色展示，长内容在卡片内滚动，不截掉字段。复制按钮复制完整内容，行号不进入剪贴板。非 JSON 错误文本按记录原样展示。
- 开关独立于 Turn 标题的轨迹折叠；实时重绘和切换对话/观测标签时保持当前展开状态。原文通过文本节点展示，不执行模型返回的 HTML。

这里查看的是请求体和响应体，认证头不会写入观测记录。主表展示新发生的事件，完整messages是每次请求的输入快照，放在Step详情里，避免把重发的历史当成新事件。

## Day 4：看检索片段怎样成为证据

只需在项目根目录启动`go -C observer run .`。新对话勾选“知识库 RAG”，选择线上方舟或本地MiniLM，观测台以`-rag -embedding ark/local`启动Agent；检索在Agent进程内初始化和调用，没有8092端口。续聊从存档恢复RAG模式与向量模型；旧存档优先读取实际工具结果中的backend，无法确定时使用默认ark。

- `search_docs` 工具详情把返回值展开为候选卡片：编号、标题、score、阈值、是否接受、正文和来源。未过阈值的候选仅保留元信息，正文不会进入模型上下文。JSON原文仍可展开。score是相似度，卡片“通过阈值”不等于事实已验证。
- 答案中的 `[D05]` 等编号，只有在本题此前实际检索到且通过阈值时才变为可点击引用。点击后进入对应工具的观测详情；编号拼错不会被当作有效引用。
- 检索结果来自下一次模型请求的 `role=tool` 消息，所以看到的是模型实际输入。若 Day 3 截断了结果，无法解析为完整检索对象时显示原始文本，不伪造完整片段。
- 左侧“Day 4 检索对比”运行10题直接召回检查与20次独立真实问答，页面按Q编号与有/无检索分组。实验每题重置上下文，界面不会把这个重置当成压缩。终端可看 `Retrieval` 输出；完整正确性依据仍需人工核对，而非只数引用。
- 实验包含多个独立上下文，因此不能当作一条普通对话续聊。自己提问请另建RAG对话。无候选过阈值时按空结果展示，最终合理拒答仍可以正常完成；“绕路”只是界面的过程启发式，不是答案质量评分。

片段正文使用文本节点展示，来源与模型输出都不会作为HTML执行。观测台只增强已有协议结果的展示，Agent无需知道网页细节。原理、10题结果和练习集中见 [Day 4学习笔记](../day-04/day-04-notes.md)。

## Skills 中心与 MCP 中心

观测台只管“装了哪些、开没开”，解析、校验和连接都交给 agent 自己的命令行模式，不在网页端另写一套规则：

| 操作 | 观测台做什么 | 实际执行者 |
| --- | --- | --- |
| 列出 skill | `GET /hub` | `go run . -skills-list`：与运行时同一个 `readSkill`，坏文件进 `skill_errors` |
| 新建 skill | 写 `skills/<name>/SKILL.md` | 写后再跑 `-skills-list`，这个目录出错就整个删掉并返回原因 |
| 测试 MCP server | `POST /hub/mcp/{name}/test` | `go run . -mcp-server … -mcp-list`：SDK 连接、协商、列工具，不请求模型 |
| 新对话 | 读 `.data/hub.json` 取快照，写进 start 事件 | agent 收到 `-skills -skill a …` 与多个 `-mcp-server` |

为什么用快照：一条对话的工具集合应当前后一致。续聊时如果按中心的最新开关重新拼参数，模型在前几轮看到的工具可能在下一轮消失，历史里的 tool_calls 就对不上了。所以续聊从最近一次 start/continue 事件读回 `skills` 与 `mcp`，中心里的改动只影响新对话。

MCP 中心的预设使用 `go run` 从源码启动，命令在项目根目录执行，无需提前准备可执行文件。首次启动需要编译（everything 还需下载模块），后续复用 Go 缓存。添加自己的 server 时也建议使用这样的源码启动命令。

### 内置远程 MCP server

```
agent（client）──POST http://127.0.0.1:8090/mcp──▶ 观测台反向代理 ──▶ 127.0.0.1:8091/mcp
                                                              agent -mcp-serve -mcp-http（常驻子进程）
```

- 工具实现仍在 agent：`-mcp-serve` 加 `-mcp-http` 后，同一个 server 对象、同一套三层校验，只把传输从 stdio 换成 Streamable HTTP。观测台只做托管和转发，不引入 MCP SDK。
- 先 `go build` 到临时目录再运行，而不是 `go run`：结束 `go run` 不会结束它编译出的子进程，Ctrl+C 后会留下进程占着端口。
- 反向代理保留原请求的 Host，`FlushInterval: -1` 让 SSE 分段立即转发；`/mcp` 同样经过本机 Host + 同源 Origin 检查，SDK 自己还有一层 DNS 重绑定防护。
- 远程与 stdio 的协议消息完全相同（discover → tools/list → tools/call），区别是：远程 server 不随 agent 启动和退出，能被多个 agent 同时使用；连接时没有子进程，也就没有 stderr 日志转发，server 日志打印在观测台终端。

能力卡片只从 agent 的终端行还原（`Skills: loaded=…`、`Skill error`、`MCP connect/initialize/tools/list/register/skip/error`），和对话流一样不加观测专用埋点。

中心能让 agent 启动任意命令，所以 `/hub` 接口只接受 Host 为 127.0.0.1 或 localhost、且 Origin（如果有）与 Host 相同的请求：其他网站无法借浏览器跨站提交，DNS 重绑定也过不了 Host 检查。

## 1. 为什么在模型请求这一层观测

agent 每次请求模型都会把完整消息历史发出去：

```
第1次请求：system, user
第2次请求：system, user, assistant(tool_calls), tool
第3次请求：system, user, assistant, tool, assistant, tool
```

所以只要站在 agent 和方舟之间，看到每次请求与响应，就能还原全过程：

| 想看到的内容 | 来自哪里 |
| --- | --- |
| 模型收到了什么 | 请求 `messages`、`tools` |
| 模型怎么想、决定调用什么 | 响应 `reasoning_content`、`content`、`tool_calls` |
| 工具返回了什么 | 下一次请求里新增的 `role: "tool"` 消息，用 `tool_call_id` 对上调用 |
| 工具执行多久 | 上一次响应到下一次请求之间的时间 |
| 模型耗时与成本 | 代理计时；响应 `usage`，含 `cached_tokens`、`reasoning_tokens` |
| 为什么停止 | `finish_reason`、agent 进程退出码 |

这就是"协议即观测接口"：观测台只依赖 OpenAI 兼容的 Chat Completions 格式，不读取 agent 源码，也不需要 agent 调用任何埋点函数。以后新增工具、修改 prompt、增加轮次或改写循环，只要还按这个协议请求模型，页面就会自动显示新内容。

## 2. 运行链路

```
浏览器 ──POST /runs──▶ 观测台 ──go run . -question ...──▶ agent
                         ▲   LLM_API_URL=http://127.0.0.1:8090/llm/<运行ID>
                         │                     │
   SSE 实时事件 ◀────────┤◀── 请求/响应原文 ───┘ 观测台原样转发 ──▶ 方舟
                         └── agent 终端输出（stdout/stderr）
```

- 普通问答启动 `go run . -question ...`；页面选择“Day 3 上下文实验”则启动 `go run . -context-lab -max-steps 60 -reasoning-effort minimal`。两种模式使用同一套代理和事件展示。
- 每次运行用 `go run .` 启动 agent，所以 agent 代码改了也不用重新部署观测台。观测台自身代码或内嵌页面改动后，要重启观测台并刷新页面。
- 运行 ID 放在代理路径里，几次运行同时进行也不会混在一起。
- agent 读取配置时环境变量优先，新对话的密钥和模型来自 agent 自己的配置；续聊沿用存档中的模型与推理强度，密钥仍从本地读取。观测台把 `LLM_API_URL` 指向该记录的代理地址。
- 观测台转发 `Authorization`，但不记录。真实上游地址从环境变量或 agent 的 `.env` 里读取。
- 事件类型：`start`（首个问题）、`continue`（续聊问题）、`request`、`response`、`stdout`、`stderr`、`exit`。事件同时写入 `observer/runs/<运行ID>.jsonl`，该目录已加入 `.gitignore`。
- 观测台启动时会读回 `runs/*.jsonl`，重启后仍可查看、回放和对比历史运行。早期存档没有 `start` 事件，问题取自第一次请求里的 user 消息。
- SSE 先回放已有事件，再推送新事件；运行结束后发送 `end` 并关闭连接。

agent 通过 `llm.go` 接受本机 `http://127.0.0.1` 观测代理；通过通用的 `-history-stdin` 参数接收续聊上下文，不需要知道观测台存档的位置。

## 3. 对话界面与三个观测视图

页面参考 Codex 客户端：左侧是对话列表和“新对话”“Day 3 上下文实验”入口，主区默认是对话流，底部是输入框。顶栏的“对话 / 观测”切换同一条记录的两种看法。

### 3.0 对话流：从模型请求还原聊天记录

对话流没有单独的数据来源，仍然只读取代理记录的请求和响应：

```
用户消息        ← 每次普通请求末尾新增的 user 消息
✻ 思考了 4.8 s  ← 响应 reasoning_content，点开看全文
✓ calculator …  ← 响应 tool_calls；结果取自下一次请求里 tool_call_id 相同的 tool 消息
最终回答        ← 没有 tool_calls 的响应 content，按少量 Markdown 渲染
── 上下文已压缩 ── ← 摘要请求，点开看摘要原文
```

- 聊天页和轨迹页共用一份回合归属。普通存档优先使用start/continue事件确定新提问；旧存档与Day 3自动对话依据末尾新user消息和上一回合的最终响应恢复边界，Day 4使用已有的题目/模式边界。
- 压缩后的请求是 `system, 保留的用户原话, 摘要, 最近消息组`。保留原话不重复显示为新问题；工具结果和失败后同请求重试继续归入原Turn，摘要指令不作为用户提问。
- 问题提交后、agent 还没发出第一次请求时（`go run` 编译需要几秒），先用 `start` / `continue` 事件里的问题占位。
- 运行中，等待模型显示“思考中…”，工具执行中显示转圈；运行异常结束或没有最终回答时，显示退出状态和最后几行终端输出。
- 每条回答下方有“在观测中查看”，跳到轨迹视图并选中这次模型调用的输出标签；点击来源引用直接打开对应工具的结果标签。

Enter 发送，Shift+Enter 换行；输入法选词时的 Enter 不会发送。

切到“观测”后，左侧记录出现勾选框（勾选 2–5 条进入对比），中间是视图，右侧是共用的 inspector。点击任意事件、节点或格子，都会在 inspector 里看到详情。

### 3.1 轨迹：事件账本 + 瀑布时间轴（对应 Trajectory 视图）

```
▾ Turn 1 · 3个Step
1  SYSTEM     初始系统规则 · 4个工具
2  USER       先查循环职责，再计算数量 × 25
   Step 1 · 请求 #1 · 2条messages · 原始输入/输出
3  ASSISTANT  调用 search_notes
4  TOOL       search_notes → 找到4项职责
   Step 2 · 请求 #2 · 4条messages · 原始输入/输出
5  ASSISTANT  调用 calculator
6  TOOL       calculator {"expression":"4*25"} → 100
   Step 3 · 请求 #3 · 6条messages · 原始输入/输出
7  ASSISTANT  回答100
8  EXIT       exit 0
```

- 每个Turn是一次用户回合，可折叠；内部按Step分组。并行工具放在同一个Step内，依赖结果的下一次模型调用进入后续Step。
- 主表按事件分类：SYSTEM仅在初始化或系统规则/工具定义变化时展示，USER是新提问，ASSISTANT包含思考、回答或工具请求，TOOL合并调用参数与真实返回结果，COMPACTED显示摘要，EXIT表示进程状态。最终回答已经是ASSISTANT事件，不重复增加回答行。
- DeepSeek Harness的CONTEXT专指程序注入的消息，不是历史的统称。本项目从模型协议与首问/续聊事件还原轨迹，不把旧messages标为CONTEXT。分组参考[官方Trajectory源码](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/client/ui-trajectory/src/client/layout.ts)，不是导入它的插件框架。
- 右侧时间轴按真实时间画条：紫色是模型调用，绿色是工具，红色是出错或绕路，执行中的条会闪烁。
- 在时间刻度上拖拽可以聚焦某一段时间，双击还原。
- 当前 agent 使用非流式响应，模型调用只有总耗时，不能像官方视图那样拆成 TTFT / decode 两段。
- 每个Step都有“X条messages”输入入口，展示实际请求中的全部messages，按原顺序编号并标注system、user、assistant、tool角色；页面条数与原始请求数组长度一致。
- 工具定义在请求的tools字段，单独列在输入详情下方，不计入messages；请求参数与完整请求JSON也在输入详情中。
- 上面示例中的Step 1输入2条（system、user），Step 2输入4条（再加assistant检索请求、tool检索结果），Step 3输入6条（再加assistant计算请求、tool计算结果）。三次请求均属于Turn 1。
- 压缩调用与压缩后的请求也按实际messages展示：保留原话、交接摘要、新问题都保留API角色，摘要另注明“历史摘要”；这不会改变Agent发送的数据或聊天页的用户消息展示。
- 右侧详情按事件提供标签页：SYSTEM的系统规则/工具定义，USER的内容/原文，ASSISTANT与COMPACTED的概览/输出/响应JSON，TOOL的概览/参数/结果/Schema/原文。完整输入有messages/工具定义/请求JSON三个标签；输出概览可跳到本次输入。工具结果在下一次请求中作为tool消息回流，不能把工具请求误当成执行结果。

### 3.2 迷宫：探索路径 + 数据轨（对应 dsh-maze）

```
          T1 · S1         T1 · S2           T1 · S3
 M1 ─────────────── M2 ─────────────── M3 ──────── A ── ■
   ╲               ↗ ╲               ↗ ╲
    [search_notes]─✕  [↺ search_notes]─✕ [↺ search_notes]─✕     绕路（红，死胡同）
       ╰──── 回退弧线（紫，虚线）─────╯
```

- **主干**：模型调用M1、M2…仍按全局请求序号排列，顶部标注所属Turn/Step；摘要标为压缩。最后是回答A和进程结束■。
- **主路径工具**：返回有效结果的工具，显示为绿色，分叉出去后再汇合到下一次模型调用。同批工具上下并排展开。
- **绕路**：返回错误、空结果，或用相同参数重复调用的工具，显示为红色，以 ✕ 结尾。
- **回退**：同名工具在绕路之后再次被调用，用紫色虚线弧连起来，节点名前标 ↺。
- 所有判定都是确定性规则，不调用模型；判定依据会显示在 inspector 里。
- 地图下面有三条数据轨，与地图按请求序号对齐：
  1. **工具调用密度**：每次模型请求发起的工具数，绕路部分标红。
  2. **Token 脉冲**：每次调用的 token 构成，按缓存命中输入、未缓存输入、推理、输出堆叠。
  3. **上下文压力**：每次请求的输入 tokens 占输入容量的比例，画出70%和90%两条线。优先从 agent 的 `Context: ... cap=...` 输出获取容量，旧记录没有该信息时手工填写。曲线展示 API 输入量；agent 的触发判断使用 `used`（包含上次完成量与增量估算），两者不要混淆。压缩标记来自摘要或视图重建。
- 地图下方的绕路清单可以逐条点击。

### 3.3 对比：多次运行按请求序号对齐（对应 trace compare）

- **指标表**：问题、模型调用、工具调用、主路径步数、绕路、回退、总 tokens、缓存命中、推理 tokens、模型耗时、总耗时、结果、回答摘要。"越少越好"的指标会把最低值标成绿色。
- **泳道**：每次运行一行，每次请求一列。格子标注所属Turn/Step，显示耗时、tokens和工具芯片，红色芯片是绕路，↺是回退。点击格子或芯片会打开该运行对应事件的详情；点击回答定位本次响应。

### 3.4 回放

已结束的运行可以按真实时间间隔重放，速度 1×–300×。打开"折叠空闲"后，长时间的等待会被压缩。回放时，轨迹和迷宫都会逐步生长。

## 4. 启动

在项目根目录执行：

```sh
go -C observer run .
# 打开 http://127.0.0.1:8090
```

参数：`-addr` 指定页面地址，默认 `127.0.0.1:8090`；`-agent` 相对于 `observer/` 指定项目目录，默认 `..`。按上述命令启动时无需额外指定目录。

要继续对话：

1. 回答结束后，直接在底部输入框写下一句话，按 Enter 发送，会延续当前对话。
2. 要继续之前的对话，先点击左侧记录。新回答和工具调用会追加到同一条对话流和轨迹里。
3. 点击“新对话”开始独立任务；不会删除旧记录。
4. 运行中和回放中不能续聊。失败或中断的任务暂不续接，避免把未完成的工具调用重新执行。

续聊并不要求原进程一直存活。观测台从已有JSONL取出最后一次成功的普通请求messages，加上对应的完整assistant回答，经stdin传给新的agent进程。原生工具调用ID、工具结果、摘要和assistant的加密字段都保留；agent恢复View，追加新问题，再走原来的预算检查与ReAct循环。以前的工具结果是历史输入，不会重新执行。

恢复的是最后的模型视图，不把压缩前的全部原文重新塞回去。新进程的Transcript从这个恢复点继续记录；更早的原始轨迹仍保留在观测台存档里。每个新提问使用新的默认10次请求预算，包含摘要；观测台Turn编号跨提问连续递增，服务重启后也不会重置。总耗时仍按整条记录的时间跨度计算，包含两次提问之间的等待。

Day 3实验包含两个独立场景；首次续聊接在33轮学习对话之后，保留账号与范围约束，不混入后面的大工具演示。之后按普通续聊处理。

要观察 Day 3：

1. 点击左侧“Day 3 上下文实验”并确认，不用填问题。
2. 对话流里能看到实验程序发出的33轮问题和回答，压缩位置显示为“上下文已压缩”分隔线，点开是摘要原文。
3. 切到“观测”：每个Turn是一次用户回合，内部Step表示任务模型调用及工具执行。点击Step的“X条messages”看完整输入，点击ASSISTANT看响应；摘要单独显示为COMPACTED，不占任务Step，但仍计入请求数。
4. 点击“终端输出”查看压缩前后大小、`Recall` 账号与学习范围、`Large tool` 截断情况和最终统计。运行中也能查看。
5. 切换“迷宫”看输入量增长和压缩后的下降。实验默认输入容量7168 token，页面从实际输出读取。

原来的终端命令直接请求方舟，没有经过代理，因此不会自动出现，也无法补录已结束的对话。通过页面重新运行才能完整观测；运行结果仍存到已有的 `observer/runs/`，每日学习目录不新增日志。

## 5. 兼容边界

- 自动兼容：工具、prompt、轮次、并行数量、消息内容、请求参数（如 `reasoning_effort`）的变化，以及将来新增的消息角色。
- 需要调整观测台的情况：agent 改用流式响应（`stream: true`）、改用其他协议格式，或命令行不再支持 `-question`。流式响应时原文仍会记录，但页面不会拆分事件；改成流式后才能补上 TTFT / decode 分段。
- 绕路规则依赖工具结果的形状：带 `error` 字段算错误；结果为空、或所有数组字段都为空算空结果。工具结果格式变化时，可能需要调整这条规则。

## 6. 学习建议

1. 打开迷宫视图看 `trace-detour.jsonl` 那次运行：三次检索都是空结果，模型换了两次关键词，所以有两条回退弧。再对照 Token 脉冲，可以看到每次重试都让输入变长。
2. 在对比视图勾选同一问题的两次运行，比较路径是否相同，以及耗时差异来自哪一轮。同样的问题，模型每次的表现也会有波动。
3. 在轨迹视图拖拽时间刻度，聚焦到工具执行那几毫秒，再和模型调用的耗时比较，判断延迟主要花在哪里。

## Day 3 上下文压缩的观测

摘要请求沿用原生messages，末尾user消息以`[上下文压缩请求]`开头。页面将它标为独立的上下文摘要调用；它的输出不作为最终回答，返回的工具请求也不会被显示为已经执行。

视图重建后消息长度可能下降。“模型输入”始终展示本次请求全部messages，不再按历史与当前输入分组；聊天页仍识别新问题，tool结果按调用ID跨历史请求关联。上下文压力轨的压缩标记来自摘要或主请求视图重建，不再把任意输入token下降都当成压缩。模型输出详情同时展示共同前缀消息数和服务端usage；前缀相同不等于缓存一定命中。
