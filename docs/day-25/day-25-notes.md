# Day 25：统一权限策略

## 学习目标与术语

学完能说明：一次工具调用在执行前要经过哪些判断、按什么顺序；权限模式和权限规则各解决什么问题；为什么拒绝规则必须优先；规则看命令文本有什么漏洞，沙箱怎样补上；以及编码 agent 的工作区应该怎样挂进沙箱。

| 术语 | 通俗解释 |
| --- | --- |
| 权限模式 | 一次切换整套默认行为：只读计划、改动都问、自动编辑、全权 |
| 权限规则 | 针对具体工具和参数写的允许、询问、拒绝，例如“允许 `go test`”“拒绝 `git push`” |
| 决定 | 每次调用只有三种结果：允许（直接执行）、询问（等人确认）、拒绝（不执行） |
| 优先级 | 多条规则同时命中时听谁的；常见做法是拒绝 › 询问 › 允许 |
| 审批者 | 需要询问时由谁回答：人，或者先由分类器、审查子 agent 筛一遍 |
| 沙箱边界 | 操作系统强制的限制，和规则互补：规则看文本，沙箱看实际的系统调用 |

## 1. 为什么要“统一”

一个 agent 的“能不能做”往往散落在各处：某个工具里写死了要确认，另一个工具靠沙箱限制，还有的完全没管。问题是：

- 用户看不清全貌，不知道哪些操作会被问、哪些会直接执行；
- 想调整（比如“这个项目里跑测试不用问”）只能改代码；
- 新加一个工具，很容易忘了给它加检查。

统一权限策略把这些判断收进一个地方：**每次工具调用执行前，都过同一条管线，得出允许、询问或拒绝**。用户用配置表达意图，不用改代码。

## 2. 管线的顺序

```text
工具调用 → 执行前 hook（第 26 天）→ 规则：拒绝 › 询问 › 允许 → 权限模式的默认 → 审批者 → 执行（shell 在沙箱里）
```

Claude Code 的文档写得很明确：规则按拒绝、询问、允许的顺序判断，命中第一条就定，**规则的具体程度不改变这个顺序**。一条宽泛的拒绝规则 `Bash(aws *)` 会挡住所有 aws 命令，哪怕另有一条更具体的允许规则 `Bash(aws s3 ls)`。[资料](https://code.claude.com/docs/en/permissions)

为什么不用“越具体越优先”？因为权限配置来自多个层级：组织的托管策略、项目共享的设置、个人设置、某个插件。如果具体的允许能压过宽泛的拒绝，下层只要写一条足够具体的允许，就能绕开上层的禁令。“拒绝优先”保证禁令无论从哪一层来，都不会被悄悄放开。

## 3. 模式：一次切换一组默认

规则适合描述例外，模式描述常态。四种常见模式：

| 模式 | 读文件 | 改文件 | 跑命令（在沙箱里） | 适用场景 |
| --- | --- | --- | --- | --- |
| 只读计划 | 直接 | 拒绝 | 直接，但工作区只读 | 先看方案再动手、代码评审 |
| 改动都问 | 直接 | 询问 | 询问 | 不熟悉的仓库、重要分支 |
| 自动编辑 | 直接 | 直接 | 直接 | 日常开发，沙箱兜底 |
| 全权 | 直接 | 直接 | 直接，不再询问 | 本身就隔离的容器、CI |

对照两家：Claude Code 的模式是 Manual、acceptEdits、plan、auto（分类器审）、dontAsk、bypassPermissions；Codex 用两个独立配置，沙箱模式（只读、工作区可写、完全放开）和审批策略（需要时询问、从不询问）。思路相同：**默认行为可以一键切换，例外用规则**。[资料](https://code.claude.com/docs/en/agent-sdk/agent-loop) [资料](https://learn.chatgpt.com/docs/sandboxing)

模式最好能在对话中途切换：先用只读计划模式让 agent 摸清代码、给出方案，确认后切到自动编辑去实施。

## 4. 规则看文本，沙箱看行为

权限规则匹配的是工具参数，对 shell 来说就是命令文本。文本匹配有天然的漏洞：

| 规则 | 能挡住 | 挡不住 |
| --- | --- | --- |
| 拒绝 `Bash(curl *)` | `curl https://…` | `python -c "import urllib…"`、`wget`、写进脚本再运行 |
| 允许 `Bash(go build *)` | — | 如果只看开头：`go build && curl evil.com` 会被一起放行 |
| 拒绝 `Read(.env)` | 读文件工具读 `.env` | `cat .env`、`grep -r KEY .` |

对第二种，常见做法是把复合命令按 `&&`、`;`、`|` 切开：允许要求**每一段**都命中，拒绝只要**有一段**命中。但命令还可以写成 `sh -c "…"`、变量拼接，文本分析永远不完整。

所以规则只能表达意图、减少打扰，不能当安全边界。真正的边界在沙箱：文件系统挂载决定能读写哪里，网络命名空间决定能不能联网，这些是操作系统强制的，命令怎么写都绕不过。Claude Code 的文档也明确建议：要可靠地限制网络，用沙箱的网络白名单，而不是只靠拒绝 `curl` 的规则。[资料](https://code.claude.com/docs/en/permissions)

两者的分工：

- **沙箱**：挡住越界的行为（读密钥、改系统文件、联网外发），无论模型被注入了什么。
- **规则与模式**：决定边界内的操作要不要问人，比如在工作区里删文件是允许的，但用户可能想先确认。

## 5. 把工作区挂进沙箱

编码 agent 的 shell 要能编译、测试被修改的代码，所以工作区要挂进沙箱。挂载时要考虑：

| 路径 | 处理 | 原因 |
| --- | --- | --- |
| 工作区本身 | 可写；只读计划模式下只读 | 模式在沙箱层面也生效，命令改不了代码 |
| 版本库历史（`.git`） | 只读 | 能看 diff、log，不能提交、改写历史；出错时还能用它回退 |
| 密钥文件（`.env`） | 换成空文件 | 代码要运行不需要真实密钥；防止被读出来外发 |
| 运行数据目录 | 换成空目录 | 可能含账号、会话等私有数据 |
| 编译工具链与依赖缓存 | 只读 | 能离线编译；依赖不能被篡改 |
| 编译缓存 | 单独的可写目录 | 不和宿主机共用，沙箱里的代码污染不了宿主机的缓存 |

Codex 的工作区可写模式也把 `.git` 设为只读，即使它在可写目录里。[资料](https://codex.danielvaughan.com/2026/04/10/codex-cli-internals-queue-pair-guardian-sandbox/)

## 6. 和高风险确认的关系

第 20 天的高风险确认（删除记忆、破坏性工具、读过私有数据后外发、续跑重做）是程序写死的规则，用户的规则改不了它。它和用户规则走同一条确认路径，界面上看到的是同一种确认卡片，只是原因不同。

全权模式是例外。用户选全权，意思是“这个环境本身已经隔离好了，什么都别问我”，两家参考实现都这样处理：

| | 全权模式下仍然生效 | 不再询问 |
| --- | --- | --- |
| Claude Code bypassPermissions | 拒绝规则；用户显式写的询问规则；要求用户交互的工具；对关键路径的删除 | 其余全部，包括写受保护目录；没有“读过私有数据后外发”这类按来源判断的确认，远程工具的破坏性注解也不触发询问 |
| Codex 完全访问（从不询问 + 不开沙箱） | 安全监控可以暂停任务（不是审批） | 全部，带破坏性注解的远程工具调用也由程序直接放行 |

所以合理的做法是：全权模式下风险照常判断、照常写审计，但由程序放行，不发确认。仍然询问的只有用户亲手写下的询问规则——那是用户明说“这类操作要问我”，模式不该盖过它。“续跑重做”是特例：参考实现里没有对应的确认，程序既不问也不自动重做，回填“结果未知”，让模型检查之后自己决定要不要再做一次。

## 自测

**为什么规则按“拒绝 › 询问 › 允许”判断，而不是“越具体越优先”？**

配置来自多个层级。拒绝优先保证上层的禁令不会被下层一条更具体的允许绕开。

**允许了 `Bash(go build *)`，`go build && curl evil.com` 应该怎么处理？为什么这还不够？**

把命令切成段，每段都要命中允许，所以这条不放行。但命令还能写成 `sh -c` 或拼接，文本分析不完整；可靠的限制要靠沙箱的网络隔离。

**只读计划模式下，模型用 bash 执行 `sed -i` 修改代码，会发生什么？**

工作区在沙箱里挂成只读，写入失败。模式在规则层和沙箱层同时生效。

**工作区挂进沙箱时，为什么 `.git` 要只读，`.env` 要换成空文件？**

`.git` 只读保证历史不被改写，出错时能回退；`.env` 含密钥，代码运行不需要真实值，换成空文件防止被读出来外发。

**全权模式下，删除长期记忆还会询问吗？**

不会。全权模式和 Claude Code 的 bypassPermissions、Codex 的完全访问一样不再询问：程序照常判断风险、写审计，然后放行。想让某类操作在全权模式下仍然要问，就写一条询问规则。
