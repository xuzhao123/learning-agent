# Day 23：编码工具与面向 agent 的接口

## 学习目标与术语

学完能说明：为什么给 agent 的文件工具要专门设计，而不是直接给它一个 shell；读、找、搜、改四类工具各自要解决什么问题；几种编辑格式各自怎样出错；“读过才能改”防住的是哪一类错误；以及工具输出为什么要有预算、超出时要怎样告诉模型。

| 术语 | 通俗解释 |
| --- | --- |
| ACI（Agent-Computer Interface） | 给 agent 用的“人机界面”：工具的名字、参数、输出格式和错误信息，都按模型的习惯与弱点设计 |
| 编辑格式 | 模型用来表达“怎么改文件”的写法，例如整体重写、字符串替换、diff、补丁 |
| 唯一匹配 | 字符串替换要求被替换的原文在文件里只出现一次，否则不知道改哪一处 |
| 读后才写（read-before-write） | 改文件之前必须先读过它；harness 记住读到的版本，写入前核对 |
| 过期（stale） | 模型读过之后，文件又被别人改了；按旧印象改会覆盖别人的改动 |
| 输出预算 | 每次工具返回的内容有上限，超出就截断，并告诉模型怎样取下一段 |
| 路径边界 | 工具只能访问指定目录；`../` 和指向外面的符号链接都要拦下 |

## 1. 为什么不直接给一个 shell

只给一个 shell，模型也能 `cat`、`grep`、`sed -i`，但有三个问题：

- **输出不受控**。`cat` 一个大文件，几万 token 一次性涌进上下文；`grep -r` 在依赖目录里搜出几千行。
- **编辑容易出错且不可检查**。`sed` 的正则和转义规则复杂，改错了往往没有任何报错；harness 也看不出它改了什么。
- **无法做细粒度的权限与审计**。一条 shell 命令可以同时读、写、联网，harness 只能整条放行或拒绝。

SWE-agent 的研究把这个问题叫作 ACI 设计：同一个模型，换一套为它设计的文件查看、搜索和编辑命令，在 SWE-bench 上的解题率明显提高。他们总结的原则包括：命令要简单、输出要简洁、编辑后立刻给出反馈、出错时给出能照着改的信息。[资料](https://arxiv.org/abs/2405.15793)

所以成熟的编码 harness 都同时提供 shell 和一组专门的文件工具。shell 负责编译、测试、运行；文件工具负责读、找、搜、改。

## 2. 四类工具各解决什么

| 工具 | 解决的问题 | 关键设计 |
| --- | --- | --- |
| 读 | 看清文件内容 | 输出带行号，方便引用和定位；按行分页；超长行截断；二进制文件拒绝 |
| 找（glob） | 知道有哪些文件 | 按路径模式匹配；跳过版本库和依赖目录；结果有上限并排序 |
| 搜（grep） | 不读全文就找到位置 | 正则搜索，返回“路径:行号:内容”；可限定目录和文件类型；结果有上限 |
| 改 | 精确修改 | 编辑格式要好写、好检查；改前核对版本；改后返回改动片段 |

一个典型的编码任务就是在这几类工具之间往返：先找、搜定位，再分段读，再改，再读一遍确认，最后用 shell 编译测试。

## 3. 编辑格式怎样出错

| 格式 | 模型要写什么 | 典型失败 |
| --- | --- | --- |
| 整体重写 | 文件的完整新内容 | 大文件又贵又慢；模型容易漏掉没注意到的部分，或者把“……其余不变”写进文件 |
| 字符串替换 | 一段原文和替换后的内容 | 原文的空白、缩进与文件不一致就找不到；原文太短会出现多处 |
| unified diff | 带行号和上下文的差异块 | 行号算错；上下文与实际不一致，整个块应用失败 |
| 补丁格式（如 apply_patch） | 按文件、按段描述增删 | 格式有一处不合规，整份补丁失败；但能一次改多个文件、多处 |

Aider 对多种编辑格式做过对比测试，结论是：格式对结果影响很大，而且不同模型擅长的格式不同；行号是模型最容易写错的部分，好的格式尽量不让模型自己算行号。[资料](https://aider.chat/docs/more/edit-formats.html) [资料](https://aider.chat/2023/12/21/unified-diffs.html)

字符串替换是当前最常见的折中：模型只需要从读到的内容里原样复制一段，再写出新内容，不用算行号。它的两个失败都能被工具准确发现并报告：

- **没找到**：告诉模型检查空白和缩进，并且不要把行号前缀复制进去。
- **出现多处**：告诉模型出现了几次、在哪几行，让它多带几行上下文，或者明确要求全部替换。

这里有一个容易忽略的细节：读工具在每行前面加了行号，模型复制原文时可能把行号带进去，或者把行号后面的分隔符当成缩进。所以错误信息里要明确提醒“不要带行号前缀”，工具描述里要写清行号的格式。

## 4. 读过才能改

设想这个顺序：

1. 模型读了文件 A，内容是版本 1。
2. 用户在编辑器里改了 A，变成版本 2；或者另一个工具调用改了它。
3. 模型按版本 1 的印象写入 A。

如果是整体重写，版本 2 的改动被悄悄覆盖；如果是字符串替换，可能替换到一个已经变了含义的位置。

做法是让 harness 记账：每次读取时记下文件内容的哈希；写入前重新读一次，算哈希比对。对不上就拒绝，并告诉模型“文件在你读过之后被改了，请重新读”。从没读过的文件也拒绝修改。

两点细节：

- **“核对 + 写入”要是一步**。两次写入并发执行时，如果先都核对、再都写入，两次核对都会通过。要用锁把核对和写入放在一起。
- **自己的写入要更新账本**。模型改完一处，账本里记下新内容的哈希；它接着改同一个文件的另一处，不需要重新读。代价是：如果模型在同一批里既局部修改、又整体重写同一个文件，整体重写会盖掉局部修改。这时整体重写建立在旧内容上，属于模型自己的矛盾，harness 只能靠“修改类调用按顺序执行”减少意外。

## 5. 输出预算

上下文是有限的，工具输出是最大的消耗来源。每个工具都要有上限，超出时不是简单截断，而是告诉模型下一步怎么做：

| 情况 | 返回给模型的信息 |
| --- | --- |
| 文件比一次读取的行数长 | 读到第几行、总共多少行、下一段从第几行开始 |
| 某一行特别长（压缩过的代码、长字符串） | 这一行截断了，标出被截断 |
| 文件太大 | 不读，建议先用搜索定位 |
| glob、grep 结果太多 | 只列前若干条，说明一共超出，建议缩小范围 |

“告诉模型怎么继续”比“返回尽量多”更重要：模型拿到明确的下一步，就会分段读或改写搜索条件；拿到一大段被截断的文字，往往会误以为已经看全了。

## 6. 路径边界

文件工具只该在用户指定的目录里工作。常见的越界方式有三种：

- 相对路径里的 `../`；
- 绝对路径直接指向别处；
- 目录里的符号链接指向外面，例如一个指向主目录密钥文件的链接。

只做字符串检查（看路径里有没有 `..`）挡不住第三种。可靠的做法是让操作系统或运行时按“以某个目录为根”的方式解析路径，每一级都检查是否跑出了根目录。Go 1.24 起的 `os.Root` 就是这样工作的：通过它打开的路径，无论怎样拼接或经过符号链接，只要解析结果在根目录之外就报错。[资料](https://go.dev/blog/osroot)

注意这只是文件工具的边界。shell 命令能做的事更多，需要第 12 天那样的 OS 沙箱来限制。

## 自测

**模型已经有 shell 了，为什么还要专门的读、搜、改工具？**

专门工具的输出可控（分页、上限、截断提示），编辑可检查（唯一匹配、版本核对、返回改动片段），权限和审计可以按“读”和“写”分开。shell 输出不受控，`sed` 改错了往往没有报错，而且一条命令可能同时读、写、联网。

**字符串替换编辑会以哪两种方式失败？工具应该怎样回复？**

原文没找到，或者出现多处。没找到时提醒检查空白、缩进，不要带行号前缀；出现多处时说明次数和行号，让模型加上下文或明确全部替换。

**“读过才能改”防住的是什么错误？为什么核对和写入要放在一把锁里？**

防住按过期内容写入、覆盖别人改动的错误。不加锁时，两次并发写入可能都先通过核对再各自写入，后写的覆盖先写的。

**读文件时为什么要告诉模型“下一段从第几行开始”，而不是尽量多返回？**

上下文有限，返回太多会挤掉其他信息；截断时不说明，模型会误以为看全了。明确的下一步让模型按需分段读。

**只检查路径里有没有 `..`，为什么不够？**

符号链接可以指向目录之外，绝对路径也可以直接指向别处。要在解析每一级路径时检查是否越出根目录，例如用 Go 的 `os.Root`。
