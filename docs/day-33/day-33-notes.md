# Day 33：模型适配层

## 学习目标与术语

学完能说明：模型请求失败时哪些该重试、哪些不该，重试要注意什么；同一个 harness 怎样同时接 Chat Completions、Responses、Anthropic Messages 三种协议而不让上层代码分叉；每个模型的窗口、能力从哪里来；为什么要把模型的回复分成“过程说明”和“最终回答”。

| 术语 | 通俗解释 |
| --- | --- |
| 暂时故障 | 过一会儿再试大概率会好的失败：限流、服务端过载、连接断开 |
| 退避重试 | 失败后等一段时间再试，等待时间逐次加长，避免一起涌回去把服务再压垮 |
| Retry-After | 服务端在响应头里告诉客户端“至少等这么久再来” |
| 适配层 | 内部只用一种消息格式，只在发出和收回时换成各家协议 |
| 思考签名 | 有的协议给模型的推理内容附一个签名，下次请求要原样带回，服务端据此确认推理没被改过 |
| 前缀缓存 | 服务端记住最近处理过的请求开头，下次相同开头直接复用 |
| 回复分段 | 把模型说的话标成“过程说明”（做事过程中的说明）或“最终回答”（这一轮的结论） |

## 1. 哪些失败该重试

模型请求失败，常见的原因可以分成两类：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 暂时故障 | 429 限流、500/502/503/504、连接失败、流在中途断开、服务端在流里报“过载” | 退避后重试 |
| 再试也一样 | 400 参数错、401/403 密钥或权限、上下文过长、额度用完、输出到了上限 | 不重试，直接报出原因 |

几个容易出错的地方：

- **429 不都是限流**：额度用完通常也是 429，但要等到额度按小时、按天重置，几秒后重试没有意义。要看错误码或说明里的 quota 一类字样。
- **Retry-After 要遵守**：服务端说了等多久就等多久；它要求的时间太长（比如一小时后额度重置），就别重试，直接报错让人处理。
- **上下文过长另有出路**：它不是暂时故障，正确的处理是压缩上下文再请求，而不是原样重试。
- **输出被截断不是故障**：结束原因是“到了输出上限”的，重试只会再截断一次；只有“流断了、根本没收到结束标记”才算暂时故障。
- **流式输出到一半再重试**：界面上已经显示了半段文字，重试会从头再来一遍。要通知界面清掉这一段，否则同一句话出现两次。
- **重试算不算预算**：重试是 harness 替模型做的，不是模型多做了一步，常见的做法是不计入“模型请求次数”预算，但在调用链上记下每次重试，方便事后看。

退避常用 1、2、4 秒这样翻倍增长，再限制次数（比如最多 3 次）。

## 2. 三种协议，一个内部格式

现在常见的模型协议有三种：

| 方面 | Chat Completions | Responses | Anthropic Messages |
| --- | --- | --- | --- |
| 系统提示词 | `system` 消息 | `instructions` | 顶层 `system` |
| 工具调用 | assistant 消息里的 `tool_calls` | 独立的 `function_call` 项 | assistant 内容里的 `tool_use` 块 |
| 工具结果 | `role: tool` 消息 | `function_call_output` 项 | 下一条 user 消息里的 `tool_result` 块 |
| 推理内容 | 各家自定义（如 `reasoning_content`） | `reasoning` 项（摘要或加密内容） | `thinking` 块，带 `signature` |
| 流式 | 带 `delta` 的 chunk | 带 `type` 的事件 | `message_start`、`content_block_*`、`message_delta`、`message_stop` |
| 输出上限 | 可选 | 可选 | **必填** `max_tokens` |
| 消息顺序 | 较宽松 | 项的列表 | user、assistant 要交替 |

适配层的做法：harness 内部只认一种格式（比如 Chat Completions 的消息），历史、检查点、日志、界面都用它；只在发请求前换成目标协议，收流时再拼回内部格式。新接一种协议，只写“换过去”和“拼回来”两段，上层的循环、压缩、恢复都不用动。

换的时候要注意：

1. **配对与顺序**：工具调用和结果靠编号配对；Messages 要求角色交替，所以相邻的工具结果和随后的提醒要合进同一条 user 消息。
2. **推理内容怎么回传**：各家规则不一样。DeepSeek 的 Chat Completions 接口要求把推理内容原样传回，否则报错；它的 Anthropic 接口则不强制；Anthropic 自家的模型要求 thinking 块连同签名原样传回；Responses 只能回传带编号或加密的 reasoning 项，只有摘要文字时没法回传。适配层要把签名一类的东西存下来，下次按目标协议放回去。
3. **结束原因与用量换成内部的叫法**：`end_turn`、`tool_use`、`max_tokens` 换成内部的“结束、要调工具、被截断”；Messages 的 `input_tokens` 不含命中缓存的部分，要和缓存读、缓存写加在一起才是“输入总量”。

## 3. 每个模型的能力从哪里来

同一家供应商下的模型，窗口、最大输出、能不能看图都不一样。用一个全局窗口（比如 26 万）套所有模型，会出两种问题：窗口大的模型被过早压缩，浪费能力；窗口小的模型超了才知道。

可靠的来源依次是：

1. 供应商的模型列表接口（不少会返回 `context_window`、`max_output_tokens`、输入模态）；
2. 官方文档；
3. 实测（比如看图能力，只能真发一张图看它答不答得出来）。

拿不准的不要猜，留空、用保守的默认值。一个名字对应多个版本时（比如套餐名背后有几个带日期的版本），取其中最小的。

## 4. 前缀缓存不是处处都有

前缀缓存能让长对话便宜、快很多，但它取决于供应商和计费方式：有的自动开启（相同前缀自动命中），有的要在请求里显式开启，有的模型或套餐根本不支持。接入时要用真实请求核对：同样的长前缀连发两次，看第二次的用量里有没有“命中缓存”的数字。看不到命中，先查是不是这种计费方式不支持，再去怀疑自己的请求前缀是否稳定。

## 5. 回复分段

模型在一轮里可能说好几段话：调工具之前说“我先看一下文件”，最后给出结论。界面和后续程序（评测、终端客户端）需要知道哪一段是最终回答。

只按“这次回复有没有工具调用”去猜，会在一种情况下猜错：模型想结束了，但 harness 的检查（比如“编译不过不能结束”）拦下了它，让它接着做。那段“想结束的话”其实只是过程说明。

可靠的做法是由 harness 在协议里标明：和工具调用一起出现的、被拦下的，标成过程说明；真正结束这一轮的，标成最终回答。Codex 的消息就带着这样的阶段标记。

## 自测

1. 429 一定该重试吗？怎么区分？
2. 为什么“输出被截断”不该重试，而“流在中途断开”可以？
3. 流式输出到一半时重试，界面上会出什么问题？怎么处理？
4. 内部只用一种消息格式有什么好处？新接一种协议要写哪几部分？
5. 三种协议里推理内容的回传规则有什么不同？适配层要为此保存什么？
6. 不知道一个模型的窗口时怎么办？一个名字对应多个版本时取哪个？
7. 看不到缓存命中，先查什么？
8. 为什么不能只按“有没有工具调用”判断最终回答？

### 自测答案

1. 不一定。限流的 429 可以退避重试；额度用完也常是 429，要等额度重置，几秒后重试没用。看错误码或说明里的 quota 一类字样，遵守 Retry-After，要求等太久就直接报错。
2. 截断是因为输出到了上限，同样的请求再发一次还会到上限；流断了是传输出了问题，没有收到结束标记，重新请求大概率能拿到完整结果。
3. 已经显示的半段文字会和重试后的完整文字叠在一起，同一句话出现两次。重试前通知界面清掉这次请求已显示的部分。
4. 历史、检查点、日志、界面、压缩、恢复都只认一种格式，不随协议分叉。新协议只写两部分：发请求前把内部格式换成它的请求体；收流时把它的事件拼回内部格式（包括结束原因和用量）。
5. DeepSeek 的 Chat Completions 要求推理内容原样传回；它的 Anthropic 接口不强制；Anthropic 自家模型要求 thinking 块连同签名传回；Responses 只能回传带编号或加密的 reasoning 项。适配层要把签名（或加密内容）和推理文字一起存下来，下次按目标协议放回去。
6. 先查供应商的模型列表接口和官方文档；都没有就留空，用保守的默认值，不要猜。一个名字对应多个版本时取最小的那个，保证不会超。
7. 先查这家供应商、这种计费方式到底支不支持缓存、要不要显式开启；用同样的长前缀连发两次看第二次的用量。确认支持之后，再查自己的请求前缀是否每次都一样。
8. 模型可能想结束却被 harness 的检查拦下，那段话没有工具调用，但不是最终回答。只有 harness 知道这一轮是不是真的结束了，所以应由它在协议里标明。
