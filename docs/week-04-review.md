# Week 4 复盘：编码 harness 的基础

前三周造出了执行循环，让它可恢复、可观测、可评测，并把危险动作交给程序和人把关。第四周换了一个问题：**让它在一个真实仓库里改代码**。为此补了改代码的工具（D23）、让模型知道身在何处的提示词（D24）、决定能不能做的统一权限（D25）、在固定时刻插入外部检查的 hooks（D26），最后用它改这个项目本身（D27）。

## 一次编码改动的一生

第三周跟着一次高风险调用走完全程；这一周跟着一次编码任务。右边是本周自用（D27 的 T2 与修复对话，DeepSeek）里每一步实际发生的事。

```text
用户输入 /self-task T2                                                   
 → 斜杠命令展开成提示词                                       D26   “/self-task 展开为 203 字的提示词”
 → UserPromptSubmit hook：问题里像有密钥就拦下                 D26   每轮都运行，全部通过
 → 系统提示词：规则 + 根目录 AGENTS.md                         D24   一个对话内不变
 → 环境提醒：工作区、bash 里的 /workspace、分支、权限模式        D24   plan → full 换模式时追加“环境变了”
 → 模型返回工具调用
 → PreToolUse hook：生成文件保护（拒绝 / 询问 / 改写）           D26   50 次，全部放行
 → 权限：用户规则 → 模式默认                                   D25   plan 模式下 edit_file 被拒 1 次
 → 高风险规则与人工确认                                        D20   本次没有触发
 → 读过才能改：比对读取时的哈希                                 D23   续聊后报“需要先读”1 次（D27 修）
 → 执行；bash 进沙箱                                          D12   ${PIPESTATUS[0]} 被 systemd-run 吃掉（D27 修）
     /workspace：edit 可写、plan 只读；.git 只读；.env 为空     D25   cd 宿主机路径失败 4 次（D27 修）
 → PostToolUse hook：gofmt 差异交回模型                        D26   45 次，全部通过
 → 下一次请求前追加提醒：子目录指令、文件被外部改过              D24   模型用 python 改了标题，提醒“被改过”，它先重读再改
 → 上下文快满时压缩                                           D4    64K 窗口下压缩后重读，同一文件读 7 次
 → 模型想结束 → Stop hook：有 .go 改动就 go build + go vet      D26   通过；预算耗尽的那两轮没有运行
 → 检查点记结局、用量、读过的文件                               D9    预算耗尽显示成“失败：exit status 1”
 → 人：review diff，沙箱外真实运行验收，合回主仓库               D27   发现 2 处文档事实错误、1 处错误理由
```

这条链里，约束由三类东西执行：

| 谁执行 | 例子 | 能保证什么 |
| --- | --- | --- |
| 提示词（请求） | 环境提醒说“plan 模式只读”；AGENTS.md 的约定 | 大多数时候被遵守，不保证 |
| harness 程序（每次都做） | 权限规则、读过才能改、hooks、沙箱挂载 | 每次调用都检查，模型绕不过 |
| 人（判断） | 批准方案、review、验收 | 方向对不对、文档写得对不对 |

D27 的计划轮里，模型看到了“plan 模式只读”，仍然调用了一次 `edit_file`；挡住它的是权限规则，不是提示词。

## 本周的几条主线

1. **确定性的约束放进 harness，不写进提示词**。gofmt、生成文件不许手改、编译不过不许结束、改之前必须读过、plan 模式不许写，都是程序每次检查。提示词负责让模型“知道”，程序负责让它“做不到”。
2. **安全边界在执行环境，规则只看文本**。权限规则匹配的是参数字符串，`bash` 命令能写成无数种样子；真正保证“plan 模式改不了代码”的是沙箱里工作区挂成只读。hook 也一样：它在宿主机上运行、失败放行，只适合做检查，不适合做唯一的安全边界。
3. **只追加、不改写**。提示词按变化频率分层，运行中的变化追加成提醒。效果有实测数字：本周自用的各轮缓存命中率在 94%–98%。
4. **状态要跟着检查点走**。本周修的 bug 里有一类反复出现：某个状态只在进程内存里，换进程（续聊、续跑）或压缩之后就丢了。读过哪些文件、加载过哪些子目录指令、环境提醒还在不在，都属于这一类。原则是：影响下一步决定的状态，要么写进检查点，要么能从视图里重新推出来。
5. **自用是最好的测试**。D22 留下的自用任务让 harness 改自己的仓库，第一次就暴露了 systemd-run 改写命令这种不跑真实任务永远发现不了的 bug。失败的工具调用要按责任分类，大多数不是模型不行，而是 harness 没给够信息、丢了状态，或者自己有 bug。

## 实测中反复出现的问题

| 现象 | 出现位置 | 原因与现状 |
| --- | --- | --- |
| 跨进程丢状态 | D24 续聊、D27 续聊 | 环境提醒被压缩进摘要后误报“变了”、子目录指令压缩后不再重发、读文件记录续聊后丢失；均已修 |
| 压缩后反复重读 | D27 修复对话 | 64K 窗口装不下跨文件任务，压缩清掉读过的内容，模型再读，直到预算用完；128K 时同一任务没有压缩、正常完成 |
| 第一次压缩丢掉用户任务 | D24 后 | 摘要输入放不下时先删了用户原话，摘要说“没有任务”；已改为先删工具往返与提醒 |
| 预算耗尽 | D27 两次 | 改动已写完，只差总结；Stop hook 不运行，界面显示“失败” |
| 外部工具的意外行为 | D27 | systemd 254 起 `systemd-run` 会替换命令里的 `${…}`；已修 |
| agent 写的文档有事实错误 | D27 三处 | “T2 手工补上”、“未落盘的请求算缺失”、“会成环”；都是人工 review 发现 |
| 方舟 HTTP 403 | 整周 | 验证全部用 DeepSeek |
| 估算的 token 偏少 | 压缩日志 | 按字节估算比真实用量低约 9%（如真实 55633、估算 50443），压缩时机偏晚；D30 换真实分词器 |

共同点：问题都出在**边界**上：进程边界、上下文窗口的边界、预算的边界、harness 与外部工具的边界。正常路径上的功能在各天的验证里都通过了，边界情况要靠真实的长任务才暴露。

## D27 遗留问题的处理建议

> 以下是建议草稿；用户确认后已修前三项中的“结局显示”“默认窗口”（改为 256K）与“域名小写”，并按用户要求去掉了每轮请求次数的默认上限（观测台默认 0 = 不限）。

| 问题 | 建议 | 理由 |
| --- | --- | --- |
| 预算耗尽显示成“失败” | 修：观测台显示协议里的结局（“预算用完 · 40 次请求”） | 改动小、每次都误导；适合当下一个自用任务 |
| 平台默认 64K 窗口 | 修：编码任务默认 128K | 实测 64K 下跨文件任务做不完 |
| plan 模式仍提供写工具 | 不修 | 权限层已经兜底，被拒一次的代价很小，还能观察模型是否守规矩 |
| 批准没有按钮 | 推迟到 D34 | 终端客户端要一起设计审批交互 |
| 预算耗尽时 Stop hook 不运行 | 推迟到 D31 | 长任务接力时由下一个会话或外部流程补检查 |
| 首字延迟不含只回工具调用的请求 | 推迟，D37 评测时再定口径 | 要先想清楚“首字”对工具调用意味着什么 |
| 规则里的域名不转小写 | 修，作为自用任务 | D26 由模型 review 发现，改动一行 |
| T5 检查点格式版本 | 推迟到 D41 或换模型时 | 需要反复权衡兼容策略 |

## 第五周最想补的三件事

> 建议草稿，以你的选择为准。

1. **文件快照与回退（D29）**：D27 里停止一轮不会撤销已经改的文件，下一轮只能从 `git diff` 猜上一轮做了什么。每次写入前快照、按轮撤销，是 H19 这个唯一的“缺”。
2. **长任务接力（D31）**：本周两次预算耗尽、一次因压缩做不完，都说明一个上下文装不下的任务需要进度文件与提交记录，让下一个会话接着做，也让最后的检查不依赖模型自己结束。
3. **真实分词器（D30）**：压缩时机依赖 token 估算，估算偏少 9% 会让压缩来得太晚；窗口一大，误差的绝对值也更大。
