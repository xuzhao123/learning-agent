# Day 32：工具声明与后台命令

## 学习目标与术语

学完能说明：为什么一个 harness 要把“工具是什么性质”集中声明在一处，这些性质分别被谁用到；第三方工具（MCP）自称的性质哪些可以信、哪些不能；长时间运行的命令为什么要做成“后台命令”，它的生命周期怎样和取消、清理对齐。

| 术语 | 通俗解释 |
| --- | --- |
| 工具声明 | 除了名字、描述和参数，再说明这个工具的“性质”：会不会改东西、能不能并行、中断后能不能重做…… |
| 只读 | 调用不改变任何状态，只是看 |
| 并发安全 | 可以和同一批里的其他调用同时执行，互不影响 |
| 可重做（幂等） | 同样的参数再执行一次，结果和副作用都不会多出来 |
| 外发 | 调用的参数会离开本机，发给网站或第三方服务 |
| 破坏性 | 会删除或覆盖东西，做了很难撤回 |
| 后台命令 | 启动后不等它结束，先拿到一个编号，之后再按编号读输出、停止 |

## 1. 为什么要集中声明

一个工具被调用时，harness 要回答好几个问题：

| 问题 | 谁关心 |
| --- | --- |
| 能不能和别的调用同时跑？ | 调度器 |
| 进程中途死掉，续跑时能不能直接重做？ | 恢复逻辑 |
| 成功后算不算读到了用户的私有数据？ | 外发检查（读过私有数据之后，外发要确认） |
| 会不会把参数发到外面？会不会破坏东西？ | 风险确认 |
| 在用户的权限规则里属于哪一类？ | 权限策略 |
| 单次最多跑多久？ | 执行器 |

最初这些答案往往散落在各处：调度器里一份“要串行的工具”名单，恢复逻辑里一份“可以重做”的名单，风险判断里一份“外发工具”名单……新加一个工具，要记得改五六个地方；漏了一处，就出现“新工具被当成可以重做，续跑时把一次付款又做了一遍”这类问题。

集中声明的做法是：每个工具在一处写一行性质，所有关心它的地方都去查这一行。新工具只需要在执行处接上、在声明处写一行。没写的工具取最保守的默认值（不能重做、不算只读）。

Claude Code 的工具接口就是这样：每个工具实现 `isReadOnly`、`isConcurrencySafe` 等方法，调度器据此把一批调用分成“可以并行的只读调用”和“必须依次执行的调用”。

## 2. 第三方工具自称的性质

MCP 让 server 在工具上带标注（annotations）：

| 标注 | 含义 | 规范给的默认值 |
| --- | --- | --- |
| `readOnlyHint` | 不修改环境 | false |
| `destructiveHint` | 可能做破坏性修改 | true |
| `idempotentHint` | 同样参数重复调用没有额外效果 | false |
| `openWorldHint` | 会和外部世界交互 | true |

规范特别说明：这些只是**提示**，客户端不应该凭它们做安全决定，因为 server 可能写错，也可能故意说谎。

所以要分开看用途：

- **用来提高效率的**：自称只读就并行、自称幂等就允许续跑时重做。信错了的代价是可能多执行一次、或者两次调用互相干扰，属于可靠性问题。
- **用来放松安全检查的**：自称只读就不问权限、自称不访问外部就不做外发检查。信错了的代价是数据被发出去、东西被删掉。

常见的取舍是：标注只能**收紧**安全检查（声明了破坏性，就确认），不能**放宽**（自称只读也照样按外发检查）；调度和续跑这类效率决定可以参考标注。

## 3. 调度：只读并行，其余串行

模型一次回复里可能发出好几个调用。全部串行最安全但最慢；全部并行最快，但两个改同一个文件的编辑、两条互相依赖的命令会出错（后一条命令常常要用前一条生成的文件，和在 shell 里写 `a; b` 一样）。

比较稳妥的规则：

```text
一批调用 ──▶ 只读的：同时执行（受并发上限约束）
          └─▶ 其余的：按模型给出的顺序一个接一个执行
```

“只读”来自工具声明。两组之间互不等待：只读调用不会被前面的写操作影响到语义（模型在发出这一批时，本来就没有看到写操作的结果）。

## 4. 允许列表放在最前面

工具列表不只是给模型看的菜单，也是执行器的允许列表：模型编出来一个不在列表里的工具名、旧记录里带着已经关掉的工具，都不能执行。

这个检查要放在**所有其他步骤之前**：如果排在 hook、权限规则、人工确认之后，一个本来就不允许的调用会先触发“请确认”，人批准了它仍然被拒绝——白白打扰了一次人。

## 5. 后台命令

一次性命令有时限（比如 30 秒）：时限一到整条命令被终止。可是有些命令本来就要跑很久，或者根本不会自己结束：

- 起一个开发服务器，再用另一条命令访问它；
- 跑一个十分钟的构建，同时做别的事；
- 监视日志、等某个文件出现。

后台命令把“启动”和“取结果”分开：

```text
启动(命令) ──▶ job_id，立刻返回
读输出(job_id, 最多等几秒) ──▶ 上次之后的新输出 + 结束没有、退出码
停止(job_id) ──▶ 剩下的输出
```

设计时要想清楚四件事：

1. **增量读**：每次只交回上次之后的新输出，不重复；输出无限增长时要有上限，丢掉最早的并如实说明。
2. **等待**：让“读输出”可以等几秒（命令结束就提前返回），否则模型只能频繁轮询，白白消耗请求。
3. **隔离一致**：后台命令和前台命令在同样的沙箱、同样的资源限制里运行，不能因为“在后台”就绕开限制。
4. **生命周期**：后台命令活多久？最简单可靠的答案是“活到这一轮结束”，结束时连同它起的所有进程一起终止（用 cgroup 这类“整组结束”的办法，而不是只杀一个进程号）。要跨轮保留，就得把它的状态写进可恢复的记录里，并处理“上一个进程死了，后台命令还在不在”的问题。

Claude Code 的 Bash 工具有 `run_in_background` 参数，配合读输出、结束后台命令的工具使用；Codex 把命令执行做成带会话编号的长期进程，可以继续写入输入、读取输出。

## 自测

1. 工具的哪几种性质会被 harness 的不同部分用到？各被谁用？
2. 散落在各处的名单会造成什么问题？集中声明后，没声明的工具应该取什么默认值？
3. MCP server 自称工具只读，可以据此做哪些决定，不能做哪些？为什么？
4. 为什么“只读并行、其余串行”比“全部并行”或“全部串行”更合适？
5. 允许列表检查为什么要放在 hook、权限和确认之前？
6. 后台命令的“读输出”为什么要支持等待？输出上限超了怎么办？
7. 后台命令只活到这一轮结束，有什么好处和代价？

### 自测答案

1. 只读、并发安全被调度器用；可重做被续跑恢复用；私有来源、外发、破坏性被风险确认用；权限类别被权限策略用；时限被执行器用。
2. 新加工具时容易漏改其中一处，出现“没声明可重做却被重做”“外发工具没被检查”之类的问题。默认值取最保守的：不能重做、不算只读（因此串行）、按“会写”的类别要权限。
3. 可以用来做效率决定：并行执行、续跑时重做。不能用来放宽安全检查：不问权限、跳过外发确认。标注是 server 自己说的，可能写错或说谎；效率决定信错了是可靠性问题，安全决定信错了会泄露或破坏数据。
4. 全部串行太慢，只读调用之间本来互不影响；全部并行会让互相依赖的写操作（连续编辑、前后两条命令）乱序。按只读与否分开，两头的好处都拿到。
5. 菜单外的调用无论如何都会被拒绝；排在后面会先打扰人确认，人批准了仍被拒绝，浪费一次人的注意力，还让人误以为批准有用。
6. 不支持等待，模型只能不停地轮询，每次都是一次模型请求；等几秒、结束就返回，用一次请求就能拿到一大段输出。超过上限时丢掉最早的输出，并在结果里说明丢了多少，不让模型以为输出是完整的。
7. 好处：不用持久化后台进程的状态，进程退出时一次清理干净，不会留下没人管的进程。代价：下一轮（新进程）不能接着读上一轮的后台命令，起的服务也随这一轮结束而停止。
