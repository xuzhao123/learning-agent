## 2. 第一个任务 T5：两版方案后暂停

[T5](../day-22/day-22-lab.md#3-自用任务集) 是“检查点加格式版本号”。`/self-task T5`，plan 模式：

| 轮次 | 请求 | 结果 |
| --- | --- | --- |
| 第 1 版方案 | 17 | 整数版本号，读到更新的版本一律拒绝 |
| 打回后第 2 版 | 13 | 只在写回检查点的地方拒绝更新的版本，只读的地方照读并提示一次；漏了“分叉也会写新检查点” |

打回之前先调研了社区做法：Codex 的会话记录（rollout JSONL）没有格式版本号，读取时宽松处理（坏行跳过并计数、字段有默认值、未知的枚举值映射为 `Unknown`）；SQLite 状态用编号迁移，允许旧程序打开新程序迁移过的库。Claude Code 的会话记录每行带写入它的 CLI 版本。由此看出本项目的真正风险：Go 的 `json.Unmarshal` 会丢掉不认识的字段，旧程序续跑新检查点再写回，数据就丢了。第 2 版方案据此只在“写回”处拦。

T5 需要反复权衡兼容策略，用户判断对当前模型偏难，改做更直接的 T2。T5 留在任务集里，以后换模型时可以拿它对照。

## 3. 第二个任务 T2：metrics 汇总首字延迟

| 轮次 | 模式 | 请求 | tokens（缓存命中） | 结局 |
| --- | --- | --- | --- | --- |
| 方案 | plan | 24 | 71 万（95%） | 正常结束 |
| 批准后实施 | edit | 40 | 106 万（94%） | 预算耗尽 |
| 改两处文档错误 | edit | 9 | 32 万（98%） | 正常结束 |

方案：只改 [metrics.go](../../internal/metrics/metrics.go)，新增 `firstTokens`，从任务的 trace 里取 chat span 的 `agent.response.first_token_ms`，排序后复用已有的最近秩法；没有这个属性的请求单列为缺失，不当作 0。方案阶段已经注意到 JSON 读回来的数字是 `float64`。

```go
ms, ok := span.Attributes["agent.response.first_token_ms"].(float64)
if !ok {
	missing++ // 有 chat span 但没有首字延迟：只回了工具调用，或请求出错
	continue
}
```

计划轮里的两个现象：

- 它知道自己在 plan 模式，仍然调用了一次 `edit_file`，被权限层拒绝；拒绝后没有绕过，而是在回答里说明需要 `edit` 权限。
- 它把仓库复制到 `/scratch`，在副本里实现、编造 trace 数据、跑出 P50/P95 与手算一致，并说明“这份数据是造的，不算验收证据”。

实施轮用满了 40 次请求：最后一次请求刚跑完 gofmt、vet、build，没来得及写总结；Stop hook 只在模型自己结束时运行，这次没有机会运行。观测台把它显示成“失败：exit status 1”，因为预算耗尽时 agent 进程以非零码退出。

人工 review 发现两处文档问题，打回后修正：

- 在 D22 的实践里写了“T2 例外：按方案手工补上”，与事实不符，T2 是 harness 做的；
- 说“崩溃时没写进 trace 的请求计入缺失”。实际上没写进去的请求在 trace 里不存在，既不算样本也不算缺失，只让样本偏少。

验收：在沙箱外用改动后的代码对这次对话的两轮跑 `go run . metrics -prefix <检查点ID>`，与协议事件（modelCall 完成事件的 `first_token_ms`）和 trace 原始记录分别计算的 P50/P95 对比：

| 轮次 | metrics 输出 | 协议事件 | trace 记录 |
| --- | --- | --- | --- |
| 方案（24 次请求） | 1310 / 2175 ms，样本 18，缺失 6 | 18 条，1310 / 2175 | 18 条，缺失 6 |
| 实施（40 次请求） | 1505 / 2523 ms，样本 15，缺失 25 | 15 条，1505 / 2523 | 15 条，缺失 25 |

样本加缺失等于请求数。缺失的全部是“只回工具调用、没有正文和推理”的回复，约占主任务请求的一半；这是 B1 的口径（首字以第一段正文或推理为准），已记入待办。

## 4. 失败的工具调用：大多是 harness 的问题

T2 两轮共 66 次工具调用，状态不是 ok 的 5 次，另有 1 次结果被悄悄改坏。按笔记第 5 节分类：

| 现象 | 类别 | 原因 |
| --- | --- | --- |
| bash 里 `cd /home/…/t2` 失败（两轮各一次） | harness 没给够信息 | 环境提醒只写了宿主机路径，没说 bash 里工作区在 `/workspace` |
| `edit_file` 报“需要先用 read_file 读过它” | harness 丢了状态 | “读过哪些文件”只在进程内存里，续聊是新进程 |
| `echo "${PIPESTATUS[0]}"` 输出为空，只好重跑 | harness 的 bug | systemd 254 起，`systemd-run` 会先把命令行里的 `${…}` 按它自己的环境替换：`x=hi; echo ${x}` 输出空 |
| plan 模式下 `edit_file` 被拒 | 规则按设计拦截 | — |
| `old_string` 没找到 | 模型正常试错 | 一次替换多行，换行没对上；随后用 `cat -A` 看清后改好 |

页面上 ✕ 显得更多，是因为“绕路”统计还把 bash 非零退出、空结果和重复调用算进去了。

## 5. 让 harness 修自己

前三类交给 harness 自己修。新开对话，工作区是新的 clone，`edit` 模式，提示里写清三处现象、修法与约束（不写测试、沙箱外由人验证）。

| 对话 | 上下文窗口 | 请求 | tokens | 结局 |
| --- | --- | --- | --- | --- |
| 第一次 | 64K | 60 | 194 万 | 预算耗尽：压缩 2 次，`workspace.go` 读了 7 次，只完成第 1、2 处 |
| 第二次 | 128K | 46 | 212 万 | 正常结束：第 3 处与文档，没有压缩 |

两点观察：

- **窗口决定任务能否做完。** 64K 时跨文件任务反复压缩，压缩后读过的内容丢了又重读，直到预算用完。观测台的设置在对话开始时拍成快照，调大窗口只对新对话生效，所以第二次是新开的对话。
- **停下不等于回滚。** 第一次对话的续聊轮在启动后被停止时，已经改了 `checkpoint.go`；第二次对话从 `git diff` 看到并接着做。文件回退是 D29 的内容。

第二次对话里仍有 2 次失败，正是它在修的问题：它运行在修复之前的 harness 上。

改动：

| 修复 | 代码 | 做法 |
| --- | --- | --- |
| `${…}` 被吃掉 | [sandbox.go](../../internal/sandbox/sandbox.go) | 带 `--expand-environment=no` 探测一次 systemd-run，认就加；旧版不认这个参数，本来也不替换 |
| bash 路径 | [context.go](../../internal/workspace/context.go)、[main.go](../../main.go) | `workspace.BashMount` 由 main 在开了 bash 且工作区挂进沙箱时设为 `/workspace`，环境提醒多一行 |
| 读文件记录跨续聊 | [workspace.go](../../internal/workspace/workspace.go)、[checkpoint.go](../../internal/agent/checkpoint.go)、[react.go](../../internal/agent/react.go) | `Seen()` 返回副本写进检查点；开局时续跑用自己的、续聊用上一轮的；编辑前仍比对哈希。子 agent 与回放分叉从空记录开始 |

人工 review 改了两处：环境提醒那段的注释和 D24 实践里写着“workspace 依赖 sandbox 会成环”，`go list` 显示 sandbox 并不依赖 workspace，改成真正的理由（文件工具不该为了 bash 的挂载点依赖沙箱包）；D24 实践插入新节后，wiki 里指向原第 2 节的链接要改。

验收（沙箱外，DeepSeek，改动后的代码，临时 clone 作工作区）：

| 检查 | 结果 |
| --- | --- |
| bash 运行 `x=hi; echo "x=${x}"; true \| true; echo "pipe=${PIPESTATUS[0]}"` | 输出 `x=hi`、`pipe=0` |
| 第一条环境提醒 | 有“bash 里的工作区：/workspace（…文件工具仍写相对路径）” |
| 第 1 轮读 README.md，第 2 轮（新进程续聊）不重读直接改 | 改动成功，检查点里有 `seen` |
| 两轮之间在外部改了文件，第 3 轮让它直接改 | 恢复的记录触发 D24 的“被改过”提醒，模型先重读再改 |

子 agent 与回放分叉从空记录开始只做了代码阅读（构造检查点时不带这个字段）；旧版 systemd 的降级路径本机无法验证。

## 6. 当前没有覆盖的范围

- **批准没有专门的入口**：靠人手动切权限（D34 做按钮）。
- **预算耗尽显示成“失败”**：观测台只看退出码，没有显示协议里的结局。
- **最后一道检查依赖模型自己结束**：预算耗尽时 Stop hook 不运行。
- **首字延迟只覆盖带正文或推理的回复**：只回工具调用的请求算缺失。
- **设置快照**：续聊不能调窗口、预算；平台默认 64K 对编码任务偏小。
- **计划模式仍提供写工具**：模型会试一次再被拒；要不要在 plan 模式下隐藏写工具，D28 复盘时决定。
- **T5 未完成**：方案 v2 留在 `test` 账号的对话里。
