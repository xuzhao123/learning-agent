# Day 27：规划与第一次自用

## 学习目标与术语

学完能说明：agent 里的“规划”其实在解决哪三个不同的问题；上下文内的 todo 清单为什么曾经有效、现在为什么要用数据决定去留；计划模式怎样让人在动手之前对齐方案，限制为什么要放在权限层而不是提示词里；长任务的进度为什么要放在上下文之外；第一次让 harness 修自己的仓库时，该观察什么、怎样给失败分类。

| 术语 | 通俗解释 |
| --- | --- |
| todo 清单 | 模型自己维护的一张待办列表，每完成一步就更新，列表内容留在上下文里 |
| 计划模式 | 一种权限模式：只能读和调查，不能改动；产出是一份方案，等人确认 |
| 批准 | 人看过方案后，把下一轮切到可以改动的模式，让 agent 按方案实施 |
| 进度外置 | 把“做到哪了”写进文件和版本历史，而不是只留在模型的上下文里 |
| 自用（dogfooding） | 用自己做的 harness 去改真实仓库，在真实任务里发现问题 |
| 预算耗尽 | 一轮的模型请求次数用完，模型还没自己结束 |

## 1. “规划”其实是三个问题

说“agent 要会规划”时，常常把三件事混在一起：

| 问题 | 发生在哪 | 典型做法 |
| --- | --- | --- |
| 一个上下文里不迷路：几十步之后还记得目标、知道下一步 | 单次会话内 | todo 清单、反复复述目标 |
| 跨会话接力：上下文用完或换了会话，下一次从哪接着做 | 会话之间 | 进度文件 + 版本历史 |
| 和人对齐：动手之前确认方向对不对 | 人与 agent 之间 | 计划模式 + 一次确认 |

三者的失败方式不同：第一个是模型走着走着忘了要干什么；第二个是新会话把做过的事重做一遍，或者以为已经做完；第三个是方向从一开始就错，做得越多浪费越大。分开看，才知道某个机制在补哪个洞。

## 2. 上下文内的 todo 清单

早期模型在长任务里容易“走丢”：目标写在上下文开头，几十次工具调用之后，模型的注意力被最近的大段工具输出占满。todo 清单的做法是让模型把计划写成列表，每做完一步就重写一遍。效果有两层：

- **复述**：每次重写都把完整目标放到上下文的末尾，离下一次决策最近（Manus 把这叫作“通过复述操控注意力”）。
- **外显**：用户和 harness 都能看到计划和进度，偏了可以及时纠正。

代价也很明确：每次更新都要占一次模型调用和一段上下文；模型可能“为了更新清单而更新清单”。

模型能力提升之后，第一层价值在下降：强模型在一个上下文里能自己安排几十步，不靠 harness 催它复述也很少忘记目标。这时 todo 清单还值不值得，不能凭感觉判断，要做**消融**：同一批任务、同一个模型，有清单和没清单各跑一遍，比较完成率、步数和成本。“社区都有”不是理由，“我觉得有用”也不是。

## 3. 计划模式：在动手之前对齐

计划模式把一次任务拆成两段：

```text
plan 模式：只读调查 → 交出方案 → 停下
                          ↓
            人：打回（附意见，再出一版） 或 批准
                          ↓
edit 模式：带着前面调查的全部上下文，按方案实施
```

几个要点：

- **同一个对话、同一个 agent**。计划模式不是另起一个“规划器”，只是这几轮的权限不同。批准后接着同一段上下文实施，调查过的代码不用重读。
- **限制放在权限层，不只写在提示词里**。告诉模型“你在计划模式”是请求；权限规则拒绝写工具、执行环境里工作区只读，才是保证。实际运行中常见的情况是：模型知道自己在计划模式，仍然顺手调用一次写工具。权限层拒绝它，并在结果里告诉它“不要绕过，在回答里说明需要什么权限”。
- **打回比批准更常用**。第一版方案常有遗漏，或在一个取舍上选错。打回时附上具体意见（例如“先查一下同类项目怎么做”），模型在保留上下文的基础上重出，比从头再来便宜得多。
- **批准是人的决定**。harness 可以提供“批准”按钮自动切换模式（Claude Code 让模型调用一个提交计划的工具，界面弹出计划等人确认），也可以由人手动把下一轮的权限切到可编辑。机制不同，责任一样：方向对不对由人判断。

计划模式下模型还可能“把活提前干了”：在临时目录里复制一份仓库，先实现、编数据、自测一遍。这能提高方案质量，但花的是计划阶段的预算，造的数据也不能当验收证据。是否允许，要看任务大小和预算。

## 4. 进度放在上下文之外

上下文会被压缩、会话会结束，所以长任务的“做到哪了”不能只留在模型脑子里。Anthropic 介绍长时间运行的编码 agent 时给出的做法是：

- 一个**进度文件**，写已完成的、正在做的、下一步；每个会话结束前更新；
- **版本历史**当作可靠的事实来源：每完成一个小目标就提交，新会话先读进度文件和最近的提交记录再动手；
- 一份**功能清单**，逐项标记是否通过验证，防止“看起来做完了”。

这和 todo 清单的区别在于：todo 清单在上下文里，帮模型这一次不迷路；进度文件在磁盘上，帮下一个会话接上。前者随模型变强价值下降，后者只要上下文有限就一直需要。[资料](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 5. 第一次自用：观察什么

harness 的问题只在真实任务里暴露。第一次自用的选题要满足：改动小、能用编译和一次真实运行判定对错、来自真实待办。太简单（改一行描述）看不出问题，太难（需要反复权衡兼容策略）又会让失败分不清是模型的问题还是任务的问题。

跑完之后看四件事：

**1. 请求花在哪。** 一轮几十次请求里，多少是读代码、多少是改、多少是验证、多少是重复读。重复读同一个文件往往说明上下文被压缩过、读到的内容丢了。

**2. 失败的工具调用按原因分类。** 不要只看“失败了几次”，要问每次失败该由谁负责：

| 类别 | 例子 | 该改哪里 |
| --- | --- | --- |
| harness 没给够信息 | 环境说明只给了宿主机路径，模型在隔离环境里用它失败 | 环境提醒 |
| harness 自己的状态丢了 | 换进程续聊后，忘了上一轮读过哪些文件 | 状态随检查点保存 |
| harness 的 bug | 命令在交给 shell 之前被外层工具改写 | 修 bug |
| 规则按设计拦截 | 计划模式下尝试写文件 | 不用改，或在计划模式下不提供写工具 |
| 模型的正常试错 | 一次替换多行，换行没对上 | 不用改 |

前三类是 harness 的问题，修好之后每个任务都受益。只有最后一类才真正是“模型不行”。

**3. 是否在预算内自己结束。** 预算耗尽不等于做错：改动可能已经写完、只是没来得及总结。界面要能区分“做砸了”和“没做完”。另外，靠“模型自己结束”触发的检查（例如编译不过就不许结束）在预算耗尽时不会运行，最后的检查要由人或外部流程补上。

**4. 上下文窗口够不够。** 跨多个文件的任务，窗口偏小时会反复压缩，压缩后又重读，形成循环，直到预算用完。调大窗口单次请求更贵，但总步数和失败都可能下降。窗口是按任务选的，不是越小越省。

最后一条经验：agent 写的文档同样要审。它可能写出与事实不符的过程描述，或给一个正确的设计配上错误的理由。代码有编译和运行把关，文档只能靠人读。

## 自测

**“规划”包含哪三个问题？各自失败时是什么样子？**

一个上下文里不迷路（走着走着忘了目标）、跨会话接力（新会话重做或误以为做完）、与人对齐（方向一开始就错）。

**todo 清单为什么曾经有效？现在怎样决定要不要？**

它让模型反复把完整目标写到上下文末尾，抵抗长上下文里的遗忘，同时让进度可见。模型变强后复述的价值下降，要用同一批任务做有、无清单的消融，比较完成率、步数和成本再决定。

**计划模式的限制为什么不能只写在提示词里？**

提示词是请求，模型仍可能调用写工具。只有权限规则拒绝写工具、执行环境里工作区只读，才能保证计划阶段不改动仓库。

**打回方案时，为什么在同一个对话里续聊，而不是重新开始？**

同一个对话保留了前面调查的全部上下文，模型只需按意见修改方案；重新开始要把代码再读一遍，花费更多也可能丢掉已经确认过的事实。

**进度文件和 todo 清单有什么区别？**

todo 清单在上下文里，帮模型这一次不迷路；进度文件在磁盘上、配合版本历史，帮下一个会话接上。上下文有限，后者就一直需要。

**一轮里有 5 次失败的工具调用，怎样判断是不是模型的问题？**

逐次按原因分类：harness 没给够信息、harness 自己丢了状态、harness 的 bug、规则按设计拦截、模型的正常试错。前三类该改 harness，只有最后一类算模型自身。

**一轮因为预算耗尽结束，能说任务失败了吗？**

不能直接这么说。改动可能已经完成，只是没写总结；要看实际产出。同时要注意，靠模型自己结束才触发的检查没有运行，需要另外补上验证。
