# 模型路由：一个 agent 接多家模型

## 学习目标

读完本文，应能回答以下问题：

1. 什么是模型路由？它要解决哪几类问题？
2. 几家供应商都说“兼容 OpenAI 接口”，接入时还会在哪些地方不一样？协议本身不同（Chat Completions 与 Responses）时怎么接？
3. 常见的路由策略有哪些？各自的依据是什么？
4. 为什么一段对话中途换模型要格外小心？
5. 多供应商时，密钥与配置应该怎样管理？

## 1. 是什么，为什么需要

模型路由是 agent 里决定“这一次请求发给哪个模型”的那一层：

```text
agent 循环 ──请求──▶ 路由层 ──▶ 供应商 A（模型 a1、a2）
                           └─▶ 供应商 B（模型 b1）
```

需要它的原因通常有四个：

- **能力**：不同模型擅长的事不同：长上下文、代码、多模态、推理深度；
- **成本与延迟**：简单的任务（分类、摘要、改写）用小模型，便宜、快；难的任务才用大模型；
- **可用性**：一家限流（HTTP 429）、宕机或欠费时，换一家继续；
- **对比与评测**：同一组任务换几个模型跑，用数据决定用哪个。

路由层把“模型是谁”从 agent 循环里拿出来：循环只说“我要一次带工具的对话补全”，路由层决定地址、模型名和密钥。

## 2. “兼容”之下的差异

很多供应商提供 OpenAI 兼容的 Chat Completions 接口：同样的 `messages`、`tools`、`tool_calls`、`usage`。这让切换供应商在大部分情况下只需换三样东西：**地址、模型名、密钥**。但细节上常有差异，接入时要逐项核对：

| 方面 | 常见差异 |
| --- | --- |
| 参数支持 | 推理强度的取值不同（有的只有 low/high，有的有 minimal、max）；不认识的参数可能被忽略，也可能报 400 |
| 推理内容 | 有的模型返回 `reasoning_content`（思考过程）；有的要求下一轮**原样传回**，否则报错；有的要求**不能**传回；有的返回加密的推理内容，只能原样回传 |
| 工具调用 | 是否支持并行调用、`tool_choice` 的取值、参数是否严格按 schema |
| 用量字段 | 缓存命中的 token 放在不同字段里，有的有多个字段 |
| 错误格式 | 上下文过长、限流、余额不足的错误码和文字各不相同 |
| 上下文窗口与输出上限 | 从几万到上百万 token，差别很大 |

所以“兼容”只是起点：一个可靠的路由层要知道每家的这些差异，或者至少在接入时用真实请求验证一遍。

### 2.1 协议本身不同：Chat Completions 与 Responses

有的服务根本不说 Chat Completions，而是 OpenAI 后来推出的 Responses 接口（Codex 用的就是它）。两者表达的是同一件事，结构却不同：

| 方面 | Chat Completions | Responses |
| --- | --- | --- |
| 系统提示词 | `messages` 里的 `system` 消息 | 单独的 `instructions` 字段 |
| 对话历史 | `messages`：每条有 `role` 和 `content` | `input`：一串**项**（item），消息只是其中一种 |
| 工具调用 | assistant 消息里的 `tool_calls` 数组 | 每个调用是独立的 `function_call` 项，带 `call_id` |
| 工具结果 | `role: tool` 的消息，用 `tool_call_id` 配对 | `function_call_output` 项，用 `call_id` 配对 |
| 工具定义 | `{type, function: {name, parameters}}` | 摊平成 `{type, name, parameters}` |
| 推理 | 各家自定义字段（如 `reasoning_content`） | `reasoning` 项：摘要文字，或只能原样回传的加密内容 |
| 流式 | 一种 chunk，靠 `delta` 里有什么区分 | 带 `type` 的事件：`response.output_text.delta`、`response.completed` 等 |
| 状态 | 无状态，每次发完整历史 | 可以由服务端保存（`store`、`previous_response_id`），也可以关掉、照旧发完整历史 |

接入这类服务，常见做法是**内部只保留一种消息格式，只在发出和收回的边上转换**（适配器）：历史、检查点、日志、界面都按内部格式写，换供应商不牵动它们。转换时要注意三点：

1. **配对关系不能丢**：一条带两个工具调用的 assistant 消息，要拆成正文和两个 `function_call` 项，结果再按 `call_id` 对回去；
2. **以最终事件为准**：流式里的片段只用于显示，完整的回答、工具调用和用量取自最后的完成事件，流在中途断了就当作没完成；
3. **语义要对齐**：结束原因、用量字段名、错误格式都换成内部的同一套，截断检查、计费统计这些下游逻辑才能不分协议。

适配器的代价是日志里存的是转换前的内部格式，不是线上原文；需要排查协议问题时，要能另外看到原始请求。

## 3. 路由策略

| 策略 | 依据 | 例子 |
| --- | --- | --- |
| 手动选择 | 用户或配置 | 界面上的模型下拉框；命令行参数 |
| 按用途 | 请求的类型 | 主任务用大模型，摘要、记忆的背景生成、重排用小模型 |
| 按难度 | 任务的预估难度 | 先用一个便宜的分类器判断难易，再决定发给谁 |
| 级联 | 先便宜后昂贵 | 先用小模型回答，置信度低或校验失败再交给大模型 |
| 故障转移 | 可用性 | 主供应商 429、5xx 或超时时，退避后改发备用供应商 |
| 负载与成本 | 实时配额、价格 | 按剩余配额或单价在几家之间分配 |

按难度和级联的路由需要评测数据支撑：要知道小模型在哪类任务上会出错，否则省下的成本会以错误答案的形式还回来。研究上的例子有 FrugalGPT（级联）和 RouteLLM（训练一个路由器，在强弱两个模型之间选择）。

故障转移要区分错误：429、5xx、超时可以换一家重试；400（参数错）、401（密钥错）换一家也没用，或者说明配置有问题。这和 Day 8 的错误分类是同一回事。

## 4. 一段对话中途换模型

在一段已经进行了几轮的对话中途换模型，问题比看上去多：

- **推理内容不通用**：A 模型的 `reasoning_content` 或加密推理块，B 模型看不懂，有的还会拒绝接收；去掉它们，又可能违反 A 模型“必须传回”的要求，以后也换不回来；
- **缓存失效**：提示词缓存按供应商、模型分别计算，换模型后前缀要重新计费；
- **行为不一致**：两个模型对同一段历史的理解和风格不同，用户会看到前后矛盾。

因此常见的做法是**一段对话固定一个模型**；要换就开一段新对话，或者先把历史压缩成一份摘要，再用新模型继续。按用途路由（主任务与摘要用不同模型）不受这个限制，因为辅助请求不写回主对话的推理内容。

## 5. 密钥与配置

- 每家一个独立的密钥变量，只放在环境变量或本地私有配置里，不进代码、日志、文档；
- 请求日志和观测系统可以记录“发给了哪家、哪个模型”，但不记录密钥；
- 密钥一旦出现在聊天记录、截图、提交历史里，就应当视为已泄露，到供应商后台作废并重新生成；
- 欠费、额度用完也是一种故障（通常是 402 或 403），要和限流区分，单纯重试不会好。

## 6. 自测

**1. 两家都兼容 OpenAI 接口，切换时最少要换哪三样？还要核对什么？**
地址、模型名、密钥。还要核对参数取值（如推理强度）、推理内容是否需要回传、工具调用的支持程度、用量与错误字段。

**2. 主任务用大模型、上下文摘要用小模型，属于哪种路由？有什么好处？**
按用途路由。摘要不需要最强的模型，用小模型可以降低成本和延迟，而且摘要请求不会把小模型的推理内容写回主对话。

**2.1 一个服务只提供 Responses 接口，而 agent 内部的历史是 Chat Completions 的消息格式。怎样接入，又不让检查点、日志和界面跟着改？**
在发出与收回的边上做适配：发请求前把消息换成 Responses 的项（system 变 `instructions`，`tool_calls` 拆成 `function_call` 项，工具结果变 `function_call_output`）；收流时按事件类型拼回内部格式，最终结果以完成事件为准，结束原因和用量换成内部的字段。内部格式不变，下游就都不用改。

**3. 为什么主供应商返回 401 时不应该自动切到备用供应商重试？**
401 说明密钥配置有问题，换一家掩盖了配置错误；应当报错让人修复。只有 429、5xx、超时这类暂时性故障才适合故障转移。

**4. 一段用 A 模型聊了三轮的对话，第四轮改用 B 模型，可能出什么问题？**
B 可能拒绝或看不懂 A 的推理内容；去掉推理内容又可能违反 A 的要求；提示词缓存失效；回答风格和结论可能与前几轮不一致。
