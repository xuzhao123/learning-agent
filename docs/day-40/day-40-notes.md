# Day 40：只追加的会话记录

## 学习目标与术语

学完能说明：为什么 agent 除了检查点，还要有一份只追加的会话记录；两者是什么关系；会话记录里记什么、不记什么；它怎样让界面在“agent 已经结束、界面才回来”的情况下仍能补齐过程。

| 术语 | 通俗解释 |
| --- | --- |
| 检查点 | 某个时刻的状态快照：上下文、预算、私有来源……用来续跑 |
| 会话记录（journal） | 按发生顺序一条条追加的事件：开始了一轮、调用了什么工具、结果如何、结束了没有；只追加，不改写 |
| 序号 | 会话记录里每条事件的编号，在一段对话里一直往后编 |
| 快照对应的位置 | 检查点写下时，会话记录写到了第几条 |

## 1. 快照与记录

只有快照时：能续跑，但看不到“中间发生过什么”。快照每次整份覆盖，上一份是什么样已经没了；过程只能靠界面自己存——界面不在时发生的事就丢了。

只追加的记录正好补上：

| | 快照（检查点） | 记录（journal） |
| --- | --- | --- |
| 回答的问题 | 现在是什么状态，从哪里接着做 | 按什么顺序发生了什么 |
| 写法 | 每次整份原子替换 | 只往后追加一条 |
| 大小 | 随上下文大小 | 随事件数增长 |
| 谁用 | agent 续跑、续聊 | 界面补读、事后审查、回放 |

两者用一个序号连起来：检查点里记下“写这份快照时，记录写到了第 N 条”。于是“第 N 条之前的事”都已经反映在这份快照里，之后的事要从记录里看。

## 2. 记什么

记 agent 发给界面的那些结构化事件：一轮开始与结束、用户消息、每次模型调用的开始与用量、每次工具调用的参数与结果、审批请求、子 agent 的进展。不记：

- 流式的增量片段（太碎，完整内容已经在“完成”事件里）；
- 给人看的终端日志行（不是结构化事件）；
- 对请求的答复（由发请求的一方记）。

## 3. 界面怎样用它补读

界面断开时，agent 会把发出的事件留在内存里，界面回来后按序号补发（B0 的接管）。但如果界面回来时 agent 已经结束——进程被杀、机器重启——内存里的那份就没了。这时：

1. 界面从自己的存档里知道已经收到第几条；
2. 打开这段对话的会话记录，找到这一轮里序号更大的事件；
3. 补进存档，再按记录里最后的状态写下这一轮的结局；没有结局的，以检查点为准。

## 自测

1. 检查点和会话记录各回答什么问题？
2. 为什么会话记录要只追加？
3. 检查点里记“写到了第 N 条”有什么用？
4. 界面回来时 agent 已经结束，没有会话记录会怎样？有了呢？

### 自测答案

1. 检查点：现在的状态、从哪里接着做；会话记录：按什么顺序发生了什么。
2. 追加不会破坏已经写下的内容，崩溃时最多丢最后一条；它是“发生过什么”的原始依据，不能被后来的状态覆盖。
3. 把快照和过程对上：第 N 条之前的事已经反映在快照里，之后的看记录。
4. 没有：界面不在时发生的事件丢失，只能从检查点知道最后的状态，不知道过程。有：按序号把缺的事件补回存档，过程完整，结局也能从记录里读到。
