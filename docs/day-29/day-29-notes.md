# Day 29：文件快照与回退

## 学习目标与术语

学完能说明：agent 改坏了文件，为什么光靠 git 还不够；快照在什么时候拍、存什么、为什么“写入之前”拍；按轮撤销时要怎样合并多次改动、怎样发现别人也改过；为什么默认把文件和对话一起退回；以及逐文件快照和整个工作树快照各自覆盖不到哪些改动。

| 术语 | 通俗解释 |
| --- | --- |
| 文件快照 | 改一个文件之前，先把它当时的内容存一份 |
| 轮（turn） | 用户发一次问题、agent 做完这件事的整个过程；撤销以轮为单位 |
| 回退（rewind） | 把文件和/或对话放回某一轮开始之前的样子 |
| 写前快照 | 先存好“改之前”，再真正写文件；顺序反过来，崩溃时就会出现改了却没法撤销的文件 |
| 内容寻址 | 按内容的哈希命名存储的文件，同样的内容只存一份 |
| 冲突 | 文件在 agent 最后一次写入之后又被别人改过；直接恢复会覆盖那些改动 |
| 对话与文件对齐 | 模型看到的历史和磁盘上的文件属于同一个时刻 |

## 1. 有 git 为什么还要文件回退

git 记录的是人决定提交的版本，agent 的改动大多发生在两次提交之间：

- **没提交的改动混在一起**。用户自己改了一半的文件、agent 这一轮的改动、agent 上一轮的改动都在同一个工作区里。`git checkout` 会把用户的那一半也冲掉。
- **粒度不对**。用户想要的是“撤销刚才那一轮”，不是“回到上一次提交”。一轮里可能改了五个文件，其中三个上一轮也改过。
- **对话不会跟着退**。用 git 把文件退回去之后，模型的上下文里还记着“我已经把 X 改成了 Y”，接着聊时它会基于一份不存在的代码继续工作。

所以编码 harness 一般自带一层轻量的“会话级”回退：只管这次会话里 agent 自己做的改动，按轮撤销，和对话的历史一起管理。它不代替 git，长期的版本历史仍然交给 git。

## 2. 退什么：对话、文件，还是两者

一次回退可以有三种做法：

| 做法 | 结果 | 适合的情况 |
| --- | --- | --- |
| 只退对话 | 模型忘掉后面几轮，文件保持现在的样子 | 改动是对的，只是对话跑偏了、想换个问法 |
| 只退文件 | 文件回到之前，模型仍记得后面几轮 | 想让模型知道“刚才那条路走不通”，再换一种改法 |
| 两者一起退 | 回到那一轮开始前的完整状态 | 整条思路都错了，从那里重来 |

Claude Code 的 `/rewind` 菜单把这三种都列出来让人选。[资料](https://code.claude.com/docs/en/checkpointing)

只退其中一边，会让模型的认识和实际文件对不上。只退文件时，模型以为自己改过的东西还在；只退对话时，模型会对着一份它没见过的代码继续工作。两种情况下，Day 23 的读后才写都能在**改文件的那一刻**拦下来：账本里记的哈希和磁盘上的内容对不上，要求重新读。但它只管写入：在动手改之前，模型的回答和计划已经建立在错误的认识上；只退对话时，被撤销那几轮新建的文件账本里没有记录，模型根本不知道它们存在。

因此一个简单而安全的默认是**两者一起退**：撤销某一轮时，文件放回那一轮开始之前，对话也接回它的上一轮，模型之后看到的历史与磁盘上的文件是同一个时刻的。

## 3. 快照：什么时候拍、存什么

### 写入之前拍

快照的顺序和 Day 9 的写前日志一样：

1. 读出文件当前的内容（不存在就记“新建”）；
2. 把这份内容存好，记下“这个文件在这一轮改之前是什么”；
3. 再真正写文件；
4. 写完记下“改之后是什么”。

如果第 2 步失败，就不要写文件：一个没法撤销的改动，不如不做。如果进程死在第 3 步，清单里有“之前”但“之后”还没确认，撤销时照样可以恢复，只是不再核对它。

### 每轮只存第一次的“之前”

同一轮里，一个文件可能被改十次。撤销只关心两个值：

- **第一次改之前**：撤销时要恢复成它；
- **最后一次改之后**：撤销前用来核对“现在的文件是不是还是我们留下的样子”。

中间的版本都不需要。快照内容按哈希命名（内容寻址），一个文件来回改也只多存一份。

一个最小的清单：

```json
{
  "files": {
    "go.mod":          {"before": "1a3b…", "after": "c917…"},
    "queue/README.md": {"created": true, "after": "603c…"}
  }
}
```

`created` 表示这一轮之前文件不存在，撤销时删除它。

### 按轮存放

快照目录跟着“轮”走，而不是跟着进程走。续跑同一轮（进程中途死掉、再接着跑）时，接着用同一份清单，“之前”仍然是这一轮开始时的样子。子 agent 是另一个进程，但它是在父 agent 的某一轮里被派出去的，它的改动也属于那一轮。

## 4. 撤销：合并、核对、全有或全无

撤销第 N 轮，意思是第 N 轮以及它之后的所有轮次都撤销。步骤：

1. **找出要撤销的轮次**：从第 N 轮沿着“下一轮接着谁”往后找，直到最新的一轮。
2. **按文件合并**：同一个文件可能在多轮里改过。最早那一轮的“之前”是要恢复成的样子；最晚那一轮的“之后”是它现在应有的样子。
3. **核对当前内容**：
   - 等于最晚的“之后”：可以恢复；
   - 已经等于最早的“之前”：跳过（比如上一次撤销做到一半）；
   - 两个都不等：有人在 agent 之后改过它，这是**冲突**。
4. **全有或全无**：只要有一个冲突，一个文件也不动，把冲突列给人看。撤销一半的工作区，比不撤销更难收拾。
5. **恢复并标记**：写回原内容、删除新建的文件，最后把这几轮标记为“已撤销”。标记放在最后，中途失败时可以再执行一次，已经恢复的文件会被识别出来跳过。

第 3 步的核对和 Day 23 的“读后才写”是同一个思路：动手之前确认眼前的文件还是自己以为的那个版本，对不上就停下来交给人，而不是覆盖。

被撤销的轮次不删除，只是不能再续跑或接着聊；调用链、审计、检查点都保留，事后仍能查清当时做了什么。撤销本身是改用户仓库的动作，要记进审计日志。

## 5. 覆盖不到的改动

逐文件快照只认得 harness 自己的文件工具。下面这些改动不在快照里：

| 改动来源 | 例子 | 后果 |
| --- | --- | --- |
| shell 命令 | `sed -i`、`rm`、`mv`、代码生成器、`go mod tidy` | 撤销不会恢复它们；如果正好改了 agent 也改过的文件，核对会发现冲突并拒绝 |
| 人或其他程序 | 编辑器里手动修改、另一个会话 | 同上 |
| 远程副作用 | 推送的提交、调用的接口、改过的数据库 | 任何文件回退都撤不回，只能靠执行前的审批（Day 20、Day 25） |

另一种做法是**整个工作树快照**：每轮开始前把整个工作区拍下来（比如用 git 写一个不挂在任何分支上的提交），撤销时整体恢复。它能覆盖 shell 的改动，代价是：每轮都要扫描整个工作树，大仓库很慢；要决定未跟踪、被忽略、很大的文件怎么处理；整体恢复时会连同用户在这段时间里的手动修改一起抹掉。

| | 逐文件快照 | 整个工作树快照 |
| --- | --- | --- |
| 拍的时机 | 每次文件工具写入之前 | 每轮开始之前 |
| 覆盖 | 只有文件工具的改动 | 工作树里的所有改动（取决于怎样处理未跟踪、被忽略的文件） |
| 代价 | 只存改过的文件 | 每轮扫描整个仓库 |
| 误伤 | 少：只动 agent 改过的文件，并核对冲突 | 多：会连带恢复人在这段时间里的修改 |

Claude Code 用的是逐文件快照，文档里明确写了 Bash 的改动不跟踪，也提醒检查点不代替版本控制。[资料](https://code.claude.com/docs/en/checkpointing) Codex CLI 曾经实现过用 git“幽灵提交”（ghost commit）整体快照工作树的撤销，后来又从产品里移除了。[资料](https://forge.lthn.ai/core/core-agent-ide/commit/e0fbc112c772f87c9386cb2de992fbf8cdcb07d7) [资料](https://codex.danielvaughan.com/2026/04/25/codex-cli-error-recovery-rollback-patterns-git-safety-nets/) 两条路线说明，完整覆盖与不误伤之间没有免费的方案。

## 6. 与对话检查点对齐

对话层面，每一轮都有自己的检查点，记着它接着哪一轮（续接链）。把文件快照也按轮存放，两者就天然对齐：

```text
轮1 ── 轮2 ── 轮3          撤销轮2：文件回到轮1结束时，对话接着轮1
 │
 └──── 轮4                 新的一轮接着轮1，轮2、轮3 留作记录、不能再接着聊
```

接着轮 1 聊时，模型看到的是轮 1 结束时的上下文，“读过哪些文件、读到的是什么版本”的账本也是轮 1 结束时的，正好和恢复后的文件一致。

一轮被接着聊过两次时（轮 1 后面既有轮 2 又有轮 4，而且都没撤销），就不知道磁盘上是哪一支的结果。这时最稳妥的做法是拒绝，让人指明，而不是猜。

## 自测

1. 用户说“撤销刚才那一轮”，为什么不能直接 `git checkout .`？
2. 为什么快照必须在写入之前存好？如果先写文件、再存快照，哪个时刻崩溃会出问题？
3. 一个文件在一轮里改了三次，快照至少要存几份内容？撤销前核对的是哪一份？
4. 撤销前发现某个文件既不是 agent 最后写入的版本，也不是原来的版本，说明了什么？应该怎么做？
5. 只退文件、不退对话，会出现什么问题？只退对话、不退文件呢？
6. agent 用 shell 跑了 `go mod tidy` 改了 `go.sum`，撤销能恢复吗？如果它之前还用编辑工具改过 `go.sum` 呢？
7. 整个工作树快照能覆盖 shell 的改动，为什么不总是用它？

### 自测答案

1. 工作区里可能还有用户自己没提交的修改，`checkout` 会一起冲掉；而且 git 的粒度是提交，不是“一轮”；对话也不会跟着退回，模型会以为自己的改动还在。
2. 先写后存时，如果进程死在“写完文件、还没存快照”之间，原来的内容已经被覆盖、又没有备份，这个改动就再也撤不回了。先存快照再写，最坏情况只是多存了一份没用上的快照。
3. 只需存一份内容：第一次改之前的版本。另外记下最后一次改之后的哈希（不需要存内容），撤销前用它核对当前文件。
4. 说明在 agent 最后一次写入之后，有别人（shell 命令、人、其他程序）改过它。应该整次撤销都不做，把冲突的文件列给人处理，不能覆盖那些改动。
5. 只退文件：模型以为改动还在，会基于不存在的代码继续回答。只退对话：模型对着一份它没见过的代码继续工作，还不知道那几轮新建的文件。两种情况读后才写都能在改文件时发现哈希对不上、要求重读，但发现得晚：在那之前的回答与计划已经错了，没读过、也不打算改的文件更发现不了。
6. 只用 shell 改的，撤销恢复不了，快照里没有它。如果之前用编辑工具改过，撤销时会发现 `go.sum` 已经不是 agent 最后写入的版本，按冲突拒绝，不会把 `go mod tidy` 的结果覆盖掉。
7. 每轮都要扫描整个仓库，大仓库很慢；要处理未跟踪、被忽略和很大的文件；整体恢复会把人在这段时间里的手动修改也一起抹掉。
