# Day 15：评测指标——成功率、可靠性、延迟与成本

## 学习目标

读完本文，应能回答以下问题：

1. agent 的指标为什么不能只看一个“成功率”？至少要看哪几个维度？
2. “完成”和“答对”有什么区别？评测为什么要区分过程（transcript）和结果（outcome）？
3. pass@k 和 pass^k 各衡量什么？为什么面向用户的 agent 更该看 pass^k？
4. 分母怎样定？运行中的、崩溃的、子任务要不要算进去？
5. 延迟为什么看分位数而不是平均值？成本为什么要算“每次成功的成本”？
6. 指标的数据该从哪里取？为什么不能只从调用链（trace）里统计？

## 1. 为什么要多个维度

agent 和普通程序有两个不同：**同样的输入，每次走的路不一样**；**一次任务包含很多步**，每一步都可能慢、贵或出错。只看成功率会掩盖很多问题：

- 两个版本成功率一样，一个平均 10 秒、另一个 60 秒；
- 成功率提高了 5%，代价是 token 翻倍；
- 成功率不变，但“被熔断”“结果未知”的任务变多了，用户体感变差。

工业界常用的划分大同小异，比如 CLEAR 框架把企业 agent 的评估分成成本（Cost）、延迟（Latency）、效果（Efficacy）、安全（Assurance）、可靠性（Reliability）五个维度。本课聚焦其中四个：**成功、可靠、延迟、成本**，再加上一个能直接指导排查的**工具可靠性**。安全留到第三周的注入攻防与审批。

## 2. 成功：完成 ≠ 答对

**完成**：任务正常结束，模型给出了最终回答，没有被预算、熔断、取消打断。它可以从运行状态里直接读出来。

**答对**：最终结果满足任务要求。它需要一个**打分器**（grader）：精确匹配、程序检查（比如文件是否真的被修改）、人工评审，或者用另一个模型按评分标准打分。

Anthropic 的 agent 评测文章特别强调两个概念的区分：

- **过程**（transcript）：agent 说了什么、调用了哪些工具；
- **结果**（outcome）：任务结束后环境的最终状态。

评分应当以结果为主：同一个目标可以有多条合理路径，按“必须先调用 A 再调用 B”打分，会惩罚合理的创新。但过程仍要读：打分器本身可能有 bug，只有翻看过程才能发现“明明做对了却被判错”。

所以一个完整的成功指标是：**完成率**（运行层面，随时可得）+ **答对率**（需要评测集和打分器）。只报告完成率时，要明确写出它不代表答对。

## 3. 可靠：pass@k 与 pass^k

同一个任务跑 k 次：

```text
pass@k = 至少有一次成功的概率     → 衡量“能不能做到”
pass^k = k 次全部成功的概率       → 衡量“能不能每次都做到”
```

τ-bench 提出 pass^k，正是为了衡量客服这类场景需要的**一致性**。它的无偏估计：一个任务跑了 n 次、成功 c 次，

```text
pass^k ≈ C(c, k) / C(n, k)      （再对所有任务取平均）
```

**算例**：某任务跑 8 次成功 6 次。

- 单次成功率 = 6/8 = 75%；
- pass^2 = C(6,2)/C(8,2) = 15/28 ≈ 53.6%；
- pass^4 = C(6,4)/C(8,4) = 15/70 ≈ 21.4%。

单次 75% 看起来不错，但“连续 4 个用户都得到正确服务”的概率只有约 21%。τ-bench 的实验里，强模型在零售场景的 pass^8 掉到约 25%。k 越大，pass@k 越接近 100%，pass^k 越接近 0：两者讲的是相反的故事。

面向用户的 agent 更该看 pass^k：用户不会因为“重试几次总有一次对”而满意。

除了重复试验，可靠性还要看**非正常结局的分布**：

| 结局 | 含义 | 能否续跑 |
| --- | --- | --- |
| 完成 | 给出最终回答 | — |
| 取消、超时 | 被用户或时限打断 | 可以 |
| 模型请求失败 | 外部服务故障 | 可以 |
| 预算耗尽 | 请求次数用完 | 不能，续跑结果一样 |
| 熔断 | 重复动作被拦下 | 不能 |
| 进程消失 | 进程被强制杀死、断电，状态停在“运行中” | 可以 |

“异常里能续跑的比例”很有用：它高，说明问题多在外部环境，可以靠重试和恢复解决；它低，说明问题在 agent 自己的决策上。

## 4. 分母

指标最容易出错的地方是分母。几个原则：

1. **运行中的任务不计入**：它们还没有结局，计入就会把完成率拉低。
2. **崩溃的任务必须计入**：它们最容易被漏掉，见第 6 节。
3. **子任务单独统计**：子 agent 是父任务的一部分，和父任务混在一起，一个父任务派 4 个子任务就会被算成 5 个任务。
4. **重试和续跑不算新任务**：同一个任务ID跑了 3 次才完成，是 1 个完成的任务（用了 3 次尝试），不是 1 成 2 败。
5. **缺数据的单独报告**：旧记录没有某个字段时，用有数据的样本做分母，并报告缺了多少，不要拿 0 去平均。

## 5. 延迟与成本

**延迟看分位数**。平均值会被少数极慢的任务拉偏，也看不出尾部体验：

```text
耗时（秒）：2 3 3 4 9 50     → 平均 11.8；P50 = 3；P95 = 50（6 个样本时就是最大值）
```

P50 说明典型体验，P95 说明最差的那一小部分用户。样本少时 P95 就是最大值附近，一定要和样本数一起报告。

**成本看“每次成功的成本”**。失败的任务同样花了钱：

```text
10 个任务，每个 3000 tokens，成功 6 个
每任务成本 = 30000 / 10 = 3000
每次成功的成本 = 30000 / 6 = 5000
```

一个版本成功率从 60% 提到 80%、每任务成本从 3000 涨到 3500，每次成功的成本反而从 5000 降到 4375。HAL 这类排行榜同时报告准确率和成本，正是因为只看准确率会奖励“花更多钱换更高分”的做法。

成本的单位最好是 token 和请求次数，再按价格换算成金额：价格会变，token 不会。缓存命中的输入通常更便宜，要单独统计。

## 6. 数据从哪里来

指标要求数据**完整**，尤其不能漏掉失败的样本。几种来源的对比：

| 来源 | 优点 | 缺点 |
| --- | --- | --- |
| 持久化的任务状态（检查点、任务表） | 每个边界同步写入，进程被杀也在；有最终结局 | 只有任务级信息 |
| 调用链（trace） | 每一步的耗时、父子关系、重试 | span 结束时才导出，崩溃时正在执行的部分丢失 |
| 界面事件 | 实时、结构化 | 只覆盖经过这个界面的任务 |
| 日志 | 最全 | 文本，统计前要解析 |

关键在于：**崩溃时丢失的恰恰是失败的那部分**。只从 trace 统计成功率，崩溃的任务没有根 span，既不进分子也不进分母，成功率被高估；卡住的工具被杀时没有 span，工具失败率被低估。这是典型的幸存者偏差。

所以通常的做法是：**结局、耗时、成本以持久化状态为准，trace 只用来归因**（“慢在哪一步”“哪个工具在出错”），并在报告里注明 trace 部分可能偏低。

## 7. 从指标到目标

指标（SLI）本身不说明好坏，需要配上目标（SLO）：比如“任务完成率 ≥ 95%”“P95 延迟 ≤ 60 秒”“每次成功 ≤ 5000 tokens”。目标让团队知道什么时候该停下功能开发、先修可靠性。目标要基于一段时间的实际数据来定，并且要和评测集（下一课）一起用：线上指标告诉你“变差了”，评测集告诉你“是哪类任务变差了”。

## 8. 自测

**1. 完成率 95% 能说明 agent 答对了 95% 的问题吗？**
不能。完成只说明给出了最终回答；答对需要评测集和打分器判断结果。

**2. 一个任务跑 5 次成功 4 次，pass^2 是多少？**
C(4,2)/C(5,2) = 6/10 = 60%。

**3. 为什么面向用户的 agent 更该看 pass^k 而不是 pass@k？**
用户每次只用一次，需要的是“每次都做到”；pass@k 衡量的是“多试几次总有一次做到”，会随 k 增大接近 100%，掩盖不一致。

**4. 只从 trace 统计成功率，会有什么偏差？**
崩溃的任务没有根 span，不进分母，成功率被高估；崩溃时卡住的工具也没有 span，工具失败率被低估。

**5. 成功率提高、每任务成本也提高，怎样判断值不值？**
看每次成功的成本：总花费除以成功数。它下降，说明多花的钱换来了更多成功。

**6. 为什么样本少时不能只看 P95？**
样本少时 P95 就是最大值附近，一个偶然的慢任务就能决定它；必须和样本数一起读。
