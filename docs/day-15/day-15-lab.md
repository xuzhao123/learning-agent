# Day 15 项目实践：5 个核心指标与采集

原理见 [Day 15 学习笔记](day-15-notes.md)。代码在 [internal/metrics](../../internal/metrics/metrics.go)，检查点新增的字段在 [checkpoint.go](../../internal/agent/checkpoint.go)。

## 1. 指标定义

```sh
go run . metrics                 # 最近 7 天结束的任务
go run . metrics -since 30m      # 只看最近 30 分钟
go run . metrics -json           # 输出 JSON，供后续评测脚本使用
```

| # | 指标 | 定义 | 数据来源 |
| --- | --- | --- | --- |
| 1 | 任务完成率 | 状态为 done 的根任务 / 根任务总数；子 agent 单独统计 | 检查点 |
| 2 | 异常结局与可恢复性 | 非正常结局按原因分布；进程消失（`running` 且锁已释放）单列；异常里能续跑的比例 | 检查点 + 任务锁 |
| 3 | 端到端延迟 | 已结束根任务的 P50 / P95（`started_at` 到最后一次写检查点） | 检查点 |
| 4 | 成本 | 每任务 tokens 与模型请求；每完成一个任务的 tokens（失败任务的花费也算进去）；缓存命中率 | 检查点 |
| 5 | 工具可靠性 | 每个工具的调用数、失败率、结果未知率、未执行数、重试次数、P95 | trace 的 `execute_tool` span |

分母的取法（对应笔记第 4 节）：

- 运行中的任务（状态 `running` 且锁被占着）不计入；锁已释放的记为“进程消失”，计入异常；
- ID 含 `-sub-` 的是子 agent，单独统计，不混进根任务；
- 续跑不产生新任务（同一个检查点ID）；观测台的每一轮续聊是新的检查点（见 [Q21](../deep-questions.md#q21)），算一个新任务；
- D15 之前的检查点没有开始时间和用量：延迟和成本只用有数据的任务做分母，并报告缺了多少。

## 2. 读代码

### 2.1 检查点新增的字段

按 [Q19](../deep-questions.md#q19) 的结论，结局、耗时、成本以检查点为准，所以检查点补了三样东西：

```go
StartedAt time.Time `json:"started_at,omitempty"` // 首次开始；续跑不变
Input     int       `json:"input_tokens"`         // 累计用量，跨续跑累加
Output    int       `json:"output_tokens"`
Cached    int       `json:"cached_tokens"`
Traces    []string  `json:"traces,omitempty"`     // 每次运行的 trace_id，指标第 5 项据此找 span
```

续跑时 `agent.Run` 把客户端的计数从检查点恢复（以前只恢复请求次数），用量因此是整个任务的。`StartedAt` 续跑不变，所以耗时包含中断的那段时间：它衡量的是用户等了多久，不是 CPU 忙了多久。

### 2.2 统计

[metrics.Compute](../../internal/metrics/metrics.go) 遍历 `.data/checkpoints/`，按 `updated_at` 过滤时间窗：

- 状态 `running` 时试着拿任务锁：拿得到说明进程已经不在了（kill -9、断电），这正是 trace 里看不到的结局；
- 按根任务、子任务分别计数，结局计入分布；
- 收集所有任务的 `traces`，再读这些 trace 文件里的 `execute_tool` span：状态在 `agent.tool.status`，重试是 span 上的 `retry` 事件。

分位数用最近秩法（第 ceil(p×n) 个），与观测台 `/trace-metrics` 相同。

## 3. 实验记录

用 Day 10 的 9 道示例题（去重后 10 道）加 2 道故障题，组成 12 个新任务，经队列（3 个 worker）用真实方舟运行：

- `f1`：调用一次 `always_fail`（Day 2 的故障工具），如实报告结果；
- `f2`：`-tool-timeout 3s` 下调用 `slow_job(8)`，让工具超时。

`go run . metrics -since <这批的时间窗>`，只看这 12 个任务的结果：

| 指标 | 结果 |
| --- | --- |
| 1 完成率 | 11/12 = 91.7% |
| 2 异常结局 | 1 个 `repeated_action`（f2）；进程消失 0；这一个异常不能续跑 |
| 3 延迟 | P50 13.1 s，P95 48.5 s（12 个样本，P95 接近最大值） |
| 4 成本 | 每任务 2791 tokens、约 2.5 次模型请求；每完成一个任务 3045 tokens；缓存命中 0 |
| 5 工具 | calculator 9 次、search_notes 3 次全部成功；`always_fail` 失败率 100%、重试 2 次；`slow_job` 结果未知率 100%，P95 3007 ms（正好是单次时限） |

从这组数字可以直接读出几件事：

1. **f2 的失败链路**：`slow_job` 超时 → 记为“结果未知”（不可重复，不自动重做）→ 模型连续调用 `check_task_status` 核对 → 第 3 次被重复动作熔断拦下。这和 [Day 13](../day-13/day-13-lab.md) 3.4 的现象相同：模型面对“结果未知”没有好的核对办法，这是一个稳定可复现的问题，适合放进 D16 的评测集。
2. **f1 算“完成”**：工具失败，但模型如实报告了失败，任务正常结束。完成不等于答对；这个任务答得对不对，要看评测集怎么定义“对”。
3. **每次完成的成本比每任务成本高约 9%**：失败任务花的 token 摊到了成功的任务上。
4. **P95 由一个慢任务决定**：最慢的是 t08（“现在几点？距离今天结束还剩多少分钟？”，3 次模型请求，48.5 秒），其次是 t01（5 次请求，23.1 秒）。请求次数多不一定最慢，单次模型请求的耗时波动更大；12 个样本里 P95 就是这个最大值。

时间窗里还混进了用旧程序跑的 12 个检查点（没有新字段）：报告如实写出“12 个旧检查点没有开始时间 / 没有用量”，延迟和成本的分母只用了有数据的 12 个。最初版本把它们也算进成本的分母，“每任务 tokens”被摊薄了一半，已修正。

## 4. 动手

1. 运行 `go run . metrics -since 24h`，对照第 1 节逐项读懂每个数字的分母。
2. 在观测台跑一个任务，执行中按两次停止（强制结束），再运行 `metrics`，看它是否出现在“进程消失”里。
3. 用 `-json` 输出，自己算一遍每次完成的成本，确认与表格一致。
4. 想一想：如果要报告 pass^3，需要怎样组织运行？（提示：同一道题跑多次，每次是不同的任务ID，按题目分组。这是 D16 的内容。）

## 5. 已知边界

- **完成 ≠ 答对**：答对率需要 D16 的评测集与打分器。
- **没有 pass^k**：需要同一道题重复运行多次，属于 D16。
- **工具指标可能偏低**：来自 trace，崩溃时正在执行的工具没有 span；报告里注明了这一点。
- **成本只到 token**：没有换算成金额，价格表因供应商和时间而变，需要时再加。
- **时间窗按最后一次写检查点**：长时间停在中途、很久以后才续跑完成的任务，会落在续跑完成的那个时间窗里。
- **一次队列运行是一个 trace**：工具指标按任务统计时，要靠 span 上的 `gen_ai.agent.id` 再分；目前按工具汇总，没有按任务拆分。
