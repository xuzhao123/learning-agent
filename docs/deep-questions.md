## Q1 熔断器的"连续重复"到底该怎么定义？

*2026-10-05 · Day 2 循环护栏*

**当前状态**：待优化：已识别相邻重复，交替动作的无进展检测未实现。

**问题**：熔断器的 repeated 计数器是跨 round 累积的，那 A 调用、B 调用、A 调用这种 A‑B‑A 会触发熔断吗？"连续重复"怎么定义才合理？

**值得琢磨的地方**：真正的死循环往往不是原地踏步，而是来回横跳。护栏防的到底是"重复"，还是"没有进展"？

**结论要点**
- 计数器确实跨轮累积，但每次只和**上一个动作**比较。A,A,A 会触发熔断；A,B,A,B… 每次都重置为 1，永远不触发，只能靠 max_steps 兜底。
- 重复本身不一定是问题。"读状态 → 修改 → 再读状态"就是正当的 A‑B‑A，因为第二次读到的结果变了。所以判断标准应该是**有没有进展**。
- 建议分两层检查：
  - **执行前**：保留相邻重复检查。它在副作用发生前就能拦下，比如连发三次同一个写操作。
  - **执行后**：按滑动窗口统计 `(动作, 结果哈希)`，最近 N 步里同一对出现 ≥3 次，就判定为无进展循环。结果在变的轮询不会被误杀。
- 两层各有代价：执行前检查发现不了循环，执行后检查又要等副作用已经发生。

**相关代码**：`react.go` 中的 `repeated` 计数与 `actionKey`。已列入 PROJECT.md「已知问题」。

## Q2 检索结果全部低于阈值时，模型实际看到什么？

*2026-10-05 · Day 4 检索注入*

**当前状态**：待优化：低分正文已过滤，元信息与库外回答规则仍需收紧。

**问题**：余弦阈值 0.4 把文档全过滤掉、正文清空之后，模型实际会看到什么？按 systemPrompt，它这时候应该做什么？

**值得琢磨的地方**：所谓"过滤"，过滤掉的只是正文。剩下的元信息照样会影响模型。

**结论要点**
- 模型看到的不是全部 24 条，而是排序后的 top‑k 条（默认 3 条）。每条的 `text` 为空，但 **id、title、source、score 都还在**，另外还有 `status: "insufficient"`。
- 按 prompt，模型此时应该只回答"资料不足，我不确定"，不带任何 `[Dxx]` 引用。
- 有三个隐患：
  1. **标题泄露**：分数略低于阈值、标题又和问题高度相关时，模型可能照着标题和通用知识补写答案，甚至引用这条文档。
  2. **重搜没有上限**：模型每次换个说法改写查询，参数都不同，熔断器拦不住（和 Q1 是同一个漏洞）。
  3. **库外问题的处理有歧义**：库外问题该用通用知识回答，还是只说资料不足，prompt 没说清楚。

**相关代码**：`retrieval.go` 中 `retrieval.Search` 的低分分支，以及 `react.go` 中的 `agent.SystemPrompt`。已列入 PROJECT.md「已知问题」。

## Q3 被取消的工具调用为什么会从 summary 里消失？

*2026-10-05 · Day 2 循环护栏 / 并行执行*

**当前状态**：已修复：Day 8 按成功、失败、未执行与结果未知逐项写入摘要。

**问题**：`agent.ExecuteBatch` 里被取消的 observation，为什么会从 summary 里消失？（提示：Attempts 和拼装条件的关系）

**值得琢磨的地方**：一个看起来无害的过滤条件，悄悄把"请求了但没执行"和"根本没请求"混为一谈。

**结论要点**
- summary 只记录 `Attempts > 0` 的调用。被取消的调用有两条路径，`Attempts` 都停在 0：
  - 排队等并发槽时被取消，走 `case <-ctx.Done()`；
  - 拿到槽后，第一次尝试前 ctx 已经取消，`runWithRetry` 先检查 ctx、后执行 `Attempts++`。
- 除了取消，任何调用都至少尝试 1 次。所以这个条件实际过滤掉的**只有被取消的调用**。
- 第三种情况：执行到一半被取消。这时结果其实是**未知**的，副作用可能已经发生，但现在会被写成"失败：context canceled"，读的人会误以为可以放心重试。

**相关代码**：`react.go` 中 `agent.ExecuteBatch`、`runWithRetry`，以及 `agent.Run` 里拼装 summary 的部分。已列入 PROJECT.md「已知问题」。

## Q4 "未执行（已取消）"该进 history、summary，还是两边都进？

*2026-10-05 · Day 1 消息历史 / Day 2 终止报告*

**当前状态**：已实现：状态同时进入历史与停止摘要，检查点和观测台中断续聊会交给模型；副作用恢复仍需幂等或确认。

**问题**：修好 Q3 之后，"未执行（已取消）"这条记录应该进 conversation history、只进 summary，还是两边都进？为什么？

**值得琢磨的地方**：同一个事实有两类读者，模型和人。两者需要的信息不一样，写入的理由也不一样。

**结论要点**
- **history 必须进，这是协议要求**：每个 `tool_call_id` 都必须有对应的 tool 结果，否则下一次请求会被 API 拒绝。但内容要写清楚是"未执行"（可以安全重做）还是"执行中被打断"（结果未知，重做前要先核对）。
- 按现在的设计，这条记录写进 history 后暂时没人读：取消后不会再请求模型，续聊也拒绝从中断处恢复。等到 D9 做 checkpoint 和中断续跑时，它才会真正被模型读到。（2026-10-07 补充：Day 9 的 `-resume` 与观测台“中断后继续提问”都会把它交给模型，后者实测中模型据此只重做了用户指定的那一项。）
- **summary 也必须进**：它是给人看的账本，告诉人哪些动作已经做了、哪些没做。对有副作用的工具来说，"未执行"本身就是关键信息。
- 修复方向：拼装 summary 时去掉 `Attempts > 0` 的条件，把状态分成"成功 / 失败 / 未执行（已取消）/ 执行中被取消、结果未知"，history 也用同样的措辞。

## Q5 "记住"前缀匹配太生硬，生产系统怎样决定写入记忆？

*2026-10-06 · Day 5 长期记忆*

**当前状态**：已实现折中方案：模型登记用户原话，程序校验并提交；漏记、误记仍待评估。

**问题**：`rememberRequest` 用 `"请记住"/"帮我记住"/"记住"` 前缀判断要不要写入记忆，很生硬。实际生产中是怎么做的？

**值得琢磨的地方**：写入入口同时决定了召回上限和污染风险。识别得越灵活，越容易把推测、注入内容写成"事实"；规则越死，越容易漏掉用户真实的意图。

**结论要点**
- 前缀匹配会误判：`记住了吗？` 被当成写入；`别忘了我对花生过敏`、`以后都用中文回答`、`Remember that…` 被漏掉。
- 生产系统一般拆成四步：**识别**（模型调用记忆工具，或会话后由模型抽取候选）→ **规范化**（把"它的端口是8092"写成不依赖上下文的事实，同时保留原话作来源）→ **调和**（检索相似旧记忆，选择新增 / 更新 / 删除 / 不变，mem0 的做法）→ **程序闸门**（来源必须是用户消息而不是工具结果、敏感信息过滤、长度与频率限制、推断类记忆降低可信度或请用户确认），最后让用户看得见、改得了。
- 时机有两种：对话中由模型调用工具写入（hot path，立即生效、增加延迟），或会话后后台抽取与整理（不影响延迟、有滞后）。
- 在"模型不能生成事实"的约束下，一个折中是：模型通过工具提交用户原话里的一段**逐字引文**，程序校验它确实是本轮用户消息的子串，再走现有拒存规则；指代消解放进派生的背景说明，不改写原文。

**后续**：2026-10-06 已按折中方案实现：前缀匹配换成 `remember_memory(quote, kind)` 工具，`remember` 校验引文逐字出自本次会话的用户消息，再走 `rejectReason`，每轮最多 3 条，本轮结束时由 `commit` 连同来源保存；用户说了“记住”但模型没登记时只打印 `Memory hint`。漏记、误记的比例待真实对话观察。

**相关代码**：[memory.go](../internal/memory/memory.go) 的 `remember`、`rejectReason`、`commit`。

## Q6 "重要但久未用"输给"不重要但刚用过"，这符合预期吗？

*2026-10-06 · Day 5 长期记忆 / 容量淘汰*

**当前状态**：保留现有策略：重要性与新近度共同淘汰，多样本效果待评估。

**问题**：淘汰分数是 `importance × 0.5^(距上次访问天数/7)`。一条 importance=0.9、30 天没碰过的 semantic 记忆，和一条 importance=0.4、昨天刚访问的 episodic 失败记录，谁先被淘汰？"重要但久未用"输给"不重要但刚用过"，这符合预期吗？你希望哪个赢？

**值得琢磨的地方**：一个乘法公式悄悄定下了"时间比重要性更重要"。半衰期 7 天意味着 importance 每过一周就打对折，用户明确要求记住的事实一个月后就排在一次性失败记录后面。

**结论要点**
- 算式没错：0.9 × 0.5^(30/7) ≈ 0.9 × 0.051 ≈ **0.046**；0.4 × 0.5^(1/7) ≈ 0.4 × 0.906 ≈ **0.362**。semantic 记忆先被淘汰。importance 相差 2.25 倍，只要多闲置约 8 天（7 × log₂2.25 ≈ 8.2）就会被时间抵消。
- 这和设计本身矛盾：semantic / procedural 的过期时间是 `never`，episodic 7 天后自动过期。也就是说"不会过期"的记忆，容量一紧张反而先走；本来过几天就会自然消失的记录，却把它挤掉了。
- 大多数场景下应该让 semantic 赢。用户事实（过敏、偏好、端口号）的价值不随时间降低，只是暂时没用到；失败记录的价值主要就在最近几天。
- 可选的修法：
  - **按类型设半衰期**：semantic 不衰减或很慢（比如 90 天），episodic 保持 7 天；
  - **加下限**：用户明确要求记住的条目，retention 不低于 importance 的某个比例；
  - **分层淘汰**：先在 episodic 里淘汰，没有 episodic 了才动 semantic；
  - **淘汰前提醒**：要删用户亲口要求记住的条目时，在观测台提示或让用户确认，不要悄悄删掉。
- 还要明确"访问"指什么：被检索命中、调入 system、还是在回答中被引用？定义不同，"冷"记忆的含义也不同。

**相关代码**：[memory.go](../internal/memory/memory.go) 的 `retention` 和保存时的容量淘汰循环。

## Q7 prompt 里写了"不必重复检索"，模型为什么还是查了？

*2026-10-06 · Day 5 长期记忆 / 实验 7.4*

**当前状态**：待观察：提示词不能保证不重复检索，需要评估后再决定执行层约束。

**问题**：M6 已经调入 system，模型还是又调了一次 `search_memory`，而工具描述里明明写着"system 中已列出的记忆不必重复检索"。prompt 里写了规则，模型照样没遵守。这说明了什么？如果是生产系统，你会怎么修，改 prompt 就够了吗？

**值得琢磨的地方**：prompt 是请求，不是约束。哪些规则可以交给模型"尽量遵守"，哪些必须由程序保证？

**结论要点**
- 这说明 prompt 里的规则只会提高模型遵守的概率，不能保证遵守。模型可能没把 system 里的条目和问题对上，也可能出于谨慎再查一遍确认。只靠措辞，没法把这种行为降到零。
- 判断标准是**违反的代价**：
  - 这里多查一次只浪费一次工具调用和一点延迟，结果仍然正确（最后引用的还是 [M6]），可以接受偶尔发生；
  - 如果违反会带来副作用、泄露或错误结论，就必须由程序拦住，比如 Q5 里引用必须逐字出自用户消息，就是程序校验。
- 生产上的修法，从轻到重：
  1. **程序去重**：`search_memory` 的处理函数知道哪些 ID 已经调入 system，命中时直接返回"M6 已在 system 中"，不再重复展示内容，也不再执行检索；
  2. **调整结构**：调入的记忆放在醒目的固定位置，标注"本轮已检索，query=…"，让模型更容易对上；
  3. **加观测**：统计"重复检索率"，作为回归指标，改 prompt 或换模型后看指标有没有变化；
  4. **评测集**：把这类场景放进固定测试，不靠一次实验的印象下结论。
- 只改 prompt 不够：效果没法保证，而且换个模型或改一处措辞就可能失效。

## Q8 短密钥能绕过 secretPattern，补还是接受？

*2026-10-06 · Day 5 长期记忆 / 敏感信息过滤*

**当前状态**：已知边界：敏感信息过滤存在漏报可能，召回会把原文送入模型请求。

**问题**：`secretPattern` 的第一部分要求 `[A-Za-z0-9_\-+/]{32,}`，如果 key 只有 20 个字符，正则就拦不住。"先脱敏再截断"防的是截断绕过，但短密钥这个洞还在。补，还是接受这个 trade-off？接受的话，理由是什么？

**值得琢磨的地方**：正则阈值是在漏报和误报之间选一个点。调低阈值，堵住的是短密钥，误伤的是哈希、路径、长单词。

**结论要点**
- 正则分两部分。带关键词的写法（`API_KEY=…`、`密码：…`）不论长短都能拦住，这就是 7.5 里 `API_KEY=abcd1234efgh` 被拒的原因。漏洞只在**没有关键词的裸密钥**，比如用户直接贴一串 20 位的 key。
- 这个漏洞是真实存在的：AWS Access Key ID（`AKIA…`）正好 20 个字符，裸贴时拦不住。
- 不能简单把阈值降到 20：20 位以上的普通字符串很多（长英文单词拼接、文件路径、短哈希），误报会让正常记忆被拒存。另外 32 的阈值本身已经会误伤 40 位的 git commit SHA。
- 比较实际的补法是**补规则，不降阈值**：
  - 加常见密钥的固定前缀：`sk-`、`ghp_`/`github_pat_`、`AKIA`、`xox[bp]-`、`AIza` 等，这些长度短也能识别；
  - 对 16–31 位、同时含大小写字母和数字的串计算熵，熵高才判定为疑似密钥；
  - 引入现成的规则库（gitleaks / detect-secrets 的规则），不要自己维护一份。
- 如果选择接受，要明确记录漏报风险：0600 只限制本地文件访问；记忆被召回后，原文仍会随请求发送给模型服务。漏报不只是本地多存一条，误报也会拒绝用户希望保留的事实。这个边界应保留在待办里，不能当作已经解决。

**相关代码**：[memory.go](../internal/memory/memory.go) 的 `secretPattern`、`rejectReason`、`redact`，以及失败记录"先脱敏再截断"的那一行。

## Q9 为什么 MCP 要用 bin/learning-agent？MCP 的实现逻辑是什么？

*2026-10-06 · Day 6–7 MCP / 观测台 MCP 中心*

**当前状态**：已实现源码启动与观测台内置远程 MCP；需区分传输方式和实际执行进程。

**问题**：观测台测试 calculator 报 `fork/exec bin/learning-agent: exec format error`。实现为什么依赖 `bin/learning-agent`？MCP 从启动到调用到底怎么运作？

**值得琢磨的地方**：MCP client 依赖的是“一条能启动 stdio server 的命令”，不是某个具体的二进制文件。同一个程序既当 client 又当 server，容易让人误以为两者绑定在一起。

**结论要点**
- 不依赖 `bin/`。它只是实验时编译好的程序，写进了预设；二进制只能在编译它的平台上运行，换平台执行就是 `exec format error`。这时进程还没启动，跟 MCP 协议无关。改用 `go run . -mcp-serve`，在哪台机器运行就编译成哪台机器的程序。
- stdio server 是独立子进程：client 写它的 stdin、读它的 stdout。HTTP server 不要求每次连接都启动子进程；观测台直接在自己进程的 /mcp 上提供 calculator。
- 协议分为发现能力、列工具、调用工具。旧版用 initialize 握手；2026-07-28 版用 server/discover 查询 server 能力，并在每个请求的 _meta 中携带版本与 client 能力。工具列表在连接时读取，tools/call 随实际模型调用发生。
- 模型不认识 MCP：client 把 MCP tool 翻译成 function 定义（`mcp_` 前缀，inputSchema 原样作为 parameters），并记下名字映射；模型调用后，由 runTool 找到对应连接转发 tools/call。
- server 侧 stdout 只用来传协议消息，日志写 stderr；参数校验分三层：schema、handler、calculate。
- 观测台的 MCP 中心只保存命令并拼接参数，“测试连接”走的是同一个 `mcp.Connect`。

## Q10 任务调度就是开启 subagent 的功能吗？

*2026-10-06 · Week 2 开始前 / Day 10 任务调度*

**当前状态**：两者已实现：队列由系统调度，子 agent 由模型委派，复用任务执行器但职责不同。

**问题**：计划里 D10 的“任务调度”，是不是就是开启 subagent 的功能？

**值得琢磨的地方**：两者都表现为“同时跑好几个 agent”，很容易混为一谈。实际上一个是基础设施层，一个是 agent 自身的行为层；而且后者可以建在前者之上。

**结论要点**
- **任务调度**：由用户或系统发起。解决排队、并发上限、幂等（重复提交不重复执行）和重试。任务之间互相独立，不关心里面跑的是不是 agent。
- **subagent**：由父 agent 的模型在循环里发起（调用 `spawn_agent`）。目的是让子任务在一份干净的上下文里完成，只把结论交回，避免父上下文被中间过程撑满。父子之间有依赖：父等子的结果再继续推理。它属于上下文工程和多智能体协作。
- **两者的关系**：subagent 需要的底座正是 D8–D10 的成果：取消随父任务传下去、单次时限、并发上限、子任务失败后重试，以及父任务崩溃后续跑时不重复执行已完成的子任务（幂等键）。本项目里队列和 `spawn_agent` 共用同一个 `agent.RunChild`。
- **子任务ID的选择也有讲究**：最初用模型给的调用ID，kill -9 后重放没问题；但 Ctrl+C 后模型会发起新的调用、调用ID变化，子任务就从头跑。改成“父任务ID + task 内容哈希”后，同样的 task 能续上原来的子任务。

**相关代码**：[child.go](../internal/agent/child.go) 的 `RunChild`；[queue.go](../internal/queue/queue.go) 的 `runTask`；[subagent.go](../internal/agent/subagent.go) 的 `spawnAgent`。笔记见 [Day 10](day-10/day-10-notes.md) 与 [子 agent](bonus-subagents/subagents-notes.md)。

## Q11 开一个沙箱就是开一个 Docker 吗？Codex、Claude Code 好像不是这么做的

*2026-10-07 · Day 11 浏览器 / Day 12 沙箱之前*

**当前状态**：隔离层次已说明，Day 12 已采用 bubblewrap、seccomp 与 cgroup；浏览器隔离仍待改进。

**问题**：计划里 D12 写的是“Docker 隔离”，讲浏览器时也说“放进容器”。但 Codex、Claude Code 在本机执行命令时，好像并不开 Docker？

**值得琢磨的地方**：“沙箱”是目标（限制一段代码能碰到什么），容器只是实现手段之一。隔离强度、启动开销、要不要额外安装，是一组连续的取舍，不同产品在不同场景选的点不一样。

**结论要点**
- **从弱到强的几层**：进程级（seccomp 限系统调用、Landlock 限文件访问）→ OS 沙箱工具（Linux 的 bubblewrap 用 namespace 给进程一个受限视图；macOS 的 Seatbelt / `sandbox-exec`）→ 容器（Docker、Podman：独立的镜像、网络、cgroups 资源上限）→ 用户态内核（gVisor）→ 微虚拟机（Firecracker、Kata）。越往后隔离越强，启动越慢、依赖越重。
- **Codex CLI（本机）**：每条命令放进平台自带的沙箱：macOS 用 Seatbelt；Linux 用 bubblewrap 加 seccomp（bwrap 不可用时退回进程内的 Landlock）；按策略只读 / 只可写工作区 / 不隔离；受限网络模式下 seccomp 禁止除 Unix socket 以外的套接字。
- **Claude Code（本机）**：Bash 沙箱同样用 macOS Seatbelt、Linux bubblewrap，网络流量经代理只放行允许的域名；`@anthropic-ai/sandbox-runtime` 可以把整个会话（含工具、hook、MCP server）包进同样的隔离。
- **为什么本机不用 Docker**：要在开发者自己的项目目录里工作，需要直接读写真实文件、用本机的工具链；每条命令起一个容器太慢，也不能假设用户装了 Docker。OS 沙箱几十毫秒、零安装（macOS）或一个小包（Linux）。
- **云端产品才普遍用容器或虚拟机**：任务跑在供应商的机器上，代码不可信、多个用户共用硬件，需要更强的隔离和可整体销毁的环境，所以用容器、gVisor 或微虚拟机。
- **和本项目的关系**：bubblewrap 和 Chrome 的沙箱一样依赖非特权 user namespace。这台机器上 `kernel.apparmor_restrict_unprivileged_userns = 1`，Ubuntu 只给 `/opt/google/chrome/chrome`、`/usr/lib/chromium/…` 和 `bwrap` 预置了放行的 AppArmor profile。我们用的 Playwright headless shell 在 `~/.cache` 下，不在名单里，所以 Chrome 沙箱起不来。正式安装 Chrome/Chromium 很可能就不再需要 `CHROME_NO_SANDBOX=1`。
- **对 D12 的启示**：沙箱不等于 Docker。D12 应先讲隔离的层次与取舍，再按场景选：本机执行可用 bubblewrap + seccomp（与 Codex、Claude Code 同一路线），需要整体销毁、资源上限和网络策略时再用容器。

**参考**：[Claude Code Sandboxing](https://code.claude.com/docs/en/sandboxing)；[Codex CLI Sandbox Internals](https://codex.danielvaughan.com/2026/05/03/codex-cli-sandbox-internals-seatbelt-bubblewrap-landlock-windows-dacl/)（第三方源码解读）。

## Q12 有了沙箱，是不是就可以给模型一个 bash 工具？

*2026-10-07 · Day 12 沙箱之前*

**当前状态**：Bash 隔离和联网审批已实现；浏览器仍可外发数据，跨工具控制待后续。

**问题**：做了沙箱之后，是不是就能加一个 bash 工具，让模型直接用 shell 命令完成任务？

**值得琢磨的地方**：这正是 Codex、Claude Code 的核心设计：一个通用的 shell 工具加一层沙箱，取代一大堆专用工具。但沙箱只划定边界，边界之内的破坏和“允许范围内的外泄”它管不了。

**结论要点**
- **为什么值得做**：一个通用工具覆盖计算、检索、读写文件、跑测试等大量需求；模型对 shell 的熟练程度远高于自定义工具。工具设计的趋势是“少量通用工具 + 安全的执行环境”。
- **沙箱挡得住的**：读取未挂载的密钥与家目录、访问内网与云元数据（断网或白名单）、fork 炸弹与资源耗尽（资源上限与超时）。
- **沙箱挡不住的**：删改工作目录里允许写的文件；把数据发往白名单内的地址；被网页注入诱导去执行合法但有害的命令。需要靠临时工作目录或快照、清空环境变量、最小网络白名单、高风险操作人工确认。
- **致命三要素**：可读不可信内容（浏览器）、可接触私密数据、有外发通道（联网的 bash）三者同时具备时，一次注入就可能导致数据外泄。常见对策是 bash 默认断网、联网命令需确认，或让读网页的 agent 不配 bash。
- **与运行时的关系**：bash 有副作用，不能列入 repeatable；超时或中断时结果按“未知”处理，不自动重试（Day 8 四种结局）。

**参考**：Simon Willison，[The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)，2025；[Claude Code Sandboxing](https://code.claude.com/docs/en/sandboxing)。

## Q13 repeatable 表标错了会怎样？该写死在代码里，还是由工具自己声明？

*2026-10-07 · Day 9 与子 agent 之后*

**当前状态**：表按工具名写死在 [react.go](../internal/agent/react.go)；MCP 工具不在表里，一律按不可重复处理。幂等键只有 spawn_agent 具备。

**问题**：如果把有副作用的工具误标成 true，kill -9 后续跑会发生什么？这张表应该一直写死在代码里，还是由工具自己声明，比如 MCP server 在声明里说明？

**值得琢磨的地方**：这张表决定的是“结果未知时，程序能否替模型重做”。标错的方向不同，后果也完全不同。

**结论要点**
- **误标的后果**：续跑时，replayBatch 会把写前日志里那批调用中的这个工具直接再执行一遍，副作用重复发生。重放得到的结果和正常结果一样是 ok，模型和用户都看不出它执行了两次。影响也不只在 kill -9：runWithRetry 里，单次超时得到“结果未知”时，同样凭这张表决定是否重试，所以平时遇到超时也会重复。
- **不对称**：把只读工具误标为 false，代价是多一次“结果未知”和一次核对；把有副作用的工具误标为 true，代价是外部状态被破坏。所以默认值只能是 false，加入表中需要逐个审核。
- **可重复是可以构造出来的**：spawn_agent 本身有副作用（会启动子进程），它能列入表中，是因为有确定的子任务 ID，重做只会续跑或取回存档。判断标准不是“没有副作用”，而是“再执行一次，外部结果不变”。
- **写死还是声明**：MCP 的工具注解里有 readOnlyHint、destructiveHint、idempotentHint，但规范把它们定为提示信息，对不受信任的 server 不能作为安全依据。我建议只在一个方向上合并：内置工具由代码表决定；MCP 工具只有在用户把该 server 标为可信时才采信 idempotentHint，否则一律为 false；本地配置可以随时把工具降为 false，升为 true 需要人工确认。
- **更根本的做法**：不依赖标记，而是让有副作用的工具接收幂等键（例如工具调用 ID），由执行端去重，或者提供状态查询。这样即使标错，也只会多查一次。

**参考**：MCP 规范 [Tool annotations](https://modelcontextprotocol.io/specification/2025-06-18/schema#toolannotations)；[Day 9 实践](day-09/day-09-lab.md)；[Wiki 检查点与恢复](../wiki/10-checkpoints-and-recovery.md)。

## Q14 检查点存 View 而不是 Transcript，续跑的正确性靠什么保证？

*2026-10-07 · Day 9 之后*

**当前状态**：检查点只保存 View；续跑时由 rebuildContext 用这份 View 重建，Transcript 只剩已截断、已压缩的内容；续跑后的第一次请求只能粗估上下文用量。

**问题**：Day 3 的压缩会丢掉原文。续跑后模型看到的上下文和中断前不完全一样，这时“接着跑”的正确性靠什么保证？还是干脆接受它不保证？

**值得琢磨的地方**：先分清“和不中断时完全相同”与“从一个有效状态继续”这两种正确性。

**结论要点**
- **下一步的输入是一样的**：检查点在每个边界保存模型当时实际收到的 View。压缩丢掉的原文，中断前的模型同样看不到。续跑后的第一次请求，与不中断时的同一步收到的是同一份 View（只是模型本身的输出不确定）。
- **真正的分叉在后面**：进程里的 Transcript 还保留全部原文，再次压缩时，keepUsers 会从中挑用户原话，清理占位符也用原文长度。续跑后 Transcript 由 View 重建，用户原话只剩上次保留或截断后的版本，所以下一次压缩的素材更少，结果也可能不同。另外，续跑后没有 API 返回的 usage，触发压缩的时机也可能提前或推迟。如果在“压缩完成、检查点尚未写入”时崩溃，续跑时还会重新做一次摘要。
- **保证的是什么**：不保证与不中断时逐字一致，模型的不确定性也让这一点无法做到。保证的是三件事：已经确认的工具结果不丢失；副作用不由程序擅自重做（Q13）；压缩前后的不变量依然成立，即首轮 system、保留的用户原话、最近的消息组和交接摘要。
- **怎样更接近不中断**：把 Transcript 以追加方式另存，用于下一次压缩取材，不放进 View；把 LastUsage/UsageAt 写进检查点；把压缩结果和检查点在同一次写入中提交，避免重复做摘要。

**参考**：[Day 3 实践](day-03/day-03-lab.md)、[Day 9 实践](day-09/day-09-lab.md)；源码 [checkpoint.go](../internal/agent/checkpoint.go)、[context_manager.go](../internal/agent/context_manager.go)。

## Q15 子任务 ID 按 task 原文哈希，换个说法就从头跑，这是期望的吗？

*2026-10-07 · 子 agent 之后*

**当前状态**：子任务 ID = 父检查点 ID + `-sub-` + task 文本 SHA-256 的前 12 位十六进制；RunChild 还会核对存档中的原问题，不一致就拒绝复用。spawn_agent 的失败和结果未知里写明 task_id，spawn_agent 可以只传 task_id 续跑已有的子任务（D14 起）。

**问题**：模型用另一种说法把同一个 task 再派一次（意思相同），哈希就变了，子任务从头跑。这是期望行为吗？如果不是，怎样让“意思相同”命中同一个子任务？

**值得琢磨的地方**：内容哈希要解决的是哪一种重复，又在什么场景下才会遇到改写措辞的情况。

**结论要点**
- **哈希能覆盖的情况**：kill -9 后，写前日志按原参数重放，文本完全相同，一定命中。按 Ctrl+C 停止时，结果被回填为“结果未知”，续跑后模型会重新调用，只有它原样照抄 task 时才能命中。改写措辞的问题就出在这里。
- **不是期望行为，但属于可以接受的保守失败**：没有命中，代价是多花时间和 token，还会多占一个子 agent 名额（每次运行上限为 4），旧的子任务检查点被搁置。反过来，如果把“意思相近”误判为同一个任务，就会把 A 的结论当成 B 的结论交给父 agent，而且不会有人察觉。两相比较，宁可多跑一次。
- **改进顺序**：
  1. 让模型直接引用 ID：结果未知或失败时，结果里也带上 task_id；spawn_agent 增加可选的 task_id 参数，用于续跑或取回已有的子任务。是否“同一个任务”由模型显式声明，程序只做精确匹配。
  2. 续跑时，把本次已经派出的子任务（ID、task 摘要、状态）放进上下文，引导模型复用，而不是重新派发。
  3. 语义相似度只用来提示“可能与某个子任务重复”，不自动合并。Day 4 已经说明，相似度超过阈值并不代表内容相同。
- **保留内容哈希作为底线**：它仍然负责重放时的精确命中；RunChild 核对原问题，可以防止同一个 ID 被用于不同的问题。
- **D14 实测补充：父任务 ID 也会变**。上面“原样照抄就能命中”只对命令行 `-resume` 成立，因为它沿用原检查点 ID。观测台停止后续聊，是从检查点取出上下文、启动一个**新检查点 ID** 的进程；综合演练里模型逐字照抄了两个 task（哈希后缀不变），子任务 ID 的前缀却随父 ID 变了，两个子任务都从头跑。已按两步修复：观测台只在“上一轮被打断”时沿用它的检查点 ID（正常结束后的新问题仍用新 ID，不复用旧结论）；再加上面的第 1 条改进，让模型用 task_id 显式引用。只做第一步时，两次真实续聊里模型都改写了 task；加上 task_id 后，模型直接引用、两个子任务都从检查点续跑。见 [Day 14 实践](day-14/day-14-lab.md#41-观测台续聊后子任务没有续跑而是重跑)。

**参考**：[子 agent 实践](bonus-subagents/subagents-lab.md#22-子任务id)；源码 [subagent.go](../internal/agent/subagent.go)、[child.go](../internal/agent/child.go)。
