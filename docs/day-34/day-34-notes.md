# Day 34：终端客户端与会话交互

## 学习目标与术语

学完能说明：为什么同一个 agent 要能接不同的界面，什么样的协议才算“够用”；运行中用户又说了话，harness 该打断还是排队；模型什么时候该停下来问人、怎么问才便宜；恢复、分叉、压缩、撤销这些会话命令各改变了什么，只退一半（只退文件或只退对话）会留下什么错位、怎样补上。

| 术语 | 通俗解释 |
| --- | --- |
| 界面（客户端） | 人看 agent 做事、给它下指令的地方：网页、终端、编辑器插件；它们共用同一个 agent 核心 |
| 插话（steer） | 一轮还在跑时用户又说了一句话，不打断正在做的事，排进下一次模型请求 |
| 结构化提问 | 模型通过一个工具向人提一个问题（可以带几个选项），等人回答再继续 |
| 会话命令 | 不交给模型、由界面直接执行的命令：恢复、分叉、压缩、撤销、切权限 |
| 分叉 | 从过去某一轮之后另起一支，原来后面的轮次保留在原处 |
| 计划批准 | 只读的计划模式下模型给出方案，人确认后切到可写模式让它照做 |

## 1. 一个核心，多个界面

成熟的编码 agent 都把“agent 核心”和“界面”分开：核心负责循环、工具、上下文；界面只负责显示过程和收集人的输入，两者之间是一套结构化协议。这样做的好处：

- 同一个核心可以有网页、终端、编辑器插件、无头（脚本、CI）多种界面；
- 协议是唯一的接口，新加一个界面不用改核心；
- 反过来，写第二个界面是检验协议的好办法：第一个界面里偷偷依赖的东西（比如去解析日志文本、直接读核心的内部文件），在第二个界面里会立刻暴露出来。

“协议够用”的标准：界面需要的每样东西——过程、结局、要人回答的问题——都能从协议里拿到；界面要做的每个动作——开始、停止、回答、插话——都有对应的消息。

## 2. 运行中又说了话：打断还是排队

agent 正在执行一个十几步的任务，用户想补一句“顺便把 B 也改了”或者“别动那个文件”。有两种处理：

| 做法 | 效果 | 适合 |
| --- | --- | --- |
| 打断 | 停下当前这一轮，用户的话作为新的一轮开始 | 方向完全错了，后面的步骤都不该做 |
| 插话 | 不打断正在执行的模型请求或工具，把这句话作为一条用户消息排进**下一次**模型请求 | 补充信息、调整细节，已经做的不用作废 |

插话的几个细节：

- **放在哪**：放在最新的工具结果之后、下一次请求之前，作为真正的用户消息（不是系统提醒），模型会像对待用户原话一样对待它。
- **赶不上怎么办**：模型可能正在写最终回答，这一轮写完就结束了，排着的话没被用上。不能悄悄丢掉：交还给界面，作为下一轮的问题发出去。
- **同样要过检查**：用户的话在进模型之前要经过的检查（比如拦截敏感信息的 hook），插话一样要过。

## 3. 模型什么时候该问人

模型拿到一个含糊的问题时，常见的失败是“自己猜”：读一大圈代码、试几种理解，最后列出五种可能让人挑。花了几十次请求，问题还在原地。另一种失败相反：动不动就问，能自己查到的也问。

一个好的提问工具要让“问”变得便宜，同时在描述里写清楚边界：

- **该问的**：需求有歧义、几种做法都合理而选错代价大、需要用户确认偏好或做决定。
- **不该问的**：读代码、看文档、跑一条命令就能知道的事。
- **怎么问**：一次一个问题；能列出 2–4 个候选就列出来，人点一下就行，也允许人另写。

harness 这一侧要处理的：

| 情况 | 处理 |
| --- | --- |
| 没有能当场回答的人（脚本、队列、子 agent） | 不提供这个工具；或者明确返回“没人能答”，让模型把问题写进最终回答 |
| 人一直没回答 | 设一个等待上限；到时告诉模型“没回答，按最稳妥、最容易撤回的做法继续，并在结尾说明” |
| 中断后续跑 | 再问一遍无妨，提问没有副作用 |

## 4. 会话命令

| 命令 | 改变了什么 | 不改变什么 |
| --- | --- | --- |
| 恢复 | 接着某一轮继续聊 | 那一轮之后的记录 |
| 分叉 | 从第 n 轮之后另起一支 | 原来第 n 轮之后的各轮（仍可以恢复回去）、磁盘上的文件 |
| 手动压缩 | 下一次请求前先把旧内容摘要掉 | 用户原话（压缩时保留） |
| 撤销 | 第 n 轮及之后：文件与对话一起退回 | 被撤销轮次的记录（标成已撤销，不删） |

文件与对话一起退，是最安全的默认：模型看到的历史和磁盘上的文件是同一个时刻的。只退一半会留下错位：

| 只退一半 | 错位 | 补救 |
| --- | --- | --- |
| 只退文件，对话不退 | 模型记得自己改过，但磁盘上已经不是那样了 | 下一轮开头用系统提醒告诉它：哪些文件被恢复了，改之前先重新读 |
| 只退对话，文件不动 | 模型不记得之后各轮的改动，磁盘上却有 | 下一轮开头告诉它：哪些文件被之后的轮次改过、改动还在，改之前先读当前内容 |
| 分叉 | 同“只退对话” | 同上 |

再配上“改之前必须读过、读过之后又被改就拒绝”这条规则（读后才写），即使模型没注意提醒，也不会对着一份它以为是旧样子的文件直接改。

## 5. 计划批准

计划模式下工具只读，模型只能读和想、给出方案。人看完方案，有三种回应：同意、提修改意见、放弃。“同意”应该是一个动作而不是一句需要人打字的话：切到可写模式，并告诉模型“计划已批准，照做”。这样批准和执行之间不会再被误解，记录里也清楚地留下“人在这里批准了”。

## 自测

1. 为什么说写第二个界面能检验协议？
2. 插话和打断各适合什么情况？插话为什么要作为用户消息而不是系统提醒？
3. 插话赶不上这一轮时该怎么处理？
4. 提问工具的描述里要写清楚什么？没有人能回答时怎么办？
5. 只退文件、只退对话各留下什么错位？怎么补救？
6. 为什么“批准计划”最好是一个动作，而不是让人打一句“可以了”？

### 自测答案

1. 第一个界面往往会偷偷依赖协议之外的东西（解析日志、读内部文件）；第二个界面只能用协议，缺什么马上暴露。两个界面都能只靠协议完成同样的事，协议才算够用。
2. 打断适合方向错了、后面的步骤都不该做；插话适合补充和调整、已做的不用作废。插话是用户的原话，作为用户消息模型才会按用户指令对待，记忆、压缩时也按用户原话保留；系统提醒是 harness 的说明，分量和用途都不同。
3. 不能丢掉：随这一轮的结局交还给界面，界面把它作为下一轮的问题发出去。
4. 该问什么（歧义、选错代价大、需要用户决定）、不该问什么（能自己查到的）、一次一个、可以给选项。没人能答时不提供这个工具，或者如实返回“没人能答”，让模型把问题写进最终回答。
5. 只退文件：模型以为自己的改动还在；只退对话：模型不知道之后的改动。都要在下一轮用提醒说明哪些文件变了，并靠“读后才写”兜底。
6. 一个动作同时完成“切到可写”和“告诉模型照做”，不会因为措辞含糊被误解，记录里也明确留下批准的时刻。
