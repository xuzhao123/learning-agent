# Day 17：失败归因——从失败样本到根因

## 学习目标

读完本文，应能回答以下问题：

1. 失败归因要回答哪两个问题？为什么“模型幻觉了”不算归因？
2. 为什么只记“第一个上游错误”？
3. 开放编码和轴心编码是什么？失败分类为什么要从数据里长出来，而不是先套一张通用表？
4. 自动归因（让模型找出错的那一步）现在有多可靠？
5. 什么是反事实回放？它怎样把“我觉得是这一步”变成证据？
6. 稳定失败和偶发失败、agent 的错和打分器的错，各要怎样区分？
7. 归因的产出应该是什么？怎样确认修复真的有效？

## 1. 归因要回答什么

一次失败的 agent 运行，往往有十几步：几次模型决定、几次工具调用、一次上下文压缩。归因要回答两个问题（Who&When 论文的定义）：

- **在哪一步**：哪一步是**决定性错误**，即改掉它，结局就会变好；
- **为什么**：这一步错的原因属于哪一类，例如工具描述误导、检索没召回、预算不够、提示自相矛盾。

“模型幻觉了”“模型不够聪明”说不出在哪一步、改什么，没法指导修复。好的归因结论像这样：“第 2 轮，模型看到‘结果未知’后去调用状态查询工具；而该工具的描述要求‘pending 时用相同 ID 继续查询’，于是陷入循环，直到被熔断拦下。”

## 2. 第一个上游错误

错误会连锁：第 2 步查错了资料，第 5 步就会基于错资料计算，第 8 步给出错答案。如果把三处都记成失败，分类计数会被放大，修复也会找错地方。

所以读轨迹时**只记第一个上游错误**，后面的多半是它引起的。这也是 Hamel Husain 与 Shreya Shankar 在 LLM 评测课程里强调的做法。

判断“上游”时沿数据流往回追：答案错 ← 用了哪份证据？← 证据是怎么拿到的？← 工具为什么这样调用？← 模型当时看到了什么？

## 3. 开放编码与轴心编码

这两个词来自质性研究（扎根理论），被借用到 LLM 应用的错误分析：

1. **开放编码**：逐条读失败轨迹，用自己的话写一句自由备注，只写第一个上游错误。此时不要套类别。例如：“超时后模型去查状态，状态工具永远返回 pending，模型照描述一直查”。
2. **轴心编码**：把备注里相似的归成一类，给类别起名并计数。例如上面这条与“检索为空后不停换关键词重搜”可以归到同一类：“无进展循环：工具结果不变，模型仍重复尝试”。
3. **迭代到饱和**：继续读新的失败，直到不再出现新类别。经验值是读到约 100 条；起步时先亲手标 30 条左右，再让模型帮忙找相似样本。

**为什么不先套一张通用分类表？** 通用表（“推理错误”“工具错误”“规划错误”）太粗，计数出来也不知道改什么。从自己系统的失败里长出来的类别，才对应具体的修复点。

公开的分类可以拿来**对照**，检查自己有没有漏掉的方向。比如 MAST（对 7 个多 agent 框架、1600 多条轨迹的标注）把失败分成三大类、14 种：

- 规格问题：没遵守任务要求、没遵守角色、重复步骤、丢失对话历史、不知道何时结束；
- agent 间失配：重置对话、不澄清、偏离任务、隐瞒信息、忽略他人输入、推理与行动不一致；
- 任务验证：提前结束、没有验证、验证错误。

其中“重复步骤”“不知道何时结束”“没有验证”对单 agent 同样常见。

## 4. 归因卡片：程序摆线索，人下结论

让模型自动找出决定性错误，目前并不可靠。Who&When（ICML 2025）在 127 个多 agent 系统的失败日志上比较了三种方法：

| 方法 | 做法 | 特点 |
| --- | --- | --- |
| 一次看全（all-at-once） | 把整条轨迹交给模型，直接问哪一步错了 | 判断“哪个 agent 负责”较好 |
| 逐步判断（step-by-step） | 从头逐步问“这一步错了吗” | 定位步骤略好，成本高，容易过早下结论 |
| 二分查找（binary search） | 把轨迹对半分，问错误在前半还是后半 | 调用次数少，但每次判断出错就会偏离 |

最好的方法找对负责 agent 的准确率约 53.5%，**找对出错步骤只有 14.2%**，推理模型也没有明显改善。

所以合理的分工是：**程序做“必然正确”的部分**——列出工具序列、标出第一个非成功的工具结果、第一个重复调用、非正常结局、哪些检查没通过；**根因由人读轨迹后判断**。一张归因卡片大致包含：

```text
题目 / 结局 / 同题其他尝试的结果（稳定失败还是偶发）
没通过的检查：评审：如实说明结果未知……（PASS 0 / FAIL 3）
第一个异常信号：第 1 轮 slow_job 返回 unknown
工具序列：第1轮 slow_job → unknown；第2轮 check_task_status → ok；第3轮 check_task_status → ok
开放编码：____________   归类：________
```

## 5. 反事实回放：用实验确认根因

读轨迹得出的根因只是假设。**反事实回放**把它变成实验：

1. 提出假设：“第 k 轮之后的那个决定是决定性错误”；
2. 从检查点恢复到第 k 轮结束时的状态，前面的步骤原样保留；
3. 在这里改变一处，例如插入一条纠正、换掉一段工具描述，然后让 agent 接着跑；
4. 多跑几次（结果有随机性），看结局是否**翻转**：
   - 多数次数翻转为成功：假设得到支持，这一步就是决定性错误，修复方向也随之明确；
   - 没有翻转：错误在别处、不止一处，或者这个改动不够，重新提出假设。

AgenTracer（2025）用这种方法给失败轨迹自动标注决定性步骤；REFLECT（2026）先让模型提出候选步骤，再做有针对性的回放验证。有针对性的纠正比随机重采样的修复成功率高约 42 个百分点。两者都说明：**有回放验证的归因比只读轨迹准确得多**。

做回放有三个前提：

- 能从中间状态恢复，例如检查点或事件日志；
- 前缀要**原样**保留，不能从头重跑，否则前面的随机性会混进来；
- 回放与原运行除了那一处改动外，参数、模型、工具都相同。

回放成功只证明“改这一处足以翻转”，不等于找到了唯一的修复方式。插入一句纠正是诊断手段；真正的修复通常落在工具描述、系统规则或执行器上，还要再用回归评测验证。

## 6. 先分清是谁错、错得稳不稳定

**agent 的错与打分器的错**：每条失败都先问一句“如果我是评审，会判它错吗？”。打分器的典型错误有：

- 格式过严：`96.12` 和 `96.124991`；
- 证据不全：评审没看到执行器重试过三次，就判 agent“编造”；
- 期望值写死：时间、网页内容这类会变的东西。

打分器错了就改打分器、重新打分，不能算进 agent 的失败分布。

**稳定失败与偶发失败**：同一道题 k 次尝试里

- 一次都没过：**稳定失败**，通常是系统性原因，优先归因，修复后效果明显；
- 有过有不过：**偶发失败**，可能来自模型随机性、外部服务抖动、竞态。要多跑几次再下结论，修复后用 pass^k 观察。

**静默失败**：轨迹里没有任何报错，工具都成功，答案却错了。随着模型变强，这类失败占比越来越高，也最难归因：需要对照参考答案逐步核对模型看到了什么、推出了什么。

## 7. 从归因到修复：闭环

```text
失败样本 → 归因卡片 → 开放编码（第一个上游错误）→ 轴心编码（分类计数）
       → 选计数最多、证据最清楚的根因 → 反事实回放验证
       → 实施修复 → 回归评测（同一批题，逐题配对对比基线）
       → 失败样本沉淀为回归题
```

几条原则：

- **按影响排序**：先修计数多、稳定复现、影响面大的类别；
- **一次只改一处**，否则回归结果分不清是哪个改动起的作用；
- **修复必须被评测证实**：目标题从失败变成通过，同时没有别的题从“全对”变成“没全对”；
- **报告写证据链**：轨迹片段、回放结果、修复前后的分数，而不是只写结论。

## 8. 自测

| 问题 | 参考答案 |
| --- | --- |
| 归因要回答哪两个问题？ | 决定性错误在哪一步，以及原因属于哪一类。 |
| 轨迹里有三处错误，为什么只记第一处？ | 后面的错误多由它连锁引起，全记会放大计数、找错修复点。 |
| 开放编码与轴心编码的顺序能反过来吗？ | 不宜。先自由描述，再从备注里归纳类别；先套类别会遗漏自己系统特有的失败。 |
| 为什么不直接让模型自动标出错的步骤？ | 公开评测中最好的方法找对步骤也只有约 14%；程序给线索，人下结论更可靠。 |
| 回放验证时为什么不能从头重跑？ | 前缀的随机性会混进来，分不清结局变化是改动引起的还是前面走了不同的路。 |
| 回放 3 次都翻转了，可以直接上线这句纠正吗？ | 不应当。它只证明那一步是决定性的；修复要落在工具描述、规则或执行器上，并跑回归评测。 |
| 评审判错了一个正确答案，算 agent 的失败吗？ | 不算。修正打分器（补证据、改评分标准）后重新打分。 |
| 同一道题 3 次里过 1 次，属于哪种失败？优先级如何？ | 偶发失败；要多跑几次确认，通常排在稳定失败之后，修复后看 pass^k。 |
