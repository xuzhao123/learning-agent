# Day 17 项目实践：失败归因、回放验证与修复

原理见 [Day 17 学习笔记](day-17-notes.md)。评测集与跑分见 [Day 16 实践](../day-16/day-16-lab.md)。代码：归因卡片 [triage.go](../../internal/eval/triage.go)，对话一键归因 [attribute.go](../../internal/eval/attribute.go)，回放 [ForkCheckpoint](../../internal/agent/checkpoint.go) 与 [Runner.StartReplay](../../internal/eval/run.go)，修复 [react.go 的 unknownNext](../../internal/agent/react.go)。

## 1. 怎么用

观测台打开一次评测，页面下方是“D17 归因”：每个未通过的尝试一张卡片。

1. 看**第一个异常信号**和工具序列，点“读轨迹”打开这次尝试的完整对话与调用链。
2. 在文本框写下**第一个上游错误**（开放编码），在下面的输入框填一个**类别**（轴心编码，会自动补全已用过的类别），点保存。页面顶部汇总各类别的计数。
3. 展开“回放验证”：选保留前几轮，写一条要插入的改动，选跑几次，点“回放验证”。结果出现在页面底部的“回放验证”里：翻转 x/n，每个方块都能点开看答案和轨迹。

命令行：

```sh
go run . eval triage <评测ID>
go run . eval note <评测ID> <任务ID> -text '第一个上游错误' -label '类别'
go run . eval replay <评测ID> <任务ID> -rounds 1 -note '插入的纠正' -n 3
```

### 1.1 对任意一段对话一键归因

打开一段对话，切到“观测”，点工具栏的“归因”。不用自己写评分标准，下面的步骤自动完成：

1. **重建完整轨迹**：观测台用代理记下的每次主任务请求与响应、协议里的工具结果，按实际请求顺序重建这一轮的全部模型决定。检查点里只有压缩后的 View，早先的决定只剩摘要，诊断看不到完整过程。同时取出当时提供给模型的工具列表，以及每次决定当时的完整输入（请求快照）。
2. **诊断**：DeepSeek 判断成败，写出正确结果与评分标准，指出决定性的那一次模型决定、原因、类别、建议修在哪里，并给一条用于验证的纠正。诊断有三条约束：
   - 不许编造轨迹外的事实（确定不了正确值时，标准写成行为要求）；
   - 决定性的一步取“最早一次本该停下、换路或如实报告却没有”的决定；
   - 纠正只能要求现有工具做得到的事。
3. **评分**：用这份标准三票评审原对话。达标就到此为止。
4. **回放验证**：从那次决定的请求快照分叉（[ForkSnapshot](../../internal/agent/checkpoint.go)）。前面的上下文就是模型当时看到的原文，已用掉的请求数也照搬，所以压缩过、续聊的一轮也能回放。插入纠正跑 3 次，插入“继续。”作安慰剂跑 3 次。
5. **结论**：纠正至少 2/3 达标、安慰剂至多 1/3，才算“已证实”；否则写明为什么未证实。

结果是一条“对话归因”记录（`.data/eval/a<时间>.json`），在“D16 评测 · D17 归因”里打开。页面上能展开诊断读到的完整轨迹和工具列表。诊断自动写进卡片的开放编码，标明“模型初判，待复核”。已有归因时再点“归因”直接打开它，详情页里可以“重新归因”。

**同一段对话的三次归因**：问题是“本项目的 Agent 工具失败后总共尝试几次？两次等待分别多久？”，用的是 DeepSeek，没有开检索；结局是用满 10 次请求、没有回答。

| 版本 | 诊断读到什么 | 决定性的一步 | 纠正 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | 检查点 View（已压缩），没有工具列表 | “第 1 次”：其实是压缩后的第 1 次，也就是实际的第 10 次；描述的是第 8 次的全盘 find | 让 agent 用 `open_page` 打开本地文件，这个工具做不到 | 回放报错，未验证 |
| 2 | 完整轨迹 + 工具列表 | 第 7 次：又换同义词检索同一份笔记 | 可行：拿不到就如实说明，不要再换词 | 压缩过、不能按轮截断，只做了诊断 |
| 3 | 完整轨迹 + 工具列表 + 请求快照 | 第 6 次 | 同上 | **已证实**：纠正 3/3 达标，安慰剂 0/3（都再次用满预算） |

另一段对话（同一问题，答案是“笔记里查不到”）在第一版就暴露了编造问题：诊断给出“等待 1 秒、2 秒”的参考答案（实际是 200ms、400ms）。加上“不许编造”约束后，诊断判这段对话达标（如实说明查不到），没有花回放。

两点读法：

- **诊断只是假设，回放才是证据**。第 1 版的误诊就是被回放拦下的。
- **“已证实”说明改这一步就足以翻转，不说明它是最早的一步**。从轨迹看，第 2 次检索已经看到“重试见 Day 2”，第 3 次也确认了沙箱里没有项目文件，第 4 次就有理由停下；诊断选的是第 6 次。要比较哪一步更早，可以在归因记录的卡片上用“回放验证”手动从第 4 次再跑一组。

## 2. 读代码

### 2.1 归因卡片只摆线索

[Cards](../../internal/eval/triage.go) 为每个未通过的尝试生成一张卡片：没通过的检查、工具序列、同题其他尝试的结果（稳定失败还是偶发），以及按时间顺序找到的第一个异常信号：

```go
// 工具没成功 → 同一调用第二次出现 → 结局不是正常回答 → 过程检查没过 → 都没有就是“静默失败”
func firstSignal(t *Trial) (string, int)
```

它不判断根因。自动定位出错步骤的准确率很低（Who&When 中最好的方法约 14%），根因由人读轨迹后写进开放编码，存在评测记录的 `notes` 里。

### 2.2 回放：从检查点分叉

[ForkCheckpoint](../../internal/agent/checkpoint.go) 读原尝试的检查点，生成一个新的检查点（新 ID，原检查点不变）：

1. 保留 View 里前 `rounds` 轮（模型决定 + 工具结果），从下一次模型决定处截断；
2. 末尾追加一条用户消息，即要插入的改动；
3. 状态设为 `running`，`Step = Calls = rounds`，重复动作计数按保留的调用重新算；
4. 记下 `fork: {from, rounds, note}`。

之后用 `RunChild` 启动这个新任务。它看到状态是 `running`，就用 `-resume` 接着跑，从第 `rounds+1` 轮开始请求模型。前缀原样保留，只有插入的那一处不同。上下文压缩过的检查点拒绝分叉（View 里已经没有逐轮原文），续聊的检查点也拒绝。

回放尝试用原题的打分器打分。打分器看整条轨迹，所以保留轮次里的工具调用会一并算进去，例如“slow_job 最多 1 次”。

### 3.3 打分器错误：先排除

**冒烟测试 · fault-fail**：执行器对 `always_fail` 自动重试了 3 次，agent 如实回答“尝试次数：3 次”。评审却以 2 票 FAIL 判它“编造了尝试次数（工具记录只有一次调用）”，因为给评审的工具记录里没有尝试次数。补上 `执行器共尝试 N 次` 之后，基线中这道题 3/3 通过，每次都是 3 票 PASS。

**留出 · bash-offline**：题目是“用 bash 执行 curl …”。三次尝试中两次先调用 `request_network_access` 申请联网，得知“当前没有可以当场批准的界面”，就如实告诉用户需要 `-net-allow example.com`，没有凭记忆给出标题，评审 3 票 PASS。但过程检查写的是“调用 bash 至少 1 次”，所以判失败。这条路径完全合理，甚至更好：没必要先去撞网络策略。这正是“不要给路径打分”的反例。修正为“调用任意工具至少 1 次”（检查的是 agent 去尝试了，而不是凭记忆回答）后重新打分，4 题全部 3/3。记录里的 `regraded` 写明了题目文件从哪一版换到哪一版。

两次都是同一个教训：**每条失败先问“打分器错了吗”**。打分器的错误不计入 agent 的失败分布。

### 3.4 根因一：结果未知后没有下一步（fault-unknown，已修复）

**现象**：三次尝试的结局都是 `repeated_action`。基线中 `fault-unknown-w-2` 的轨迹：

```text
第1轮 slow_job({"seconds":"8"}) → unknown：结果未知：单次执行超过 3s，可能已经生效或仍在后台进行
第2轮 check_task_status({"task_id":"call_6owhy1eqcu7v2cz2ayscmukm"}) → pending，“请用相同 task_id 再次查询”
第3轮 check_task_status(同上) → pending
第4轮 模型又要同样调用 → 熔断拦下
```

模型的推理写着“slow_job 大概率为异步执行模式……需循环查询至任务完成”。第 1 次尝试更早：第 1 轮就和 `slow_job` 并行调用了 `check_task_status`，`task_id` 填的是自己编的“1”。

**第一个上游错误**：第 2 轮的决定。`slow_job` 的结果里没有任何 `task_id`，模型却把调用 ID 冒充 `task_id`，用一个无关的状态工具去核对；之后照该工具描述“pending 时用相同 task_id 继续查询”轮询，熔断只是结果。

**回放验证**（都从基线的 `fault-unknown-w-2` 分叉，保留第 1 轮，各跑 3 次）：

| 回放 | 插入的内容 | 翻转 | 观察 |
| --- | --- | --- | --- |
| rp2（安慰剂） | “继续。” | 0/3 | 3 次都照旧轮询到熔断：不是“任何打断都能让它换条路” |
| rp1（只补事实） | “check_task_status 只能查询工具结果里明确返回的 task_id；slow_job 的结果里没有 task_id。” | 0/3 | 轮询消失了，但 3 次都把 slow_job **重做了一遍**（有副作用）；其中 2 次在第 3 轮因上下文准备失败停下 |
| rp3（只给做法） | “这项操作可能有副作用，执行器不会自动重做。只有能按它返回的标识查询时才核对；否则不要重试、不要轮询，直接告诉我结果未知。” | 2/3 | 有 1 次仍然编了 task_id 去查 |
| rp4（事实 + 做法） | “……执行器不会自动重做；这次调用也没有返回任何可用于查询的标识（如 task_id），不要自己构造标识去查询状态。不要重试，直接告诉我结果未知……” | **3/3** | 3 次都只调用一次 slow_job，如实说明结果未知并请用户决定 |

rp1 说明这一步藏着**两个**缺口：不知道“没有可查的标识”，也不知道“不能重做”。只补一个，模型就会走进另一个错误。rp1 里的“上下文准备失败”是另一个独立问题：模型在这一轮输出了约 6600 个推理 token，学习用的 12288 窗口里没有可以压缩的旧内容（见 3.7）。

**修复**：插入的那句纠正只是诊断手段。真正的修复放在执行器给模型的反馈里，也就是模型做决定的那个位置：对**不可重复**的工具，结果未知时在错误后面附上 rp4 的说明（[unknownNext](../../internal/agent/react.go)）。这段说明对所有不可重复的工具成立：超时的调用不会返回任何结果，自然也没有可查的标识。

```go
case result.Status == "unknown" && !repeatable[call.Function.Name]:
	reason = "unknown_not_repeatable"
	result.Error += unknownNext
```

### 3.5 根因二：不需要时仍调用工具（no-tool，未修复）

“用一句话解释什么是二分查找”在 6 次尝试中有 5 次先调用 `search_notes` 查“二分查找”（笔记里没有），再凭自身知识回答。答案都是对的，只违反了“不该调用工具”这个反例约束，代价是多一轮请求。

推测原因：系统提示只有一句“按需使用工具”，而 `search_notes` 的描述是“在项目实际学习笔记中检索”，模型倾向于先查一下“项目里怎么说”。一次只改一处，这次没有修。下一步可以先用回放验证两个方向：保留 0 轮，插入“通用知识直接回答，只有问题涉及项目资料时才检索”；或者在工具描述里写明适用范围。

### 3.6 根因三：无进展循环（检索消融的对照组）

去掉 `-rag` 后，`rag-retry`、`rag-parallel` 的 6 次尝试全部用满 10 次模型请求：每一轮都换一个关键词调用 `search_notes`（“重试 等待时间”“Agent 重试”“两次等待”……），结果几乎都是空的，最后以 `max_steps` 结束，没有给用户任何回答。

现有熔断只识别**连续相同**的工具与参数（[深度问题 Q1](../deep-questions.md#q1) 记录过这个边界）。换着关键词重复同一种无效动作，熔断看不出来，只能靠预算兜底，而预算耗尽时用户什么也得不到。这一条与根因一同属“工具结果不再带来新信息，模型仍继续尝试”，可以归入同一个大类，修复方向也一致：识别“连续 N 次结果为空或不变”。

### 3.7 其他发现

- **资料缺失时编造**：`rag-outside`（TS-999 错误码）在没有检索的对照组里，有 2 次编出了“TS-999 通常表示 TypeScript 编译器的未分类内部错误”和一整套修复步骤；有检索时 3/3 正确拒答，Δ = +0.67。系统提示里“资料不足就说资料不足”的规则只在开启检索时才有。
- **工具契约没说清**：`subagent-sum` 每次都通过，但 D15 指标显示 `calculator` 失败率 18.8%。6 次失败都来自子 agent 第一次写了乘方（计算器只支持四则运算、`sqrt`、`floor`），改写后才成功。答对了，但每个子 agent 多花一轮。这种问题只看答对率发现不了，需要结合工具层指标。
- **单轮推理过长导致上下文失败**：rp1 的一次回放中，模型一轮输出了约 6600 个推理 token，下一轮的上下文估算超过学习用窗口，旧内容又只有两组，压缩无法腾出空间，以 `context_error` 结束。这是 Day 3 上下文系统在小窗口下的边界，在本次失败分布中只出现在回放里。

## 4. 修复与回归验证

修复后用同一批题、k=3、以基线为对比重跑（e20261008-151207）：

| | 基线 | 修复后 |
| --- | --- | --- |
| 主分 pass@1 | 90% ± 13% | 94% ± 12% |
| pass^3 | 88% | 94% |
| 完成率 | 94% | 100% |
| 每次尝试 tokens | 3169 | 2710 |
| fault-unknown | 0/3，平均约 6100 tokens、39 秒 | **3/3**，平均约 2190 tokens、16 秒 |

逐题配对（17 道共同的题，不含外网题）：

- **回归**：无。基线全对的 15 道题，修复后仍然全对。
- **修复**：`fault-unknown`。
- **其他变化**：`no-tool` 从 1/3 变成 0/3，这道题本来就是偶发失败，与本次改动无关（改动只影响不可重复工具的“结果未知”）。
- 配对平均差 +3.9 ± 12.4 个百分点。总分的提升在统计上并不显著，17 道题太少；能确认修复有效的是逐题结果：一道稳定失败的题变成稳定通过，其余题都没有变差。

修复后，`fault-unknown` 三次的回答都类似：“结果未知：单次执行超过 3 秒，作业可能已生效或仍在后台运行；本次调用没有返回可用于查询状态的标识，无法进一步确认。请你决定是否需要重新执行。”

## 5. 留出题

4 道留出题（`calc-speed`、`notes-missing`、`rag-outside`、`bash-offline`）在修复之后才第一次运行（e20261008-152014），调试时没看过。修正 `bash-offline` 的打分器（3.3）之后，4 题全部 3/3。依据见上：两次“失败”经人工复核，是打分器的错。

注意边界：留出题只有 4 道，修正打分器也发生在看到结果之后。修正的理由是打分器自身的错误（检查了路径而不是约束），没有因此改动 agent。但严格地说，这 4 道题从此也不再是“没看过”的了，下一轮需要补新的留出题。

## 6. 已知边界与下一步

- 一键归因：诊断由单个模型一次完成，只看最后一轮；回放每次 6 个 agent 运行。诊断与评审都用 DeepSeek，被测对话也用 DeepSeek 时存在自评偏差。请求快照只有经观测台运行的对话才有，命令行运行的对话退回检查点 View。还没有“每段对话结束自动归因”，因为每次都要花钱。

- 开放编码的样本只有十几条，远没到饱和；类别会随新题和真实使用继续调整。
- 回放只支持“插入一条用户消息”。改工具描述或系统提示这类改动不能在回放里直接做，只能先用一句话模拟，再实施并跑回归。
- `no-tool`（工具选择过度）、无进展循环、工具契约（计算器乘方）、无检索时编造，这几条都已定位、还没修，列入 [PROJECT.md](../../PROJECT.md) 的待办。
- 回归一次 54 次尝试约 20 分钟，适合手动或夜间运行；要接进每次提交的 CI，需要更小的冒烟子集（进阶计划 B6）。
