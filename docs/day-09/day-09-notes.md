# Day 9：检查点与恢复——进程死了，任务还能接着跑

## 学习目标

读完本文，应能回答以下问题：

1. 一个 agent 任务要恢复，需要保存哪些状态？哪些不需要保存？
2. 检查点应该在什么时候写？“写前日志”解决什么问题？
3. 怎样写文件，才能保证崩溃后读到的不是半个文件？
4. 恢复时发现上次有一批工具调用没有结果，该怎样处理？
5. 快照式恢复和事件重放式恢复有什么区别？
6. 为什么预算和熔断计数也必须保存？
7. 同一个任务被两个进程同时续跑，会出什么问题？怎样防止？

## 1. 为什么需要检查点

agent 任务越来越长：一次深度调研可能要几十次模型请求、几十分钟。这期间进程可能因为很多原因中断：

- 发布新版本、机器维护，进程收到 SIGTERM；
- 内存不足被系统杀掉（OOM），或被 SIGKILL 直接杀掉；
- 模型服务短暂不可用，任务以错误退出；
- 用户关掉了终端。

如果只能从头再来，代价有三层：已经花掉的时间和 token 白费；做过的有副作用的操作会再做一遍；长任务在不稳定的环境里可能永远完成不了。

检查点（checkpoint）就是在执行途中把“恢复所需的全部状态”写到进程外，之后由新进程读出来接着跑。

## 2. 要保存什么

判断标准只有一个：**新进程只读这份文件，能不能做出和原进程一样的下一步？**

| 状态 | 是否保存 | 原因 |
| --- | --- | --- |
| 模型看到的消息（system、用户问题、assistant 回答、工具结果） | 保存 | 下一次请求就是它 |
| 已用的预算（请求次数、token、费用） | 保存 | 否则“崩溃—恢复”会把预算清零 |
| 熔断与重复检测的计数 | 保存 | 否则死循环可以靠崩溃绕过熔断 |
| 运行配置（工具开关、模型、时限） | 保存 | 恢复后的工具集合必须和原来一致 |
| 已决定、还没有结果的动作 | 保存 | 见第 3 节 |
| 结局（完成、停止原因、答案） | 保存 | 调度方据此决定续跑、放弃还是直接返回 |
| 缓存、索引等派生数据 | 不保存 | 可以重建 |
| 网络连接、子进程、文件句柄 | 不能保存 | 恢复时重新建立 |

最后一行常被忽略：MCP server 是个子进程，数据库连接是个 socket，它们都没法写进文件。恢复时要重新连接，而且要接受**外部世界可能已经变了**：上次读到的文件可能已被修改，上次查的价格可能已经过期。

## 3. 什么时候写

### 3.1 边界

一轮 agent 循环有两个天然边界：

```text
  ┌─ 模型请求 ─┐            ┌─ 执行工具 ─┐
──┤            ├─ ① ────────┤            ├─ ② ──▶ 下一轮
  └────────────┘ 模型决定了   └────────────┘ 结果都已写回
                 要调用什么
```

只在 ② 写检查点，会漏掉一种情况：进程死在执行工具的途中，新进程只知道上一轮结束时的状态，会重新请求模型；模型可能做出不同的决定，而上次已经发出的调用（比如一封邮件）无人知晓。

### 3.2 写前日志

在 ① 也写一次：**先把“要执行哪些调用”落盘，再执行**。这就是数据库里的写前日志（write-ahead logging）：先记录意图，再产生效果。恢复时只要看到“有调用、没结果”，就知道这一批是在执行中断的，可以逐项处理（第 5 节）。

按崩溃位置列出来：

| 进程死在…… | 最后一次检查点 | 恢复时 |
| --- | --- | --- |
| 模型请求途中 | 上一轮的 ② | 重新请求模型。只浪费一次请求，没有副作用 |
| ① 之后、工具开始前 | ① | 这批调用都没执行，但新进程无法确定，只能按“结果未知”处理 |
| 工具执行途中 | ① | 有的执行了、有的没有，逐项处理 |
| ② 之后 | ② | 直接进入下一轮 |

第二行说明写前日志的代价：它让“没开始”和“做了一半”看起来一样，所以只能按保守的一侧处理。想区分得更细，就要在每个工具开始和结束时各写一次，用更多的写入换更精确的恢复。

## 4. 怎样写才可靠

**原子替换**。直接覆盖写文件时，进程若死在写到一半，就留下半个文件，新旧版本都没了。标准做法：

```text
写入 checkpoint.json.tmp  →  rename 成 checkpoint.json
```

在 POSIX 文件系统上，同一目录内的 rename 是原子的：任何时刻读到的要么是完整的旧版本，要么是完整的新版本。

**持久性**。rename 完成只说明数据进了操作系统的页缓存。进程崩溃不影响页缓存，数据最终会写入磁盘；整机断电则可能丢失。要防断电，需要 `fsync` 文件、再 `fsync` 目录，每次写入多花几毫秒。这是一个取舍：多数 agent 场景里，丢掉最后一轮的结果只意味着重做一轮。

**单一写者**。同一个检查点同时只能有一个进程在写，否则两份进度互相覆盖。第 7 节讲怎样保证。

## 5. 恢复时怎样处理“有调用、没结果”

逐项看工具的性质：

| 工具性质 | 例子 | 恢复时 |
| --- | --- | --- |
| 只读 | 查询、搜索、计算 | 直接重新执行 |
| 带幂等键 | 带订单号的下单、带任务ID的子任务 | 用同一个键重新执行，服务端保证只生效一次 |
| 有副作用、没有幂等键 | 发邮件、写文件、调用第三方 API | 不重做；回填“结果未知”，由模型或人先核对外部状态 |

协议还有一个硬约束：每个 `tool_call_id` 都必须有对应的 tool 结果，否则下一次请求会被拒绝。所以“不重做”也要写一条结果，内容说清楚是“结果未知，可能已执行”，而不是“失败”。

**核对**（reconciliation）比重做更可靠：恢复后先查一下外部世界。比如查发件箱有没有这封邮件、查订单状态、查目标文件的修改时间。这要求系统提供可查询的接口；没有接口，“结果未知”就只能交给人。

## 6. 两种恢复模型

| | 快照式 | 事件重放式 |
| --- | --- | --- |
| 保存什么 | 每个边界的完整状态 | 每个事件（“调用了 X，结果是 Y”） |
| 怎样恢复 | 读最新快照，接着跑 | 从头重新执行代码，遇到已记录的事件直接用记录的结果，不真的执行 |
| 对代码的要求 | 状态能完整序列化 | 代码必须是确定性的：同样的事件序列走同样的路径 |
| 代表 | LangGraph 的 checkpointer（每一步保存图的状态） | Temporal（Workflow 按事件历史重放，Activity 的结果写进历史） |

agent 循环里，“确定性”主要被模型打破：同样的输入，模型可能给出不同的回答。所以事件重放式系统都把模型调用当作一种 Activity，记下它的结果，重放时直接使用。两种模型殊途同归：**模型的每个决定一旦记录，就不能再改**。

## 7. 一个任务只能有一个执行者

假设进程 A 卡顿了几十秒，监控以为它死了，又启动进程 B 续跑同一个任务。A 恢复后，两个进程会同时执行、同时写检查点，副作用加倍，进度互相覆盖。

防止的办法是让执行者**独占**任务：

- **单机**：文件锁（`flock`）。持锁进程无论怎么退出，包括被 SIGKILL，操作系统都会释放锁。所以“状态是运行中，但锁没人持有”就说明上一个进程已经死了，可以接手。
- **多机**：租约（lease）。执行者在数据库里登记“我持有这个任务到 T 时刻”，并定期续期（心跳）。过期没续期，别人才能接手。租约要配合**防护令牌**（fencing token）：每次接手时令牌加一，写入时带上令牌，旧执行者醒来后的写入因令牌过期被拒绝。

## 8. 恢复时的配置与版本

- **配置要和原来一致**：保存启动参数，恢复时原样使用。否则原来开了检索、恢复后没开，模型会调用一个不存在的工具。
- **代码版本可能变了**：发布新版本后续跑旧任务，检查点格式、工具名、system prompt 都可能不同。常见做法是在检查点里记版本号，不兼容时拒绝续跑或做迁移。
- **哪些停止原因值得续跑**：被取消、超时、模型服务暂时故障，续跑有意义；预算耗尽、熔断、模型给出无效调用，续跑会得到同样的结果，应当如实报告，不自动续跑。

## 9. 自测

**1. 只在每轮结束时写检查点，进程死在发邮件的工具里，恢复后会怎样？**
新进程从上一轮结束处重新请求模型，模型可能再次决定发邮件，导致重复发送；也可能改变主意，那封已经发出的邮件就没有任何记录。写前日志能让恢复时知道“这封邮件可能已经发出”。

**2. 为什么不能直接覆盖写检查点文件？**
进程若死在写到一半，文件只剩前半部分，新旧状态都丢了。先写临时文件、再原子 rename，读到的始终是完整的某个版本。

**3. 恢复时没有保存已用的请求次数，会出什么问题？**
预算被清零。一个陷入死循环、每次都因某种原因崩溃的任务，可以靠“崩溃—恢复”无限地请求模型。

**4. 恢复时发现一个“查询天气”和一个“下单”调用都没有结果，怎样处理？**
查询天气是只读的，直接重新执行；下单有副作用，有订单幂等键就用同一个键重做，没有就回填“结果未知”，先查订单状态再决定。

**5. 文件锁和租约各适合什么场景？**
文件锁只在同一台机器、同一个文件系统上有效，进程死了内核自动释放，简单可靠。多台机器竞争同一个任务时要用租约加心跳，并用防护令牌挡住醒来的旧执行者。

**6. Temporal 重放时为什么不会重复调用模型？**
模型调用作为 Activity 执行，结果写进事件历史；重放时遇到已记录的 Activity，直接返回记录的结果，不真的执行。
