# Week 3 复盘：评测与安全

第一周造出了执行循环，第二周让它在出事时可恢复、可观测。第三周回答两个问题：**它到底做得好不好**（D15–17：指标、评测、归因），以及**它会不会做不该做的事**（D18–21：不可信内容、权限、确认、审计）。前一半用数据代替感觉，后一半把边界从“靠模型自觉”挪到“程序和人守住”。

## Day 15–21 各一句话

| 天 | 主题 | 一句话 |
| --- | --- | --- |
| Day 15 | 评测指标 | 完成率、异常结局与可恢复性、端到端延迟、成本、工具可靠性五个指标；结局与成本以检查点为准，trace 只用于工具层归因；完成不等于答对。 |
| Day 16 | 评测集与回归 | 固定题目、参考答案和打分器，不固定模型回答；先确定性检查，开放题由另一家模型三票评审；pass@1 按题聚类算标准误，pass^k 看稳定性，消融看一个能力值多少分。 |
| Day 17 | 失败归因 | 只记第一个上游错误；开放编码归类；从检查点或请求快照分叉回放，纠正组翻转、安慰剂组不翻转，才算证实根因。 |
| Day 18 | 不可信内容 | 工具结果里的文字是资料，不是指令；三份无害资料观察答案偏离与工具偏离，不要求一定打穿。 |
| Day 19 | 权限边界 | 工具结果由程序标记来源与 `data_only`；执行器按本轮工具列表做允许检查，恢复路径同样检查；模型提示不是权限。 |
| Day 20 | 高风险确认与多租户 | 删除、破坏性、含私有数据后的外发、重做中断的操作，执行前由程序判定、界面上的人确认；没人回答就不做。顺带补上结果日志与无进展检测；补做多租户：数据按租户分目录、观测台登录、每次访问核对租户。 |
| Day 21 | 审计日志 | agent 与观测台各记亲眼所见，写进同一份只追加、带哈希链的日志；高风险动作写不进审计就不执行。 |

## 一次高风险调用的一生

第二周跟着一次普通工具调用走完全程；这一周给它加上了评测与安全的几道关口：

```text
模型返回 tool_calls
 → 窗口熔断：最近 6 个动作里同一动作第 3 次就拦下                       D20
 → 写前日志（检查点）                                                  D9
 → 允许列表：不在本轮工具列表里 → 拒绝，不重试                          D19
 → 风险规则：删除 / 破坏性 / 含私有数据后的外发？                        D20
     ├ 审计 approval_request（写不进 → 不执行）                         D21
     ├ tool/requestApproval → 界面上的人
     │     ├ 人点“允许”：观测台先记 user_decision，再回复 agent         D21
     │     └ 没界面 / 超时 / 拒绝 → denied
     └ 审计 approval_decision                                          D21
 → 执行（时限、分类重试、结果未知）                                     D8
 → 结果日志：这一项一结束就落盘                                         D20
 → 审计 tool_call（有副作用或经过确认的）                               D21
 → 回填：外层标记 source / data_only                                   D19
 → 无进展检测：整轮结果都见过 → 提示 → 熔断                              D20
 → 读到私有数据 → 标记任务，之后的外发都要确认                          D20
 → 结束：检查点记结局（D15 指标的依据），评测按题打分（D16），失败归因（D17）
```

## 本周的几条主线

1. **用数据代替感觉**。改一处提示词、修一个 bug，都先问“哪道题、几次里翻转了几次”。D17 的 fault-unknown 修复就是这样：先回放验证（纠正 3/3、安慰剂 0/3），再改代码，再回归（0/3 → 3/3，没有回归）。
2. **完成、答对、安全是三件事**。D15 的完成率说的是有没有正常结束，D16 的通过率说的是答没答对，D18–20 关心的是过程中有没有做多余或危险的事。一个回答正确的任务，也可能中途试图外发数据。
3. **模型负责判断，程序负责授权，人负责拍板**。来源标记和 system 规则帮助模型做对；允许列表、风险规则和确认流程保证它做错时也不会造成后果；不可撤回、外发这类决定交给人。D20 的子 agent 实验里，模型绕开“不要换工具重试”的提示自己去打开网址，拦下它的是程序规则。
4. **每个决定都要留下能核对的记录**。检查点记任务状态，trace 记耗时与父子关系，结果日志记每项调用是否完成，审计记谁批准了什么。四者职责不同，不互相替代。

## 实测中反复出现的问题

| 现象 | 出现位置 | 原因与现状 |
| --- | --- | --- |
| 方舟请求返回 HTTP 403 | D18–21 | 外部账号或配额问题；这几天的验证改用 DeepSeek，D17 的方舟“用满预算”没能复测 |
| 题量小、置信区间宽 | D16 | 主分 17 题，95% 区间约 ±13 个百分点；评审模型与人工没有系统校准 |
| 有夹带内容的对照组也通过 | D19 | 简单样本没能诱导模型偏离；结论只能是“程序边界生效”，不能说“标记提升了防护” |
| 模型换工具绕过拒绝 | D20 | 子 agent 外发被拒后，父 agent 自己去开同一个网址；程序规则同样拦下 |
| 通用题先查学习笔记 | D17 | 工具选择过度（6 次中 5 次），还没修 |

共同点：模型的行为在边界状态下不稳定，靠提示词只能提高概率；能确定的只有程序检查。而“程序检查是否生效”本身也需要评测和审计来证明。

## 第四周最想补的三件事

> 以下是根据本周实测整理的**建议草稿**，最终以你自己的选择为准。

1. **实战项目带上评测与审计**（D22–24）：选一个真实任务，从第一天起就有固定题集、指标和审计记录，评测报告里同时给出答对率、成本和高风险动作统计。
2. **把注入与确认写成一篇完整的故事**（D25）：从“断网 Bash 加浏览器能外发”（Q12），到 D18–19 的实验、D20 的确认、D21 的审计，各层挡住了什么、没挡住什么。
3. **系统设计题准备**（D27）：本周的模块正好是“设计一个 Agent 运行平台”的安全与质量部分，尤其是项目里只做到单机的部分（多租户的 TLS、配额与加密）和只学了概念的部分（审计锚定、评测接 CI）。

## 待你确认的理解

本周功能都有真实运行记录，但下列理解尚未由你复述确认，暂不记为已掌握：

- Day 15：完成与答对的区别；为什么结局要以检查点为准，而不是 trace。
- Day 16：pass^k 怎么算，为什么比 pass@k 更适合面向用户的 agent；标准误为什么按题聚类。
- Day 17：为什么只记第一个上游错误；回放验证为什么要配安慰剂对照。
- Day 18–19：为什么正文自称 system 不能增加权限；来源标记与允许列表各保证什么。
- Day 20：确认请求为什么不能交给模型回答；按任务标记私有数据（而不是按值）的取舍；结果日志能和不能解决什么。
- Day 21：调用链为什么不能兼作审计；哈希链能发现哪些篡改、发现不了哪一种；为什么人的点击要由界面和 agent 各记一次。
