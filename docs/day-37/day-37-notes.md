# Day 37：基线与消融

## 学习目标与术语

学完能说明：改 harness 的一处设计之前，怎样用数据判断它值不值得；消融实验怎样设计才比较得出结论；题目少的时候能下多强的结论；几个常见的候选（工具结果格式、提示词指引、清单工具、清理旧工具结果、工具定义按需加载）各自影响什么，用什么指标看。

| 术语 | 通俗解释 |
| --- | --- |
| 基线 | 现在的做法跑出来的成绩，所有改动都和它比 |
| 消融 | 只改一处（加上或去掉一个组件），其余全不变，再跑同一批题，看分数变了多少 |
| 减法消融 | 把现有的一个组件拿掉，看它是不是真的有用 |
| 配对比较 | 同一道题在两组里各自的通过率相减，再对所有题求平均；比两组总分直接相减更稳 |
| 过程指标 | 不看答对没有，看过程：请求次数、输入 token、缓存命中、单工具请求占比 |
| 噪声 | 同一个设置跑两次结果也会不同；分差要大于噪声才算数 |

## 1. 为什么要消融

harness 里很多设计来自直觉或别人的经验：“提示词里加一句会更好”“给模型一个清单工具它会更有条理”。这些话对不对，取决于你的模型、你的工具、你的任务。消融把“我觉得”变成“跑出来是这样”：

- **加法**：加上一个候选，看分数是否上升、代价（token、时间）是否可接受。
- **减法**：拿掉一个现有组件，看分数是否下降；不下降说明它可能是多余的，可以删掉省代价。

## 2. 设计一组消融

| 原则 | 原因 |
| --- | --- |
| 一次只改一处 | 改两处，分数变了也不知道是哪一处的功劳 |
| 同一个模型、同一批题、同样的预算 | 只让被比较的那一处不同 |
| 每次从同一个干净的起点开始 | 编码题会改环境；共用环境会污染（见 Day 36） |
| 配对比较 | 题目之间难度差别很大；同一道题前后比，能消掉难度带来的差 |
| 先定好看什么指标 | 事后挑指标，总能挑出一个“变好了”的 |
| 记录代价 | 分数一样时，便宜的更好 |

## 3. 题目少的时候能说什么

几道题、每题跑两三次，95% 区间往往有几十个百分点宽。这时：

- 只有很大的差别（比如一组全过、另一组全不过）才算信号；
- 逐题看：差别集中在哪几道题、失败的原因是不是这个改动引起的；
- 过程指标往往比通过率更敏感：同样都通过了，请求次数少一半也是实打实的收益；
- 结论写成“这批题上没有看到差别”，而不是“没有用”。

## 4. 常见候选与该看的指标

| 候选 | 可能的收益 | 可能的代价 | 看什么 |
| --- | --- | --- | --- |
| 工具结果用纯文本而不是 JSON | 文件内容不被转义，模型复制原文更准确；token 更少 | 结构信息（状态、来源）要另外表达 | 编辑一次成功的比例、输入 token |
| 编码提示词加用法指引 | 并行读取、少走弯路、该问就问 | 提示词变长；指引可能被过度执行 | 请求次数、单工具请求占比、通过率 |
| 上下文内的 todo 清单 | 多步任务不漏步骤 | 每次更新清单都占一次工具调用 | 通过率、请求次数 |
| 清理之前各轮的工具结果 | 后面各轮的请求变小 | 清理处之后缓存失效一次；模型可能要重读 | 每轮输入 token、缓存命中、是否要重读 |
| 工具定义按需加载 | 工具很多时省下常驻的定义 | 加载时改变工具列表，缓存失效 | 工具定义占请求的比例：比例小就不值得做 |

最后一项不一定要跑实验：先量一下工具定义占请求的多少。只占百分之几、又总是命中缓存，按需加载省不下什么，反而多一次往返和一次缓存失效。

## 自测

1. 为什么一次只改一处？
2. 配对比较比直接比总分好在哪里？
3. 5 道题、每题 2 次，一组 80%、一组 60%，能说哪组更好吗？还能看什么？
4. 清理旧工具结果为什么会让缓存失效？怎样让它每轮只失效一次？
5. 什么时候不值得做“工具定义按需加载”？

### 自测答案

1. 改了几处，分数变化无法归到其中任何一处。
2. 题目难度差别大，同一道题前后相减能消掉难度的影响，方差小得多。
3. 不能：差 2 次通过，在这个样本量下在噪声范围内。可以逐题看差别出在哪、原因是什么，并比较请求次数、token 这类过程指标。
4. 提示缓存按请求前缀匹配；把中间的旧结果换成占位，从那里往后的前缀都变了。每轮开头一次性清理到上一轮为止，这一轮之后的请求前缀保持稳定，下一轮只清新增的部分，之前清过的保持原样。
5. 工具定义只占请求的一小部分、并且总在缓存里时；按需加载反而带来额外的往返和缓存失效。
