# Day 31：长任务接力与独立验证

## 学习目标与术语

学完能说明：一个做不完一个会话的任务，怎样让下一个会话接着做而不是从头再来；为什么“完成没有”不能由写代码的模型自己说了算；独立验证由谁来做、看什么；预算用完、半途停下时 harness 该自己做什么。

| 术语 | 通俗解释 |
| --- | --- |
| 长任务 | 一个上下文窗口、一次请求预算做不完的任务，要分好几个会话 |
| 接力 | 每个会话结束前把“做到哪、下一步做什么”写下来，下一个会话先读它 |
| 功能清单 | 把任务拆成一项项可以验证的功能，每项附一条检查是否达到的命令 |
| 自评 | 写代码的模型自己说“做完了” |
| 独立验证 | 由另一方（另一个只读的 agent、另一家模型、或者一条命令）判定是否达到 |
| 收尾检查 | 任务不正常结束时，harness 不再问模型，自己跑一次检查，告诉人留下的状态能不能用 |

## 1. 为什么长任务会出问题

一个任务做不完一个会话，常见的失败有三种：

1. **从头再来**：新会话不知道上次做了什么，重新读一遍代码、重新做一遍已经做完的事。
2. **一次做太多**：模型想一口气做完，做到一半上下文满了或预算用完，留下一堆半成品，下一个会话不知道哪些能用。
3. **过早宣布完成**：模型看到一部分功能能跑，就说“全部完成”；或者测试没真跑，凭印象说“通过了”。

Anthropic 介绍长时间运行的 agent 时给出的做法是：第一个会话专门做初始化——把需求拆成详细的功能清单（初始全部标为“未通过”）、写一份进度说明、做一次 git 提交；之后每个会话只挑一项来做，做完验证，更新清单和进度说明，再提交。

## 2. 进度文件：给下一个会话看的交接单

一份好的进度文件至少有三部分：

```text
目标：给命令行工具加 pow 和 max 两个子命令
功能清单：
  F1  pow a b 输出 a 的 b 次方       检查：go run . pow 2 10 输出 1024    未通过
  F2  max 输出任意多个整数的最大值    检查：go run . max 3 9 2 输出 9       未通过
交接说明：
  （上一个会话）F1 已通过；F2 还没开始，main.go 的 switch 里加一个分支即可
```

几个要点：

- **每项都要能验证**：“代码写得更好”不能验证；“这条命令的输出是 1024”可以。检查命令最好不依赖网络，任何时候都能重跑。
- **初始全部未通过**：清单是待办，不是成果。
- **一次只做一项**：做完一项、验证一项，失败了也只坏这一项。
- **交接说明写给陌生人**：下一个会话什么都不记得，要写清做到哪、卡在哪、下一步。

## 3. 谁说了算：独立验证

“这一项做完了没有”如果由写代码的模型自己判断，它天然倾向于认为自己做对了；如果它还能直接改进度文件里的状态，那清单就失去了意义。

独立验证的要点：

| 要点 | 做法 |
| --- | --- |
| 状态只能经验证改 | 进度文件里的“通过”只能由验证这一步写；编辑工具不能改这个文件；被别的途径改了，以 harness 自己留的记录为准 |
| 证据来自执行 | 先真跑检查命令，看退出码和输出，而不是看模型说了什么 |
| 判定者独立 | 让另一家模型（或另一个只读的 agent）对照功能描述和真实输出下结论，只给它证据，不给写代码的模型的说法 |
| 验证不能改现场 | 检查命令在只读的环境里跑，验证本身不会把没写完的代码“修好” |
| 两道都过才算 | 退出码为 0 是必要条件；再加上判定者认可，防止“命令写得太松、什么都能过” |

为什么要第二道？检查命令是写代码的模型自己拟的，可能拟得太松（比如只检查“输出不为空”）。判定者对照功能描述看输出，能发现“命令过了但功能没做到”。反过来，它不能推翻失败的命令：退出码不为 0 一律不通过。

## 4. 半途停下时：收尾检查

预算用完、模型报错、超时、陷入死循环时，任务会停在中间。这时候 harness 不应该再请求模型（模型正是问题所在），而是自己跑一次检查，例如“工作区有改动的话，编译能不能通过”，把结论记下来：人一眼就知道留下的状态能不能用、下一个会话要不要先修编译。

人主动按停止的不算：那是人自己决定停在这里。

## 5. 和 git 的关系

把进度和代码一起提交，是最自然的接力载体：下一个会话 `git log` 就能看到每一步。但如果 harness 为了安全把版本库设成只读（模型不能提交、不能改写历史），提交就要交给人，或者交给 harness 在明确授权后代为执行。进度文件本身仍然在工作区里，下一个会话照样能读到。

## 自测

1. 长任务常见的三种失败是什么？
2. 功能清单的每一项为什么要配一条检查命令？什么样的检查命令好？
3. 为什么清单初始要全部是未通过？
4. 为什么“通过”不能由写代码的模型自己改？怎样防止它绕过？
5. 独立验证为什么要两道都过：命令退出码为 0，加上判定者认可？
6. 检查命令为什么要在只读的环境里跑？
7. 任务半途停下时，harness 为什么要自己跑检查，而不是再问模型？

### 自测答案

1. 新会话从头再来；一次做太多、留下半成品；过早宣布完成。
2. 有检查命令，“做完没有”就变成可以重复执行、看结果的事，而不是谁说了算。好的检查命令不联网、任何时候都能重跑、检查的是功能描述里说的行为，退出码 0 表示达到。
3. 清单是待办，不是成果；从未通过开始，每一项的“通过”都必须有一次验证作为来源。
4. 写代码的模型倾向认为自己做对了，能改状态就等于自评。防法：编辑工具拒绝改这个文件；harness 在模型够不到的地方留一份权威记录，读的时候核对，被改过就恢复；没有验证记录的“通过”一律当作未通过。
5. 检查命令是写代码的模型拟的，可能太松，什么都能过；判定者对照功能描述看真实输出，能发现“命令过了但功能没做到”。但判定者不能推翻失败的命令，退出码不为 0 一律不通过。
6. 验证应该只观察、不改变：如果检查命令能写工作区，它可能顺手“修好”或改坏代码，验证的就不是模型留下的现场了。
7. 半途停下往往正是因为模型出了问题（预算用完、报错、绕圈），再问它不可靠也不经济；harness 自己跑一次固定的检查，结论客观，还能告诉人留下的状态能不能用。
