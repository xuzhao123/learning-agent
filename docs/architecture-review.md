# Harness 架构评估（2026-10-19，D30 之后）

> 范围：D1–D30 与各扩展完成后的代码和文档。方法：对照 [D22 参考架构](day-22/day-22-notes.md#2-五层结构)、[第四周的五条主线](week-04-review.md#本周的几条主线) 和 [AGENTS.md](../AGENTS.md) 的约定阅读源码；用 `.data/` 里的已有存档做了两项统计；外部对照取 2026 年 9–10 月的公开资料（部分是二手资料，已在文中注明）。本次没有改代码，也没有运行模型。
>
> 规划的改动见 [plan.md](../plan.md#week-5--会话与长任务)，待办见 [PROJECT.md](../PROJECT.md#当前待办与实现边界)。

## 1. 结论

1. **和原有思路基本一致。** 五层结构、策略管线的顺序、“审批由 harness 发起、界面上的人回答”、“只追加不改写”这几条都落在了代码里，而且有实测数据支撑。偏离有四处，其中两处的共同点是：原则只靠写代码时记得遵守来维持，代码结构本身不保证。具体是工具性质散在 8 处，影响下一步决定的状态散在各个包里。这两处改起来不大，已排进 D32 和 D38–D40。
2. **结构上接近前沿，作为编码 harness 还算不上最先进。** 2026 年 7 月一份综述归纳了 10 条趋同的运行时做法，这里 8 条已有、2 条部分做到；结果未知的语义、审计哈希链和带安慰剂对照的回放归因比多数开源 harness 更严格。主要差距在四处：模型请求没有重试，审批者只有人，“完成”由写代码的模型自己判断，运行中不能插话。
3. **计划之外值得做的事按收益排了序（第 4 节）。** 小而直接的三项放进现有课程：模型请求重试、工具声明、独立验证。中等的三项作为 D38–D40 的候选：状态收拢、自动审查者、子 agent 控制面。大的一项是只追加的会话记录，先写明到什么时候该做，暂不排期。

## 2. 和原有思路是否一致

### 2.1 守住的部分

| 原有思路 | 现在的实现与证据 |
| --- | --- |
| 一个核心，多种界面 | 观测台、`RunChild`、队列、评测都通过 `-app-server` 的 JSON-RPC 驱动 agent，不再解析终端文本（B0）。终端客户端留给 D34 |
| 审批由 harness 发起，界面上的人回答 | D20 的风险确认、D25 的询问和联网审批都走 `tool/requestApproval`；没有界面、超时或拒绝都不执行 |
| 策略管线有固定顺序 | `ExecuteBatch` 中依次是 PreToolUse hook → 规则 deny › ask › allow → 权限模式 → D20 风险 → 人确认 → 执行。hook 只能收紧用户写的规则，不能绕开（顺序上的一处小偏差见 2.2 ⑤） |
| 上下文按缓存来设计 | 首轮的系统提示词固定不变，之后的变化以 `<system-reminder>` 追加在末尾；第四周自用时各轮缓存命中 94%–98% |
| 确定性约束放进 harness | 读后才写（内容哈希核对与写入同锁）、plan 模式下工作区只读挂载、Stop hook 做编译检查，都由程序判断 |
| 边界在执行环境 | 每次 bash 调用都新开一个沙箱，`.git` 只读，`.env` 和 `.data` 换成空的，出口共用 `netguard` |
| 学习约定 | 一个进程只跑一个任务；用真实模型验证；不写测试文件；功能开关来自命令行或设置快照。这些都守住了 |

### 2.2 偏离的地方

**① 工具的“性质”散在 8 处。** 新增一个工具，最多要改这些地方：工具定义（`tools.Definitions` 和各包的定义）、`dispatch.go` 的分发、`react.go` 的 `repeatable`（能否重做）与 `sequential`（是否串行）名单、`trackPrivate`（是否读到私有数据）、`approval.go` 的 `outbound`（是否外发）、`permission.go` 的分类、`runAttempt` 的时限，以及系统提示词里的规则。MCP 工具只能参与其中一项，就是 server 声明的“破坏性”。其余几项都按默认处理：可以并行，不可重做。这违背了“机制与策略分开、能声明的不写死”，D22 发现的“并行调度不分只读与修改”（T4）和 Q13 的 repeatable 误标都属于这一类。D32 的后台命令工具一加进来，又要改一遍这 8 处。参考做法：MCP 的工具标注（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`），以及 Claude Code、Codex 里每个工具自己声明的只读和并发安全属性。

**② 影响下一步决定的状态，只靠写代码时记得存进检查点。** `main.go` 定义了约 61 个命令行参数，直接设置约 25 个包级变量；运行中会变的状态分散在各个包里：读过的文件、加载过的子目录指令和提醒在 `workspace` 包，私有来源和循环检测在 `agent` 包，用户原话在 `memory` 包。每加一种状态，都要记得在 `save()` 里写一行，在续跑、续聊、压缩三条路径上各恢复一次。D24、D27 和 10-18 各修过一次这类 bug，第四周第 4 条主线说的就是它。把配置留作全局变量没有问题（一个进程只跑一个任务），需要收拢的只是“运行中会变、影响下一步的状态”：放进一个结构，由检查点整体保存。它也是“环境状态只发变化”（H03 缺的那一项）的前提。

**③ 会话记录不是只追加。** 参考架构的状态层是只追加的会话记录（Codex 叫 rollout），恢复、分叉和回退都从它推出来。本项目在每个边界整份重写检查点 JSON（目前最大约 490 KB），里面只存发给模型的 View；完整的事实分散在 7 处：检查点、`.calls` 结果日志、观测台代理存档、trace、审计、`.files` 快照、`outputs`。每一处在当天的课程里都是对的选择，但 PROJECT 待办里这几条其实同出一源：只存 View、首次用量只能粗估、delta 不落盘、观测台重启后接不回运行中的 agent、回放分叉依赖观测台的请求存档、检查点没有格式版本（T5）。

**④ 观测台越来越像第二个核心。** 它同时是界面、模型代理（保存原始请求）、内置 MCP、设置、登录、评测、导入和归因：`server.go` 1691 行，`index.html` 3495 行。“一个核心，多种界面”要求界面保持轻薄。现在最具体的耦合是：归因回放要用的“模型当时看到的请求”只在经观测台代理的运行里才有。这一处暂不需要动，做 ③ 时会自然解开。

**⑤ 允许列表没有排在最前面。** AGENTS 写的是“先过允许列表”，代码里允许列表的检查在 `runTool` 中，排在 hook、规则和确认之后。所以在 plan 或 ask 模式下，模型编出来的 `mcp_*` 工具会先向人发出确认请求，人批准之后才被拒绝；读过私有数据后的外发判断也会先触发。改法是把允许列表检查提到 `ExecuteBatch` 的开头，可以和 ① 一起做。

## 3. 是不是最先进

### 3.1 已经在前面的部分

一份 2026 年 7 月的综述（联合国大学，见来源）归纳了 harness 运行时正在趋同的 10 条做法。本项目已有 8 条：有界的循环、受控的写入、两段式压缩、大输出落盘、可恢复的会话、轨迹留存、按范围授权的工具、生命周期 hooks。部分做到的有 2 条：只读并行（按写死的名单）和供应商抽象（只有 OpenAI 兼容接口）。

以下几点比多数开源 harness 更严格：

- **结果未知（unknown）是独立的结局**，配合写前日志、续跑时补齐中断的那一批，以及不可重复的调用先问人。多数 harness 超时就当失败处理。
- **审计用哈希链**，人的点击由界面和 agent 各记一次，确认请求写不进审计就不执行。
- **归因结论以回放为准**：从模型当时的请求分叉，纠正 3 次、安慰剂 3 次。
- **上下文计数经过实测**：误差 1%–2%，缓存命中按实测数据决定，不靠猜。

### 3.2 和 2026 年 10 月的 Codex、Claude Code 相比

| 方面 | 前沿做法 | 本项目 | 计划里有没有 |
| --- | --- | --- | --- |
| 模型请求的可靠性 | 按错误类型退避重试，流中断后重连，两家都有 | 主请求失败即停止（`CallKeeping` 不重试）；一次 429 或断流就结束整个任务 | 只在待办和进阶计划 A4 里，主线没排 → **调入 D33** |
| 审批者 | Claude Code 的 auto mode 用分类器判断每个动作，2026-09 末起成为交互会话的默认（二手资料）；Codex 0.160 加入可选的 Guardian 审查（非官方追踪） | 只有人；没有界面就拒绝。实际只能在“经常被问”和 full 之间二选一 | 没排，而且和 D20 的约定冲突 → **D38–D40 候选，先改约定** |
| 怎样判定完成 | 生成与评估分离：独立的评估者按规格实际操作产物（Anthropic 的长时运行 harness）；自评容易误报“已完成” | 模型说完成就算完成，Stop hook 的编译检查兜底；预算耗尽时连这一步也不跑 | D31 只有进度文件 → **D31 加独立验证** |
| 运行中插话 | Codex 0.163 默认开启中途插话（二手资料） | 只能停止，或者等这一轮结束再续聊 | D34 已排 |
| 子 agent | 可以 fork 一份继承上下文和缓存的子 agent；子 agent 默认在后台运行，可以多层嵌套，会话之间能互发消息 | 独立子进程，只回摘要，可以按 task_id 续跑 | D38–D40 候选 |
| 模型协议 | 原生协议（Responses / Messages）：推理内容跨轮携带，可以控制缓存 | 只用 Chat Completions；方舟几乎不命中缓存，原因没查 | D33 已排，**现有密钥就能做**（见第 4 节 O6） |
| 工具定义按需加载、用脚本编排工具 | ToolSearch；在代码里调用工具 | 每次请求都带全部工具定义 | D37 消融已排 |
| 代码智能 | Claude Code 的 LSP 插件：编辑后给诊断，提供只读的跳转工具 | 没有；gofmt 与编译 hook 是粗略的近似 | 没排 → 用 PostToolUse hook 配置，不改 harness |
| 扩展打包 | 插件包；Claude Code 2026-10 加入 mods（代码级扩展） | 没有打包 | 没排，优先级低 |
| 工具结果格式 | 读文件返回纯文本加行号 | 整个 Observation 用 `json.Marshal` 编码：换行、引号被转义，`<`、`>`、`&` 被转成 `<` 一类（Go 默认的 HTML 转义）。实测一次对话读了 11 个文件、共 15,410 字符，其中有 122 处这种转义；存档里 113 次 `edit_file` 失败 10 次，没有一次能归到转义上 | 没排 → **D37 消融候选** |

### 3.3 “最先进”不应该是目标

前沿 harness 正在随模型变强做减法：每次换模型，都要重新问一遍哪些机制只是在弥补模型的不足（见来源里的 harness 工程综述）。本项目的长期目标是“能设计、实现和迭代 harness”，衡量标准是能不能用数据判断一个机制该不该存在，而不是功能清单有多长。所以：

- **D36–D40 的“评测 → 归因 → 改 → 回归”是整份计划最重要的部分**，新增功能不能挤占它。
- 在 D37 加一组**减法消融**：分别去掉重复动作熔断、无进展提示、结果未知时给模型的下一步说明、每轮 16 项调用上限，看在当前模型下哪些仍然有用。

## 5. 一次自用对话的复查（10-19）

对象是观测台里的一段真实对话：DeepSeek flash，工作区是本仓库，权限 full，5 轮、78 次模型请求。前两轮是问答和排查，后三轮让 harness 在输入框里加上下文用量环并改了两次。输入 595 万 token，缓存命中 98.4%，按当时的低谷价约 0.06 美元。成本不是问题，问题出在验证和上下文。
