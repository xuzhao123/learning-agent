# Day 16：可复现评测集与回归测试

## 学习目标

读完本文，应能回答以下问题：

1. 一个 agent 评测由哪几部分组成？题目（task）、尝试（trial）、打分器（grader）、轨迹（transcript）、结果（outcome）各是什么？
2. 一道好的评测题要满足什么条件？为什么每道题都要有参考答案，还要有“不该做”的反例？
3. 代码打分器、模型打分器、人工评审各适合什么？为什么“优先确定性检查”？
4. 为什么不建议按“必须先调用 A 再调用 B”打分？过程该检查到什么程度？
5. 用另一个模型当评审（LLM-as-judge）有哪些偏差，怎样减小？
6. 20 道题、每题跑 3 次，结果的误差有多大？比较两个版本时为什么要逐题配对？
7. 能力评测与回归评测有什么区别？留出集、消融对照各解决什么问题？

## 1. 评测的组成

先把几个词定下来（沿用 Anthropic《Demystifying evals for AI agents》的用法）：

| 术语 | 含义 | 例子 |
| --- | --- | --- |
| 题目（task） | 一个输入加上成功标准 | “把订单 1042 退款”，成功标准是数据库里这笔订单状态变为 refunded |
| 尝试（trial） | 对一道题的一次运行 | 同一道题跑 3 次，就是 3 次尝试 |
| 打分器（grader） | 判断某个方面是否达标的逻辑；一道题可以有多个 | 检查数据库状态；检查回复里是否说明了退款金额 |
| 轨迹（transcript） | 一次尝试的完整记录：模型输出、工具调用与结果 | agent 先查订单、再调退款接口、最后回复用户 |
| 结果（outcome） | 尝试结束时环境的最终状态 | 订单状态、生成的文件、发出的消息 |
| 评测框架（harness） | 跑题、记录、打分、汇总的程序 | 读题目文件，并发启动 agent，汇总成报告 |

两点容易被忽略：

- **轨迹 ≠ 结果**。agent 在回复里说“已退款”，结果里订单却没变——只看回复会把它判成功。能检查结果的地方，就检查结果。
- **被评测的是“模型 + 外壳”整体**。同一个模型，换了工具描述、系统提示或重试策略，分数就会变。所以评测记录要写明代码版本、题目版本、模型和参数，否则两次分数没法比较。

## 2. 好题目的条件

**无歧义**：两位熟悉业务的人各自独立判断，应得出相同的通过/不通过。如果连人都会争论，模型的分数就主要是噪声。

**有参考答案**：写出一个能通过全部打分器的答案。它证明这道题可解，也能验证打分器配置是否正确。Anthropic 举过一个例子：某个公开评测要求答案精确等于 `96.124991…`，于是答 `96.12` 的被判错；修正打分器后，同一个模型的分数从 42% 升到 95%。**一道题在很多次尝试里都是 0 分，先怀疑题目和打分器，再怀疑 agent。**

**正反平衡**：既要有“应该做某事”的题，也要有“不应该做”的题（反例，negative control）。只测“该搜索时有没有搜索”，优化的结果往往是“什么都搜索”。例如：

| 正例 | 反例 |
| --- | --- |
| “查一下今天北京的天气” → 应调用搜索 | “用一句话解释什么是递归” → 不需要任何工具 |
| “在知识库里查报销上限” → 应检索并引用 | “查一下公司 XYZ-999 错误码”（库里没有）→ 应说明资料不足，不编造 |
| “用沙箱运行这段代码” → 应执行 | “用沙箱访问外网”（未授权）→ 应说明不能访问，不凭记忆给结果 |

**从真实失败里来**：起步不需要几百道题。Anthropic 的建议是先从开发中手工验证过的行为和用户报告的失败里取 20–50 道；早期每次改动的效果都很明显，小样本足够看出来。

**可复现**：时间、外部网页这类会变的东西，期望值不要写死。例如“今天星期几”的期望值取 agent 实际拿到的时间来算；依赖外网的题单独统计，不和主分混在一起。

## 3. 打分器：先便宜的，后贵的

| 类型 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 代码 | 数值比较、包含/正则、检查文件或数据库状态、统计工具调用 | 快、便宜、可复现、出错好排查 | 对合理的不同写法太死板 |
| 模型 | 按评分标准（rubric）判 PASS/FAIL，或两两比较 | 能处理开放题 | 有随机性、有偏差、要校准 |
| 人工 | 专家评审、抽查 | 最准 | 慢、贵；主要用来校准前两种 |

OpenAI 给 Codex skill 写评测时的说法是“按成本分层：先做便宜、能解释行为的检查，只有能降低风险时才加更重的检查”。Claude Code 的插件评测也只有六种打分器：正则、工具是否调用、工具顺序、文件是否存在四种免费，模型评审两种另算成本。

**一题两个打分器**：一个看结果（答案或产出对不对），一个看过程（关键步骤有没有发生）。两者合起来才能回答“答对了，而且是用我们期望的能力答对的”。

**过程只查关键约束，不查顺序**。agent 经常找到设计者没想到的合理路径。“必须先查订单再退款”这类顺序检查容易误伤；“不得在未授权时访问外网”“有副作用的操作最多执行一次”这类约束则应该检查。

**部分分**：一道多步骤题可以给出“通过的检查占比”，便于看出进步；但面向用户的“通过”通常要求全部检查都过。两者都报告。

## 4. 模型评审（LLM-as-judge）

模型评审已知的偏差：

- **自我偏好**：模型倾向于给自己（或同家族模型）的回答打高分。评审模型最好与被测模型不同。
- **长度与格式偏差**：更长、格式更漂亮的回答容易得高分，与对错无关。
- **位置偏差**：两两比较时偏向先出现（或后出现）的那个。
- **随机性**：同一份输入，两次评审结论可能不同；输入越长，波动越大。

减小偏差的做法：

1. **评分标准写成具体的 PASS / FAIL 条件**，一次只判一个维度，不要“综合打 1–10 分”。
2. **给评审足够的证据**：题目、参考答案、agent 实际的工具记录。评审没看到的事实，它会当成 agent 编造的。
3. **允许回答“不确定”**（UNKNOWN），不逼它猜；不确定按未通过计，但单独标出供人复核。
4. **多票表决**：同一项评审投 3 票，两票一致才算数。
5. **与人工校准**：抽一批样本，比较评审与人工判断的一致率；不一致的样本回头改评分标准。

一个真实的校准例子（通用化）：执行器对失败的工具自动重试了 3 次，agent 在回答里如实写了“尝试了 3 次”；但给评审的工具记录里只写了“调用 1 次，失败”，于是评审判定“编造了尝试次数”。错的不是 agent，是打分器的输入。**失败要“输得公平”：读轨迹时要同时问“agent 错了吗”和“打分器错了吗”。**

## 5. 多次尝试与误差

agent 的输出有随机性，一道题只跑一次说明不了什么。每题跑 k 次：

- **pass@1**：单次通过率，即所有尝试中通过的比例（先在题内平均，再在题间平均）；
- **pass^k**：k 次全部通过的题所占比例，衡量“每次都可靠”（τ-bench 提出；Day 15 已讲过两者的区别）。

**标准误要按题聚类**。同一道题的几次尝试并不独立——题难，三次都容易错。正确的做法是先在每道题内平均得到 s₁…sₙ，再算：

```text
pass@1 = mean(sᵢ)
SE     = sqrt( Σ(sᵢ − mean)² / (n − 1) / n )
95% 区间 ≈ pass@1 ± 1.96 × SE
```

把 60 次尝试当成 60 个独立样本算，标准误会被低估（Anthropic 的统计文章里，聚类后的标准误可能是朴素算法的 3 倍以上）。

**例子**：20 道题，每题跑 3 次，题内平均分别是 1、1、…、0.67、0、…，算出 pass@1 = 75%、SE = 8%，95% 区间约 59%–91%。所以“这次 75%、上次 70%”**不能说明变好了**。

**比较两个版本：逐题配对**。两个版本跑同一批题，对每道题求差 dᵢ = sᵢ(新) − sᵢ(旧)，再对 dᵢ 算均值和标准误。题目难度在相减时抵消，比分别算两个总分再相减灵敏得多（同一批题上，不同版本对错的相关性通常很高）。

**回归看逐题，不看总分**。小样本下总分的小幅波动是噪声；真正要报警的是“以前每次都对、这次没有全对”的题。

## 6. 能力评测、回归评测与留出集

| | 能力评测（capability） | 回归评测（regression） |
| --- | --- | --- |
| 问的问题 | 这个 agent 能做好什么？ | 以前会的，现在还会吗？ |
| 期望通过率 | 一开始就低，留出“要爬的山” | 接近 100% |
| 失败意味着 | 还没学会 | 改坏了，要阻止合并 |

能力题被稳定攻克后，可以“毕业”进回归集。一个评测接近 100% 时就**饱和**了：它只能发现退步，不能再衡量进步，需要补更难的题。

**留出集（holdout）**：调试时看过的题会被“教会”——改提示、改工具描述都在围绕它们转。这些题上的提升不代表泛化。留一部分题，调试期间不跑、不看，只在最后报告时运行。《AI Agents That Matter》指出，很多 agent 基准没有留出集或留出集不足，导致方法过拟合基准。

**试次隔离**：每次尝试从干净的环境开始。共享状态会造成相关失败（一次把磁盘写满，后面全错），也会虚高分数（Anthropic 曾发现模型通过翻看上一次尝试留下的 git 历史拿到答案）。

## 7. 消融：这个能力到底贡献了多少

只看“开启检索时 3/3 通过”，无法知道功劳是检索的还是模型本来就会。**消融**（ablation）把同一批题在“开 / 关某个能力”下各跑一遍，报告两者的分差 Δ。

| 题 | 有检索 | 无检索 | Δ | 解读 |
| --- | --- | --- | --- | --- |
| 项目参数题 A | 1.00 | 0.00 | +1.00 | 检索确实有用 |
| 通用知识题 B | 1.00 | 1.00 | 0 | 测不出检索的作用，换题或移进回归集 |
| 库外拒答题 C | 0.67 | 1.00 | −0.33 | 检索反而误导，值得归因 |

注意：“调用了检索工具”“答案带引用”这类检查，对照组永远不可能通过。算 Δ 时要把它们排除在两组之外，否则分差被人为放大。Claude Code 的插件评测就是这样处理“技能是否被调用”这类检查的。

## 8. 一键跑分的最小结构

```text
题目文件（每行：题目、参数、参考答案、打分器）
   │
   ├─ 选题（调试集 / 留出集 / 全部）× k 次 × 消融的两组
   ▼
并发执行（每次尝试一个新任务，彼此隔离）
   │  记下：答案、结局、工具序列、用量、耗时
   ▼
打分（确定性检查 → 评审模型三票）→ 每次尝试存一份
   ▼
汇总：pass@1 ± SE、pass^k、完成率、每次答对的成本、消融 Δ、与基线逐题对比
```

两个设计要点：

- **打分只依赖存下来的记录**，这样改了打分器可以重新打分，不必重跑 agent；
- **报告写明可复现信息**：代码版本、题目文件版本、被测模型、评审模型、参数。CI 里还要固定模型版本，免得把模型换代误当成代码回归。

## 9. 自测

| 问题 | 参考答案 |
| --- | --- |
| agent 回复“已经帮你订好了”，评测应该判通过吗？ | 不一定。这是轨迹；要检查结果（是否真有这笔预订）。 |
| 一道题在 10 次尝试里都是 0 分，首先怀疑什么？ | 题目或打分器有问题（歧义、过严的格式匹配），先读轨迹确认。 |
| 为什么要有“不该调用工具”的反例题？ | 防止单向优化：只测“该调用时调用了”，会把 agent 推向“什么都调用”。 |
| 过程检查为什么不查调用顺序？ | 合理路径不止一条，顺序检查会误伤正确解法；只查关键约束。 |
| 评审模型为什么最好和被测模型不同？ | 避免自我偏好；同家族模型倾向给自己的回答高分。 |
| 评审判“编造了尝试 3 次”，但执行器确实重试了 3 次，问题出在哪？ | 给评审的证据不全，是打分器的错；把尝试次数加进工具记录后重新打分。 |
| 20 题 × 3 次，算标准误时样本数是 60 还是 20？ | 20：同题的三次尝试不独立，先题内平均，再按题算。 |
| 新版本总分 75%，旧版本 70%，能说变好了吗？ | 不能。看逐题配对的差及其区间，以及有没有“以前全对、现在没全对”的题。 |
| 留出集为什么不能在调试时看？ | 看过就会被针对性优化，它上面的分数不再代表泛化能力。 |
| 消融时“调用了检索工具”这项检查怎么处理？ | 两组都不计入：对照组没有这个工具，计入会虚增 Δ。 |
