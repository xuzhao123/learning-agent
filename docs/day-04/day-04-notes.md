# Day 4：检索增强生成（RAG）与 Agent

## 学习目标

读完本文，应能回答以下问题：

1. 为什么不能把所有资料直接放进上下文窗口，RAG 解决的是哪一类问题。
2. 离线索引与在线查询各包含哪些环节，每个环节的设计取舍是什么。
3. 检索放在 Agent 的固定前置步骤和放成一个工具，各适合什么场景。
4. 向量相似度、top-k、阈值分别代表什么，为什么分数不是正确率。
5. 混合检索、重排和上下文化切块分别弥补向量检索的哪些不足。
6. 如何分层评估 RAG：检索质量、生成忠实度、拒答能力与成本。

## 1. 问题：模型知道什么，以及还需要知道什么

大语言模型的知识有两个来源：

- **参数知识**：训练时写入权重，覆盖面广，但有截止时间，无法知道私有资料，也不能指出依据。
- **上下文知识**：本次请求放进窗口的内容，可以是最新的、私有的，并且可以引用。

最直接的做法是把全部资料塞进上下文，但它很快会遇到四个限制：

| 限制 | 说明 |
| --- | --- |
| 容量 | 窗口有上限；资料库通常远大于窗口 |
| 成本与延迟 | 输入 token 按量计费，长输入也拖慢首个 token |
| 注意力稀释 | 长上下文中，位于中段的信息更容易被忽略（"lost in the middle"） |
| 权限与时效 | 不同用户能看的资料不同；资料会更新，整包注入难以控制 |

**检索增强生成（Retrieval-Augmented Generation, RAG）** 的思路是：资料留在窗口外，每次只取回与当前问题相关的少量片段，放进上下文，再让模型基于这些片段生成回答。它把"知道什么"从模型参数中部分剥离出来，交给可更新、可审计的外部存储。

RAG 解决的是**知识获取**问题，而不是推理能力问题。如果正确片段已经在上下文中，模型仍然算错或误读，那是生成环节的问题，增加检索不能修复它。

## 2. 系统结构：离线索引与在线查询

```text
离线索引：  采集 → 清洗 → 切块 → 附加元数据 → 向量化 → 写入索引
                                                        │
在线查询：  问题 → 查询改写 → 召回 → 过滤 → 重排 → 组装上下文 → 生成 → 引用
```

**离线索引**在资料变化时运行，决定"能被找到的单位是什么"。**在线查询**在每次提问时运行，决定"这一次取回什么、放多少"。

两个阶段必须使用**同一个向量模型和同样的预处理**。不同模型的向量位于不同空间，维度可能也不同；即使维度相同，跨模型比较相似度也没有意义。因此索引应携带版本信息（模型名、模型版本、维度、预处理与指令、语料指纹），任何一项变化都要重建索引，而不是混用旧向量。

## 3. RAG 在 Agent 中的位置

检索可以放在两个位置：

| 方式 | 流程 | 适合 | 代价 |
| --- | --- | --- | --- |
| 前置检索（pipeline） | 每次提问先检索，再把结果和问题一起交给模型 | 问答型产品、问题形态稳定 | 不需要检索时也检索；只能检索一次 |
| 工具式检索（agentic） | 把检索定义为工具，模型决定是否检索、检索什么、检索几次 | 多步任务、需要改写查询或多跳查找 | 多一次以上模型调用；模型可能跳过检索或查询写得不好 |

工具式检索不需要新的循环结构，它就是一次普通的工具调用：

```text
system → user
      → assistant(tool_calls: search(query="退款 时限", k=3))
      → tool(返回片段、来源、分数)
      → assistant(基于片段回答，并标注来源)
```

要点：

- 模型只生成查询，不读取索引。向量只用于排序，不会作为 Observation 交给聊天模型。
- 检索结果以 `role=tool` 消息回填，通过 `tool_call_id` 与请求配对；下一次模型调用才能看到它。
- 模型可以根据第一次结果改写查询再检索（**多跳检索**），例如先查到"产品型号"，再按型号查保修条款。
- 工具定义与系统提示需要说明：何时必须检索、只能依据哪些结果作答、证据不足时如何表述。

两种方式也可以组合：先做一次前置检索作为默认上下文，同时保留检索工具供模型补充查找。

## 4. 切块：检索的基本单位

切块（chunking）决定检索能命中的最小语义单元。粒度的取舍：

- **太小**：丢失条件与主体。只剩"额外重试 2 次"，读者不知道是什么在重试、是否包含首次执行。
- **太大**：一块混合多个主题，查询一个概念会带回大量无关内容，挤占窗口并引入干扰；向量也会被多个主题"平均"，区分度下降。

常见策略：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 固定长度 + 重叠 | 按 token 数切分，相邻块重叠一部分 | 无结构的长文本；重叠缓解跨边界的指代 |
| 结构感知 | 按标题、段落、条目、函数等自然边界切分 | 文档、FAQ、代码，有清晰结构时首选 |
| 语义切分 | 按相邻句子的语义变化点切分 | 结构弱但主题会切换的文本 |
| 父子块（small-to-big） | 用小块检索以提高精度，命中后返回所在的大块 | 既要精确定位又要完整上下文 |

每个块应保存**元数据**：编号、标题、来源、更新时间、权限标签等。元数据可用于过滤（只查某产品线、只查当前用户有权限的资料）、引用展示与审计。

还要注意向量模型的**最大序列长度**。超过上限的文本通常会被静默截断，尾部内容不参与向量化，检索时就"找不到"。建库时应检查每块的 token 数，超长的块应拆分，而不是依赖截断。

## 5. 向量检索：表示与相似度

### 5.1 Embedding

向量模型（embedding model）把文本映射为固定维度的向量，语义相近的文本方向接近。检索常用**双塔（bi-encoder）**结构：问题和文档分别独立编码，文档向量可以离线预先计算，查询时只需编码问题，再做向量比较。

问题与文档在形式上不对称：问题短，文档长且是陈述句。许多模型因此要求为两者加不同的前缀或指令，例如 E5 系列的 `query:` 与 `passage:`，或者在查询侧加入"根据问题找到能回答它的文本"这类任务说明。使用哪种前缀以模型说明为准，建库与查询必须分别保持一致。

### 5.2 相似度

设查询向量为 q，文档向量为 d：

```text
余弦相似度  cos(q, d) = (q · d) / (|q| |d|)        取值 −1 到 1，越大越相似
```

若事先把所有向量**归一化为单位长度**，则 `cos(q, d) = q · d`，余弦相似度就等于点积，计算最简单。此时欧氏距离与余弦单调相关：`|q − d|² = 2 − 2·cos(q, d)`，三种度量给出相同的排序。

### 5.3 规模

几十到几万条文档时，逐条计算点积（暴力检索）完全可行，结果精确。规模更大时使用**近似最近邻（ANN）**索引，如 HNSW（分层图）、IVF（倒排聚类）、PQ（乘积量化压缩），以少量召回损失换取数量级的速度提升。向量数据库提供的正是这类索引，以及元数据过滤、增量更新与持久化。

## 6. top-k、阈值与"资料不足"

**top-k** 是最多取回的候选数，不是证据数。k 越大，漏掉正确片段的概率越低，但噪声、延迟和窗口占用随之增加。例如问"年假能否跨年结转"，排第一的可能是讲"年假天数"的片段，排第二的才是说明"未休天数可结转到次年一季度"的片段；只取 k=1 就会漏掉关键条件。

**相似度阈值**用于过滤明显无关的候选。需要理解三点：

1. **分数不是正确率。** 0.6 不代表 60% 的概率正确，它只表示向量方向的接近程度。
2. **分数不可跨模型比较。** 不同模型的分数分布差别很大：一个模型的相关片段常在 0.7 以上，另一个可能集中在 0.5 左右。阈值必须针对具体模型和语料校准。
3. **校准方法**：准备一批标注了相关文档的问题，分别画出相关与不相关候选的分数分布，选择能较好分开两者的位置，并用另一批问题验证。

低于阈值的候选，最好在检索层就去掉正文，只保留标识和分数用于调试，避免模型把弱相关内容当作证据。

"资料不足"有两种，处理方式不同：

| 类型 | 表现 | 例子 |
| --- | --- | --- |
| 主题缺失 | 所有候选分数都很低 | 在技术文档库里问"差旅报销每晚上限" |
| 主题相关但事实缺失 | 候选可能过阈值，但正文没有所问的事实 | 文档讲了"错误处理与重试"，但没有定义某个具体错误码 |

第二种更危险：模型容易用相关内容拼凑出一个看似合理的回答。阈值无法识别这种情况，只能要求模型核对正文是否真正回答了问题。

## 7. 弥补向量检索的不足

### 7.1 关键词检索与 BM25

向量检索擅长匹配语义相近的不同措辞，但对**精确标识**（错误码、型号、函数名、缩写）不可靠。关键词检索正好互补。BM25 是最常用的词项打分函数：

```text
score(D, Q) = Σ IDF(t) · f(t,D)·(k1+1) / ( f(t,D) + k1·(1 − b + b·|D|/avgdl) )
```

- f(t,D)：词 t 在文档 D 中的频次，饱和增长（由 k1 控制，常取 1.2–2.0），出现十次不等于十倍相关。
- IDF(t)：越罕见的词权重越高。
- b：文档长度归一化强度，常取 0.75，避免长文档仅因词多而占优。

中文需要先分词，或按字的 n-gram 建索引。

### 7.2 混合检索与结果融合

把向量召回与 BM25 召回的候选合并。两者分数量纲不同，不宜直接相加，常用 **RRF（Reciprocal Rank Fusion）** 只按名次融合：

```text
RRF(d) = Σ_i 1 / (k + rank_i(d))      k 常取 60
```

### 7.3 重排（rerank）

双塔模型分别编码问题和文档，交互有限。**交叉编码器（cross-encoder）**把问题与候选拼在一起联合计算相关性，精度更高但更慢，因此只用于对召回的前几十个候选重新排序，再取前几个进入上下文。典型链路是：多路召回 → 融合去重 → 重排 → 取 top-n。

### 7.4 上下文化切块（Contextual Retrieval）

孤立的块常缺少主语或背景，例如"该季度收入增长 3%"不知道指哪家公司。Anthropic 提出的 Contextual Retrieval 在建库时让 LLM 读整篇文档，为每块生成一段通常 50–100 token 的说明，再把说明与原块一起做向量化和 BM25 索引。

其公开实验中（top-20 检索失败率）：

- 仅对向量使用上下文化：失败率相对降低 35%；
- 向量与 BM25 都上下文化：降低 49%；
- 再加重排：降低 67%。

这些数字依赖该实验的数据集与设置。代价是建库时每块都要调用一次 LLM，并且生成的说明也可能出错。给块加上标题等元数据能起到一部分类似作用，但不等同于这项技术。

## 8. 上下文组装、引用与安全

**上下文组装**决定取回的片段如何进入窗口：

- 去重，并合并来自同一文档的相邻片段；
- 控制总长度：片段与对话历史、工具结果共享窗口，超长会被截断或触发压缩；
- 排列顺序：把最相关的片段放在开头或结尾，减少中段被忽略。

**引用**让回答可核查，但引用本身不等于正确。核查时需确认三件事：

1. 被引用的片段确实在本次检索结果中返回过，而不是模型凭记忆编出的编号；
2. 该片段通过了相关性过滤；
3. 片段正文确实支持回答中的具体断言，包括数字、条件与肯定或否定关系。

常见错误是"引用正确的片段，却把否定说成肯定"，或"引用相关但不支持结论的片段"。

**安全边界**：

- 检索内容是**数据，不是指令**。文档中可能包含"忽略之前的规则"之类的文本（间接提示注入）。系统提示应声明这一点，但提示词不能单独构成完整防护，还需要来源可信度控制与输出约束。
- **权限过滤要在检索阶段完成**。先把无权访问的片段交给模型、再要求它不要说出来，是不可靠的。

## 9. 评估：分层看问题

RAG 的失败可能发生在任何一层，只看最终回答无法定位原因。应该分层测量：

| 层 | 指标 | 回答的问题 |
| --- | --- | --- |
| 检索 | hit@k / recall@k、MRR、nDCG | 正确片段有没有被找回，排在第几 |
| 生成 | 忠实度（groundedness）、答案正确率 | 回答是否只基于片段，是否答对 |
| 引用 | 引用精确率、引用召回率 | 引用的片段是否支持结论，关键结论是否都有引用 |
| 拒答 | 库外问题拒答率、无依据断言数 | 资料不足时是否承认，而不是编造 |
| 成本 | 模型调用次数、token、延迟、向量请求数 | 质量提升付出了多少代价 |

**评估集的构建**：

- 同时包含库内可答题和库外不可答题，后者专门测试拒答；
- 为每道题标注相关文档和人工评阅依据，评阅依据不发给模型；
- 用于调参的题目与最终评估的题目分开（留出集），否则结果会偏乐观；
- 做对照实验时控制变量：同一模型、推理强度、步数预算和回答标准，只改变"是否提供检索"。还要确保对照组没有其他途径接触到资料。

小样本的教学评估只能说明机制是否生效，不能推断生产环境的正确率。

## 10. 常见失败模式

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 该检索时没检索 | 工具描述或系统提示没有说明何时必须检索 | 看模型是否发起了检索调用 |
| 检索不到相关片段 | 查询措辞偏离、切块不当、超长被截断、精确词匹配差 | 直接用问题检索，看相关片段的名次与分数 |
| 检索到了但回答没用上 | 片段太多或位置不佳，干扰过强 | 减少 k，调整顺序，加入重排 |
| 用了错误片段 | 主题相近但事实不同；阈值过低 | 核对正文，提高阈值或改进切块 |
| 回答与片段相反 | 误读否定、条件或数字 | 引用核查，改写容易误读的原文 |
| 回答过时 | 索引未随资料更新 | 索引版本、更新时间元数据 |
| 越权泄露 | 未在检索时做权限过滤 | 检索层按用户权限过滤 |

## 11. 与长上下文和记忆的关系

- **长上下文窗口不会取代 RAG。** 窗口变大后可以多放资料，但成本、延迟与注意力稀释仍在；资料库规模、权限与更新也仍然需要检索层管理。两者常配合使用：检索出较多候选，再借助长窗口一起交给模型。
- **RAG 不等于长期记忆。** 本文讨论的是只读的外部知识。长期记忆还要处理写入（保存什么）、更新与冲突、遗忘与删除、隐私与隔离，是另一个独立的设计问题。

## 12. 自测

**1. 工具式 RAG 中，检索工具执行完为什么还要再调用一次模型？**
工具只是取回资料。资料作为 tool 消息回填后，下一次请求才把它交给模型，模型这时才能结合问题生成回答。

**2. 回答里带有引用，能否说明回答正确？**
不能。需要确认片段确实被本次检索返回、通过了过滤，并且正文支持回答中的具体断言。

**3. 换了 embedding 模型以后，旧阈值还能用吗？旧索引呢？**
都不能直接用。分数分布随模型变化，阈值要重新校准；不同模型的向量不在同一空间，索引必须重建。

**4. k 越大召回越好，为什么不一直调大？**
噪声、窗口占用与延迟同时增加，过多的弱相关片段还会干扰生成。应同时测检索指标、回答质量与成本，再决定 k。

**5. 候选分数过了阈值，为什么仍可能应该拒答？**
主题相近不等于事实齐全。片段讨论了相关主题，却可能根本没有所问的那个事实。

**6. 为什么错误码类问题适合加入 BM25？**
错误码是精确标识，语义向量对它区分度低；关键词匹配能直接命中包含该标识的文档。

**7. 如何证明"加了检索更好"？**
构建包含可答题与不可答题的评估集，在其他条件相同的前提下对比有无检索，分层统计检索命中、答案正确率、引用有效性、拒答与成本，并在留出集上确认结论。
