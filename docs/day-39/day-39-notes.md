# Day 39：子 agent 的控制面

## 学习目标与术语

学完能说明：父 agent 除了“派出去、等它做完”还需要哪些控制子 agent 的手段；后台运行、等待、插话、停止各解决什么问题；“分叉”和“全新上下文”的子 agent 各适合什么；后台子 agent 的生命周期该怎样和父 agent 的一轮对齐。

| 术语 | 通俗解释 |
| --- | --- |
| 前台子 agent | 父 agent 派出后停下来等它做完，拿到结论再继续 |
| 后台子 agent | 派出后立刻拿回一个任务ID，父 agent 接着做别的，之后再取结论 |
| 等待 | 父 agent 停下来等某个（或任意一个）后台子 agent 做完 |
| 插话 | 给还在跑的子 agent 补一句说明，不打断它，排进它的下一次模型请求 |
| 分叉 | 子 agent 带着父 agent 当前的对话开始，而不是一个空白的上下文 |

## 1. 为什么需要控制面

只有“派出去、等它做完”时：

- 两件互不相关的事，父 agent 要么自己做、要么派出去干等，不能一边等子 agent 一边自己做别的；
- 派出去之后发现说漏了一个条件，只能等它做完再派一次；
- 方向错了，只能等它把预算用完。

控制面就是补上这几个动作：

| 动作 | 解决什么 |
| --- | --- |
| 后台派出 | 父 agent 不被一个子任务卡住 |
| 等待（某一个或任意一个） | 在需要结论的时候再取，可以设上限，到时没做完先做别的 |
| 插话 | 补充条件、收窄范围，已经做的不作废 |
| 停止 | 方向错了或结论不需要了，及时止损；停下时写好检查点，之后还能接着做 |

插话和停止用的是父子之间同一套协议：父 agent 就是子 agent 的“界面”，界面能对 agent 做的事（插话、中断），父 agent 也能对子 agent 做。

## 2. 分叉还是全新上下文

| | 全新上下文 | 分叉 |
| --- | --- | --- |
| 子 agent 看到什么 | 只有父 agent 写的任务说明 | 父 agent 到目前为止的整段对话，加上任务 |
| 任务说明要写多少 | 要把背景、约束、期望输出都写清楚 | 只写要它做什么 |
| 上下文成本 | 小 | 和父 agent 一样大 |
| 适合 | 独立的子任务（查一个资料、改一个文件） | 依赖前面讨论的子任务（“按我们刚才定的格式，试一下方案 B”） |

分叉要注意两件事：

- **身份**：父对话里的用户消息是对父 agent 说的（比如“派一个子 agent 去做 X”），子 agent 读到会以为是对自己说的，可能再去派子 agent。要在分叉的对话末尾说清“你是被派出的子 agent，只做下面这个任务”。
- **工具与规则**：子 agent 的工具和父 agent 不同，系统提示词要换成子 agent 自己的。

## 3. 生命周期

后台子 agent 不能比父 agent 的这一轮活得更久而没人管：

- 父 agent 想结束这一轮时，如果还有后台子 agent 在跑，提醒它一次：先取回结论或停掉；
- 这一轮真的结束时，还在跑的统一停下，写好检查点，结论下一轮可以用任务ID取回。

和后台 shell 命令（Day 32）是同一个原则：后台的东西跟着这一轮走，结束时清理干净。

## 自测

1. 只有前台子 agent 时，有哪三种做不到的事？
2. 插话和停止为什么可以复用父子之间的协议？
3. 什么样的子任务适合分叉？分叉时要额外处理什么？
4. 父 agent 想结束时还有后台子 agent 在跑，harness 应该怎么做？

### 自测答案

1. 一边等子 agent 一边自己做别的；派出后补充条件；方向错了及时停下。
2. 父 agent 对子 agent 来说就是界面；界面能发的插话、中断请求，父 agent 也能发。
3. 依赖前面讨论内容的子任务；要说清子 agent 的身份（不要把父对话里的指令当成对自己说的），并换成子 agent 自己的系统提示词。
4. 提醒一次，让它先取回结论或停掉；这一轮结束时把还在跑的停下、写好检查点，下一轮可以续跑取回。
