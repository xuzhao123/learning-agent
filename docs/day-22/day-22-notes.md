# Day 22：Agent Harness 参考架构

## 学习目标与术语

学完能说明：harness 在模型之外负责什么；一个成熟的编码 harness 分哪几层、一次请求怎样穿过它们；提示词为什么要按固定顺序组装；一次工具调用要经过哪些判断才执行；沙箱和审批为什么是两条独立的防线；以及怎样用一批真实任务检验一个 harness。

| 术语 | 通俗解释 |
| --- | --- |
| Harness | 包在模型外面的那一层：组织上下文、提供并执行工具、决定动作能不能做、保存会话。模型负责推理，harness 负责其余一切 |
| Turn | 用户发一次消息，到 agent 给出最终回复为止的一轮工作，中间可以有几十次模型调用和工具调用 |
| Thread / Session | 一段对话，由很多 turn 组成；可以恢复、分叉 |
| Item | Turn 里的一个条目：一段用户消息、一次模型回复、一次工具调用及其结果 |
| 客户端协议 | 界面和 harness 之间的事件约定：界面发起 turn、插话、中断；harness 推送事件、发出审批请求 |
| 提示缓存（Prompt caching） | 模型服务记住请求开头那段内容的计算结果，下一次开头相同时直接复用，省钱也省时间 |
| 稳定前缀 | 每次请求开头那段不变的内容：系统指令、工具定义、项目指令 |
| 系统提醒 | harness 追加在对话里的一小段说明，比如“你之前读过的文件刚被改了” |
| 压缩（Compaction） | 上下文快满时，用更短的内容替换旧内容，通常先清掉旧的工具输出，再做摘要 |
| 策略管线 | 每次工具调用执行前依次经过的判断：hook、规则、权限模式、审批者 |
| 规则 | 按工具和参数写的允许、询问、拒绝，例如“`npm test` 直接允许”“`rm -rf` 拒绝” |
| 权限模式 | 一次切换整套默认行为，例如只计划不改、编辑免问、全部放行 |
| Hook | 用户在固定时刻挂上的外部程序，例如工具执行前、执行后、会话结束时，可以拦截或补充信息 |
| OS 沙箱 | 由操作系统强制的边界，限制命令能读写哪些文件、能不能联网 |
| 文件检查点 | 改文件之前先存一份旧内容，出错时按步回退 |
| 自用（Dogfooding） | 用自己做的工具完成自己的真实工作，以此发现问题 |

## 1. Harness 是什么

同一个模型，放在不同的 harness 里，表现会差很多。模型只会读一段输入、写一段输出；它看到什么、能调用哪些工具、调用会不会被执行、执行结果怎样回到下一次输入、对话怎样保存和恢复，都由 harness 决定。

OpenAI 在介绍 Codex 时，把协调用户、模型和工具的那部分称为 harness，并说明 Codex 的命令行、云端和编辑器插件共用同一个 harness。Anthropic 的 Claude Code 文档也用了同一个词：Claude Code 就是模型外面那一层，提供工具并管理模型看到的上下文。[资料](https://openai.com/index/unrolling-the-codex-agent-loop) [资料](https://code.claude.com/docs/en/how-claude-code-works)

所以学习 harness，不是学某个产品的用法，而是学这一层要解决哪些问题、通常怎样解决。

## 2. 五层结构

把 Codex 与 Claude Code 公开的设计叠在一起，可以得到一个大致相同的分层：

```text
界面        终端 · IDE · 桌面与网页 · 无头/CI · SDK · 云端
              │  客户端协议：开始 turn、插话、中断 ↓   事件、增量、审批请求 ↑
Harness 核心（一个会话）
  上下文引擎   按固定顺序组装请求；压缩；工具定义按需加载
  Agent 循环   组装请求 → 模型采样 → 解析 → 策略管线 → 执行 → 回填 → 下一步
  执行面       文件 · 搜索 · Shell（在 OS 沙箱里）· Web · MCP · 子 agent · 编排工具
              │
扩展层        项目指令 · Skills · Hooks · 斜杠命令 · MCP 配置 · 子 agent 定义 · 插件
状态层        会话记录 · 恢复与分叉 · 文件检查点 · 记忆 · 计划状态 · 遥测
```

几个关键关系：

- **一个核心，多种界面**。各种界面都是同一个核心的客户端，靠同一套事件协议驱动。新增一种界面，不用重写循环。
- **审批由 harness 发起、界面回答**。harness 在执行前发出审批请求，等界面上的人回答；没有界面时，只能按预先配置的规则处理。
- **扩展层是配置文件，不是代码**。改项目指令、加一条权限规则、挂一个 hook，都不需要改 harness 本身。
- **状态层分两种回退**：对话可以恢复和分叉，文件可以按检查点回退。两者独立，远程系统上的副作用两者都撤不回。

## 3. 用一个任务走一遍

用户说：“测试挂了，修一下。”

| 步骤 | 发生了什么 | 哪一层负责 |
| --- | --- | --- |
| 1 | 界面发出“开始 turn”，带上这句话 | 界面、协议 |
| 2 | 按顺序组装请求：系统指令、工具定义、项目指令、环境信息、历史、这句话 | 上下文引擎 |
| 3 | 模型流式返回：先说要跑测试，再给出调用 `shell("go test ./...")` | 循环、模型客户端 |
| 4 | 这条命令过策略管线：没有 hook 反对，规则里“测试命令直接允许”命中，不用问人 | 策略管线 |
| 5 | 命令在沙箱里运行，只能写工作区，不能联网；输出太长时截断 | 执行面、OS 沙箱 |
| 6 | 结果追加进历史，界面收到一条“工具调用完成”事件 | 循环、协议 |
| 7 | 模型读了两个文件（只读调用，可以并行），然后发起一次编辑 | 循环、执行面 |
| 8 | 编辑过策略管线：当前模式要求编辑前问人，于是发出审批请求，人点了允许 | 策略管线、协议 |
| 9 | 编辑前先给文件存一份快照，再写入 | 执行面、状态层 |
| 10 | 再跑一次测试，通过；模型给出不带工具调用的回复，turn 结束 | 循环 |

如果第 9 步改坏了，用户可以按检查点回退文件；如果整段思路都错了，可以从第 6 步分叉对话，换一种做法。

## 4. 上下文引擎：顺序决定成本

每次模型调用，harness 都要把整段上下文重新发一遍。一个 turn 里有 30 次模型调用，开头那段系统指令和工具定义就要发 30 次。提示缓存能让模型服务复用“开头相同的部分”，前提是开头真的一字不差。

所以成熟的 harness 会按变化频率排序：

| 位置 | 内容 | 变化频率 |
| --- | --- | --- |
| 最前 | 系统指令、工具定义 | 几乎不变 |
| 其次 | 项目指令（按目录层级合并） | 一个会话内不变 |
| 再次 | Skills 索引、记忆摘要 | 会话级 |
| 然后 | 环境信息：工作目录、git 状态、沙箱与权限 | 偶尔变化 |
| 最后 | 对话历史 | 只往后追加 |

两条规则由此而来：

1. **历史只追加，不改写**。改动前面任何一个字，后面的缓存全部失效。
2. **变化用追加表达**。工作目录换了、某个文件被外部改了、计划更新了，harness 都追加一条系统提醒，而不是回头修改前面的环境信息。

简单算一笔账。假设固定前缀 20k token，每次调用新增 2k，一个 turn 调用 30 次：

- 没有缓存时，30 次一共要处理约 20k × 30 + 2k × (1 + 2 + … + 30) ≈ 600k + 930k = 1.53M token。
- 有缓存时，只有新增部分需要完整计算，约 2k × 30 = 60k，其余按缓存价计费。

压缩也要照顾缓存和信息量：先清掉旧的工具输出（体积最大、价值衰减最快），还不够再做摘要；摘要之后，前缀会重建一次。

## 5. 策略管线：一次调用要过几关

模型提出的每次工具调用，都要先经过策略管线：

```text
工具调用 → ① hook（执行前） → ② 规则 deny › ask › allow → ③ 权限模式 → ④ 审批者 → 执行
```

| 关卡 | 看什么 | 典型配置 |
| --- | --- | --- |
| ① 执行前 hook | 用户自己的程序拿到调用参数，可以拒绝、要求询问、放行或改写参数 | “禁止改 `migrations/` 目录” |
| ② 规则 | 工具名加参数模式；先看拒绝，再看询问，最后看允许，命中第一条就定 | `Bash(npm test)` 允许，`Bash(curl *)` 拒绝 |
| ③ 权限模式 | 没被规则覆盖时的默认行为 | 只计划不改；编辑免问；全部放行 |
| ④ 审批者 | 需要询问时由谁回答 | 人；或分类器、审查子 agent 先筛一遍，有风险再找人 |

两个容易错的地方：

- **拒绝规则优先于一切放行**。Claude Code 的规则按拒绝、询问、允许的顺序判断，具体程度不影响顺序；hook 返回放行，也绕不过命中的拒绝规则。这样，组织下发的拒绝规则不会被个人配置或某个插件悄悄放开。[资料](https://code.claude.com/docs/en/permissions)
- **规则看的是命令文本**。`Bash(curl *)` 拦得住 `curl`，拦不住 `python -c "import urllib..."`，也拦不住写进脚本再运行。只要命令能写成别的样子，文本规则就有漏洞，所以还需要下一节的沙箱。

## 6. 沙箱和审批是两条轴

| | 审批：越界前问人 | 审批：从不问 |
| --- | --- | --- |
| 沙箱：只读或只写工作区 | 日常交互的常用组合 | 自动化任务：越界直接失败 |
| 沙箱：完全放开 | 每一步都依赖人的判断 | 只适合本身就隔离的容器或虚拟机 |

- **沙箱**由操作系统强制，管的是实际的系统调用：能打开哪些文件、能不能建网络连接。命令怎么写都绕不过去。它只约束 shell 及其子进程；harness 主进程和自带的文件工具不在沙箱里，由策略管线管。
- **审批**决定越过边界时怎么办：问不问、问谁。它能理解意图（“这次删除是用户要求的”），但人会疲劳，规则会有漏洞。

Codex 把两者做成两个独立配置：`sandbox_mode`（只读、工作区可写、完全放开）和 `approval_policy`（需要时询问、从不询问）。Claude Code 用权限模式和规则做审批，用可选的沙箱约束 shell；两份配置里的路径和域名最后会合并成一份沙箱配置。[资料](https://learn.chatgpt.com/docs/sandboxing) [资料](https://code.claude.com/docs/en/permissions)

为什么两者都要：提示注入可能让模型写出看似无害、其实越界的命令，审批没看出来，沙箱仍会拦下；反过来，沙箱允许的操作也可能不是用户想要的，比如删光工作区，这要靠审批和文件检查点。

## 7. 扩展层：写配置就生效

扩展点有一个共同要求：用户不改 harness 代码，就能改变它的行为。

| 扩展点 | 解决什么 | 进上下文的方式 |
| --- | --- | --- |
| 项目指令（AGENTS.md / CLAUDE.md） | 项目约定、构建命令、禁区 | 会话开始时整份放进前缀 |
| Skills | 某类任务的做法 | 只放名字和简介，用到时再读正文 |
| Hooks | 在固定时刻插入确定性的检查或动作 | 不进上下文；结果可以作为提醒追加 |
| 斜杠命令 | 常用提示词的快捷方式 | 用户触发时展开 |
| MCP 配置 | 接外部工具服务 | 工具定义可以按需加载 |
| 子 agent 定义 | 有固定职责和工具范围的助手 | 在独立上下文里运行，只回摘要 |
| 插件 | 把以上几样打成一个包分发 | 由各部分自己决定 |

多份配置按层级合并：组织下发的托管策略最高，然后是命令行参数、项目本地、项目共享、用户全局。Hook 的约定通常很简单：事件以 JSON 从标准输入传进去，程序用退出码或标准输出里的 JSON 表达决定，例如退出码 2 表示拦下。[资料](https://code.claude.com/docs/en/hooks) [资料](https://developers.openai.com/codex/hooks)

## 8. 两家的不同取舍

| 方面 | Codex | Claude Code | 取舍 |
| --- | --- | --- | --- |
| 编辑工具 | 模型写补丁（apply_patch） | 唯一字符串替换（Edit） | 补丁适合一次改多处，但格式出错就整体失败；字符串替换简单可靠，但要求替换目标在文件里唯一 |
| 安全配置 | 沙箱模式 + 审批策略两个独立旋钮 | 权限模式 + 规则，沙箱可选 | 两个旋钮概念清楚；模式加规则更细，组合更多 |
| 客户端协议 | app-server：双向 JSON-RPC，Thread/Turn/Item | SDK 消息流 + 权限回调 | 协议方式适合多种界面和远程；SDK 方式适合嵌进应用代码 |
| 模型接口 | Responses API | Messages API | 各自贴合自家模型的推理、缓存与压缩能力 |

这些差别说明，参考架构给的是“要有哪些层、每层解决什么”，不是唯一的实现。

## 9. 怎样检验一个 harness

功能做出来不等于好用。一个直接的办法是选一批自己仓库里的真实小任务，让 harness 去完成，看它卡在哪一步。选题有三条标准：

- **真实**：来自真实待办，不为测试专门编造。
- **可判定**：编译、运行一条检查命令或看一处输出，就能判断做没做对。
- **覆盖不同能力**：有的只改一行描述，有的要跨几个文件，有的要先读懂并发逻辑，有的需要越过沙箱边界。

同一批题在每次改进 harness 之后都重跑一遍，前后对比才有意义。题量够了，再给每题配上校验命令，就成了正式的评测集。

## 自测

**一个模型换到另一个 harness 里，为什么表现会变？**

模型看到的上下文、能用的工具、调用会不会被执行、结果怎样回到下一次输入，都由 harness 决定。同样的推理能力，输入和工具不同，结果就不同。

**提示词为什么要“前缀稳定、历史只追加”？工作目录里的文件变了，harness 应该怎么告诉模型？**

提示缓存只复用一字不差的开头部分；改动前面任何内容，后面的缓存都会失效，成本和延迟随之上升。文件变化应追加一条系统提醒，不回头修改前面的环境信息。

**一条拒绝规则命中了，但执行前 hook 返回了放行，最后谁说了算？为什么这样设计？**

拒绝规则说了算。拒绝优先，保证上层（组织、项目）下发的禁止项不会被下层配置或某个扩展悄悄放开。

**沙箱和审批各挡住什么？为什么只用其中一个不够？**

沙箱由操作系统强制，管实际的文件和网络访问，命令怎么写都绕不过，但它不理解意图，也不管 shell 以外的工具。审批理解意图，能拦下“合法但不该做”的操作，但依赖人的判断和文本规则，可能被换种写法绕过。两者互补。

**文件检查点和对话分叉有什么区别？哪些事两者都撤不回？**

文件检查点回退的是磁盘上的文件内容，对话分叉回退的是模型看到的历史。已经发生的远程副作用，比如发出去的请求、改过的数据库、完成的部署，两者都撤不回，只能靠执行前的审批。

**Skills 和项目指令都是给模型看的说明，为什么进上下文的方式不同？**

项目指令每次都相关，放进稳定前缀，一次缓存、多次复用。Skills 数量多、各自只在少数任务里有用，常驻只放简介，用到时再加载正文，节省上下文。
