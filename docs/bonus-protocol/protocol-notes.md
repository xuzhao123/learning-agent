# 扩展：agent 与界面之间的结构化协议

## 学习目标

读完本文，应能回答以下问题：

1. agent 核心和界面（命令行、网页、IDE）之间，为什么需要一个专门的协议，而不是让界面去读日志？
2. JSON-RPC 2.0 的请求、响应、通知各是什么？一行一条消息的传输方式有什么好处？
3. 会话为什么分成 Thread、Turn、Item 三层？Item 的生命周期为什么要有开始、增量、完成？
4. “服务端主动向客户端发请求”解决了什么问题？审批流程怎样设计才安全？
5. 子 agent、嵌套调用时，事件和请求怎样逐级转发？
6. 为什么不直接用 MCP 承载这件事？

## 1. 问题从哪里来

一个 agent 往往不止一个界面：命令行、网页、编辑器插件，甚至另一个 agent。它们都需要知道同一件事：agent 现在在做什么。

最省事的做法是让界面读 agent 的日志，用正则去匹配“开始调用工具”“任务ID是多少”这样的行。这种做法很快会出问题：

- **日志是给人看的**：措辞一改、多打一个空格，界面就解析不出来；日志和数据混在一起，谁都不敢改。
- **只能单向**：agent 想在执行到一半时问用户“允许访问这个网站吗”，日志做不到。只能先结束这一轮，让用户在下一轮回答。
- **嵌套更乱**：子 agent 的输出被父 agent 转发时，只能靠加前缀区分，界面要再拆一次。

所以成熟的 agent 产品会在核心和界面之间定义一个**结构化、双向**的协议。OpenAI Codex 的 app-server 就是一个例子：命令行、VS Code 插件、网页版、桌面应用和第三方 IDE 共用同一个 agent 核心，通过同一个协议与它通信。

## 2. 传输：JSON-RPC 2.0，一行一条

JSON-RPC 2.0 只定义了三种消息：

| 消息 | 字段 | 含义 |
| --- | --- | --- |
| 请求 | `id`、`method`、`params` | 需要对方回复 |
| 响应 | `id`、`result` 或 `error` | 用同一个 `id` 回复对应的请求 |
| 通知 | `method`、`params`，没有 `id` | 告诉对方一件事，不需要回复 |

```text
界面 → agent   {"jsonrpc":"2.0","id":1,"method":"turn/start","params":{"question":"现在几点？"}}
agent → 界面   {"jsonrpc":"2.0","id":1,"result":{}}
agent → 界面   {"jsonrpc":"2.0","method":"item/started","params":{"item":{"id":"call_1","type":"toolCall",…}}}
agent → 界面   {"jsonrpc":"2.0","id":7,"method":"network/requestApproval","params":{"domain":"pypi.org",…}}
界面 → agent   {"jsonrpc":"2.0","id":7,"result":{"decision":"allow"}}
```

几个要点：

- **双方都能发请求**。`id` 只在发起方自己的编号空间里唯一，回复时带回同一个 `id`，发起方据此把响应交给正在等待的那次调用。
- **一行一条**（JSON Lines）：读一行就是一条完整消息，不需要长度前缀，用 stdio、管道、socket 都能传。代价是消息里不能有未转义的换行，JSON 编码天然满足。
- **协议和日志分开**：stdout 只放协议，给人看的日志放 stderr。否则一行日志混进来就会破坏解析。
- **未知的方法要回错误**（JSON-RPC 规定 `-32601 Method not found`），未知的通知直接忽略。这让新旧版本可以共存：旧界面不认识新通知，不会出错。

## 3. 会话模型：Thread、Turn、Item

```text
Thread（会话）：可以保存、恢复、分叉
 └ Turn（一轮）：用户的一次提问，到 agent 给出回答或停下为止
    ├ Item：用户消息
    ├ Item：一次模型调用        started → (delta …) → completed
    ├ Item：一次工具调用        started → completed（带结果或错误）
    └ Item：一次上下文压缩      started → completed
```

- **为什么分三层**：界面需要在不同粒度上展示和操作。Thread 决定“哪段对话”，Turn 决定“哪一轮可以中断、哪一轮的结局是什么”，Item 决定“这一步花了多久、结果是什么”。
- **为什么 Item 有开始和完成两个事件**：只发完成事件，界面在一个慢工具执行的几十秒里什么都不知道。开始事件让界面立刻显示“正在执行”，完成事件再补上结果。流式输出时中间再插入 delta（增量），界面就能逐字显示。
- **Item 要有稳定的 ID**：开始和完成靠 ID 配对；同一个工具调用的 ID 最好和模型协议里的 `tool_call_id` 一致，界面才能把“模型请求了什么”和“工具做了什么”对上。
- **一轮的结局要明确**：`turn/completed` 带上结局（完成、被中断、预算耗尽、熔断……）。界面不用再从最后几行日志猜。

## 4. 服务端主动发请求：审批

协议双向之后，agent 可以在执行到一半时**暂停**，向界面发一个请求，等到回复再继续：

```text
agent：执行 request_network_access(pypi.org)
  → 发请求 network/requestApproval，在这里等待
界面：显示“允许 / 拒绝”按钮
  → 用户点击 → 回复 {"decision":"allow"}
agent：收到回复，把 pypi.org 加入白名单，本轮接着执行
```

设计时要考虑几种情况：

- **谁能回答**：回复只能来自界面连接，模型碰不到这个通道。模型只能“发起请求”，不能“批准请求”，这是审批的安全前提。
- **等多久**：人可能不在。等待要有上限，到时返回“暂未答复”，让模型结束本轮、说明原因，而不是无限期卡住整个任务。
- **没有人能回答时**：命令行直接运行、后台队列里，根本没有可以点按钮的人。应该如实返回“当前没有可批准的界面”，并给出别的路径（比如下次启动时显式授权），而不是假装批准或假装拒绝。
- **中断**：等待期间用户按了停止，等待要随之取消，这次调用记为“结果未知”。

中断本身也可以做成一个请求（`turn/interrupt`）。它和 Ctrl+C 走同一条“两段式停止”：先收尾、写好检查点，再退出。比起直接发信号，协议请求能拿到“已经收到”的确认，失败时再退回到信号。

## 5. 嵌套：父 agent 是子 agent 的界面

子 agent 也用同一个协议启动时，父 agent 就是它的“界面”：

```text
网页 ⇄ 观测台 ⇄ 父 agent ⇄ 子 agent
```

- **事件向上转发**：子 agent 的通知被包一层（比如 `subagent/message`，带上子任务ID）交给父 agent 的界面。界面把它原样应用到这个子 agent 的状态上，处理逻辑和父 agent 完全一样。
- **请求向上转发，回复向下传回**：子 agent 要审批时，父 agent 把请求转给自己的界面，拿到回复再交回子 agent。整条链上任何一层都可能没有界面（比如后台队列），那就由这一层如实回答“没人能批准”。
- **日志不走协议**：子 agent 的日志仍然是文本，由父 agent 转发；协议只承载结构化信息。

## 6. 为什么不用 MCP

MCP 定义的是“模型调用外部工具”：客户端发 `tools/call`，服务端执行并返回结果，一问一答。agent 与界面之间需要的东西它装不下：长时间运行的会话、流式增量、执行到一半的审批、会话的保存与恢复。OpenAI 起初尝试用 MCP 承载 Codex 与 IDE 的通信，后来改成了 app-server，原因正是“很难让 MCP 的语义适配 IDE 的需要”。

两者不冲突：agent **对外调用工具**用 MCP，agent **对界面汇报和接受控制**用自己的会话协议。

## 7. 取舍与边界

- **连接跟着进程走**：用 stdio 时，界面进程退出，连接就断了，正在运行的 agent 没人接管。要做到断开后重连，需要一个独立于界面存活的进程（daemon），或者让事件先落盘，界面重启后按序号补读。
- **旧数据的兼容**：协议上线前的历史记录只有日志。可以写一个兼容层，把旧日志换算成同样的事件，只对旧数据使用；新数据不经过它。
- **协议也要版本管理**：新增字段和新通知可以向后兼容；改字段含义、删除字段就需要版本号或新的方法名。

## 8. 自测

**1. 为什么协议消息和日志必须分到不同的通道？**
混在一起时，任何一行日志都可能被当成协议消息，或者破坏正在解析的消息；分开之后，日志可以随意改写，不会影响界面。

**2. 双方都能发请求时，响应怎么找到对应的请求？**
每一方给自己发出的请求编号，回复时带回同一个 `id`；发起方维护“等待中的请求”表，收到响应就交给对应的等待者。

**3. Item 只发完成事件会有什么问题？**
慢操作执行期间界面什么都不知道，无法显示进度，也无法在中途展示“正在等待审批”这类状态。

**4. 审批请求为什么不能让模型回答？**
模型可能被它读到的内容注入指令，如果它能批准，攻击者只要诱导它“允许访问 attacker.example”就能打开外发通道。回复只能来自界面连接上的人。

**5. 后台队列里的子 agent 发起审批，应该怎样回答？**
如实回答“当前没有可批准的界面”，让 agent 返回待批准状态并说明原因；不能默认批准，也不该当成用户拒绝。

**6. 为什么 agent 与界面的通信不用 MCP？**
MCP 是一问一答的工具调用，缺少长会话、流式增量、执行中的审批和会话恢复这些语义。
