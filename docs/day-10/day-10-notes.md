# Day 10：任务调度——队列、并发控制与幂等

## 学习目标

读完本文，应能回答以下问题：

1. 为什么不直接在请求里执行 agent 任务，而要经过队列？
2. 并发上限由什么决定？怎样估算一批任务要跑多久？
3. 至多一次、至少一次、恰好一次三种投递语义有什么区别？“恰好一次”实际上是怎样实现的？
4. 幂等键由谁生成？同一个键配不同的请求该怎么办？
5. 一个任务显示“运行中”，怎样判断执行它的进程是不是已经死了？
6. 任务失败后，哪些该重试、哪些该进死信队列？

## 1. 从一个任务到一批任务

前几天的 agent 一次只跑一个任务。真实系统里任务是源源不断提交的：用户发起调研、定时触发的报表、批量处理的文档。直接在收到请求的地方执行，会遇到几个问题：

- **提交方要一直等着**：一个任务跑十分钟，HTTP 连接早就超时了；
- **没有上限**：一百个请求同时到达，就同时发起一百路模型请求，很快被限流（HTTP 429）或耗尽内存；
- **失败无处重来**：执行到一半进程重启，任务就丢了。

队列把“提交”和“执行”分开：

```text
提交方 ──▶ 队列（持久化） ──▶ worker × N ──▶ 执行任务 ──▶ 结果存储
  立刻拿到任务ID          按顺序取任务        每个 worker 同时只跑一个      提交方按ID查询
```

## 2. 并发控制

### 2.1 为什么要设上限

每个任务都要消耗有限的资源：模型服务的请求速率与 token 速率配额、每个进程的内存、下游 API 的限流、预算。并发上限就是所有这些约束里最紧的那一个。超过它，多出来的任务只会排队、被限流、互相拖慢，总吞吐量并不会更高。

### 2.2 两种常见写法

- **固定数量的 worker**：启动 N 个 worker，从同一个队列里取任务。worker 数就是并发上限。
- **信号量**：每个任务开始前先获取一个许可，一共 N 个许可，结束时归还。

两者等价，前者更适合“任务列表”，后者更适合“任务随时产生”的场景。

### 2.3 估算：利特尔法则

稳定状态下，**系统里的平均任务数 = 到达速率 × 平均停留时间**（L = λW）。反过来，N 个 worker 能维持的吞吐量约为 N / 平均执行时间。

例子：10 个任务，每个平均 20 秒，3 个 worker。吞吐量约为每秒 3/20 = 0.15 个任务，总耗时约 10 / 0.15 ≈ 67 秒。任务长短不均时，最后一个长任务会拖尾，实际总耗时会更长一些。

## 3. 投递语义

worker 取到任务、执行、报告完成，这三步之间任何一处都可能崩溃。按“崩溃后任务会怎样”分三种语义：

| 语义 | 做法 | 崩溃后 | 代价 |
| --- | --- | --- | --- |
| 至多一次 | 取出即删除，再执行 | 任务丢失 | 不会重复 |
| 至少一次 | 执行完才删除；取出时只是“暂时隐藏” | 隐藏到期后重新出现，被再执行一次 | 可能重复 |
| 恰好一次 | 至少一次 + 执行端去重 | 重新出现，但执行端认出它已完成 | 需要幂等键和结果存储 |

以 Amazon SQS 为例：worker 收到消息后，消息在**可见性超时**（默认 30 秒）内对其他 worker 不可见；worker 处理完调用删除，否则超时后消息重新可见。这就是租约：worker 在一段时间内“持有”任务，过期别人就能接手。任务比租约长时，worker 要定期延长租约（心跳）。

网络上无法真正做到“消息恰好传递一次”。工程上说的恰好一次，指的是**效果恰好一次**：允许重复投递，但处理端用幂等保证重复的投递不产生第二次效果。

## 4. 幂等设计

### 4.1 幂等键

幂等指同一个操作执行一次和执行多次，效果相同。对“创建”类操作，靠**幂等键**实现：

1. 提交方为每个逻辑操作生成一个唯一的键（通常是 UUID，或业务上天然唯一的ID，如订单号）；
2. 服务端收到请求，先查这个键：
   - 没见过：执行，把“键 → 结果”保存下来；
   - 已完成：直接返回保存的结果，不再执行；
   - 正在执行：拒绝或等待，不能再启动第二个；
3. 网络失败时，提交方用**同一个键**重试。

键必须由**提交方**生成：只有提交方知道“这两次请求是同一个意图的重试”，还是“用户确实想做两次”。

### 4.2 键与请求必须匹配

同一个键配了不同的请求内容，说明调用方出错了（比如复用了变量）。服务端不能把旧结果当成新请求的结果返回，应当报错。Stripe 的 API 就是这样：比较新请求与原请求的参数，不一致时返回错误。

### 4.3 显式的键与内容哈希

不想让提交方管理键时，可以用请求内容的哈希作为键：同样的内容自动去重。缺点是用户真的想把同一个问题问两次时做不到，因此适合“同样的输入就该得到同样的结果”的批处理。

### 4.4 “先查再做”的竞态

```text
worker A：查键 → 没有    ……    执行
worker B：      查键 → 没有    ……    执行      ← 重复
```

查询和占有必须是一个原子操作：数据库唯一约束、`INSERT … ON CONFLICT`、Redis 的 `SET NX`、单机上的文件锁。拿到占有权的那一个才能执行。

### 4.5 幂等要贯穿到底

任务级的幂等只能保证“同一个任务不会被启动两次”。任务内部的工具调用如果有副作用，崩溃恢复时仍可能重复执行（Day 9 第 5 节）。真正的端到端幂等，要把幂等键一路传到产生副作用的那个 API：子任务的ID由父任务ID派生，外部请求带上由任务ID和步骤号派生的键。

## 5. 任务级的失败处理

| 失败 | 例子 | 处理 |
| --- | --- | --- |
| 暂时性 | 模型服务 503、网络中断、进程被杀 | 退避后重试；有检查点就续跑，不从头再来 |
| 确定性 | 参数非法、预算耗尽、熔断 | 不重试，标记失败并报告原因 |
| 反复失败 | 每次执行都让 worker 崩溃的“毒消息” | 超过最大次数后移入**死信队列**，留给人检查，不再阻塞正常任务 |

重试次数要有上限，并且计入整个任务的生命周期（包括续跑），否则一个毒消息会无限循环。

## 6. 停止与取消

调度方收到停止信号时：

1. 不再派发新任务；
2. 把取消传给正在执行的任务：子进程先发 SIGINT，给它时间写检查点，超过宽限期再强制结束；
3. 等所有在途任务结束，汇报哪些完成、哪些中断、哪些还没开始；
4. 重新启动后，已完成的跳过，中断的续跑，没开始的照常执行。

有一个细节：终端按 Ctrl+C 时，信号会发给整个前台进程组。如果子进程和调度方在同一个组里，子进程会同时收到终端的信号和调度方转发的信号，一共两次。常见做法是让子进程在自己的进程组里运行，由调度方统一转发。

## 7. 用进程还是线程执行任务

| | 同一进程内（goroutine/线程） | 每个任务一个子进程 |
| --- | --- | --- |
| 启动开销 | 很小 | 较大（进程启动、加载配置） |
| 隔离 | 共享内存与全局状态，一个任务崩溃可能拖垮全部 | 相互隔离；可以单独限制资源、单独杀掉 |
| 取消 | 只能协作式取消 | 协作式之外，还能强制结束 |
| 适合 | 短小、可信、无全局状态的任务 | 长时间、需要隔离、可能失控的任务 |

agent 任务通常运行时间长、会执行外部代码，越来越多的平台为每个任务分配独立的进程、容器甚至虚拟机，这也是 Day 12 沙箱的基础。

## 8. 自测

**1. 一个模型账号限制每分钟 60 次请求，每个任务平均每分钟发 6 次请求。并发上限大约多少？**
约 10。超过 10 个任务同时运行时，请求速率超过配额，多出来的请求会被限流，吞吐量不会再提高。

**2. 为什么说“恰好一次”是至少一次加上幂等？**
网络和进程随时可能失败，系统无法确认对方是否收到，只能重发，所以投递只能保证至少一次。处理端用幂等键识别重复的投递并直接返回已有结果，效果上就是恰好一次。

**3. 提交方第一次请求超时，第二次用了新的幂等键，会怎样？**
服务端把它当成新操作，如果第一次其实已经成功，就会执行两次。重试必须沿用原来的键。

**4. 同一个幂等键，第二次请求的金额和第一次不一样，服务端应怎样处理？**
返回错误。这多半是调用方的 bug，返回旧结果或执行新请求都不对。

**5. 任务状态是“运行中”，但执行它的机器已经宕机。单机和多机分别怎样发现？**
单机用文件锁：进程死后内核释放锁，能拿到锁就说明原进程已不在。多机用租约：执行者定期续期，过期未续期就可以接手，同时用防护令牌防止旧执行者恢复后继续写入。

**6. 一个任务每次执行都会让 worker 崩溃，不加处理会怎样？**
它会被反复投递、反复让 worker 崩溃，占用重试资源，甚至阻塞队列。应限制最大尝试次数，超过后移入死信队列。
