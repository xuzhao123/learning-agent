# Go 代码评审

来源：用户在 Day 5 要求记住的流程“代码评审先跑构建，再看逻辑”。这里把它展开成可执行的步骤。

## 第一步：构建与静态检查（必须先做）

按顺序检查，任一项失败就先报告它，不进入逻辑评审：

1. `go build ./...`：能否编译。
2. `go vet ./...`：常见可疑写法（格式串不匹配、复制锁、无效比较等）。
3. `gofmt -l .`：是否有未格式化的文件。

当前环境如果没有执行命令的工具，**不要假装已经运行**。明确告诉用户需要先运行这三条命令，并请用户贴出输出；同时阅读代码，把肉眼就能确定的编译错误（未使用的变量或导入、类型不匹配、缺少返回值）列在“构建”一节。

## 第二步：逻辑评审检查点

逐项检查，只报告确实存在的问题：

- **错误处理**：error 是否被忽略；包装时是否保留原因（`%w`）；失败路径是否释放资源。
- **边界条件**：空输入、nil、零值、切片越界、整数溢出、除零。
- **并发**：共享数据有没有锁或通道保护；goroutine 能否退出；`WaitGroup` 的 Add 是否在启动前。
- **资源**：文件、响应体、锁是否在所有路径上关闭或释放（`defer` 的位置）。
- **上下文与超时**：外部调用是否接收 `context.Context`，取消后能否尽快返回。
- **输入信任**：来自用户、模型或网络的数据是否在使用前校验。

## 输出格式

1. **构建**：已确认的编译问题，或“需要用户运行后提供输出”。
2. **问题清单**：按严重程度分为“必须修 / 建议修 / 可选”，每条写清位置、原因和修改建议。
3. **结论**：能否合并；不能合并时，列出最少需要做的修改。

没有发现问题的检查点不必逐条写“没问题”。
